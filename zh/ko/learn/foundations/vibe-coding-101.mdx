氛围编程能让你更快地将想法变成软件。无需从代码入手，而是先描述你想要实现什么，再借助 AI 将其转化为可查看、测试和改进的可运行应用。

Replit 正是为这一流程而打造。你可以在同一个地方描述想法、预览结果、提供反馈、进行修改并发布。

本页介绍氛围编程的思维方式。下一页 [使用 Agent 构建](/zh/ko/learn/build-with-agent) 将展示 Agent 如何使用工具。[有效提示](/zh/ko/learn/effective-prompting) 将介绍如何编写更清晰的指令。

<div id="section">
  ## 软件曾经是团队协作的循环
</div>

软件通常由团队打造。

产品经理或创始人定义要构建什么，以及为什么要构建。设计师塑造用户体验。开发者将想法转化为可运行的软件。团队成员测试、提供反馈、发现漏洞，并决定哪些内容已准备好上线。

这种协作之所以强大，是因为每个角色都带来不同类型的判断。产品决定什么最重要。设计决定应该带来怎样的感受。工程决定应该如何运作。测试决定它是否真正可用。

但这个循环可能很慢。每一项变更都必须经过交接：说明想法、设计流程、编写代码、审查结果、测试并修复。

氛围编程压缩了这个循环。

借助 Replit，你可以亲自推进更多产品构建工作。无需等待每一步都在不同人员和工具之间流转，你可以定义目标、生成第一个版本、测试、提供反馈并持续改进。

<div id="section-2">
  ## 你的角色将发生转变
</div>

不必是开发者，也能开始构建。

在氛围编程中，你的角色更像是产品负责人：由你来决定该做什么、做给谁、什么最重要，以及结果是否足够好。

Agent 负责协助实现，但主导权始终在你手中。

你需要带来的：

* 目标
* 受众
* 品味
* 约束条件
* 反馈
* 对上线内容的决策

Agent 能帮你做的：

* 把想法变成可运行的软件
* 应用变更
* 解释运行行为
* 调试问题
* 让应用持续迭代改进

你主导得越好，Agent 就能构建得越好。

<div id="section-3">
  ## 五项原则
</div>

遵循以下五项简单原则，氛围编程的效果最佳：

1. 从目标出发。
2. 小步快跑，分块构建。
3. 管理好上下文。
4. 审查并测试。
5. 根据反馈改进。

第一项原则决定方向，后四项则循环往复：构建一个小模块，提供正确的上下文，审查、改进，再构建下一个模块。

这些原则比写出完美的第一条提示词更重要。一步到位就得到最终应用的情况很少见。目标是让这个循环保持清晰、持续推进。

<div id="section-4">
  ## 从目标出发
</div>

一次好的氛围编程，始于一次好的产品对话：

它是为谁打造的？他们应该能做什么？什么让它真正有用？

在让 Replit 构建之前，先描述你想要的结果。

<AiPrompt>
  为一家本地面包店构建一个简单的网站。顾客应能查看今日特惠、了解餐饮服务，并提交餐饮服务请求。整体风格要温暖、精致，并且便于在移动设备上使用。
</AiPrompt>

之所以有效，是因为它为 Replit 提供的是产品目标，而不只是一个任务。它说明了目标用户、核心功能，以及第一个版本应有的感觉。

你还不需要了解技术实现。先从应用正常运行时应具备哪些条件开始。

<div id="section-5">
  ## 以小块方式构建
</div>

小块是指足够完整、可以直接试用的产品片段。

以烘焙店网站为例，第一块可以是：

* 展示今日特惠的主页
* 餐饮服务预订表单
* 适配移动端的布局

这就足以用来验证想法了。你可以打开看看、点几下，然后决定接下来改进什么。

不要一次性要求做出整个产品。大而全的请求既难以检查，也容易被误解。小块能让你在不失控的前提下稳步推进。

第一块跑通后，再添加下一块。

<AiPrompt>
  Add a confirmation message after someone submits the catering request form. Keep the rest of the page unchanged.
</AiPrompt>

这条指示够小、够清晰，也便于测试。

<div id="section-6">
  ## 管理上下文
</div>

上下文就是 Replit 用来理解你需求的信息。

好的上下文可能包括：

* 这个应用面向谁
* 它要解决什么问题
* 现在需要包含哪些内容
* 哪些可以留到以后再做
* 哪些内容不能改动
* 示例、截图、草图、文件或数据
* 关于语气、风格和品牌的说明

管理上下文，就是在恰当的时机提供恰当的信息。

如果你还在做同一个功能，就留在同一个对话里，这样 Replit 能沿用之前的决定。如果你要开始做另一个功能，或者对话已经变得杂乱，不妨把重点简要总结一下，然后另开一个对话。

例如：

<AiPrompt>
  Context: this bakery site is for busy parents ordering birthday cakes. Keep the form short, make pickup details obvious, and avoid anything that feels corporate. For this change, only improve the catering request section.
</AiPrompt>

这并不是单纯地堆砌更多文字，而是在帮助 Replit 保持专注。

<div id="section-7">
  ## 审查并测试
</div>

Agent 可以构建应用，但最终结果是否正常运行，还得由你来判断。

每次做出重要更改后，都打开应用，像目标用户一样亲自使用。不要只看 Agent 所说的更改内容，要实际走一遍流程。

问问自己：

* 用户能否完成主要操作？
* 页面是否易于理解？
* 在移动设备上能否正常运行？
* 是否有重要功能被破坏？
* Replit 是否改动了原本应该保持不变的内容？
* 现在是否已经足够好，可以继续构建？

审查和测试是最需要产品判断的环节。你需要确认软件是否符合预期。

<div id="section-8">
  ## 通过反馈不断改进
</div>

每个片段的第一个版本都只是草稿，这很正常。

氛围编程靠反馈变得更好。告诉 Replit 保留什么、修改什么、删除什么，以及接下来可以尝试什么。

不要这样说：

<AiPrompt>
  Make it better.
</AiPrompt>

试试这样说：

<AiPrompt>
  Make the catering request form easier to scan. Keep the same fields, but improve the spacing, labels, and submit button. Do not change the specials section.
</AiPrompt>

好的反馈是具体的：在保护已有成果的同时，只改进应用的某一处。

当某个片段可以正常工作后，回到循环中，继续构建下一个小片段。

如果改动跑偏了，就缩小范围。

<AiPrompt>
  That changed too much. Keep the new button style, but restore the original layout and only update the catering form.
</AiPrompt>

通过反馈不断改进，正是让产品持续推进而不失控的方法。

<div id="section-9">
  ## 好的氛围编程是什么感觉
</div>

出现以下情况，说明你的方向是对的：

* 你能用平实的语言说清楚目标
* 每次改动都小到足以逐一审查
* Agent 构建完成后，你知道该测试什么
* 你会主动提供上下文，而不是猜测 Agent 知道些什么
* 你不仅告诉 Agent 要改什么，还告诉它要保留什么
* 每一轮下来，应用都变得更好用

氛围编程并不意味着抛出一个想法就撒手不管，而是缩短想法、软件、反馈与改进之间的距离。
