В этом руководстве описано, как вручную скопировать App в другое рабочее пространство или аккаунт. Вы скопируете код и данные, настроите новое App, а затем перенаправите пользователей на него.

Ничего не перемещается и не удаляется. Старый проект остаётся на прежнем месте, а две копии не синхронизируются. После завершения работы вы можете оставить старый проект или удалить его.

<Note>
  Ищете встроенный перенос в один клик? См. [Перенос App в Teams](/ru/ja/teams/identity-and-access-management/transfer-app-to-teams). Используйте это руководство, если этот вариант недоступен или вам нужно скопировать проект между аккаунтами.
</Note>

<div id="section">
  ## Перед началом
</div>

Вам потребуется:

* Доступ к старому проекту и новому рабочему пространству или аккаунту.
* Около часа сосредоточенной работы для окончательного переноса. Предыдущие шаги можно выполнять в течение нескольких дней.
* Если у вашего приложения есть собственный веб-адрес, доступ к месту, где управляется соответствующий домен.

Два элемента не копируются автоматически и требуют больше всего времени: **база данных** и **веб-адрес**. В этом руководстве рассматриваются оба.

<Note>
  Если администратор рабочего пространства включил [запрет экспорта исходного кода](/ru/ja/teams/enterprise-privacy-settings#ban-source-code-export), вы не сможете скачать проект в виде ZIP-архива. Перед началом проконсультируйтесь с администратором рабочего пространства — он сможет подтвердить, разрешено ли ручное копирование, и объяснить, как перенести код и базу данных.
</Note>

<div id="section-2">
  ## Запланируйте время простоя
</div>

Представьте, что вы открываете второй магазин, прежде чем закрыть первый. На короткое время старый магазин уже закрыт, а новый ещё не открыт. В это время никто не сможет пользоваться вашим приложением.

**Как долго приложение будет недоступно?** Обычно от 15 до 60 минут. Это зависит от объёма данных в базе данных и скорости обновления веб-адреса.

**Будут ли потеряны данные?** Только если кто-то добавит данные в старое приложение после копирования базы данных. Чтобы этого избежать, переведите старое приложение в офлайн *до* создания окончательной копии. В этом руководстве шаги расположены именно в таком порядке.

**Можно ли всё отменить?** Да. Старый проект не удаляется. Если что-то пойдёт не так, просто снова опубликуйте старое приложение — и оно будет работать точно так же, как раньше.

**Когда это следует делать?** Выберите время, когда приложением пользуется меньше людей. Если возможно, заранее предупредите пользователей.

<div id="1">
  ## Шаг 1: скопируйте код в новый проект
</div>

Выберите один из способов. На этом этапе старое приложение продолжит работать. Оба способа переносят код, но GitHub всегда переносит историю коммитов, а ZIP — только если в нём есть папка `.git`:

|                              | Через GitHub                                                                  | Через ZIP-файл                                                                                                                       |
| ---------------------------- | ----------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------ |
| **Файлы кода**               | Только закоммиченные и отправленные файлы                                     | Все файлы на диске, включая незафиксированные изменения                                                                              |
| **История коммитов**         | Полная история удалённого репозитория                                         | Полная история, если ZIP содержит папку `.git`. История не переносится, если `.git` исключена, чтобы уложиться в ограничения импорта |
| **Папки зависимостей**       | В соответствии с `.gitignore`                                                 | Исключаются (`node_modules`, `.venv`, `build` и т. д.); переустанавливаются при импорте                                              |
| **Требования**               | Учётная запись GitHub, подключённая к обеим учётным записям Replit            | Нет                                                                                                                                  |
| **Постоянная синхронизация** | Обе копии могут отправлять изменения в один репозиторий и получать их из него | Нет — разовый снимок                                                                                                                 |
| **Лучше всего подходит для** | Проектов, для которых нужно долгосрочное резервное копирование через Git      | Быстрых разовых копий                                                                                                                |

<div id="github">
  ### Через GitHub
</div>

<Steps>
  <Step title="Отправьте старый проект на GitHub">
    В старом проекте откройте [панель Git](/ru/ja/features/workspace-tools/git-interface), подключите репозиторий GitHub, затем создайте коммит и отправьте изменения. Если вы не хотите делать код общедоступным, используйте приватный репозиторий.
  </Step>

  <Step title="Предоставьте новому аккаунту доступ">
    Если новое рабочее пространство принадлежит другому аккаунту Replit, соответствующему аккаунту GitHub потребуется доступ к репозиторию. Для приватных репозиториев добавьте этот аккаунт GitHub в качестве соавтора или используйте общую организацию GitHub.
  </Step>

  <Step title="Импортируйте в новом рабочем пространстве">
    Войдите в новый аккаунт, откройте [replit.com/import](https://replit.com/import), выберите **GitHub**, подключите аккаунт GitHub и выберите репозиторий. Инструкции по устранению неполадок см. в разделе [Импорт из провайдеров](/ru/ja/build/import-from-providers).
  </Step>

  <Step title="Проверьте копию">
    Откройте новый проект и убедитесь, что файлы и история коммитов на месте. Replit устанавливает зависимости и настраивает команду запуска во время импорта.
  </Step>
</Steps>

<Warning>
  GitHub получает только закоммиченные и отправленные изменения. Файлы, соответствующие `.gitignore`, и незафиксированные изменения останутся в старом проекте. Не коммитьте в репозиторий секретные данные или дампы баз данных.
</Warning>

<div id="zip">
  ### Через ZIP-файл
</div>

<Steps>
  <Step title="Скачайте старый проект">
    В старом проекте откройте меню с тремя точками в верхней части дерева файлов и выберите **Download as zip**.

    Если файл успешно скачался и его размер меньше 200 МБ, переходите к следующему шагу.

    ZIP-файлы размером более 200 МБ могут скачиваться успешно. Однако [импорт ZIP](/ru/ja/build/import-from-providers#limitations) не принимает файлы размером более 200 МБ, поэтому Replit не сможет создать из него новый проект. Если скачивание не удалось или размер ZIP превышает 200 МБ, создайте архив меньшего размера:

    1. В старом проекте откройте инструмент **Shell**.

    2. Вставьте следующую команду и нажмите Enter. Она создаст файл `project.zip` и исключит папки, которые Replit может восстановить самостоятельно:

       ```bash theme={null}
       zip -r project.zip . -x ".cache/*" "node_modules/*" ".venv/*" "venv/*" ".pythonlibs/*" "build/*" "target/*" ".next/*" "__pycache__/*"
       ```

    3. Проверьте размер файла. Вставьте следующую команду и нажмите Enter. Она покажет размер в МБ (например, `150M` для 150 МБ):

       ```bash theme={null}
       du -h project.zip
       ```

    4. Если размер превышает 200 МБ, уменьшите архив, исключив историю изменений. Вставьте обе строки и нажмите Enter:

       ```bash theme={null}
       rm project.zip
       zip -r project.zip . -x ".cache/*" ".local/*" ".git/*" "node_modules/*" ".venv/*" "venv/*" ".pythonlibs/*" "build/*" "target/*" ".next/*" "__pycache__/*"
       ```

       Исключайте `.local` и `.git`, только если нужно уменьшить ZIP до размера менее 200 МБ. При этом эти папки не удаляются из старого проекта. Однако ZIP без `.git` не будет содержать историю коммитов проекта. Если вам нужно сохранить историю, используйте способ с GitHub.

    5. Найдите `project.zip` в дереве файлов, откройте меню с тремя точками рядом с ним и выберите **Download**.

    В папке `.cache` хранится внутреннее состояние Replit, включая кэшированные значения секретов. Всегда исключайте её из ZIP-файлов, создаваемых вручную. Если в проекте есть другие большие сгенерированные папки, добавьте их в список исключений.
  </Step>

  <Step title="Импортируйте в новом рабочем пространстве">
    Войдите в новую учётную запись, откройте [replit.com/import](https://replit.com/import), выберите **ZIP** и загрузите файл.
  </Step>

  <Step title="Проверьте копию">
    Откройте новый проект и убедитесь, что файлы на месте. Если ZIP содержит папку `.git`, история коммитов также будет перенесена. Если вы использовали команду для создания уменьшенного архива, новый проект будет создан без истории коммитов. Replit переустановит зависимости, исключённые при создании архива.
  </Step>
</Steps>

<div id="2">
  ## Шаг 2. Настройте новое приложение
</div>

Старое приложение всё ещё работает. На этом шаге настройте новое приложение, используя *тестовую копию* данных, чтобы затем быстро выполнить окончательное переключение.

<Steps>
  <Step title="Добавьте Secrets">
    Значения Secrets (ключи API, пароли) не переносятся из старого проекта. Откройте инструмент [Secrets](/ru/ja/core-concepts/project-editor/app-setup/secrets) в обоих проектах и вручную скопируйте каждое значение. Не забудьте также Secrets для развертывания.
  </Step>

  <Step title="Повторно подключите коннекторы и другие сервисы">
    Повторно подключите каждую интеграцию через **Tools → Connectors** в новом проекте. О том, как воссоздать App Storage, соавторов и всё остальное, см. в разделе [Воссоздайте то, что не копируется](#re-create-what-doesnt-copy-over).
  </Step>

  <Step title="Опубликуйте новое приложение">
    [Опубликуйте](/ru/ja/features/publishing/overview) новый проект. Для него будут созданы собственный веб-адрес `replit.app` и отдельная пустая рабочая база данных. Пока не подключайте пользовательский домен.
  </Step>

  <Step>
    Следуйте инструкциям ниже в разделе [Скопируйте базу данных](#copy-the-database), указав **рабочую** базу данных нового проекта в качестве целевой. Так вы получите реальные данные для тестирования. На шаге 3 эта копия будет заменена актуальными данными.
  </Step>

  <Step>
    Откройте новое приложение по адресу `replit.app` и используйте его так же, как пользователи. Исправьте все неполадки, прежде чем продолжить. На этом этапе это ещё не повлияет на пользователей.
  </Step>
</Steps>

<div id="3">
  ## Шаг 3. Переключите пользователей на новое приложение
</div>

На этом этапе приложение будет недоступно. Выполните все действия подряд за один раз.

<Steps>
  <Step title="Переведите старое приложение в офлайн">
    В старом проекте откройте инструмент **Publishing** и выберите **Unpublish**. Приложение станет недоступно. С этого момента никто не сможет добавлять новые данные, поэтому следующая копия будет полной.
  </Step>

  <Step title="Сделайте последнюю копию базы данных">
    Следуйте инструкциям в разделе [Копирование базы данных](#copy-the-database), указав в качестве цели **рабочую** базу данных нового проекта. Эта копия будет содержать все актуальные данные.
  </Step>

  <Step title="Направьте веб-адрес на новое приложение">
    Если приложение использует пользовательский домен, в старом проекте откройте **Publishing → Domains** и отключите домен. В новом проекте откройте **Publishing → Domains** и [подключите его](/ru/ja/features/publishing/custom-domains#connect-a-domain-you-already-own). Если Replit предложит это сделать, обновите записи у регистратора домена, например GoDaddy или Namecheap.

    Новый адрес может стать доступен всем пользователям через несколько минут или несколько часов. До этого некоторые посетители могут видеть ошибку.

    Если приложение использует только адрес `replit.app`, сообщите пользователям новый адрес.
  </Step>

  <Step title="Убедитесь, что новое приложение работает">
    Откройте веб-адрес и убедитесь, что новое приложение загружается вместе с данными. Приложение снова доступно.
  </Step>
</Steps>

<div id="section-3">
  ## Копирование базы данных
</div>

Копирование кода не затрагивает базу данных. Для копирования данных используются инструменты PostgreSQL `pg_dump` и `pg_restore`. Они доступны в Shell обоих проектов. На шаге 2 и шаге 3 используется этот же раздел. Команды всегда одинаковы. Меняется только *целевая база данных*.

<Warning>
  Данные, записанные после выполнения `pg_dump`, не войдут в копию. Перед окончательным копированием на шаге 3 сначала отключите старое приложение.
</Warning>

<Steps>
  <Step title="Экспорт данных из старого проекта">
    Откройте инструмент **Shell** в старом проекте. Вставьте следующую команду и нажмите Enter. В дереве файлов будет создан файл `backup.dump`:

    ```bash theme={null}
    pg_dump -Fc "$DATABASE_URL" --no-owner --no-privileges -f backup.dump
    ```

    Эта команда экспортирует **базу данных для разработки**. Рабочие данные обычно находятся в **рабочей** базе данных. Чтобы экспортировать их:

    1. Откройте инструмент **Database**, выберите рабочую базу данных и откройте **Settings**.
    2. Скопируйте строку подключения.
    3. В приведённой выше команде замените `"$DATABASE_URL"` строкой подключения, сохранив кавычки.

    Если не удаётся её найти, см. [сведения о подключении](/ru/ja/features/data-and-storage/connection-details).
  </Step>

  <Step title="Перемещение файла дампа в новый проект">
    В дереве файлов старого проекта откройте меню с тремя точками рядом с `backup.dump` и скачайте файл. Затем загрузите его в новый проект с помощью опции **Upload files** в дереве файлов.

    Если вы скопировали код через GitHub, не коммитьте дамп. Перенесите его отдельно, чтобы данные не попали в репозиторий.
  </Step>

  <Step title="Импорт данных в новом проекте">
    Откройте инструмент **Shell** в новом проекте. Вставьте следующую команду и нажмите Enter:

    ```bash theme={null}
    pg_restore --clean --if-exists --single-transaction --no-owner --no-privileges --exit-on-error -d "$DATABASE_URL" backup.dump
    ```

    По умолчанию команда импортирует данные в **базу данных для разработки** нового проекта. Это необходимо на шаге 2.

    Для окончательного копирования на шаге 3 нужна **рабочая** база данных. В новом проекте откройте инструмент **Database**, выберите рабочую базу данных, откройте **Settings**, скопируйте строку подключения и используйте её вместо `"$DATABASE_URL"`.

    Команда удаляет совпадающие объекты в целевой базе данных, а затем загружает данные. Если она завершится без вывода, всё прошло успешно.
  </Step>
</Steps>

<Note>
  Если `pg_restore` завершается с ошибкой роли или политики, база данных использует пользовательские роли PostgreSQL, которых ещё нет в новом проекте. [Свяжитесь с поддержкой](https://replit.com/support).
</Note>

<Note>
  Если новый проект использует [устаревшую базу данных Neon для разработки](/ru/ja/features/data-and-storage/development-and-production#legacy-development-database), в процессе публикации доступна опция **настроить рабочую базу данных с текущими данными разработки**. Она копирует всё, что находится в базе данных для разработки на момент публикации. Это подходит для тестирования, но для окончательного переключения используйте описанные выше шаги, чтобы перенести самые актуальные данные.
</Note>

<div id="section-4">
  ## Воссоздайте то, что не копируется
</div>

Остальные настройки проекта находятся вне файловой системы. Воссоздайте каждый из этих элементов в новом проекте:

| Элемент             | Что нужно сделать                                                                                                                                                                                                                    |
| ------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **Secrets**         | Значения Secrets не переносятся из старого проекта. Добавьте их заново, включая секреты развёртывания, в инструменте [Secrets](/ru/ja/core-concepts/project-editor/app-setup/secrets) нового проекта.                                      |
| **Account Secrets** | [Подключите](/ru/ja/core-concepts/project-editor/app-setup/secrets#manage-account-secrets) их в новом проекте. Если новый проект принадлежит другому аккаунту, сначала добавьте их в этот аккаунт.                                      |
| **App Storage**     | Бакеты не переносятся. В пределах одного аккаунта [добавьте существующий бакет](/ru/ja/features/data-and-storage/object-storage#bucket-access-management). При переносе между аккаунтами скачайте объекты и загрузите их в новый бакет. |
| **Connectors**      | Повторно подключите каждую интеграцию через **Tools → Connectors** в новом проекте. См. [обзор интеграций](/ru/ja/features/integrations/overview).                                                                                      |
| **Deployments**     | Копия остаётся непубличной. Выполните [публикацию](/ru/ja/features/publishing/overview) из нового рабочего пространства, как описано в [шаге 2](#step-2-set-up-the-new-app).                                                            |
| **Custom Domains**  | Удалите домен из старого развёртывания, привяжите его к новому развёртыванию и обновите DNS-записи. Это описано в [шаге 3](#step-3-switch-your-users-to-the-new-app).                                                                      |
| **Collaborators**   | Снова пригласите соавторов в новое рабочее пространство и настройте [доступ](/ru/ja/teams/identity-and-access-management/groups-and-permissions).                                                                                       |
| **Agent history**   | Беседы Agent и возможность отката к [чекпоинтам](/ru/ja/features/version-control/checkpoints-and-rollbacks) остаются в старом проекте. Коммиты чекпоинтов переносятся вместе с историей Git, но откатиться к ним из копии нельзя.       |

<div id="section-5">
  ## Если возникли проблемы
</div>

Старый проект по-прежнему доступен. Чтобы вернуться к нему:

1. В старом проекте откройте инструмент **Publishing** и выберите **Publish**.
2. Если вы перенесли пользовательский домен, верните его тем же способом.

Приложение снова будет работать с данными, которые были на момент отключения. Ничего не потеряно.

<div id="section-6">
  ## Очистка
</div>

Подождите около недели, чтобы убедиться, что новое приложение работает корректно. Затем:

* Удалите `backup.dump` из обоих проектов и с устройств. Каждая копия содержит полный экспорт данных.
