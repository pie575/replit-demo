Clerk Auth даёт вашему приложению собственную выделенную систему аутентификации на базе [Clerk](https://clerk.com). В отличие от [Replit Auth](/ru/pt/core-concepts/project-editor/auth-and-security/authentication), который использует систему входа Replit и создаёт учётные записи Replit, Clerk Auth разворачивает для вашего приложения **отдельный тенант Clerk**. Пользователи создают учётные записи прямо в вашем приложении — а не учётные записи Replit, — и вы полностью контролируете оформление, способы входа и процесс регистрации.

<Note>
  **Clerk Auth и Replit Auth** — с **Clerk Auth** (эта страница) ваше приложение получает собственный тенант аутентификации с полностью настраиваемым оформлением и учётными записями пользователей, независимыми от Replit. С **[Replit Auth](/ru/pt/core-concepts/project-editor/auth-and-security/authentication)** пользователи входят под учётными записями Replit и видят страницы входа с оформлением Replit. Выбирайте Clerk Auth, если хотите использовать собственное оформление на экране входа или вам нужны учётные записи пользователей, не связанные с Replit.
</Note>

<div id="clerk-auth-vs-replit-auth-em-resumo">
  ## Clerk Auth и Replit Auth: кратко
</div>

|                                  | Clerk Auth                                                                       | Replit Auth                                              |
| -------------------------------- | -------------------------------------------------------------------------------- | -------------------------------------------------------- |
| **Учётные записи пользователей** | Пользователи создают учётные записи в вашем app (учётная запись Replit не нужна) | Пользователи входят с учётной записью Replit             |
| **Оформление**                   | Полностью настраивается — название app, значок и цвета                           | Страница входа с оформлением Replit                      |
| **Учётные данные SSO**           | Собственные учётные данные OAuth для каждого провайдера                          | Используются общие OAuth-приложения Replit               |
| **Окружения**                    | Раздельные окружения разработки и продакшена                                     | Единое окружение                                         |
| **Приглашения**                  | Нет интеграции с приглашениями Replit                                            | Регистрации засчитываются в программе приглашений Replit |
| **Лучше подходит для**           | Apps с собственным оформлением, профессиональных и коммерческих продуктов        | Быстрой настройки, apps, где оформление Replit допустимо |

<div id="primeiros-passos">
  ## Начало работы
</div>

Чтобы добавить Clerk Auth в ваш app, упомяните это в prompt для Agent:

```
Помоги мне создать app, который [ваша идея app], и он должен включать Clerk Auth.
```

Agent берёт всё на себя — создаёт тенант Clerk, сохраняет учётные данные, настраивает маршруты и добавляет middleware. Вам не потребуется ни учётная запись Clerk, ни ручная настройка.

<div id="como-o-clerk-auth-funciona-com-o-replit">
  ## Как Clerk Auth работает с Replit
</div>

Когда Agent настраивает Clerk Auth для вашего app, он:

1. **Создаёт отдельный тенант Clerk** — ваш app получает собственное приложение Clerk с раздельными средами разработки и продакшена
2. **Выдаёт учётные данные** — ключи API и Secrets сохраняются как переменные окружения
3. **Настраивает прокси** — аутентификация без сбоев работает на вашем опубликованном домене
4. **Настраивает маршруты входа и регистрации** — в ваш app добавляются готовые React-компоненты Clerk
5. **Добавляет серверное промежуточное ПО** — маршруты API защищаются с помощью Express-middleware от Clerk

<Note>
  Вам не нужно создавать учётную запись Clerk или管 управлять инфраструктурой. Replit берёт всё это на себя автоматически.
</Note>

<div id="capacidades">
  ## Возможности
</div>

<div id="o-que-suportado">
  ### Что поддерживается
</div>

Clerk Auth предоставляет вашему приложению:

* **Независимые учётные записи пользователей** — пользователи вашего приложения не являются пользователями Replit; они существуют только в Clerk-тенанте вашего приложения
* **Полностью настраиваемые страницы входа** — название приложения, логотип, цвета, шрифты и тексты на страницах входа и регистрации задаются в коде вашего приложения
* **SSO с вашим брендингом** — укажите собственные учётные данные OAuth для каждого провайдера, чтобы на экране согласия OAuth отображались название и оформление вашего приложения, а не стандартные значения
* **Аутентификация по электронной почте и паролю** — встроенные регистрация и вход с подтверждением адреса электронной почты
* **Вход через социальные сети (SSO)** — дайте пользователям возможность входить через Google, GitHub, Apple или X (Twitter)
* **Управление пользователями** — просматривайте, ищите и модерируйте пользователей в панели Auth
* **Управление сессиями** — безопасные токены сессий с автоматическим управлением
* **Среды разработки и продакшена** — протестируйте аутентификацию в среде разработки, прежде чем запускать её вживую

<Note>
  Большую часть настроек Clerk Auth можно выполнить с помощью инструмента **Auth** в Project Editor — учётная запись Clerk не нужна, и заходить в панель Clerk тоже не потребуется.
</Note>

<div id="o-que-no-suportado">
  ### Что не поддерживается
</div>

Следующие возможности на данный момент недоступны в Clerk Auth (в сравнении с внешним приложением Clerk, которое вы настраиваете самостоятельно). Подробное описание различий смотрите в [этом FAQ](#how-does-clerk-auth-compare-to-external-clerk).

* **Вход по номеру телефона** — вход и подтверждение через SMS
* **Поддержка MFA** — многофакторная аутентификация для конечных пользователей
* **Полный набор SSO-провайдеров** — сейчас поддерживаются только Google, GitHub, Apple и X
* **Тенанты организаций** — функции организаций и командного членства в Clerk

<div id="ambientes-de-desenvolvimento-e-produo">
  ## Среды разработки и продакшена
</div>

Для каждого app с Clerk Auth создаются две полностью независимые среды Clerk: среда **разработки**, которая обслуживает ваш app в разработке и в предпросмотре, пока вы его создаёте, и среда **продакшена**, которая обслуживает ваш опубликованный app. Эти среды изолированы друг от друга изначально — у них отдельные ключи API и отдельные хранилища пользователей.

<div id="chaves-de-api-separadas">
  ### Отдельные ключи API
</div>

У каждой среды свои публикуемые и секретные ключи API. Ключи, доступные вашему приложению, переключаются автоматически в зависимости от того, где оно запущено — в разработке или в продакшене:

* В вашем workspace секреты `CLERK_PUBLISHABLE_KEY` и `CLERK_SECRET_KEY` содержат **тестовые ключи** (`pk_test...` и `sk_test...`), которые указывают на среду разработки.

<Frame>
  <img src="/assets/mirror/clerk-check-dev-keys-5a23f6b7dd0c.png" alt="Инструмент Secrets в Workspace с CLERK_SECRET_KEY и CLERK_PUBLISHABLE_KEY с префиксами sk_test_ и pk_test_" width="1946" height="402" data-path="images/workspace/auth/clerk-check-dev-keys.png" />
</Frame>

* Когда вы публикуете приложение, опубликованный деплой работает с **боевыми ключами** (`pk_live...` и `sk_live...`), которые указывают на среду продакшена. Чтобы проверить префиксы, откройте **Publishing → Overview → Adjust settings** и посмотрите `CLERK_PUBLISHABLE_KEY` и `CLERK_SECRET_KEY`.

<Frame>
  <img src="/assets/mirror/clerk-check-prod-keys-acccd7f68da1.png" alt="Publishing Overview с secrets продакшен-приложения: CLERK_SECRET_KEY и CLERK_PUBLISHABLE_KEY с префиксами sk_live_ и pk_live_" width="1924" height="1664" data-path="images/workspace/auth/clerk-check-prod-keys.png" />
</Frame>

<Note>
  Переключать среды вручную не нужно — Replit сам управляет ключами для разработки и продакшена. Просто разрабатывайте, тестируйте и публикуйте — всё уже настроено.
</Note>

<Warning>
  Не заменяйте тестовые ключи боевыми, не редактируйте их в панели Secrets и не настраивайте ничего вручную в панели Clerk. Это нарушит автоматическое переключение между разработкой и продакшеном и не поддерживается в Clerk Auth под управлением Replit.
</Warning>

<div id="armazenamentos-de-usurios-separados">
  ### Раздельные хранилища пользователей
</div>

У каждой среды своё хранилище пользователей. Учётные записи, зарегистрированные в среде разработки, **не** существуют в продакшене, и наоборот:

* Пользователь, зарегистрировавшийся во время тестирования в приложении разработки/предпросмотра, создаётся только в хранилище среды разработки.
* Пользователь, зарегистрировавшийся в вашем опубликованном приложении, создаётся только в хранилище продакшена.
* Сессии, метаданные пользователя и любые данные, связанные с `userId` из Clerk, точно так же ограничены той средой, в которой была создана учётная запись.

Это ожидаемое поведение. Чтобы посмотреть пользователей в каждой среде, откройте панель **Auth** в своём Workspace и переключайтесь между разработкой и продакшеном с помощью переключателя среды на вкладке **Users**.

<Note>
  Среда разработки — это место, где вы экспериментируете и создаёте, а продакшен обслуживает реальных пользователей вашего работающего приложения. Эти две среды намеренно изолированы, поэтому учётные записи и данные, созданные в разработке, не появятся в продакшене.
</Note>

<div id="gerenciando-usurios">
  ## Управление пользователями
</div>

**Панель Auth** в Project Editor даёт полную картину по аутентифицированным пользователям. Поскольку Clerk Auth создаёт для вашего app отдельное хранилище пользователей, перечисленные здесь пользователи — это учётные записи в вашем app, а не учётные записи Replit.

<Frame>
  <img src="/assets/mirror/clerk-users-4940ed365605.png" alt="Вкладка пользователей Clerk Auth с аутентифицированными пользователями на панели Auth" width="2136" height="794" data-path="images/workspace/auth/clerk-users.png" />
</Frame>

На вкладке **Users** вы можете:

* **Просматривать всех пользователей** с такими данными, как эл. почта, имя, последний вход и дата создания учётной записи
* **Искать и фильтровать**, чтобы найти нужных пользователей
* **Блокировать и разблокировать пользователей**, управляя доступом к вашему app
* **Сортировать пользователей** по разным критериям
* **Переключать окружения** — переключайтесь между разработкой и продакшеном, чтобы управлять пользователями в каждом из них

<div id="personalizando-sua-pgina-de-login">
  ## Настройка страницы входа
</div>

Оформление страниц входа и регистрации — название приложения, логотип, цвета, шрифты и тексты — задаётся в коде вашего App, а не на панели Auth. Чтобы изменить его, попросите Agent:

```
Обнови мою страницу входа: используй [название вашего app] в качестве заголовка, [опишите ваш логотип] и подбери цвета под мой сайт.
```

Под капотом это управляется свойствами `appearance` и `localization`, которые передаются в `<ClerkProvider>`, а также файлом логотипа в каталоге `public/` вашего приложения. Agent синхронизирует их с общей темой вашего приложения.

<Note>
  Название приложения, которое отображается на **экране согласия Google, Apple, GitHub или X** (это экран, появляющийся после того, как пользователь нажимает «Войти через Google» и т. п.), задаётся отдельно — оно берётся из приложения OAuth, зарегистрированного у соответствующего провайдера, и **не** меняется при редактировании кода вашей страницы входа. Чтобы изменить его, настройте [собственные учётные данные OAuth](#configuring-oauth-credentials-for-an-sso-provider) для этого провайдера.
</Note>

<div id="configurando-provedores-de-login">
  ## Настройка провайдеров входа
</div>

Clerk Auth поддерживает Google, GitHub, Apple и X в качестве провайдеров входа через соцсети. На вкладке **Configure** панели Auth вы определяете, какие провайдеры отображаются на странице входа, и — в продакшене — использует ли каждый провайдер учётные данные OAuth, управляемые Replit, или ваши собственные учётные данные для входа с фирменным оформлением.

<Frame>
  <img src="/assets/mirror/clerk-configure-60169c473d64.png" alt="Вкладка Configure с SSO-провайдерами в боковой панели, выбранным окружением Production и списком провайдеров с переключателями включения и действиями «Изменить»" width="923" height="378" data-path="images/workspace/auth/clerk-configure.png" />
</Frame>

Откройте вкладку **Configure**. В боковой панели в разделе **SSO providers** выберите **Development** или **Production**: **Development** обслуживает приложение для разработки и предпросмотра в Workspace, а **Production** — ваш опубликованный app. У каждого окружения свой список в основной панели. Здесь вы можете:

* **Включить или отключить провайдера** — с помощью переключателя задайте, отображается ли провайдер на странице входа. Отключённые провайдеры пользователям не видны.
* **Настроить собственные учётные данные OAuth (только продакшен)** — см. раздел [Настройка учётных данных OAuth для провайдера SSO](#configuring-oauth-credentials-for-an-sso-provider) ниже.

<div id="configurando-credenciais-oauth-para-um-provedor-sso">
  ### Настройка учётных данных OAuth для провайдера SSO
</div>

По умолчанию провайдеры используют **учётные данные, управляемые Replit**: вход работает сразу, но на экране согласия OAuth отображается брендинг Replit. Переключитесь на **Custom credentials**, чтобы использовать собственный OAuth-клиент из консоли разработчика провайдера — тогда на экране согласия будут показаны название и брендинг вашего app.

1. Откройте **панель Auth** в Project Editor. Перейдите на вкладку **Configure** и в разделе **SSO providers** на боковой панели выберите **Production**.

<Frame>
  <img src="/assets/mirror/clerk-configure-60169c473d64.png" width="923" height="378" data-path="images/workspace/auth/clerk-configure.png" />
</Frame>

2. Нажмите значок **Edit** рядом с провайдером, который хотите настроить. По умолчанию выбран вариант **Replit-managed credentials**.

<Frame>
  <img src="/assets/mirror/clerk-sso-default-credentials-525090775408.png" alt="Панель редактирования провайдера с вариантами учётных данных, управляемых Replit, и собственных учётных данных" width="1468" height="960" data-path="images/workspace/auth/clerk-sso-default-credentials.png" />
</Frame>

3. Выберите **Custom credentials**. Панель развернётся и покажет поля учётных данных, а также контрольный список **Provider setup** со значениями, которые нужно зарегистрировать на стороне провайдера.

<Frame>
  <img src="/assets/mirror/clerk-sso-custom-credentials-f24112a5cf07.png" alt="Панель собственных учётных данных с полями идентификатора клиента и секрета OAuth, а также контрольный список настройки провайдера с URL обратного вызова перенаправления и источниками JavaScript" width="1468" height="2246" data-path="images/workspace/auth/clerk-sso-custom-credentials.png" />
</Frame>

4. Следуйте инструкциям, чтобы завершить настройку. В них есть прямые ссылки на консоль и соответствующие справочные документы. Эти же документы можно найти в разделе [Дополнительные ресурсы](#additional-resources) для вашего провайдера.
5. Заполните все необходимые значения учётных данных.
6. В консоли разработчика провайдера зарегистрируйте каждую запись из контрольного списка **Provider setup** в портале разработчика провайдера. С помощью значков копирования скопируйте каждое значение в точности и отмечайте пункты по мере выполнения либо выберите **Mark all as done**, когда закончите.
7. Выберите **Save changes**.

<div id="verificando-novamente-a-configurao-aps-alteraes-de-domnio">
  ### Повторная проверка настройки после изменения домена
</div>

Операции, связанные с доменом, — например, привязка нового внешнего домена или [покупка домена через Replit](/ru/pt/cloud-services/deployments/domain-purchasing), — могут изменить URL обратного вызова для перенаправления и источники JavaScript вашего приложения. В таком случае для любого провайдера, настроенного с собственными учётными данными, может потребоваться регистрация новых значений в его консоли разработчика.

После изменения домена вернитесь на вкладку **Configure**. Напоминания о настройке отображаются в виде значков предупреждения на вкладке, на боковой панели и рядом с провайдерами в списке **SSO providers**. Значок предупреждения и надпись **setup steps remaining** рядом с провайдером означают, что в его контрольном списке **Provider setup** появились новые пункты.

<Frame>
  <img src="/assets/mirror/clerk-sso-setup-reminders-a5b092846006.png" alt="Вкладка Configure и боковая панель с предупреждением о настройке, а также список провайдеров SSO со значком предупреждения и надписью 'setup steps remaining' рядом с провайдером после изменения домена" width="923" height="378" data-path="images/workspace/auth/clerk-sso-setup-reminders.png" />
</Frame>

Откройте панель редактирования провайдера, скопируйте обновлённые значения в разделе **Provider setup**, зарегистрируйте их в консоли разработчика провайдера и выберите **Mark all as done**.

<div id="configurao-de-domnio-para-verificao-de-e-mail">
  ## Настройка домена для подтверждения электронной почты
</div>

Если ваш App поддерживает **регистрацию по электронной почте и паролю**, Clerk отправляет код подтверждения во входящие каждого нового пользователя. Настройка домена для доставки писем гарантирует, что такие письма будут приходить с адреса вашего App, а не задерживаться или блокироваться спам-фильтрами.

<div id="quando-voc-precisa-dessa-configurao">
  ### Когда эта настройка нужна
</div>

Настраивать DNS-записи требуется только в том случае, если к вашему app привязан **внешний домен, управляемый другим провайдером** (например, домен, зарегистрированный в Cloudflare, GoDaddy, Namecheap или аналогичном сервисе).

Никаких настроек не нужно, если ваш app работает на:

* поддомене `.replit.app`
* домене, [купленном через Replit](/ru/pt/cloud-services/deployments/domain-purchasing)

В обоих случаях DNS-записями управляет сама Replit.

<div id="adicionar-registros-dns-para-envio-de-e-mail">
  ### Добавление DNS-записей для отправки писем
</div>

Чтобы приложение могло отправлять письма с подтверждением от имени вашего внешнего домена, добавьте набор DNS-записей у регистратора домена.

1. В Project Editor откройте **Publishing**.
2. Выберите **Domains**.
3. Найдите привязанный внешний домен и выберите **Manage**.
4. В разделе **Authentication DNS setup required** скопируйте записи CNAME, которые показывает Replit, — именно они нужны Clerk для отправки писем с подтверждением с вашего домена.
5. Войдите в панель вашего DNS-провайдера (Cloudflare, GoDaddy, Namecheap и т. д.) и добавьте каждую запись в точности так, как показано.

<Frame>
  <img src="/assets/mirror/clerk-domain-8797ea9f41fc.png" alt="Панель управления доменом с разделом настройки DNS для аутентификации и записями CNAME для доставки писем через Clerk" width="1156" height="1524" data-path="images/workspace/auth/clerk-domain.png" />
</Frame>

Распространение изменений DNS может занять до 48 часов. Как только записи заработают, при регистрации по электронной почте и паролю коды подтверждения будут автоматически отправляться с вашего домена — никаких дополнительных действий в панели Auth не потребуется.

<div id="soluo-de-problemas">
  ### Устранение неполадок
</div>

* **Письма с подтверждением не приходят** — убедитесь, что каждая запись добавлена в точности так, как показано на панели Manage, включая завершающие точки, если этого требует ваш DNS-провайдер. Проверьте папку «Спам» у получателя.
* **Записи по-прежнему не обнаружены** — дождитесь распространения DNS (до 48 часов) и снова проверьте на панели Manage, не осталось ли записей, отмеченных как отсутствующие.

<div id="melhores-prticas-de-segurana">
  ## Рекомендации по безопасности
</div>

* **Всегда проверяйте на сервере** — Проверяйте аутентификацию в маршрутах API, а не только в пользовательском интерфейсе
* **Используйте переменные окружения** — Никогда не прописывайте ключи или secrets прямо в коде
* **Подключайте middleware прокси первым** — Прокси Clerk должен монтироваться до парсеров тела запроса в вашем приложении Express
* **Не перенаправляйте главную страницу на страницу входа** — Оставьте лендинг доступным для неаутентифицированных посетителей

<div id="faq">
  ## Часто задаваемые вопросы
</div>

<div id="preciso-de-uma-conta-clerk-para-usar-o-clerk-auth">
  ### Нужна ли учётная запись Clerk, чтобы использовать Clerk Auth?
</div>

Нет. Тенант Clerk, на котором работает Clerk Auth, создаётся и управляется автоматически платформой Replit, когда Agent настраивает ваш app, — вам не нужно регистрироваться в Clerk и самостоятельно администрировать какую-либо инфраструктуру Clerk.

<div id="posso-acessar-o-painel-do-clerk-para-a-instncia-clerk-gerenciada-pela-replit">
  ### Могу ли я получить доступ к панели Clerk для экземпляра Clerk, управляемого Replit?
</div>

Нет. Экземпляр Clerk, управляемый Replit, в панели Clerk не отображается. Управляйте им через инструмент **Auth** в Project Editor — именно там вы настраиваете провайдеров, просматриваете пользователей и переключаетесь между средами разработки и продакшена.

<div id="minha-chave-publicvel-do-clerk-comea-com-pk_test-como-fao-para-mudar-para-uma-chave-ao-vivo">
  ### Мой публикуемый ключ Clerk начинается с `pk_test`. Как переключиться на рабочий ключ?
</div>

Этого делать не нужно. Ключи `pk_test...` и `sk_test...`, которые вы видите на панели Secrets в workspace, относятся к среде Clerk **разработки** вашего приложения и используются во время разработки. При публикации приложения деплой автоматически запускается с ключами `pk_live...` и `sk_live...` для среды продакшена. Чтобы убедиться в этом, откройте **Publishing → Overview → Adjust settings** в своём Workspace и проверьте значение `CLERK_PUBLISHABLE_KEY` для опубликованного приложения — оно будет начинаться с `pk_live`. Не редактируйте эти ключи вручную. Подробности см. в разделе [Среды разработки и продакшена](#development-and-production-environments).

<div id="por-que-no-consigo-fazer-login-no-meu-app-publicado-com-a-conta-que-criei-durante-o-desenvolvimento">
  ### Почему я не могу войти в опубликованное приложение под учётной записью, созданной во время разработки?
</div>

Среды **разработки** и **продакшена** в Clerk Auth используют раздельные хранилища пользователей. Учётная запись, созданная в приложении в режиме разработки или в предпросмотре, существует только в среде разработки и при публикации не копируется в продакшен — в опубликованном приложении вам потребуется зарегистрироваться заново. То же самое касается любых данных, связанных с `userId` из Clerk. Откройте **панель Auth** в своём Workspace и с помощью переключателя среды на вкладке **Users** просмотрите пользователей в каждой из сред. Подробности см. в разделе [Раздельные хранилища пользователей](#separate-user-stores).

<div id="o-clerk-auth-gratuito">
  ### Clerk Auth бесплатный?
</div>

Пока Clerk Auth бесплатен. Позже может появиться оплата по факту использования — как у других сервисов Replit с тарификацией за использование. Любые будущие списания будут проходить через ваш существующий биллинг Replit: отдельный счёт или способ оплаты в Clerk не потребуется.

<div id="o-clerk-auth-tem-limite-de-mau-como-os-planos-externos-do-clerk">
  ### Есть ли в Clerk Auth ограничение на MAU, как во внешних тарифах Clerk?
</div>

Нет. Clerk Auth не ограничивает число ежемесячных активных пользователей (MAU), в отличие от внешних тарифов Clerk, где лимит MAU зависит от уровня тарифа.

<div id="como-o-clerk-auth-se-compara-ao-clerk-externo">
  ### Чем Clerk Auth отличается от внешнего Clerk?
</div>

У тенанта Clerk, которым управляет Replit и на котором работает Clerk Auth, есть ряд особенностей по сравнению с приложениями Clerk, которые вы создаёте в собственной учётной записи Clerk (**внешний Clerk**). В таблице ниже показано, чем они различаются на сегодняшний день — это отражает текущее состояние Clerk Auth, и набор поддерживаемых возможностей продолжит развиваться.

|                                         | Clerk Auth                                                                        | Внешний Clerk                            |
| --------------------------------------- | --------------------------------------------------------------------------------- | ---------------------------------------- |
| **Настройка**                           | Разворачивается автоматически силами Replit                                       | Настраивается самостоятельно             |
| **Владение тенантом Clerk**             | Управляется Replit, принадлежит вашему приложению                                 | Принадлежит вашей учётной записи Clerk   |
| **Структура тарифов**                   | Сейчас бесплатно (в будущем планируется оплата по факту использования)            | Подписка + оплата по факту использования |
| **Выставление счетов**                  | Счета от Replit (сейчас бесплатно)                                                | Счета в вашей учётной записи Clerk       |
| **Ограничение MAU**                     | Без ограничений                                                                   | Ограничение по уровню тарифа             |
| **Настройка прокси и домена**           | Автоматически для replit.app и купленного домена, вручную для привязанного домена | Вручную                                  |
| **SSO-провайдеры**                      | Поддерживаются отдельные провайдеры: Google, Apple, GitHub, X                     | Поддерживается больше провайдеров        |
| **Интерфейс управления пользователями** | Инструмент Auth в Project Editor                                                  | Панель приложения Clerk                  |
| **SMS**                                 | Не поддерживается                                                                 | Поддерживается                           |
| **MFA**                                 | Не поддерживается                                                                 | Поддерживается                           |
| **Тенанты организаций**                 | Не поддерживается                                                                 | Поддерживается                           |

<div id="quais-configuraes-comuns-do-clerk-auth-preciso-fazer-manualmente">
  ### Какие типичные настройки Clerk Auth нужно выполнить вручную?
</div>

Большая часть настройки Clerk Auth автоматизирована, но некоторые параметры требуют действий за пределами инструмента **Auth**:

* **Собственные учётные данные OAuth для SSO-провайдеров** — если вы хотите, чтобы на экране согласия провайдера отображались название и оформление вашего приложения (вместо стандартных значений Replit), зарегистрируйте OAuth-приложение в консоли разработчика провайдера и вставьте полученные учётные данные в панель Auth. См. [Настройка учётных данных OAuth для SSO-провайдера](#configuring-oauth-credentials-for-an-sso-provider).
* **DNS-записи для подтверждения адресов электронной почты на внешних доменах** — если к вашему приложению привязан внешний домен, управляемый другим провайдером, потребуется добавить DNS-записи, чтобы письма с подтверждением отправлялись с вашего домена. См. [Настройка домена для подтверждения электронной почты](#domain-setup-for-email-verification).

<div id="posso-trazer-meu-prprio-app-clerk-em-vez-de-usar-o-gerenciado-pela-replit">
  ### Могу ли я использовать собственное приложение Clerk вместо управляемого Replit?
</div>

Да. Если для вашего App уже создано приложение Clerk под управлением Replit, сначала удалите его и только потом подключайте собственное внешнее приложение Clerk:

1. Откройте панель **Auth** в Project Editor.
2. Перейдите на вкладку **Configure**.
3. Прокрутите страницу вниз и нажмите **Delete Clerk app**.

При удалении приложения Clerk удаляется управляемый Replit тенант Clerk и освобождаются все привязанные к нему домены — после этого вы сможете подключить собственное приложение Clerk и снова использовать эти домены. Если для вашего App приложения Clerk под управлением Replit ещё нет, этот шаг можно пропустить и сразу подключить своё внешнее приложение Clerk.
