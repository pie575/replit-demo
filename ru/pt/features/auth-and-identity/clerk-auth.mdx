Clerk Auth даёт вашему приложению собственную выделенную систему аутентификации на базе [Clerk](https://clerk.com). В отличие от [Replit Auth](/ru/pt/features/auth-and-identity/authentication), который использует систему входа Replit и создаёт учётные записи Replit, Clerk Auth разворачивает для вашего приложения **отдельный тенант Clerk**. Пользователи создают учётные записи прямо в вашем приложении — а не в Replit, — а вы полностью контролируете оформление, способы входа и весь процесс входа.

<Note>
  **Clerk Auth и Replit Auth** — с **Clerk Auth** (эта страница) ваше приложение получает собственный тенант аутентификации с полностью настраиваемым оформлением и учётными записями пользователей, независимыми от Replit. С **[Replit Auth](/ru/pt/features/auth-and-identity/authentication)** пользователи входят через учётные записи Replit и видят страницы входа с оформлением Replit. Выбирайте Clerk Auth, если хотите использовать собственное оформление при входе или вам нужны учётные записи пользователей, не связанные с Replit.
</Note>

<div id="clerk-auth-vs-replit-auth-em-resumo">
  ## Clerk Auth и Replit Auth: краткое сравнение
</div>

|                                  | Clerk Auth                                                                                    | Replit Auth                                                     |
| -------------------------------- | --------------------------------------------------------------------------------------------- | --------------------------------------------------------------- |
| **Учётные записи пользователей** | Пользователи создают учётные записи прямо в вашем приложении (учётная запись Replit не нужна) | Пользователи входят с помощью учётной записи Replit             |
| **Оформление**                   | Полностью настраиваемое — название, значок и цвета вашего приложения                          | Страница входа с фирменным оформлением Replit                   |
| **Учётные данные SSO**           | Собственные учётные данные OAuth для каждого провайдера                                       | Используются общие OAuth-приложения Replit                      |
| **Среды**                        | Отдельные среды разработки и продакшена                                                       | Единая среда                                                    |
| **Реферальная программа**        | Нет интеграции с реферальной программой Replit                                                | Регистрации засчитываются в реферальную программу Replit        |
| **Подходит для**                 | Приложений с собственным брендом, профессиональных и коммерческих продуктов                   | Быстрой настройки и приложений, где оформление Replit приемлемо |

<div id="comeando">
  ## Начало работы
</div>

Чтобы добавить Clerk Auth в приложение, упомяните его в prompt для Agent:

```
Помоги мне создать приложение, которое [ваша идея приложения], и в нём должен быть Clerk Auth.
```

Agent берёт всё на себя — создаёт тенант Clerk, сохраняет учётные данные, настраивает маршруты и добавляет middleware. Вам не понадобится ни учётная запись Clerk, ни ручная настройка.

<div id="como-o-clerk-auth-funciona-com-o-replit">
  ## Как Clerk Auth работает с Replit
</div>

Когда Agent настраивает Clerk Auth для вашего приложения, он:

1. **Создаёт выделенный тенант Clerk** — ваше приложение получает собственное приложение Clerk с раздельными средами разработки и продакшена
2. **Выдаёт учётные данные** — ключи API и секреты сохраняются как переменные окружения
3. **Настраивает прокси** — аутентификация без проблем работает на вашем опубликованном домене
4. **Настраивает маршруты входа и регистрации** — в ваше приложение добавляются готовые React-компоненты Clerk
5. **Добавляет middleware на стороне сервера** — ваши маршруты API защищаются с помощью Express-middleware от Clerk

<Note>
  Вам не нужно создавать учётную запись Clerk или管理 какую-либо инфраструктуру. Replit управляет всем автоматически за вас.
</Note>

<div id="capacidades">
  ## Возможности
</div>

<div id="o-que-suportado">
  ### Что поддерживается
</div>

Clerk Auth предоставляет вашему приложению:

* **Независимые учётные записи пользователей** — пользователи вашего приложения не являются пользователями Replit; они существуют только внутри Clerk-тенанта вашего приложения
* **Полностью брендированные страницы входа** — название, логотип, цвета, шрифты и тексты вашего приложения на страницах входа и регистрации задаются в коде приложения
* **SSO с вашим брендингом** — укажите собственные учётные данные OAuth для каждого провайдера, чтобы на экране согласия OAuth отображались название и оформление вашего приложения, а не стандартные значения
* **Аутентификация по электронной почте и паролю** — встроенные регистрация и вход с подтверждением по электронной почте
* **Вход через социальные сети (SSO)** — дайте пользователям возможность входить через Google, GitHub, Apple или X (Twitter)
* **Управление пользователями** — просматривайте, ищите и модерируйте пользователей на панели Auth
* **Управление сессиями** — безопасные токены сессий управляются автоматически
* **Среды разработки и продакшена** — протестируйте аутентификацию в среде разработки перед публикацией

<Note>
  Большую часть настроек Clerk Auth можно выполнить в инструменте **Auth** редактора проекта — учётная запись Clerk не требуется, и заходить в панель Clerk не нужно.
</Note>

<div id="o-que-no-suportado">
  ### Что не поддерживается
</div>

Перечисленные ниже возможности сейчас недоступны в Clerk Auth (в отличие от внешнего приложения Clerk, которое вы настраиваете самостоятельно). Подробное сравнение см. в [этом разделе FAQ](#how-does-clerk-auth-compare-to-external-clerk).

* **Вход по номеру телефона** — вход и подтверждение через SMS
* **Поддержка MFA** — многофакторная аутентификация для конечных пользователей
* **Полный набор провайдеров SSO** — сейчас поддерживаются только Google, GitHub, Apple и X
* **Тенанты организаций** — возможности Clerk для работы с организациями и участниками команды

<div id="ambientes-de-desenvolvimento-e-produo">
  ## Среды разработки и продакшена
</div>

Каждое приложение с Clerk Auth получает две полностью независимые среды Clerk: среду **разработки**, которая обслуживает приложение в режиме разработки/Preview, пока вы над ним работаете, и среду **продакшена**, которая обслуживает опубликованное приложение. Эти среды изолированы друг от друга по замыслу — у них разные ключи API и разные базы пользователей.

<div id="chaves-de-api-separadas">
  ### Отдельные ключи API
</div>

У каждого окружения есть собственные публикуемый и секретный ключи API. Ключи, доступные вашему приложению, подставляются автоматически в зависимости от того, запущено оно в среде разработки или в продакшене:

* В вашем workspace секреты `CLERK_PUBLISHABLE_KEY` и `CLERK_SECRET_KEY` содержат **тестовые ключи** (`pk_test...` и `sk_test...`), которые указывают на окружение разработки.

<Frame>
  <img src="/assets/mirror/clerk-check-dev-keys-5a23f6b7dd0c.png" alt="Инструмент Secrets в Workspace показывает CLERK_SECRET_KEY и CLERK_PUBLISHABLE_KEY с префиксами sk_test_ и pk_test_" width="1946" height="402" data-path="images/workspace/auth/clerk-check-dev-keys.png" />
</Frame>

* Когда вы публикуете приложение, опубликованное развёртывание работает с **боевыми ключами** (`pk_live...` и `sk_live...`), которые указывают на окружение продакшена. Чтобы проверить префиксы, откройте **Publishing → Overview → Adjust settings** и посмотрите `CLERK_PUBLISHABLE_KEY` и `CLERK_SECRET_KEY`.

<Frame>
  <img src="/assets/mirror/clerk-check-prod-keys-acccd7f68da1.png" alt="Publishing Overview показывает секреты приложения в продакшене: CLERK_SECRET_KEY и CLERK_PUBLISHABLE_KEY с префиксами sk_live_ и pk_live_" width="1924" height="1664" data-path="images/workspace/auth/clerk-check-prod-keys.png" />
</Frame>

<Note>
  Переключать окружения вручную не нужно — Replit управляет ключами разработки и продакшена автоматически. Просто разрабатывайте, тестируйте и публикуйте — всё уже настроено.
</Note>

<Warning>
  Не заменяйте тестовые ключи боевыми, не редактируйте их в панели Secrets и не настраивайте ничего вручную в панели Clerk. Это нарушит автоматическое переключение между разработкой и продакшеном и не поддерживается при использовании Clerk Auth под управлением Replit.
</Warning>

<div id="bases-de-usurios-separadas">
  ### Раздельные базы пользователей
</div>

У каждой среды своя база пользователей. Учётные записи, зарегистрированные в среде разработки, **не** существуют в среде продакшена, и наоборот:

* Пользователь, зарегистрировавшийся при тестировании в dev/preview-версии приложения, создаётся только в базе среды разработки.
* Пользователь, зарегистрировавшийся в вашем опубликованном приложении, создаётся только в базе продакшена.
* Сессии, метаданные пользователей и любые данные, которые вы привязываете к `userId` из Clerk, тоже доступны только в той среде, где была создана учётная запись.

Это ожидаемое поведение. Чтобы посмотреть пользователей в каждой среде, откройте **панель Auth** в своём Workspace и переключайтесь между разработкой и продакшеном с помощью переключателя среды на вкладке **Users**.

<Note>
  Среда разработки — это место, где вы экспериментируете и создаёте приложение; продакшен обслуживает реальных пользователей вашего приложения. Эти две среды изолированы намеренно, поэтому учётные записи и данные, созданные в разработке, в продакшене не появятся.
</Note>

<div id="gerenciando-usurios">
  ## Управление пользователями
</div>

**Панель Auth** в редакторе проекта даёт полное представление об аутентифицированных пользователях. Поскольку Clerk Auth создаёт для вашего приложения отдельную базу пользователей, перечисленные здесь пользователи — это учётные записи в вашем приложении, а не учётные записи Replit.

<Frame>
  <img src="/assets/mirror/clerk-users-4940ed365605.png" alt="Вкладка пользователей Clerk Auth с аутентифицированными пользователями на панели Auth" width="2136" height="794" data-path="images/workspace/auth/clerk-users.png" />
</Frame>

На вкладке **Users** вы можете:

* **Просматривать всех пользователей** с такими данными, как адрес электронной почты, имя, последний вход и дата создания учётной записи
* **Искать и фильтровать**, чтобы найти нужных пользователей
* **Блокировать и разблокировать пользователей**, управляя доступом к приложению
* **Сортировать пользователей** по различным критериям
* **Переключать среду** — переходите между средой разработки и продакшеном, чтобы управлять пользователями в каждой из них

<div id="personalizando-sua-pgina-de-login">
  ## Настройка страницы входа
</div>

Визуальное оформление страниц входа и регистрации — название приложения, логотип, цвета, шрифты и тексты — задаётся в коде вашего приложения, а не на панели Auth. Чтобы изменить его, попросите Agent:

```
Обнови мою страницу входа: используй [название вашего приложения] в качестве
заголовка, [опишите ваш логотип] и подбери цвета в тон моему сайту.
```

Внутри это управляется свойствами `appearance` и `localization`, передаваемыми в `<ClerkProvider>`, а также файлом логотипа в каталоге `public/` вашего приложения. Agent синхронизирует их с остальным оформлением приложения.

<Note>
  Название приложения, которое отображается **на самом экране согласия Google, Apple, GitHub или X** (экран, появляющийся после того, как пользователь нажимает &quot;Sign in with Google&quot; и т. п.), задаётся отдельно — оно берётся из приложения OAuth, зарегистрированного у этого провайдера, и **не** меняется при редактировании кода вашей страницы входа. Чтобы изменить его, настройте [пользовательские учётные данные OAuth](#configuring-oauth-credentials-for-an-sso-provider) для этого провайдера.
</Note>

<div id="configurando-provedores-de-login">
  ## Настройка провайдеров входа
</div>

Clerk Auth поддерживает Google, GitHub, Apple и X в качестве провайдеров входа через социальные сети. На вкладке **Configure** панели Auth вы задаёте, какие провайдеры отображаются на странице входа, а в среде продакшена — использует ли каждый провайдер учётные данные OAuth, управляемые Replit, или ваши собственные, чтобы оформить вход в фирменном стиле.

<Frame>
  <img src="/assets/mirror/clerk-configure-60169c473d64.png" alt="Вкладка Configure с провайдерами SSO в боковой панели, выбранным Production и списком провайдеров с переключателями активации и действиями Edit" width="923" height="378" data-path="images/workspace/auth/clerk-configure.png" />
</Frame>

Откройте вкладку **Configure**. В боковой панели в разделе **SSO providers** выберите **Development** или **Production**: **Development** обслуживает приложение в режиме разработки и предпросмотра в Workspace, а **Production** — ваше опубликованное приложение. У каждой среды свой список в основной панели. Здесь вы можете:

* **Включить или отключить провайдера** — с помощью переключателя задайте, отображается ли провайдер на странице входа. Отключённые провайдеры пользователям не видны.
* **Настроить собственные учётные данные OAuth (только Production)** — см. раздел [Настройка учётных данных OAuth для провайдера SSO](#configuring-oauth-credentials-for-an-sso-provider) ниже.

<div id="configurando-credenciais-oauth-para-um-provedor-sso">
  ### Настройка учётных данных OAuth для провайдера SSO
</div>

По умолчанию провайдеры используют **учётные данные, управляемые Replit**: вход работает без настройки, но на экране согласия OAuth отображается фирменный стиль Replit. Переключитесь на **Custom credentials**, чтобы использовать собственный клиент OAuth из консоли разработчика провайдера — тогда на экране согласия будут показаны название и фирменный стиль вашего приложения.

1. Откройте **панель Auth** в редакторе проекта. Перейдите на вкладку **Configure**, затем в разделе **SSO providers** на боковой панели выберите **Production**.

<Frame>
  <img src="/assets/mirror/clerk-configure-60169c473d64.png" width="923" height="378" data-path="images/workspace/auth/clerk-configure.png" />
</Frame>

2. Нажмите значок **Edit** рядом с провайдером, который хотите настроить. По умолчанию выбран вариант **Replit-managed credentials**.

<Frame>
  <img src="/assets/mirror/clerk-sso-default-credentials-525090775408.png" alt="Панель редактирования провайдера с вариантами Replit-managed credentials и Custom credentials" width="1468" height="960" data-path="images/workspace/auth/clerk-sso-default-credentials.png" />
</Frame>

3. Выберите **Custom credentials**. Панель развернётся и покажет поля учётных данных, а также контрольный список **Provider setup** со значениями, которые нужно зарегистрировать на стороне провайдера.

<Frame>
  <img src="/assets/mirror/clerk-sso-custom-credentials-f24112a5cf07.png" alt="Панель пользовательских учётных данных с полями OAuth client ID и secret, а также контрольным списком Provider setup с URL обратных вызовов перенаправления и источниками JavaScript" width="1468" height="2246" data-path="images/workspace/auth/clerk-sso-custom-credentials.png" />
</Frame>

4. Следуйте инструкциям, чтобы завершить настройку. В них есть прямые ссылки на консоль и на соответствующую справочную документацию. Эти справочные материалы для вашего провайдера также можно найти в разделе [Дополнительные ресурсы](#additional-resources).
5. Заполните все обязательные поля учётных данных.
6. В портале разработчика провайдера зарегистрируйте каждый пункт из контрольного списка **Provider setup**. Используйте значки копирования, чтобы скопировать каждое значение в точности, и отмечайте пункты по мере выполнения либо выберите **Mark all as done**, когда закончите.
7. Нажмите **Save changes**.

<div id="revalidando-a-configurao-aps-alteraes-de-domnio">
  ### Повторная проверка настроек после изменения домена
</div>

Операции, связанные с доменом, — например, привязка нового внешнего домена или [покупка домена через Replit](/ru/pt/build/domain-purchasing) — могут изменить URL-адреса обратного вызова для перенаправления и источники JavaScript вашего приложения. В этом случае для каждого провайдера, настроенного с собственными учётными данными, может потребоваться зарегистрировать новые значения в его консоли разработчика.

После изменения домена вернитесь на вкладку **Configure**. Напоминания о настройке отображаются в виде значков предупреждения на вкладке, на боковой панели и рядом с провайдером в списке **SSO providers**. Значок предупреждения и надпись **setup steps remaining** рядом с провайдером означают, что в контрольном списке **Provider setup** этого провайдера появились новые пункты для выполнения.

<Frame>
  <img src="/assets/mirror/clerk-sso-setup-reminders-a5b092846006.png" alt="Вкладка Configure и боковая панель с предупреждением о настройке, а также список SSO providers со значком предупреждения и надписью «setup steps remaining» рядом с провайдером после изменения домена" width="923" height="378" data-path="images/workspace/auth/clerk-sso-setup-reminders.png" />
</Frame>

Откройте панель редактирования провайдера, скопируйте обновлённые значения из раздела **Provider setup**, зарегистрируйте их в консоли разработчика провайдера и выберите **Mark all as done**.

<div id="configurao-de-domnio-para-verificao-de-e-mail">
  ## Настройка домена для подтверждения электронной почты
</div>

Если в вашем приложении есть **регистрация по электронной почте и паролю**, Clerk отправляет код подтверждения на почту каждого нового пользователя. Настройка домена для отправки писем гарантирует, что такие письма будут приходить с адреса вашего приложения, а не задерживаться или блокироваться спам-фильтрами.

<div id="quando-voc-precisa-dessa-configurao">
  ### Когда эта настройка необходима
</div>

Настраивать DNS-записи нужно только в том случае, если к вашему приложению привязан **внешний домен,管理 которым управляет другой провайдер** (например, домен, зарегистрированный в Cloudflare, GoDaddy, Namecheap или аналогичном сервисе).

Никакой настройки не требуется, если ваше приложение доступно по:

* субдомену `.replit.app`
* домену, [приобретённому через Replit](/ru/pt/build/domain-purchasing)

В обоих случаях Replit управляет DNS-записями за вас.

<div id="adicione-registros-dns-para-o-envio-de-e-mail">
  ### Добавьте DNS-записи для отправки писем
</div>

Чтобы разрешить приложению отправлять письма с кодами подтверждения с вашего внешнего домена, добавьте набор DNS-записей у своего доменного регистратора.

1. В редакторе проекта откройте **Publishing**.
2. Выберите **Domains**.
3. Найдите привязанный внешний домен и выберите **Manage**.
4. В разделе **Authentication DNS setup required** скопируйте записи CNAME, которые показывает Replit, — именно они нужны Clerk для отправки писем подтверждения с вашего домена.
5. Войдите в панель своего DNS-провайдера (Cloudflare, GoDaddy, Namecheap и т. д.) и добавьте каждую запись в точности так, как показано.

<Frame>
  <img src="/assets/mirror/clerk-domain-8797ea9f41fc.png" alt="Панель Manage домена с разделом Authentication DNS setup required и записями CNAME для отправки писем Clerk" width="1156" height="1524" data-path="images/workspace/auth/clerk-domain.png" />
</Frame>

Распространение изменений DNS может занять до 48 часов. Как только записи заработают, регистрация по электронной почте и паролю начнёт автоматически доставлять коды подтверждения с вашего домена — никаких дополнительных действий в панели Auth не потребуется.

<div id="soluo-de-problemas">
  ### Устранение неполадок
</div>

* **Письма для подтверждения не приходят** — убедитесь, что каждая запись добавлена в точности так, как показано на панели Manage, включая завершающие точки, если этого требует ваш DNS-провайдер. Проверьте папку «Спам» у получателя.
* **Записи по-прежнему не обнаружены** — дождитесь распространения DNS (до 48 часов) и снова проверьте на панели Manage, не осталось ли записей, отмеченных как отсутствующие.

<div id="melhores-prticas-de-segurana">
  ## Рекомендации по безопасности
</div>

* **Всегда выполняйте проверку на сервере** — проверяйте аутентификацию в маршрутах API, а не только в интерфейсе
* **Используйте переменные окружения** — никогда не прописывайте ключи и секреты прямо в коде
* **Подключайте middleware прокси первым** — прокси Clerk должен монтироваться раньше body parsers в вашем приложении Express
* **Не перенаправляйте главную страницу на страницу входа** — лендинг должен оставаться доступным для неаутентифицированных посетителей

<div id="faq">
  ## Часто задаваемые вопросы
</div>

<div id="preciso-de-uma-conta-clerk-para-usar-o-clerk-auth">
  ### Нужен ли аккаунт Clerk, чтобы использовать Clerk Auth?
</div>

Нет. Тенант Clerk, на котором работает Clerk Auth, Replit создаёт и обслуживает автоматически, когда Agent настраивает ваше приложение, — вам не нужно регистрироваться в Clerk и самостоятельно управлять его инфраструктурой.

<div id="posso-acessar-o-painel-do-clerk-para-a-instncia-clerk-gerenciada-pelo-replit">
  ### Могу ли я зайти в панель управления Clerk для экземпляра Clerk, управляемого Replit?
</div>

Нет. Экземпляр Clerk, управляемый Replit, через панель управления Clerk недоступен. Управляйте им через инструмент **Auth** в редакторе проекта — именно там вы настраиваете провайдеров, просматриваете пользователей и переключаетесь между средами разработки и продакшена.

<div id="minha-chave-publicvel-do-clerk-comea-com-pk_test-como-eu-troco-para-uma-chave-ativa">
  ### Мой публикуемый ключ Clerk начинается с `pk_test`. Как переключиться на рабочий ключ?
</div>

Этого не требуется. Ключи `pk_test...` и `sk_test...`, которые вы видите на панели Secrets в workspace, относятся к среде Clerk **разработки** вашего приложения и используются во время разработки. При публикации приложения развёртывание автоматически запускается с ключами `pk_live...` и `sk_live...` из среды продакшена. Чтобы убедиться в этом, откройте **Publishing → Overview → Adjust settings** в своём Workspace и проверьте значение `CLERK_PUBLISHABLE_KEY` для опубликованного приложения — оно будет начинаться с `pk_live`. Не редактируйте эти ключи вручную. Подробности смотрите в разделе [Среды разработки и продакшена](#development-and-production-environments).

<div id="por-que-no-consigo-fazer-login-no-meu-app-publicado-com-a-conta-que-criei-durante-o-desenvolvimento">
  ### Почему я не могу войти в опубликованное приложение под учётной записью, созданной во время разработки?
</div>

В Clerk Auth среды **Разработка** и **Продакшен** имеют раздельные базы пользователей. Учётная запись, созданная в dev/preview-версии приложения, существует только в среде разработки и не переносится в продакшен при публикации — в опубликованном приложении потребуется зарегистрироваться заново. То же касается любых данных, привязанных к `userId` из Clerk. Откройте **панель Auth** в своём Workspace и с помощью переключателя среды на вкладке **Users** просмотрите пользователей в каждой из сред. Подробности см. в разделе [Раздельные базы пользователей](#separate-user-stores).

<div id="o-clerk-auth-gratuito">
  ### Clerk Auth бесплатный?
</div>

Пока Clerk Auth предоставляется бесплатно. В дальнейшем может появиться тарификация по факту использования — по аналогии с другими сервисами Replit с оплатой за использование. Все будущие списания будут проходить через ваш действующий счёт в Replit: отдельный счёт или способ оплаты от Clerk вам не понадобится.

<div id="o-clerk-auth-tem-um-limite-de-mau-como-os-planos-externos-do-clerk">
  ### Есть ли в Clerk Auth ограничение на MAU, как во внешних тарифах Clerk?
</div>

Нет. Clerk Auth не ограничивает число ежемесячных активных пользователей (MAU) — в отличие от внешних тарифов Clerk, где лимит MAU зависит от уровня тарифа.

<div id="como-o-clerk-auth-se-compara-ao-clerk-externo">
  ### Чем Clerk Auth отличается от внешнего Clerk?
</div>

У управляемого Replit тенанта Clerk, на котором работает Clerk Auth, есть ряд особенностей по сравнению с приложениями Clerk, которые вы создаёте в собственной учётной записи Clerk (**внешний Clerk**). В таблице ниже показано, чем они различаются на текущий момент — это отражает нынешнее состояние Clerk Auth, и набор поддерживаемых возможностей будет расширяться.

|                                         | Clerk Auth                                                                        | Внешний Clerk                            |
| --------------------------------------- | --------------------------------------------------------------------------------- | ---------------------------------------- |
| **Настройка**                           | Разворачивается автоматически силами Replit                                       | Настраиваете самостоятельно              |
| **Владение тенантом Clerk**             | Управляется Replit, принадлежит вашему приложению                                 | Принадлежит вашей учётной записи Clerk   |
| **Схема тарификации**                   | Сейчас бесплатно (в будущем планируется оплата по факту использования)            | Подписка + оплата по факту использования |
| **Выставление счетов**                  | Счета от Replit (сейчас бесплатно)                                                | Счета в вашей учётной записи Clerk       |
| **Ограничение по MAU**                  | Без ограничений                                                                   | Ограничения по тарифным уровням          |
| **Настройка прокси и домена**           | Автоматическая для replit.app и купленного домена, ручная для привязанного домена | Ручная                                   |
| **Провайдеры SSO**                      | Поддерживаются отдельные провайдеры: Google, Apple, GitHub, X                     | Поддерживается больше провайдеров        |
| **Интерфейс управления пользователями** | Инструмент Auth в редакторе проекта                                               | Панель управления приложением Clerk      |
| **SMS**                                 | Не поддерживается                                                                 | Поддерживается                           |
| **MFA**                                 | Не поддерживается                                                                 | Поддерживается                           |
| **Тенанты организаций**                 | Не поддерживается                                                                 | Поддерживается                           |

<div id="que-configurao-comum-do-clerk-auth-eu-preciso-tratar-manualmente">
  ### Какие типичные настройки Clerk Auth нужно выполнять вручную?
</div>

Большая часть настройки Clerk Auth выполняется автоматически, но некоторые параметры требуют действий за пределами инструмента **Auth**:

* **Собственные учётные данные OAuth для SSO-провайдеров** — если вы хотите, чтобы на экране согласия провайдера отображались название и оформление вашего приложения (а не значения Replit по умолчанию), зарегистрируйте OAuth-приложение в консоли разработчика провайдера и вставьте полученные учётные данные на панель Auth. См. [Настройка учётных данных OAuth для SSO-провайдера](#configuring-oauth-credentials-for-an-sso-provider).
* **DNS-записи для подтверждения электронной почты на внешних доменах** — если к вашему приложению привязан внешний домен, управляемый другим провайдером, потребуется добавить DNS-записи, чтобы письма с подтверждением доставлялись с вашего домена. См. [Настройка домена для подтверждения электронной почты](#domain-setup-for-email-verification).

<div id="posso-usar-meu-prprio-app-clerk-em-vez-do-gerenciado-pelo-replit">
  ### Могу ли я использовать собственное приложение Clerk вместо управляемого Replit?
</div>

Да. Если для вашего приложения уже создано приложение Clerk, управляемое Replit, сначала удалите его, а затем подключайте собственное внешнее приложение Clerk:

1. Откройте панель **Auth** в редакторе проекта.
2. Перейдите на вкладку **Configure**.
3. Прокрутите страницу до конца и нажмите **Delete Clerk app**.

Удаление приложения Clerk удаляет тенант Clerk, управляемый Replit, и освобождает все связанные с ним домены — после этого вы сможете подключить собственное приложение Clerk и повторно использовать эти домены. Если для вашего приложения ещё нет приложения Clerk, управляемого Replit, этот шаг можно пропустить и сразу интегрировать своё внешнее приложение Clerk.
