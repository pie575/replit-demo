Ce guide explique comment copier manuellement une app vers un autre workspace ou compte. Vous copiez le code, configurez la nouvelle app, copiez vos données, puis redirigez vos utilisateurs vers la nouvelle app.

Rien n’est déplacé ni supprimé. L’ancien projet reste exactement là où il se trouve, et les deux copies ne sont pas synchronisées. Une fois l’opération terminée, vous choisissez de conserver ou de supprimer l’ancien projet.

<Note>
  Vous recherchez le transfert intégré en un clic ? Consultez [Transférer une App vers Teams](/fr/pt/teams/identity-and-access-management/transfer-app-to-teams). Utilisez ce guide lorsque cette option n’est pas disponible ou lorsque vous devez copier d’un compte à l’autre.
</Note>

<div id="antes-de-comear">
  ## Avant de commencer
</div>

Vous avez besoin de :

* D’un accès tant à l’ancien projet qu’au nouveau workspace ou compte.
* D’environ une heure à consacrer à la transition finale. Les étapes précédentes peuvent s’étaler sur plusieurs jours.
* Si votre app possède une adresse web personnalisée, d’un accès à l’endroit où vous gérez ce domaine.

Deux éléments ne sont pas copiés automatiquement et nécessitent le plus de temps : votre **base de données** et votre **adresse web**. Ce guide traite des deux.

<Note>
  Si l’administrateur de votre workspace a activé [Bloquer l’exportation du code source](/fr/pt/teams/enterprise-privacy-settings#ban-source-code-export), vous ne pouvez pas télécharger le projet au format ZIP. Contactez l’administrateur de votre workspace avant de commencer : il pourra confirmer si une copie manuelle est autorisée et vous indiquer comment déplacer le code et la base de données.
</Note>

<div id="planeje-o-tempo-de-inatividade">
  ## Prévoyez une période d’indisponibilité
</div>

Voyez cela comme l’ouverture d’une deuxième boutique, puis la fermeture de la première. Pendant une courte période, l’ancienne boutique est fermée et la nouvelle n’est pas encore ouverte. Durant ce temps, personne ne peut utiliser votre application.

**Combien de temps l’application sera-t-elle hors ligne ?** Généralement, de 15 à 60 minutes. Cela dépend de la quantité de données contenues dans votre base de données et de la rapidité avec laquelle votre adresse web est mise à jour.

**Vais-je perdre des données ?** Uniquement si quelqu’un ajoute des données à l’ancienne application après que vous avez copié la base de données. Pour éviter cela, vous mettez l’ancienne application hors ligne *avant* d’effectuer la copie finale. Les étapes de ce guide sont organisées de façon à ce que ce soit le cas.

**Puis-je annuler cette opération ?** Oui. L’ancien projet n’est pas supprimé. En cas de problème, republiez l’ancienne application et elle fonctionnera exactement comme avant.

**Quand dois-je effectuer cette opération ?** Choisissez un moment où peu de personnes utilisent votre application. Prévenez vos utilisateurs à l’avance, si possible.

<div id="etapa-1-copiar-o-cdigo-para-um-novo-projeto">
  ## Étape 1 : Copier le code dans un nouveau projet
</div>

Choisissez une méthode. L&#39;ancienne App reste active pendant cette étape. Les deux méthodes transfèrent votre code. GitHub transfère toujours l&#39;historique de vos commits, tandis qu&#39;un fichier zip ne le transfère que s&#39;il inclut le dossier `.git` :

|                              | Via GitHub                                                                | Via un fichier zip                                                                                                                          |
| ---------------------------- | ------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------- |
| **Fichiers de code**         | Uniquement les fichiers que vous committez et envoyez (push)              | Tout ce qui se trouve sur le disque, y compris les modifications non commités                                                               |
| **Historique des commits**   | Historique complet sur le dépôt distant                                   | Historique complet si le zip inclut le dossier `.git`. Aucun historique si vous excluez `.git` pour rester sous la limite d&#39;importation |
| **Dossiers de dépendances**  | Suit votre `.gitignore`                                                   | Exclus (`node_modules`, `.venv`, `build` et similaires) ; réinstallés lors de l&#39;importation                                             |
| **Exigences**                | Un compte GitHub connecté aux deux comptes Replit                         | Aucune                                                                                                                                      |
| **Synchronisation continue** | Les deux copies peuvent effectuer des push et des pull vers le même dépôt | Aucune — copie unique                                                                                                                       |
| **Idéal pour**               | Les projets que vous souhaitez sauvegarder dans Git à long terme          | Les copies uniques et rapides                                                                                                               |

<div id="via-github">
  ### Via GitHub
</div>

<Steps>
  <Step title="Envoyez l’ancien projet sur GitHub">
    Dans l’ancien projet, ouvrez le [panneau Git](/fr/pt/features/workspace-tools/git-interface), connectez un dépôt GitHub, puis effectuez un commit et un push. Utilisez un dépôt privé, sauf si vous souhaitez rendre le code public.
  </Step>

  <Step title="Accordez l’accès au nouveau compte">
    Si le nouveau workspace appartient à un autre compte Replit, le compte GitHub associé doit avoir accès au dépôt. Pour un dépôt privé, ajoutez ce compte GitHub comme collaborateur ou utilisez une organisation GitHub partagée.
  </Step>

  <Step title="Importez dans le nouveau workspace">
    Connectez-vous au nouveau compte, ouvrez [replit.com/import](https://replit.com/import), sélectionnez **GitHub**, connectez le compte GitHub et choisissez le dépôt. Consultez [Importer depuis un fournisseur](/fr/pt/build/import-from-providers) en cas de problème.
  </Step>

  <Step title="Vérifiez la copie">
    Ouvrez le nouveau projet et vérifiez que les fichiers et l’historique des commits sont présents. Replit installe les dépendances et configure les commandes d’exécution lors de l’importation.
  </Step>
</Steps>

<Warning>
  GitHub ne reçoit que ce que vous commitez et envoyez. Les fichiers correspondant à `.gitignore` et les modifications non commitées sont exclus. Ne commitez jamais de valeurs Secrets ni d’exports de bases de données dans le dépôt.
</Warning>

<div id="via-arquivo-zip">
  ### Par fichier zip
</div>

<Steps>
  <Step title="Téléchargez l’ancien projet">
    Dans l’ancien projet, ouvrez le menu à trois points en haut de l’arborescence des fichiers et choisissez **Télécharger au format zip**.

    Si le téléchargement réussit et que le fichier fait moins de 200 MB, passez à l’étape suivante.

    Un fichier zip de plus de 200 MB peut être téléchargé avec succès. Cependant, l’[importation de ZIP](/fr/pt/build/import-from-providers#limitations) rejette les fichiers de plus de 200 MB : Replit ne peut donc pas l’utiliser pour créer le nouveau projet. Si le téléchargement échoue ou si le zip fait plus de 200 MB, créez-en un plus petit :

    1. Dans l’ancien projet, ouvrez l’outil **Shell**.

    2. Collez cette commande et appuyez sur Entrée. Elle crée un fichier nommé `project.zip` et exclut les dossiers que Replit peut recréer automatiquement :

       ```bash theme={null}
       zip -r project.zip . -x ".cache/*" "node_modules/*" ".venv/*" "venv/*" ".pythonlibs/*" "build/*" "target/*" ".next/*" "__pycache__/*"
       ```

    3. Vérifiez la taille. Collez cette commande et appuyez sur Entrée. Elle affiche la taille en MB, par exemple `150M` pour 150 MB :

       ```bash theme={null}
       du -h project.zip
       ```

    4. Si la taille est supérieure à 200 MB, réduisez le fichier en excluant l’historique de vos modifications. Collez les deux lignes et appuyez sur Entrée :

       ```bash theme={null}
       rm project.zip
       zip -r project.zip . -x ".cache/*" ".local/*" ".git/*" "node_modules/*" ".venv/*" "venv/*" ".pythonlibs/*" "build/*" "target/*" ".next/*" "__pycache__/*"
       ```

       Excluez `.local` et `.git` uniquement si vous devez réduire le zip à moins de 200 MB. Ces exclusions ne suppriment aucun dossier de l’ancien projet. Toutefois, un zip sans `.git` n’inclut pas l’historique des commits du projet. Utilisez la méthode GitHub si vous devez préserver cet historique.

    5. Trouvez `project.zip` dans l’arborescence des fichiers, ouvrez le menu à trois points à côté du fichier, puis sélectionnez **Télécharger**.

    Le dossier `.cache` stocke l’état interne de Replit, notamment les valeurs Secrets mises en cache. Excluez-le toujours des fichiers zip que vous créez manuellement. Si votre projet comporte d’autres dossiers générés volumineux, ajoutez-les à la liste d’exclusion.
  </Step>

  <Step title="Importez dans le nouveau workspace">
    Connectez-vous au nouveau compte, ouvrez [replit.com/import](https://replit.com/import), sélectionnez **ZIP** et téléversez le fichier.
  </Step>

  <Step title="Vérifiez la copie">
    Ouvrez le nouveau projet et vérifiez que vos fichiers sont présents. Si le zip inclut le dossier `.git`, l’historique de vos commits est également inclus. Si vous avez utilisé la commande pour créer un fichier plus petit, le nouveau projet démarre sans historique de commits. Replit réinstalle les dépendances exclues pendant l’importation.
  </Step>
</Steps>

<div id="etapa-2-configurar-o-novo-app">
  ## Étape 2 : Configurer la nouvelle App
</div>

L’ancienne App est toujours active. À cette étape, configurez la nouvelle App pour qu’elle soit entièrement fonctionnelle avec une *copie de test* de vos données, afin que la bascule finale soit rapide.

<Steps>
  <Step title="Ajoutez vos Secrets">
    Les valeurs stockées dans Secrets (clés API, mots de passe) ne quittent jamais l’ancien projet. Ouvrez l’outil [Secrets](/fr/pt/core-concepts/project-editor/app-setup/secrets) dans les deux projets et copiez-les manuellement, une par une. Incluez tous les secrets de déploiement.
  </Step>

  <Step title="Reconnectez les connecteurs et les autres services">
    Reconnectez chaque intégration dans **Tools → connecteurs** du nouveau projet. Consultez [Recréez ce qui n’est pas copié](#recrie-o-que-nao-e-copiado) pour App Storage, les collaborateurs et tout le reste.
  </Step>

  <Step title="Publiez la nouvelle App">
    [Publiez](/fr/pt/features/publishing/overview) le nouveau projet. Il dispose de sa propre adresse web `replit.app` et de sa propre base de données de production vide. Ne connectez pas encore votre domaine personnalisé.
  </Step>

  <Step>
    Suivez les instructions de la section [Copier la base de données](#copiar-o-banco-de-dados) ci-dessous, en utilisant la base de données de **production** du nouveau projet comme destination. Vous disposerez ainsi de données réelles pour vos tests. L’étape 3 remplacera cette copie par vos données les plus récentes.
  </Step>

  <Step>
    Ouvrez la nouvelle App à l’adresse `replit.app` et utilisez-la comme le feraient vos utilisateurs. Corrigez tout problème avant de continuer. Vos utilisateurs ne sont pas encore affectés.
  </Step>
</Steps>

<div id="etapa-3-direcionar-seus-usurios-para-o-novo-app">
  ## Étape 3 : rediriger vos utilisateurs vers la nouvelle app
</div>

Cette étape entraîne une interruption de service. Effectuez-la en une seule session.

<Steps>
  <Step title="Mettre l’ancienne app hors ligne">
    Dans l’ancien projet, ouvrez l’outil **Publishing** et sélectionnez **Unpublish**. Votre app est désormais hors ligne. Personne ne peut plus ajouter de données à ce stade. La copie que vous effectuerez ensuite sera donc complète.
  </Step>

  <Step title="Copier la base de données une dernière fois">
    Suivez les instructions de [Copier la base de données](#copiar-o-banco-de-dados) ci-dessous, en utilisant la base de données de **production** du nouveau projet comme destination. Cette copie contient toutes vos données les plus récentes.
  </Step>

  <Step title="Rediriger votre adresse web vers la nouvelle app">
    Si votre app utilise un domaine personnalisé : dans l’ancien projet, ouvrez **Publishing → Domains** et déconnectez le domaine. Dans le nouveau projet, ouvrez **Publishing → Domains** et [connectez-le](/fr/pt/features/publishing/custom-domains#connect-a-domain-you-already-own). Mettez à jour les enregistrements auprès de votre fournisseur de domaine (par exemple, GoDaddy ou Namecheap) si Replit vous le demande.

    La nouvelle adresse peut mettre de quelques minutes à quelques heures avant de fonctionner pour tout le monde. D’ici là, certains visiteurs peuvent voir une erreur.

    Si votre app utilise uniquement une adresse `replit.app`, partagez la nouvelle adresse avec vos utilisateurs.
  </Step>

  <Step title="Confirmer que la nouvelle app est en ligne">
    Ouvrez votre adresse web et vérifiez que la nouvelle app se charge avec vos données. Votre app est de nouveau en ligne.
  </Step>
</Steps>

<div id="copiar-o-banco-de-dados">
  ## Copier la base de données
</div>

La copie du code n’affecte pas votre base de données. Copiez les données à l’aide des outils PostgreSQL `pg_dump` et `pg_restore`, disponibles dans le Shell des deux projets. Les étapes 2 et 3 renvoient toutes deux à cette page. Les commandes sont les mêmes à chaque fois. Seule la *destination* change.

<Warning>
  Les données écrites après l’exécution de `pg_dump` ne sont pas incluses dans la copie. Pour la copie finale à l’étape 3, mettez d’abord l’ancienne app hors ligne.
</Warning>

<Steps>
  <Step title="Exportez les données de l’ancien projet">
    Ouvrez l’outil **Shell** dans l’ancien projet. Collez cette commande et appuyez sur Entrée. Elle crée un fichier nommé `backup.dump` dans votre arborescence de fichiers :

    ```bash theme={null}
    pg_dump -Fc "$DATABASE_URL" --no-owner --no-privileges -f backup.dump
    ```

    Cela exporte la base de données de **développement**. Vos données de production se trouvent généralement dans la base de données de **production**. Pour l’exporter :

    1. Ouvrez l’outil **Database**, sélectionnez la base de données de production et ouvrez **Paramètres**.
    2. Copiez la chaîne de connexion.
    3. Dans la commande ci-dessus, remplacez `"$DATABASE_URL"` par la chaîne de connexion, en conservant les guillemets.

    Consultez les [détails de connexion](/fr/pt/features/data-and-storage/connection-details) si vous ne parvenez pas à la trouver.
  </Step>

  <Step title="Déplacez le fichier dump vers le nouveau projet">
    Dans l’arborescence de fichiers de l’ancien projet, sélectionnez le menu à trois points à côté de `backup.dump` et téléchargez-le. Téléversez-le ensuite vers le nouveau projet avec l’option **Téléverser des fichiers** de l’arborescence de fichiers.

    Si vous avez copié le code via GitHub, ne validez pas le dump. Déplacez-le séparément afin que vos données n’atteignent jamais le dépôt.
  </Step>

  <Step title="Importez les données dans le nouveau projet">
    Ouvrez l’outil **Shell** dans le nouveau projet. Collez cette commande et appuyez sur Entrée :

    ```bash theme={null}
    pg_restore --clean --if-exists --single-transaction --no-owner --no-privileges --exit-on-error -d "$DATABASE_URL" backup.dump
    ```

    Tel qu’il est écrit, cela importe les données dans la base de données de **développement** du nouveau projet. C’est ce que vous voulez à l’étape 2.

    Pour la copie finale à l’étape 3, vous devez plutôt utiliser la base de données de **production**. Dans le nouveau projet, ouvrez l’outil **Database**, sélectionnez la base de données de production, ouvrez **Paramètres**, copiez la chaîne de connexion et utilisez-la à la place de `"$DATABASE_URL"`.

    Cela supprime tous les objets correspondants de la base de données de destination, puis charge les données. Si l’opération se termine sans afficher de sortie, elle a réussi.
  </Step>
</Steps>

<Note>
  Si `pg_restore` échoue avec des erreurs de rôle ou de politique, votre base de données utilise des rôles PostgreSQL personnalisés qui n’existent pas encore dans le nouveau projet. [Contactez l’assistance](https://replit.com/support) pour obtenir de l’aide.
</Note>

<Note>
  Si le nouveau projet utilise une [base de données de développement Neon héritée](/fr/pt/features/data-and-storage/development-and-production#legacy-development-database), le flux de publication propose **Configurer votre base de données de production avec vos données de développement actuelles**. Cela copie les données présentes dans la base de données de développement au moment de la publication. Cette option convient aux tests, mais pour le basculement final, utilisez les étapes ci-dessus afin d’obtenir les données les plus récentes.
</Note>

<div id="recrie-o-que-no-copiado">
  ## Recréez les éléments non copiés
</div>

Le reste de la configuration du projet se trouve en dehors du système de fichiers. Recréez chaque élément dans le nouveau projet :

| Élément                    | À faire                                                                                                                                                                                                                                                                                                 |
| -------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Secrets**                | Les valeurs des secrets ne quittent jamais l’ancien projet. Ajoutez-les de nouveau dans l’outil [Secrets](/fr/pt/core-concepts/project-editor/app-setup/secrets) du nouveau projet, y compris les secrets de déploiement.                                                                                  |
| **Secrets de compte**      | [Associez-les](/fr/pt/core-concepts/project-editor/app-setup/secrets#manage-account-secrets) au nouveau projet. Si le nouveau projet se trouve dans un compte différent, ajoutez-les d’abord à ce compte.                                                                                                  |
| **App Storage**            | Les buckets ne sont pas déplacés. Au sein du même compte, [ajoutez le bucket existant](/fr/pt/features/data-and-storage/object-storage#bucket-access-management) au nouveau projet. Entre différents comptes, téléchargez les objets et importez-les dans un nouveau bucket.                               |
| **Connecteurs**            | Reconnectez chaque intégration dans **Tools → Connectors** du nouveau projet. Consultez la [vue d’ensemble des intégrations](/fr/pt/features/integrations/overview).                                                                                                                                       |
| **Déploiements**           | La copie n’est pas publiée. [Publiez-la](/fr/pt/features/publishing/overview) depuis le nouvel workspace, comme dans l’[étape 2](#etapa-2-configurar-o-novo-app).                                                                                                                                  |
| **Domaines personnalisés** | Supprimez le domaine de l’ancien déploiement, associez-le au nouveau et mettez à jour vos enregistrements DNS. Cette procédure est abordée dans l’[étape 3](#etapa-3-direcionar-seus-usuarios-para-o-novo-app).                                                                                         |
| **Collaborateurs**         | Invitez de nouveau les collaborateurs et configurez l’[accès](/fr/pt/teams/identity-and-access-management/groups-and-permissions) dans le nouvel workspace.                                                                                                                                        |
| **Historique de l’Agent**  | Les conversations avec l’Agent et les retours en arrière de [checkpoint](/fr/pt/features/version-control/checkpoints-and-rollbacks) restent associés à l’ancien projet. Les commits de checkpoint sont conservés dans votre historique Git, mais vous ne pouvez pas revenir à ces commits depuis la copie. |

<div id="se-algo-der-errado">
  ## En cas de problème
</div>

L’ancien projet est toujours là. Pour revenir en arrière :

1. Dans l’ancien projet, ouvrez l’outil **Publishing** et sélectionnez **Publier**.
2. Si vous avez déplacé un domaine personnalisé, remettez-le à son emplacement d’origine de la même manière.

Votre app est de nouveau en ligne avec les données qu’elle contenait lorsque vous l’avez mise hors ligne. Rien n’a été perdu.

<div id="limpeza">
  ## Nettoyage
</div>

Attendez environ une semaine pour vous assurer que la nouvelle App fonctionne correctement. Ensuite :

* Supprimez `backup.dump` des deux projets et de votre appareil. Chaque copie contient une exportation complète de vos données.
* Vous pouvez également supprimer l’ancien projet.
