여기서는 게시와 배포에 대한 내용을 다룹니다. 단계별 문제 해결 방법은 [배포 문제 해결](/ko/build/troubleshooting)을, 배포 type과 Monitoring은 [Autoscale Deployments](/ko/features/publishing/deployment-types#autoscale)와 [배포 모니터링](/ko/features/publishing/monitoring-a-deployment)을 참고하세요.

<AccordionGroup>
  <Accordion title="&#x22;Creating Autoscale service&#x22;에서 게시에 실패합니다. 어떻게 디버그하나요?">
    대부분의 Autoscale 게시 실패는 deployment logs를 확인하면 해결할 수 있습니다:

    1. **Publishing**을 열고 실패한 deployment를 찾습니다.
    2. 해당 항목 옆의 three-dot menu를 선택해 logs를 엽니다.
    3. 로그 출력을 복사한 뒤 새 Agent chat을 열어 붙여넣고, 무엇이 문제이고 어떻게 해결하면 되는지 물어보세요.

    Run command를 설정했는데도 `No run command configured` 오류가 나타난다면, deployment 설정을 열고 run command 연결을 해제했다가 다시 추가한 뒤, 저장하고 republish하세요. 자세한 내용은 [Troubleshooting deployments](/ko/build/troubleshooting)를 참고하세요.
  </Accordion>

  <Accordion title="앱을 성공적으로 게시했는데 Internal Server Error가 표시되는 이유는 무엇인가요?">
    게시는 성공했지만 라이브 앱에서 500 오류가 반환된다면, 문제는 Replit의 인프라가 아니라 앱 코드에 있습니다.

    1. **Publishing**을 열어 로그를 확인한 뒤 전체 오류 텍스트를 복사합니다.
    2. 새 Agent chat을 열고 로그를 붙여넣은 다음, 오류의 원인이 무엇인지 물어봅니다.
    3. 수정 사항을 적용하고 다시 게시합니다.

    Agent가 문제를 찾지 못한다면 **Publishing → History**를 열어 마지막으로 정상 작동한 버전을 찾아 다시 배포하세요. [deployment 문제 해결](/ko/build/troubleshooting)을 참고하세요.
  </Accordion>

  <Accordion title="배포가 빌드 또는 마이그레이션 중에 멈췄습니다. 어떻게 해야 하나요?">
    1. `Cmd+K`(Mac) 또는 `Ctrl+K`(Windows)로 명령 팔레트를 열고 **Restart compute**를 검색해 선택합니다.
    2. **Publishing**을 열고 **Publish**를 선택해 새 deployment를 시작합니다.
    3. 다시 실패하면 점 3개 메뉴에서 실패한 deployment의 logs를 열어 빌드 로그를 복사한 뒤, 진단을 위해 새 Agent chat에 붙여넣으세요.

    deployment가 계속 멈춰 있다면 전체 빌드 로그와 함께 [Replit Support에 문의](https://replit.com/support)하세요. [deployments 문제 해결](/ko/build/troubleshooting)도 참고하세요.
  </Accordion>

  <Accordion title="앱은 게시되었지만 속도가 느리거나 시간 초과가 발생합니다. 무엇을 확인해야 하나요?">
    1. deployment logs에서 반복되는 타임아웃 또는 메모리 부족 메시지가 있는지 확인하세요.
    2. deployment 리소스의 CPU 또는 메모리 limit을 확인하세요. [deployment 모니터링](/ko/features/publishing/monitoring-a-deployment)을 참고하세요.
    3. 새 Agent chat을 열고 최근 logs를 붙여넣은 뒤, Agent에게 병목 지점을 찾아달라고 요청하세요.

    주요 원인으로는 인덱스가 없는 database 쿼리, 블로킹 동기 작업, 메모리 누수 등이 있습니다. [Autoscale deployments](/ko/features/publishing/deployment-types#autoscale)에서는 0으로 축소된 뒤 들어오는 첫 요청이 몇 초 정도 걸릴 수 있는데, 이는 정상적인 콜드 스타트입니다.
  </Accordion>

  <Accordion title="배포 기록에 빌드 실패가 표시됩니다. 원인을 어떻게 확인하나요?">
    **Publishing → History**를 열고 실패한 deployment를 선택한 뒤 빌드 logs를 확인하세요. `ERROR` 또는 `FAILED`로 표시된 첫 번째 줄을 찾으세요. 대개 그 줄이 근본 원인이고, 그 이후 줄들은 연쇄적으로 발생한 결과입니다. 해당 부분을 복사해 새 Agent chat에 붙여넣고 진단을 요청하세요. 빌드 실패는 대부분 dependencies 누락, 잘못된 run command, database migration 실패에서 비롯됩니다. [deployment 모니터링하기](/ko/features/publishing/monitoring-a-deployment)를 참고하세요.
  </Accordion>

  <Accordion title="내 앱이 에디터 Preview에서는 작동하는데 Publish하면 작동하지 않는 이유는 무엇인가요?">
    이는 거의 항상 환경 간 설정 차이 때문입니다. 다음을 확인하세요.

    * 개발 환경의 [Secrets](/ko/core-concepts/project-editor/app-setup/secrets) pane에 있는 모든 키가 deployment secrets에도 설정되어 있는지 확인하세요. 두 환경은 서로 분리되어 있습니다.
    * `DATABASE_URL`이 개발용이 아닌 production database를 가리키는지 확인하세요.
    * 하드코딩된 `localhost` 또는 `127.0.0.1` 참조가 없는지 확인하세요. 대신 상대 경로나 환경 기반 URL을 사용하세요.

    그런 다음 deployment logs에서 production 관련 오류를 확인하세요. [deployment 문제 해결](/ko/build/troubleshooting)을 참고하세요.
  </Accordion>

  <Accordion title="Autoscale Deployment가 계속 재시작됩니다—SIGTERM 또는 종료 코드 1은 무엇을 의미하나요?">
    [Autoscale deployments](/ko/features/publishing/deployment-types#autoscale)는 설계상 주기적으로 재시작됩니다. 로그에 `SIGTERM`이 표시되면 프로세스가 정상적으로 종료되었다는 뜻이며, 이는 정상적인 동작입니다. `Exit code 1`은 프로세스가 자체적으로 충돌했다는 의미이므로, 바로 앞 줄에서 실제 오류를 확인하세요.

    재시작이 너무 잦아 사용자에게 영향을 줄 정도라면, 처리되지 않은 프로미스 거부(unhandled promise rejection), 메모리 부족 오류, 또는 시작 실패를 유발하는 누락된 environment variables가 있는지 확인하세요.
  </Accordion>

  <Accordion title="환경 변수를 업데이트했는데 게시한 App에 적용되지 않는 이유는 무엇인가요?">
    Replit은 development와 production의 secret을 각각 별도의 저장소에 보관하므로, 한쪽을 변경해도 다른 쪽에는 반영되지 않습니다. [development Secrets](/ko/core-concepts/project-editor/app-setup/secrets) pane은 editor에서만 사용할 수 있으며, published app은 deployment secrets에서 값을 읽어옵니다.

    live app의 변수를 업데이트하려면 deployment secrets에서 값을 설정한 다음, **Publishing**을 열고 **Publish**를 선택해 다시 게시하세요. 새 값은 새 deployment가 시작될 때 적용됩니다. 자세한 내용은 [deployment 문제 해결](/ko/build/troubleshooting)을 참고하세요.
  </Accordion>

  <Accordion title="코드를 변경하지 않고 재배포하려면 어떻게 하나요?">
    **Publishing**을 열고 **Publish**를 선택하세요. 변경 사항이 없어도 Replit이 현재 코드를 빌드해 게시합니다. secret을 업데이트한 후, database 일시 정지를 해제한 후, 또는 dependency 업데이트를 반영하려는 경우에 유용합니다.

    앱이 응답하지 않지만 전체 재배포까지는 부담스럽다면, `Cmd+K`(Mac) 또는 `Ctrl+K`(Windows)로 명령 팔레트를 열고 **Restart compute**를 검색해 선택하세요.
  </Accordion>

  <Accordion title="앱을 게시한 후 배포 리전을 변경할 수 있나요?">
    아니요. 앱을 게시한 뒤에는 publishing geography를 기존 앱에서 바로 변경할 수 없습니다. 앱을 옮기려면 remix한 후 새 리전에 해당 Remix를 게시하세요. 자세한 내용은 [Project geography](/ko/features/publishing/project-geography)를 참고하세요.

    database 리전도 마찬가지로 바로 변경할 수 없습니다. remix한 앱에는 다른 `.replit.app` 서브도메인이 할당될 수 있으므로, 고정된 URL이 필요하다면 먼저 [custom domain](/ko/features/publishing/custom-domains)을 연결하고 deployment secrets를 다시 추가하세요.
  </Accordion>

  <Accordion title="PCI 또는 보안 검사에서 게시된 앱의 GAESA 쿠키가 감지되는 이유는 무엇인가요?">
    Google의 서빙 인프라는 요청을 올바른 인스턴스로 라우팅하기 위해 게시된 Replit App에 `GAESA`(Google App Engine session affinity) 쿠키를 추가합니다. 이 쿠키의 값은 의미를 알 수 없는 라우팅 식별자일 뿐이며, 민감한 정보나 애플리케이션 데이터는 포함하지 않습니다.

    일부 security scanner는 `GAESA`에 `Secure` 또는 `HttpOnly` 속성이 설정되어 있지 않다는 이유로 이를 문제로 표시합니다. 이 쿠키는 여러분의 App이 생성하는 것이 아니며, 게시된 앱에서는 변경하거나 비활성화할 수 없습니다.

    PCI 규정 준수 검사나 security scan에서 이 쿠키가 보고되면, 해당 finding이 오탐임을 스캔 vendor에 이의 제기하세요. 이때 쿠키 이름을 명시하고, Google 인프라가 요청 라우팅을 위해 설정하는 쿠키라는 점을 설명하면 됩니다. 여러분의 게시된 앱은 이 쿠키를 읽거나 변경하거나 비활성화할 수 없으며, 쿠키에는 민감한 데이터가 담겨 있지 않습니다.

    여러분이 build하는 App의 규정 준수는 여러분의 책임입니다. [공동 책임 모델](/ko/features/security/shared-responsibility-model)을 참조하세요. 스캔 vendor가 더 자세한 정보를 요청한다면 [Replit Support에 문의](https://replit.com/support)하세요.
  </Accordion>

  <Accordion title="내 앱을 오프라인으로 전환하거나 게시를 취소하려면 어떻게 해야 하나요?">
    **Publishing**을 열고 deployment를 종료하는 옵션을 선택한 후 확인합니다. 앱이 offline 상태가 되며 deployment 요금이 더 이상 발생하지 않습니다. project 파일과 코드, database는 삭제되지 않고 live deployment만 중지됩니다. 이 deployment에 연결된 custom domain은 연결이 해제되므로, 다시 republish할 때 재등록해야 합니다.

    비용이 걱정된다면, [Autoscale deployments](/ko/features/publishing/deployment-types#autoscale)는 트래픽이 없을 때 0으로 scale되므로 굳이 종료하지 않아도 됩니다.
  </Accordion>
</AccordionGroup>
