<div id="adicionar-cabealhos-de-resposta">
  ## Ajouter des en-têtes de réponse
</div>

Les **en-têtes de réponse** personnalisés vous permettent d’ajouter des directives d’en-tête HTTP aux requêtes correspondant à des chemins spécifiques.
Un en-tête de réponse est une paire nom-valeur qui indique aux navigateurs comment
interagir avec le contenu demandé.

Par exemple, vous pouvez spécifier l’en-tête `Access-Control-Allow-Origin` pour indiquer à quels domaines le navigateur peut accéder pour cette page.
Pour créer cette entrée, ajoutez ce qui suit au fichier `.replit` situé dans le répertoire racine de votre Replit App :

```
[[deployment.responseHeaders]]
path = "/*"
name = "Access-Control-Allow-Origin"
value = "origin"
```

Cet en-tête de réponse inclut les paramètres suivants :

* **path**: modèle de chemin d’URL correspondant aux ressources demandées
* **name**: nom de l’en-tête HTTP
* **value**: valeur de l’en-tête HTTP

Vous pouvez ajouter plusieurs entrées `deployment.responseHeaders` au fichier `.replit`.

Pour appliquer les modifications de configuration, republiez votre Replit App.

<div id="criar-uma-pgina-404-personalizada">
  ## Créer une page 404 personnalisée
</div>

Une page 404 personnalisée s’affiche lorsque les utilisateurs demandent des chemins d’URL qui ne correspondent à aucun fichier ni à aucune règle de votre app publiée.

Pour ajouter une page 404 personnalisée, créez son contenu dans un fichier nommé `404.html`, situé dans le répertoire racine de votre Replit App.

Lorsqu’ils tentent d’accéder à un chemin d’URL inexistant, les utilisateurs voient le HTML généré par la page 404 personnalisée.

<div id="definir-rewrites-de-caminho-de-url">
  ## Définir des réécritures d’URL
</div>

Vous pouvez définir des réécritures d’URL pour modifier le chemin d’URL d’une requête avant qu’elle ne soit traitée par votre Replit App.
L’URL d’origine reste visible dans le navigateur, mais le serveur charge la ressource définie dans la règle de réécriture.

Par exemple, vous pouvez spécifier que toutes les requêtes commençant par `/app` chargent le contenu du fichier `/app/index.html`.
Pour créer cette entrée, ajoutez ce qui suit au fichier `.replit` situé dans le répertoire racine de votre Replit App :

```
[[deployment.rewrites]]
from = "/app/*"
to = "/app/index.html"
```

* **from** : modèle de chemin d’URL correspondant aux ressources demandées
* **to** : chemin de réécriture correspondant à un fichier de votre déploiement statique.

Vous pouvez ajouter plusieurs entrées `deployment.rewrites` au fichier `.replit`.
Le serveur interprète les entrées dans l’ordre indiqué et ignore les doublons.

Pour appliquer les modifications de configuration, vous devez republier votre Replit App.

Les sections suivantes décrivent les contraintes des règles de réécriture d’URL.

<div id="correspondncia-de-caminho">
  ### Correspondance de chemins
</div>

Les restrictions suivantes s’appliquent aux paramètres `from` et `to` des règles de réécriture :

* Les correspondances doivent être exactes, sauf si un `*` est présent
* Un `*` correspond au reste du chemin
* Un `*` n’est valide qu’à la fin d’un chemin
* Lorsque vous incluez `*` dans le paramètre `from`, vous pouvez également l’inclure dans le paramètre `to` pour représenter la partie correspondante du chemin

Par exemple, si le fichier `.replit` contient la règle de réécriture suivante :

```
[[deployment.rewrites]]
from = "/v1/*"
to = "/v2/*"
```

Lorsqu’un utilisateur accède au chemin `/v1/about-us.html`, la règle de réécriture sert le fichier situé à l’emplacement `/v2/about-us.html`.

<div id="shadowing">
  ### Shadowing
</div>

Le shadowing se produit lorsqu’une réécriture correspond à un chemin d’URL qui correspond également à un fichier de votre déploiement statique.
Dans ce cas, le serveur cloud ignore la réécriture et sert directement le fichier.

Par exemple, supposons que votre app publiée contienne les fichiers suivants :

* `index.html`
* `about.html`

Le fichier `.replit` contient la réécriture suivante :

```
[[deployment.rewrites]]
from = "/*"
to = "/index.html"
```

Lorsqu’un utilisateur visite `/register.html`, le serveur réécrit la requête vers `/index.html` et sert ce fichier.
Cependant, si un utilisateur visite `/about.html`, le serveur ignore la réécriture et sert le fichier `about.html`, car il existe déjà dans votre déploiement statique.

<div id="restries-de-domnio">
  ### Restrictions de domaine
</div>

Les réécritures fonctionnent uniquement pour les requêtes adressées au domaine principal de votre déploiement statique et ne
peuvent rediriger que vers des fichiers de ce déploiement.
