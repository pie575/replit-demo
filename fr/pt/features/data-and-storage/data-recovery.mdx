Les erreurs arrivent : une modification de schéma malencontreuse, des lignes supprimées ou une session Agent qui tourne mal. Replit propose une solution de récupération pour chaque base de données.

| Base de données | Méthode de récupération                                    | Disponibilité                                                                                               |
| --------------- | ---------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------- |
| Développement   | Retour à un checkpoint                                     | Tous les plans                                                                                              |
| Production      | Restauration à un instant précis et sauvegardes planifiées | Core : jusqu&#39;à 7 jours d&#39;historique. Pro et Enterprise : jusqu&#39;à 28 jours (7 jours par défaut). |

<div id="restaure-seu-banco-de-dados-de-desenvolvimento">
  ## Restaurez votre base de données de développement
</div>

Vous pouvez ramener votre app et votre base de données de développement à un état antérieur grâce à la [fonctionnalité de rollback](/fr/pt/features/version-control/checkpoints-and-rollbacks/). Cela restaure votre base de données à n&#39;importe quel checkpoint créé par Agent.

<Frame>
  <img src="/assets/mirror/checkpoint-rollback-476fde84864b.png" alt="Interface de rollback de checkpoint affichant les options de rollback" width="3154" height="2366" data-path="images/replitai/checkpoint-rollback.png" />
</Frame>

<Info>
  Veillez à sélectionner « Database » sous « Additional rollback options » lorsque vous restaurez l&#39;état d&#39;un checkpoint. Votre base de données retrouve ainsi l&#39;état dans lequel elle se trouvait au moment du checkpoint.
</Info>

<div id="restaure-seu-banco-de-dados-de-produo">
  ## Restaurez votre base de données de production
</div>

Pour les bases de données de production, vous pouvez effectuer une restauration à un instant précis grâce à la restauration à un instant précis.

<Frame>
  <img src="/assets/mirror/database-rollbacks-f13dd20874ae.jpg" alt="Interface de restauration de base de données affichant les options de rollback" width="1082" height="708" data-path="images/databases/database-rollbacks.jpg" />
</Frame>

La profondeur de restauration disponible dépend de votre plan et de votre configuration de rétention. Le plan Core conserve jusqu&#39;à 7 jours d&#39;historique, tandis que les plans Pro et Enterprise en conservent jusqu&#39;à 28. Chaque plan démarre avec 7 jours, et vous pouvez modifier cette fenêtre dans les paramètres de votre base de données de production. Les fenêtres plus longues consomment davantage de stockage : augmenter la rétention fait donc grimper vos coûts d&#39;utilisation. Si vous rétrogradez de Pro vers Core, votre fenêtre de rétention est ramenée à 7 jours.

<Warning>
  Restaurer votre base de données ne restaure pas le code de votre app, et faire un rollback de votre app ne restaure pas votre base de données. Pour ramener les deux au même instant : restaurez la base de données, puis [effectuez un rollback vers le checkpoint correspondant](/fr/pt/features/version-control/checkpoints-and-rollbacks/) et publiez de nouveau votre app.
</Warning>

<div id="agende-backups-do-banco-de-dados-de-produo">
  ## Planifier les sauvegardes de la base de données de production
</div>

Les sauvegardes planifiées créent un point de restauration complet par jour. Replit programme la sauvegarde aux alentours de minuit, dans le fuseau horaire actuel de votre navigateur, lorsque vous activez ou modifiez la planification.

1. Ouvrez l&#39;outil **Database** et sélectionnez la base de données de production.
2. Ouvrez **Settings**, puis développez **Scheduled backups** sous **Advanced**.
3. Pour activer les sauvegardes planifiées, sélectionnez une durée de rétention dans **Keep backups for**.

Les durées de rétention disponibles dépendent de votre plan. Core permet jusqu&#39;à 7 jours. Pro et Enterprise permettent jusqu&#39;à 28 jours.

<div id="custos-de-armazenamento">
  ### Coûts de stockage
</div>

Replit mesure séparément chaque catégorie de stockage de la base de données de production :

| Catégorie de stockage                               | Prix par Gio par mois |
| --------------------------------------------------- | --------------------: |
| Stockage logique de la base de données              |                 $0.35 |
| Stockage de restauration à un instant précis (PITR) |                 $0.20 |
| Stockage des sauvegardes planifiées                 |                 $0.09 |

<Note>Les coûts de stockage de la base de données bénéficient actuellement d&#39;une remise de 100 %.</Note>

Les frais de $0.35 pour le stockage logique s&#39;appliquent, que vous utilisiez le PITR, les sauvegardes planifiées ou les deux. Le stockage des sauvegardes planifiées coûte moins cher par Gio que le stockage PITR. Si des points de restauration quotidiens suffisent, des sauvegardes planifiées associées à une fenêtre PITR plus courte peuvent réduire vos coûts de stockage de récupération. Votre coût total de sauvegarde dépend du volume de sauvegarde stocké et de la durée de rétention.

Le PITR offre davantage de points de restauration au sein de votre fenêtre. Les sauvegardes planifiées, elles, en offrent un par jour : choisissez donc la méthode de récupération la mieux adaptée à vos besoins.

<Note>
  La planification utilise votre décalage UTC actuel. Un changement d&#39;heure
  saisonnier peut décaler l&#39;heure de la sauvegarde d&#39;une heure tant que vous
  n&#39;avez pas mis à jour la planification. Les fuseaux horaires ayant des
  décalages fractionnaires utilisent l&#39;heure la plus proche.
</Note>

<div id="restaure-um-backup-agendado">
  ### Restaurer une sauvegarde planifiée
</div>

1. Ouvrez **Scheduled backups** dans les paramètres de la base de données de production.
2. Sélectionnez **View all backups**.
3. Sélectionnez **Restore** en regard du point de restauration souhaité.
4. Saisissez `restore`, puis sélectionnez **Continue**.

La restauration remplace le contenu de votre base de données par les données de la sauvegarde sélectionnée. Les données actuelles ne sont pas supprimées, mais les services connectés peuvent se reconnecter brièvement.

<div id="soluo-de-problemas-em-falhas-de-publicao">
  ## Résolution des échecs de publication
</div>

Si la publication échoue en raison de problèmes de base de données :

1. **Consultez les journaux de publication** pour y repérer les messages d&#39;erreur précis concernant la connectivité de la base de données ou les conflits de schéma
2. **Passez en revue les modifications récentes du schéma** afin d&#39;identifier d&#39;éventuels conflits avec le code existant de l&#39;application
3. **Testez vos modifications dans un aperçu de déploiement** avant de tenter une nouvelle publication
