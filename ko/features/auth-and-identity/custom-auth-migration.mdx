앱에 자체 authentication 시스템이나 사용자 store, session 로직이 있다면 이 페이지를 참고하세요. [Clerk Auth](/ko/features/auth-and-identity/clerk-auth)로 옮기는 작업은 단순한 코드 변경이 아니라 데이터와 신원 정보의 마이그레이션입니다. 계획 없이 진행하면 다시 찾아온 사용자가 기존 데이터에 대한 접근 권한을 잃은 것처럼 보일 수 있습니다.

<Note>
  **Replit Auth를 사용 중이신가요?** 자동 마이그레이션 절차는 조건을 충족하는 Replit Auth 앱에만 제공됩니다. 이 경우 [Replit Auth에서 Clerk로 마이그레이션하기](/ko/features/auth-and-identity/migrate-auth-to-clerk)를 참고하세요.

  Replit은 커스텀 인증 시스템을 자동으로 마이그레이션하지 않습니다. 이 페이지는 자동 import 절차가 아니라 계획 수립과 검증에 대한 안내를 제공합니다.
</Note>

<div id="plan-identity-continuity">
  ## 아이덴티티 연속성 계획
</div>

* 현재 사용자와 앱 데이터를 연결해 주는 안정적인 값을 파악하세요. 사용자 ID, 이메일 주소, 사용자 이름 또는 별도의 계정 레코드일 수 있습니다.
* 소유권, 권한, 구독, 환경설정, 감사 기록 등 해당 값에 의존하는 모든 테이블과 서비스를 빠짐없이 목록으로 정리하세요.
* 로그인 동작을 변경하기 전에, 새 아이덴티티 시스템이 기존 로컬 레코드를 각각 어떻게 매칭할지 결정하세요.
* 전환 이후 신규 사용자에게 어떤 방식으로 아이덴티티를 부여하고 로컬 레코드와 연결할지 정의하세요.

<Warning>
  제공업체의 사용자 ID, 이메일 주소, 첫 로그인 시 생성되는 새 계정이 기존 레코드와 당연히 일치할 것이라고 가정하지 마세요. 전환 전에 대표 계정 몇 개로 매핑을 검증하세요.
</Warning>

<div id="account-credentials-and-sessions">
  ## 계정 자격 증명 및 세션
</div>

* 비밀번호 해시, OAuth 아이덴티티, MFA 인증 요소, 인증 완료 상태, 활성 세션을 각각 따로 정리해 두세요. 항목마다 이식성과 보안 요구 사항이 다를 수 있습니다.
* 실제 계정에 적용하기 전에, 선택한 제공업체의 최신 문서를 기준으로 비밀번호 마이그레이션 방식을 검증하세요. 자격 증명을 안전하게 옮길 수 없다면 비밀번호 재설정이나 계정 연결 flow를 계획하세요.
* OAuth 아이덴티티나 활성 세션이 자동으로 이전된다고 가정하지 마세요. 기존 사용자가 다시 로그인하는 방법과 중복 계정을 방지할 방법을 미리 설계하세요.
* 대체 방안을 명확히 계획하지 않았다면 인가 정보와 앱 고유 데이터는 로컬 데이터 모델에 그대로 두세요. 인증과 인가는 별도의 마이그레이션 작업이 필요한 경우가 많습니다.

<div id="test-before-cutover">
  ## 전환 전 테스트
</div>

* 민감하지 않은 대표 계정과 데이터를 사용해 프로덕션이 아닌 환경에서 테스트하세요.
* 기존 계정으로 로그인한 후 dashboard, 프로필, 저장된 항목처럼 사용자별 데이터를 불러오는 페이지를 열어 보세요.
* 권한 규칙, 계정 복구, 로그아웃, 신규 계정 생성 flow를 검증하세요.
* 전환 중에는 중복 레코드와 접근 실패 여부를 모니터링하세요. 검증이 완료될 때까지 rollback 계획을 유지하세요.

<div id="get-help">
  ## 도움 받기
</div>

* 커스텀 인증 시스템을 Replit이 관리하는 Clerk Auth로 마이그레이션해야 한다면, 프로덕션 계정 데이터를 변경하기 전에 [Replit Support에 문의](https://replit.com/support)하세요.
* 다른 제공업체로 인증을 관리하고 있다면, 해당 제공업체의 최신 마이그레이션 문서를 참고하고 전환 전에 ID 매핑을 검증하세요.
