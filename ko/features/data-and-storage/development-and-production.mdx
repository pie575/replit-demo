모든 Replit App은 두 개의 데이터베이스를 사용합니다. **development database**는 여러분과 Agent가 앱을 만들면서 자유롭게 실험하는 공간입니다. **production database**는 게시된 앱을 구동하는 실제 데이터를 저장하므로, 개발을 이어가는 동안에도 실사용 데이터를 안전하게 지킬 수 있습니다.

</Frame>

<div id="how-they-compare">
  ## 비교
</div>

| 항목          | 개발 데이터베이스                    | 프로덕션 데이터베이스               |
| ----------- | ---------------------------- | ------------------------- |
| **목적**      | 실험 및 기능 개발                   | 실제 사용자 서비스 및 비즈니스 데이터 저장  |
| **데이터**     | 테스트 데이터, 더미 레코드, 소규모 dataset | 실제 사용자 데이터, 비즈니스에 중요한 정보  |
| **생성 시점**   | 모든 Replit App 생성 시 자동으로 생성   | 앱을 publish할 때             |
| **Agent**   | Agent가 테이블을 생성하고 수정할 수 있음    | Agent가 접근할 수 없음           |
| **변경**      | 잦은 schema 변경, 빠른 반복          | 신중하게 계획된 변경을 publish 시 적용 |
| **Billing** | 모든 Replit App에 무료로 포함        | 사용량 기반                    |

<Note>
  Agent는 production database를 수정할 수 없습니다. production database를 안전하게 보호하기 위한 제한입니다.

  대신 Agent는 development database를 편집할 수 있습니다. publish하는 시점에 Agent가 development database 구조에 적용한 변경 사항(열 또는 테이블 추가 및 삭제)이 production database에 반영됩니다.

  production data는 언제든지 직접 편집할 수 있습니다. **Database** 도구를 열고 production database를 선택한 뒤, **My Data**를 열고 **Edit**를 켜세요.
</Note>

<div id="create-a-production-database-when-you-publish">
  ## 게시할 때 production database 만들기
</div>

published app은 개발 중에 사용하는 development database와 분리된 자체 production database를 갖습니다.

* **현재 인프라(Helium)**: 게시 과정에서 필요할 때 Replit이 production database를 자동으로 만들어 줍니다. 따로 설정할 것이 없습니다.
* **레거시 Neon development database**: production database를 게시 설정에서 직접 만들어야 합니다. 게시하는 동안 **Production database settings**를 열고 **Create production database**를 켠 다음, 현재 개발 데이터를 그대로 복사하려면 **Set up your production database with your current development data**도 함께 켜세요.

<Frame caption="Publishing의 production database 설정">
  <img src="/assets/mirror/production-database-settings-8855bf453da9.png" alt="Create production database 옵션이 표시된 게시 설정" width="1406" height="1207" data-path="images/databases/shared-database-migration/production-database-settings.png" />
</Frame>

<Warning>
  개발 데이터는 live app에서 사용해도 안전한 경우에만 production으로 복사하세요. 개발 데이터에는 테스트 계정, 샘플 레코드, 미완성 콘텐츠가 포함될 수 있습니다.
</Warning>

게시 후에는 published app이 production database를 사용하고 Project Editor는 계속 development database를 사용하므로, 이후의 개발 변경 사항이 라이브 데이터를 직접 변경하지 않습니다.

<div id="connection-pooling">
  ## 연결 풀링
</div>

기본적으로 production database에는 연결 풀링이 활성화되어 있지 않습니다. 앱은 `DATABASE_URL` 연결 문자열로 데이터베이스에 직접 연결하므로, 대부분의 프레임워크에서는 자체 클라이언트 측 연결 풀을 관리해야 합니다.

<Note>
  각 Neon 프로젝트에는 직접 연결 문자열과 풀링 연결 문자열이 함께 제공됩니다. 직접 연결 문자열의 형태는 `postgresql://neondb_owner:<password>@<host>.<region>.neon.tech/<db>?sslmode=require`입니다.

  풀링 연결을 사용하려면 호스트 뒤에 `-pooler`를 붙이세요: `postgresql://neondb_owner:<password>@<host>-pooler.<region>.neon.tech/<db>?sslmode=require`.
</Note>

production 연결 문자열이 노출되었다면 [production database 자격 증명을 재생성](/ko/features/data-and-storage/connection-details#regenerate-production-database-credentials)하세요.

<div id="making-safe-changes-to-your-production-database">
  ## production database를 안전하게 변경하기
</div>

database 변경 사항이 포함된 업데이트를 게시할 때는 다운타임이나 데이터 손실을 막기 위해 신중한 계획이 필요한 변경들이 있습니다.

<Info>
  게시하는 동안 published app에 짧은 다운타임이 발생할 수 있습니다. database를 변경할 때는 충돌을 방지하고 데이터를 보호하기 위해 변경 사항이 적용되는 동안 앱을 일시적으로 중지해야 할 수 있습니다.
</Info>

다음과 같은 유형의 변경에는 일반적으로 주의가 필요합니다.

* 애플리케이션 코드가 여전히 참조하고 있는 **database 열 삭제**
* 기존 코드가 처리할 수 없는 방식의 **열 데이터 유형 변경**
* 기존 테이블에 기본값 없이 **필수 필드 추가**
* 기존 쿼리를 망가뜨리는 **테이블 또는 열 이름 변경**
* 기존 애플리케이션 로직을 거부할 수 있는 **constraints 수정**

<div id="test-changes-with-a-deployment-preview">
  ### deployment 미리 보기로 변경 사항 테스트하기
</div>

deployment 미리 보기는 production 환경을 임시로 격리해 복제한 것으로, 실제 사용자에게 영향을 주기 전에 database 변경 사항과 애플리케이션 업데이트를 테스트해 볼 수 있습니다. 다음과 같은 용도로 활용하세요.

* database 변경 사항을 적용한 상태에서 주요 사용자 flow 전반에 걸쳐 앱이 정상적으로 동작하는지 확인
* 기존 데이터가 제대로 마이그레이션되었는지, 새 필드에 예상한 값이 들어 있는지 확인
* 쿼리 응답 시간에 성능 저하가 발생하지 않는지 관찰

<div id="billing-and-resource-usage">
  ## 청구 및 리소스 사용량
</div>

프로덕션 데이터베이스는 서버리스 데이터베이스 제공업체인 Neon을 통해 사용량 기준으로 청구됩니다. 데이터베이스는 5분간 활동이 없으면 유휴 상태로 전환되어 컴퓨팅 시간 청구가 중지되며, 쿼리를 받으면 즉시 다시 활성화됩니다.

Database 도구의 시작 화면에는 **Billing Period**와 **Hours of Compute Used**가 표시됩니다. 데이터베이스별 스토리지를 확인하려면 해당 데이터베이스의 **Settings** 탭을 여세요. 모든 Replit App의 사용량을 확인하려면 **Settings** → **Account** → **Account usage**로 이동한 후 **PostgreSQL Storage**와 **PostgreSQL Compute** 행을 펼치세요.

Replit의 데이터베이스 사용량 요금 부과 방식은 [Deployments and Database Billing](/ko/billing/about-usage-based-billing#databases)을 참고하세요.

<div id="removing-a-production-database">
  ## production database 제거하기
</div>

<Warning>
  제거 작업은 7일의 retention period가 지나면 되돌릴 수 없습니다. 진행하기 전에 중요한 데이터는 반드시 백업하세요. database에는 7일간의 소프트 삭제 기간이 있어 이 기간에는 복원이 가능하니, 도움이 필요하면 지원팀에 문의하세요. 7일이 지나면 database는 완전히 삭제되어 복구할 수 없습니다.
</Warning>

<Accordion title="database 제거 방법">
  **Database** 도구에서:

  1. database를 선택한 다음 **Settings** tab을 엽니다
  2. **Remove database**를 선택한 후 **Yes, Remove database**를 선택해 확인합니다
</Accordion>

<div id="legacy-development-database">
  ## 레거시 development database
</div>

2025년 12월 4일 이전에는 development database가 <a href="https://neon.com/" target="_blank">Neon</a>에서 호스팅되었습니다. 새로 생성되는 development database는 모두 Replit 자체 인프라(Helium)에서 호스팅됩니다. 앱이 어느 쪽을 사용하는지는 **Settings** 탭에서 확인할 수 있습니다. `DATABASE_URL`에 `neon.tech`가 포함되어 있으면 레거시 Neon이고, `helium`이면 현재 인프라입니다.

| **기능**                  | **Replit (현재)**                                                                           | **Neon (레거시)**                                                                                                     |
| ----------------------- | ----------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------ |
| **호스팅**                 | Replit 자체 인프라에서 호스팅                                                                       | Neon(서드파티 provider)에서 호스팅                                                                                          |
| **Billing**             | 모든 Replit App에 무료로 포함                                                                     | usage-based billing. 자세한 내용은 [Publishing 및 Database Billing](/ko/billing/about-usage-based-billing#databases)을 참조하세요. |
| **복구 기능**               | [rollback 기능](/ko/features/data-and-storage/data-recovery)으로 원하는 checkpoint 시점으로 database 복원 | point-in-time restore(PITR): 백업 retention 기간 내 임의 시점으로 복구.                                                         |
| **연결 보안**               | 앱 내부에서만 접근할 수 있으며 외부에 노출되지 않습니다.                                                          | 전체 연결 문자열을 사용했습니다. 유출되면 누구나 database에 접근해 수정할 수 있었습니다.                                                             |
| **Remix 동작**            | [Remix](/ko/build/remix-an-app)하면 격리와 보안을 위해 데이터를 복사한 새 development database가 생성됩니다.         | 모든 사본이 동일한 database를 재사용하므로, remix에서 변경한 내용이 원본 앱에 영향을 줄 수 있었습니다.                                                  |
| **Database 생성**         | Replit App마다 자동으로 생성됩니다.                                                                  | 직접 설정해야 했습니다.                                                                                                      |
| **Publishing workflow** | Publishing 시 environments 간 격리를 위해 별도의 production database가 생성됩니다.                        | Development와 production이 동일한 database를 공유해, 개발 중 의도치 않은 변경이 production 앱에 영향을 줄 수 있었습니다.                           |

<div id="database-infrastructure-upgrade">
  ## 데이터베이스 인프라 업그레이드
</div>

Replit은 development database를 Neon에서 Replit이 직접 운영하는 관리형 PostgreSQL 인프라인 **Helium**으로 업그레이드하고 있습니다. 업그레이드는 자동으로 진행되며, Project Editor에서 앱을 열 때 앱당 한 번 실행되고 모든 데이터는 그대로 유지됩니다.

변경 사항:

* **더 낮은 지연 시간과 더 큰 저장 용량**: database가 앱과 함께 Replit 인프라에서 실행되며, 저장 용량 limit이 10GB에서 20GB로 늘어납니다.
* **동일한 데이터베이스 엔진**: Helium은 Neon과 동일한 버전인 PostgreSQL 16을 사용합니다. 쿼리, schema, 데이터 모두 기존과 동일하게 동작합니다.
* **연결 정보 자동 업데이트**: `DATABASE_URL`이 Helium을 가리키도록 업데이트됩니다. 기존 Neon 연결 문자열은 참고용으로 Secrets에 `NEON_DATABASE_URL`로 저장됩니다.
* **개별 PG 변수 제거**: `PGHOST`, `PGPORT`, `PGUSER`, `PGPASSWORD`가 제거됩니다. 대신 `DATABASE_URL`을 사용하세요.

업그레이드가 진행되는 동안 **&quot;Upgrading your database&quot;** 진행 화면이 표시됩니다. 대용량 데이터베이스는 몇 분에서 몇 시간까지 걸릴 수 있으며, tab을 닫았다가 나중에 다시 돌아와도 됩니다. 업그레이드 중 문제가 발생하면 자동으로 건너뛰었다가 다음에 앱을 열 때 다시 시도합니다. 완료되면 확인 대화 상자가 나타납니다.

대부분의 builder는 업그레이드 후 별도로 조치할 사항이 없습니다. 다음 항목에 해당한다면 확인하세요:

* **하드코딩된 Neon 연결 문자열**: `neon.tech` 연결 문자열을 참조하는 코드는 `DATABASE_URL` 환경 변수를 사용하도록 업데이트하세요.
* **사용자 지정 PostgreSQL 역할**: 역할과 permissions는 자동으로 이전되지만 역할 비밀번호는 복사되지 않습니다. 새 database에서 사용자 지정 역할의 비밀번호를 재설정하세요.

<div id="ssl-connection-errors-after-the-upgrade">
  ### 업그레이드 후 SSL 연결 오류
</div>

`The server does not support SSL connections`와 같은 오류가 나타난다면 연결 코드가 SSL 핸드셰이크를 강제하고 있는 것입니다. Neon은 SSL을 요구했지만, Helium은 앱과 함께 로컬에서 실행되므로 SSL을 사용하지 않습니다. SSL 설정을 환경에 따라 조건부로 적용하세요:

<CodeGroup>
  ```js JavaScript theme={null}
  // 변경 전 (업그레이드 후 동작하지 않음)
  const pool = new Pool({
    connectionString: process.env.DATABASE_URL,
    ssl: { rejectUnauthorized: false },
  });

  // 변경 후 (development와 production 모두에서 동작)
  const pool = new Pool({
    connectionString: process.env.DATABASE_URL,
    ssl:
      process.env.NODE_ENV === "production"
        ? { rejectUnauthorized: false }
        : false,
  });
  ```
</CodeGroup>

<Tip>
  Drizzle, Prisma, Sequelize 같은 ORM을 사용한다면 해당 문서에서 SSL 설정을 조건부로 구성하는 방법을 확인하세요. 원칙은 동일합니다. development database에서는 SSL을 비활성화하고, production에서는 활성화하면 됩니다.
</Tip>

<div id="forked-apps-that-shared-a-database">
  ### database를 공유하던 fork된 apps
</div>

기존 Neon 시스템에서는 app을 fork하면 원본 app의 `DATABASE_URL`이 그대로 복사되어, 두 apps와 각각의 published 버전이 모두 동일한 database에 연결되었습니다. 공유된 레거시 database는 **2026년 6월 8일**에 종료되었습니다. published app이 작동하지 않거나 데이터에 접근할 수 없게 되었다면 [공유 database를 사용하는 published app 문제 해결하기](/ko/features/data-and-storage/shared-database-migration)를 참고하거나 [지원팀에 문의](https://replit.com/support)하세요.
