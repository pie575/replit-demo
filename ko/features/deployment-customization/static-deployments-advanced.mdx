<div id="add-response-headers">
  ## 응답 헤더 추가
</div>

사용자 지정 **응답 헤더**를 사용하면 특정 경로와 일치하는 요청에 HTTP 헤더 지시문을 추가할 수 있습니다.
응답 헤더는 요청된 콘텐츠를 어떻게 다뤄야 하는지 브라우저에 알려주는 이름-값 쌍입니다.

예를 들어 `Access-Control-Allow-Origin` 헤더를 사용하면 해당 페이지에 브라우저가 접근할 수 있는 도메인을 지정할 수 있습니다.
이 항목을 만들려면 Replit App의 root directory에 있는 `.replit` 파일에 다음 내용을 추가하세요.

```
[[deployment.responseHeaders]]
path = "/*"
name = "Access-Control-Allow-Origin"
value = "origin"
```

이 응답 헤더에는 다음 매개변수가 포함됩니다.

* **path**: 요청된 리소스와 일치하는 URL 경로 패턴
* **name**: HTTP 헤더 이름
* **value**: HTTP 헤더의 값

`.replit` 파일에 `deployment.responseHeaders` 항목을 여러 개 추가할 수 있습니다.

변경한 구성을 적용하려면 Replit App을 다시 게시하세요.

<div id="reserved-headers">
  #### 예약된 HTTP 헤더
</div>

Replit은 다음 HTTP 헤더를 예약해 두었으며, 이러한 HTTP 헤더는 직접 구성할 수 없습니다.

```text [expandable] theme={null}
Accept-Ranges
Age
Allow
Alt-Svc
Connection
Content-Encoding
Content-Length
Content-Range
Date
Location
Server
Set-Cookie
Trailer
Transfer-Encoding
Upgrade
```

<Tip>
  HTTP 헤더에 대해 자세히 알아보려면 MDN 웹 문서의

  <a href="https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers" target="_blank">
    HTTP 헤더
  </a>

  문서를 참조하세요.
</Tip>

<div id="create-a-custom-404-page">
  ## 사용자 지정 404 페이지 만들기
</div>

사용자가 게시된 앱의 어떤 파일이나 규칙과도 일치하지 않는 URL 경로를 요청하면 사용자 지정 404 페이지가 표시됩니다.

사용자 지정 404 페이지를 추가하려면 Replit App의 root directory에 `404.html` 파일을 만들고 페이지 내용을 작성하세요.

사용자가 존재하지 않는 URL 경로에 접근하려고 하면 사용자 지정 404 페이지가 렌더링된 HTML로 표시됩니다.

<div id="define-url-path-rewrites">
  ## URL 경로 재작성 정의
</div>

Replit App이 요청을 처리하기 전에 요청의 URL 경로를 변경하도록 URL 재작성을 정의할 수 있습니다.
원래 URL은 브라우저에 그대로 표시되지만, 서버는 재작성 규칙에 정의된 리소스를 불러옵니다.

예를 들어 `/app`으로 시작하는 모든 요청이 `/app/index.html` 파일의 내용을 불러오도록 지정할 수 있습니다.
이 항목을 추가하려면 Replit App의 root directory에 있는 `.replit` 파일에 다음 내용을 추가하세요.

```
[[deployment.rewrites]]
from = "/app/*"
to = "/app/index.html"
```

* **from**: 요청된 리소스와 일치하는 URL 경로 패턴
* **to**: 재작성된 경로로, Static Deployment의 파일에 해당합니다.

`.replit` 파일에는 `deployment.rewrites` 항목을 여러 개 추가할 수 있습니다.
서버는 나열된 순서대로 항목을 해석하며, 중복된 항목은 무시합니다.

구성 변경 사항을 적용하려면 Replit App을 다시 게시해야 합니다.

다음 섹션에서는 URL 재작성 규칙의 제약 조건을 설명합니다.

<div id="path-matching">
  ### 경로 매칭
</div>

재작성 규칙의 `from` 및 `to` 매개변수에는 다음과 같은 constraints가 적용됩니다.

* `*`가 없으면 경로가 정확히 일치해야 합니다
* `*`는 경로의 나머지 부분 전체와 일치합니다
* `*`는 경로 맨 끝에서만 사용할 수 있습니다
* `from` 매개변수에 `*`를 사용한 경우, `to` 매개변수에도 `*`를 넣어 일치한 경로 부분을 나타낼 수 있습니다

예를 들어 `.replit` 파일에 다음과 같은 재작성이 있다고 가정해 보겠습니다.

```
[[deployment.rewrites]]
from = "/v1/*"
to = "/v2/*"
```

사용자가 `/v1/about-us.html` 경로에 접속하면 재작성이 `/v2/about-us.html`에 있는 파일을 제공합니다.

<div id="shadowing">
  ### 섀도잉
</div>

섀도잉은 재작성이 일치시키는 URL 경로가 Static Deployment의 실제 파일과도 일치할 때 발생합니다.
이 경우 클라우드 서버는 재작성을 무시하고 해당 파일을 그대로 serve합니다.

예를 들어, published app에 다음 파일이 포함되어 있다고 가정해 보겠습니다.

* `index.html`
* `about.html`

그리고 `.replit` 파일에 다음과 같은 재작성이 정의되어 있습니다.

```
[[deployment.rewrites]]
from = "/*"
to = "/index.html"
```

사용자가 `/register.html`을 방문하면 서버는 요청을 `/index.html`로 재작성하여 해당 파일을 제공합니다.
반면 사용자가 `/about.html`을 방문하는 경우, 해당 파일이 Static Deployment에 존재하므로 서버는 재작성 규칙을 무시하고 `about.html` 파일을 제공합니다.

<div id="domain-restrictions">
  ### 도메인 제한
</div>

재작성은 Static Deployment의 기본 도메인으로 들어오는 요청에만 적용되며,
Static Deployment 내의 파일로만 연결할 수 있습니다.
