Ce guide propose une liste de contrôle de sécurité complète pour vérifier que votre application créée en vibe coding respecte les bonnes pratiques de sécurité.

Replit offre de nombreuses fonctionnalités de sécurité [par défaut](/fr/ja/features/security/overview), mais il est important de comprendre et de mettre en place des mesures de sécurité supplémentaires, adaptées aux besoins spécifiques de votre application.

<div id="section">
  ## Prérequis
</div>

* Un compte Replit
* Des connaissances de base du langage de programmation utilisé
* Savoir utiliser l&#39;éditeur de projet
* Une application en cours de développement sur Replit

<div id="section-2">
  ## Sécurité front-end
</div>

<AccordionGroup>
  <Accordion title="HTTPS partout" icon="lock">
    Replit utilise HTTPS par défaut pour toutes les applications. Vous n&#39;avez rien à craindre !
  </Accordion>

  <Accordion title="Validation et assainissement des entrées" icon="shield-check">
    Validez et assainissez systématiquement les entrées utilisateur afin de prévenir les attaques de script intersite (XSS) :

    ```javascript theme={null}
    // À éviter : utilisation directe des entrées utilisateur
    element.innerHTML = userInput;

    // À privilégier : assainir les entrées avant de les utiliser
    import { sanitize } from 'some-sanitizer-library';
    element.innerHTML = sanitize(userInput);
    ```

    Demandez à Agent :

    ```
    Help me validate and sanitize inputs to protect against XSS attacks
    ```
  </Accordion>

  <Accordion title="Ne stockez pas de données sensibles dans le navigateur" icon="eye-slash">
    Utilisez Replit Secrets pour stocker des informations sensibles, telles que des clés API.

    Ne transmettez pas de secrets côté client et ne les stockez pas aux emplacements suivants :

    * Stockage local
    * Stockage de session
    * JavaScript côté client
    * Cookies sans attributs de sécurité appropriés

    Demandez à Agent :

    ```
    Help me keep sensitive data out of the browser. Am I doing this correctly?
    ```
  </Accordion>

  <Accordion title="Protection contre les CSRF" icon="shield">
    Mettez en place une protection contre la falsification de requêtes intersites (CSRF) dans vos formulaires :

    ```javascript theme={null}
    // Exemple d'implémentation d'un jeton CSRF
    const csrfToken = generateToken();
    session.csrfToken = csrfToken;
    ```

    Demandez à Agent :

    ```
    Help me implement CSRF tokens for forms
    ```
  </Accordion>
</AccordionGroup>

<div id="section-3">
  ## Sécurité du back-end
</div>

<AccordionGroup>
  <Accordion title="Principes de base de l’authentification" icon="key">
    Lors de la mise en place de l’authentification :

    * Utilisez Replit Auth lorsque c’est possible
    * Utilisez des bibliothèques éprouvées si vous mettez en place une authentification personnalisée
    * Ne stockez jamais les mots de passe en clair

    Demandez à Agent :

    ```
    Help me implement authentication for my application with Replit Auth
    ```
  </Accordion>

  <Accordion title="Contrôle d’autorisation" icon="user-lock">
    Vérifiez toujours les autorisations avant d’exécuter une action :

    ```javascript theme={null}
    // Exemple de contrôle d’autorisation
    if (!user.canAccess(resource)) {
      return res.status(403).send('Access denied');
    }
    ```

    Demandez à Agent :

    ```
    Help me implement authorization checks for my application
    ```
  </Accordion>

  <Accordion title="Protection des points de terminaison API" icon="shield">
    Sécurisez les points de terminaison API :

    * Ajoutez une authentification aux points de terminaison sensibles
    * Configurez CORS de manière appropriée
    * Envisagez de limiter le débit des requêtes

    Demandez à Agent :

    ```
    How do I properly authenticate endpoints in my app?
    ```
  </Accordion>

  <Accordion title="Protection contre les injections SQL" icon="database">
    Agent utilise un ORM par défaut, ce qui contribue à prévenir les injections SQL. Si vous rédigez des requêtes de base de données personnalisées :

    ```javascript theme={null}
    // Mauvais : concaténation de chaînes dans les requêtes
    db.query(`SELECT * FROM users WHERE username = '${username}'`);

    // Bon : requêtes paramétrées avec un ORM
    db.query('SELECT * FROM users WHERE username = ?', [username]);
    ```
  </Accordion>

  <Accordion title="En-têtes de sécurité" icon="code">
    Ajoutez des en-têtes de sécurité importants à votre application :

    ```html theme={null}
    <!-- Dans index.html ou via votre back-end -->
    <meta http-equiv="X-Frame-Options" content="DENY">
    <meta http-equiv="X-Content-Type-Options" content="nosniff">
    <meta http-equiv="Content-Security-Policy" content="default-src 'self'">
    ```

    Analysez votre site sur [securityheaders.com](https://securityheaders.com) pour obtenir des recommandations.

    Demandez à Agent :

    ```
    Can you add the security headers to my application?
    ```
  </Accordion>
</AccordionGroup>

<div id="section-4">
  ## Pratiques de sécurité continues
</div>

<AccordionGroup>
  <Accordion title="Maintenir les dépendances à jour" icon="arrow-rotate-right">
    Vérifiez régulièrement les paquets obsolètes susceptibles de présenter des vulnérabilités :

    ```bash theme={null}
    npm audit
    ```
  </Accordion>

  <Accordion title="Gestion appropriée des erreurs" icon="exclamation">
    N&#39;exposez pas d&#39;informations sensibles dans les messages d&#39;erreur :

    ```javascript theme={null}
    // Bad: Exposing sensitive details
    catch (err) {
      res.status(500).send(`Database error: ${err.message}`);
    }

    // Good: Generic error message
    catch (err) {
      console.error(err); // Log internally
      res.status(500).send('An error occurred');
    }
    ```

    Demandez à Agent :

    ```
    Help me implement proper error handling for my application
    ```
  </Accordion>

  <Accordion title="Sécurité des cookies" icon="cookie">
    Lorsque vous utilisez des cookies :

    * Définissez l&#39;indicateur HttpOnly pour empêcher l&#39;accès par JavaScript
    * Utilisez l&#39;attribut Secure pour imposer le HTTPS
    * Implémentez l&#39;attribut SameSite pour prévenir les attaques CSRF

    Demandez à Agent :

    ```
    Help me secure my cookies for my application
    ```
  </Accordion>

  <Accordion title="Sécurité des téléversements de fichiers" icon="upload">
    Si votre application autorise l&#39;upload de fichiers :

    * Limitez les types et les tailles de fichiers
    * Analysez les fichiers à la recherche de logiciels malveillants si possible
    * Stockez les fichiers dans le stockage d&#39;objets de Replit
    * N&#39;utilisez pas les noms de fichiers fournis par les utilisateurs : générez de nouveaux noms

    Demandez à Agent :

    ```
    Help me secure my file uploads for my application
    ```
  </Accordion>

  <Accordion title="Limitation de débit" icon="clock">
    Implémentez une limitation de débit, en particulier sur les points de terminaison d&#39;API liés à l&#39;authentification :

    ```javascript theme={null}
    // Example rate limiting middleware
    const rateLimit = require('express-rate-limit');

    const limiter = rateLimit({
      windowMs: 15 * 60 * 1000, // 15 minutes
      max: 100 // limit each IP to 100 requests per windowMs
    });

    app.use('/api/', limiter);
    ```

    Demandez à Agent :

    ```
    Help me implement rate limiting for my application
    ```
  </Accordion>
</AccordionGroup>

  ## Liste de contrôle
</div>

Voici une liste de contrôle pour encadrer vos pratiques de sécurité.

<div id="section-6">
  ## Sécurité du frontend
</div>

|   | Mesure de sécurité                                     | Description                                                                                          |
| - | ------------------------------------------------------ | ---------------------------------------------------------------------------------------------------- |
| ☐ | HTTPS partout                                          | Prévient les écoutes passives et les attaques de l&#39;intercepteur (man-in-the-middle) élémentaires |
| ☐ | Validation et assainissement des entrées               | Validez toutes les entrées utilisateur pour prévenir les attaques XSS                                |
| ☐ | Ne stockez pas de données sensibles dans le navigateur | Ne placez aucun secret dans le stockage local ni dans le code côté client                            |
| ☐ | Protection CSRF                                        | Implémentez des jetons anti-CSRF pour les formulaires et les requêtes modifiant l&#39;état           |
| ☐ | N&#39;exposez pas de clés API dans le frontend         | Conservez toujours les identifiants d&#39;API côté serveur                                           |

<div id="section-7">
  ## Sécurité du backend
</div>

|   | Mesure de sécurité                       | Description                                                                                                |
| - | ---------------------------------------- | ---------------------------------------------------------------------------------------------------------- |
| ☐ | Principes de base de l’authentification  | Utiliser des bibliothèques éprouvées et stocker correctement les mots de passe (hachage + sel)             |
| ☐ | Contrôle d’autorisation                  | Toujours vérifier les autorisations avant d’effectuer une action                                           |
| ☐ | Protection des points de terminaison API | Mettre en œuvre une authentification appropriée pour tous les points de terminaison API                    |
| ☐ | Protection contre les injections SQL     | Utiliser des requêtes paramétrées ou un ORM et ne jamais utiliser de SQL brut avec les entrées utilisateur |
| ☐ | En-têtes de sécurité de base             | Mettre en œuvre X-Frame-Options, X-Content-Type-Options et HSTS                                            |
| ☐ | Protection contre les DDoS               | Utiliser un CDN ou un service cloud doté de fonctionnalités intégrées d’atténuation des DDoS               |

<div id="section-8">
  ## Bonnes pratiques de sécurité
</div>

|   | Mesure de sécurité                      | Description                                                                                           |
| - | --------------------------------------- | ----------------------------------------------------------------------------------------------------- |
| ☐ | Maintenir les dépendances à jour        | La plupart des vulnérabilités proviennent de bibliothèques obsolètes                                  |
| ☐ | Gestion appropriée des erreurs          | Ne divulguez aucun détail sensible dans les messages d&#39;erreur                                     |
| ☐ | Sécurité des cookies                    | Définissez les attributs HttpOnly, Secure et SameSite                                                 |
| ☐ | Sécurité des téléversements de fichiers | Validez le type et la taille des fichiers, et analysez-les à la recherche de contenu malveillant      |
| ☐ | Limitation de débit                     | À mettre en place sur tous les endpoints d&#39;API, en particulier ceux liés à l&#39;authentification |
