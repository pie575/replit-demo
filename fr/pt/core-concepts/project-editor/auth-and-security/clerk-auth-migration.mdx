---
title: "Migrer une application existante vers Clerk Auth"
description: "Bonnes pratiques pour migrer une application existante avec son propre système d'authentification vers Clerk Auth sans perdre de comptes utilisateurs ni de données historiques."
---

Si votre application dispose déjà d&#39;un système d&#39;authentification fonctionnel et d&#39;une base de données d&#39;utilisateurs réels, passer à [Clerk Auth](/fr/pt/core-concepts/project-editor/auth-and-security/clerk-auth) **ne se résume pas à une modification du code** : c&#39;est une migration de données. Sans plan réfléchi, chaque ligne existante de votre table `users` sera inconnue de Clerk : les nouveaux comptes sont créés lors de la première connexion, aucun ne correspond à vos données historiques, et les clients qui reviennent ont l&#39;impression d&#39;avoir « perdu » leur compte.

En réalité, il n&#39;y a que deux choses à bien faire.

<Note>
  Cette page s&#39;adresse aux développeurs qui exploitent déjà une application avec leur propre système d&#39;authentification. Si vous démarrez une nouvelle application, consultez la [présentation de Clerk Auth](/fr/pt/core-concepts/project-editor/auth-and-security/clerk-auth) : aucune migration n&#39;est nécessaire.
</Note>

<div id="1-importe-seus-usurios-existentes-para-o-clerk">
  ## 1. Importez vos utilisateurs existants dans Clerk
</div>

Chaque utilisateur actif de votre application doit exister en tant qu&#39;utilisateur Clerk *avant* la mise en service de Clerk Auth. Au minimum, chaque importation doit inclure :

* **E-mail** (obligatoire)
* **Métadonnées de profil disponibles** : nom, statut de vérification et toute autre information que vous souhaitez afficher dans le panneau Auth
* **Hash du mot de passe** : le hash existant du mot de passe de l&#39;utilisateur
* **Algorithme de hachage** : l&#39;algorithme/le format de ce hash, exactement comme Clerk l&#39;attend

L&#39;algorithme de hachage est l&#39;élément le plus facile à mal configurer. Clerk n&#39;accepte qu&#39;un ensemble précis de formats de hash de mots de passe, chacun associé à un identifiant de chaîne spécifique (`bcrypt`, `scrypt_firebase`, `argon2i`, `pbkdf2_sha256`, etc.). Consultez la liste complète et le format exact de condensat requis pour chacun dans la [référence de l&#39;API de création d&#39;utilisateur de Clerk](https://clerk.com/docs/reference/backend/user/create-user).

Cette étape requiert davantage qu&#39;un prompt d&#39;une ligne. L&#39;Agent chargé de la migration doit avoir une **compréhension approfondie de la façon dont les mots de passe sont hachés dans votre code actuel** — bibliothèque utilisée, paramètres (facteur de coût, disposition du salt, pepper, etc.) et correspondance avec l&#39;un des algorithmes pris en charge par Clerk. Un prompt bien formulé ressemble à ceci :

```
Lisez mon code d'authentification existant et identifiez exactement comment les mots de passe sont hachés
(bibliothèque, algorithme, paramètres et comment la valeur stockée est formatée).
Ensuite, écrivez un script d'importation unique qui, pour chaque utilisateur dans ma table users,
appelle l'API Backend de Clerk avec l'e-mail, les métadonnées de profil, le digest de mot de passe au format
exact attendu par l'algorithme Clerk correspondant, et la valeur correcte de `passwordHasher`.
Dites-moi quel algorithme Clerk vous avez choisi et pourquoi avant d'exécuter.
```

Si votre méthode de hachage ne correspond clairement à aucun des algorithmes pris en charge par Clerk, les utilisateurs importés ne pourront pas se connecter avec leur mot de passe existant. Dans ce cas, importez-les sans hash et envoyez un e-mail de réinitialisation du mot de passe au moment de la transition.

<div id="2-resolva-usurios-clerk-de-volta-para-seus-ids-de-usurio-existentes">
  ## 2. Faites correspondre les utilisateurs Clerk à leurs identifiants utilisateur existants
</div>

Une fois connectés, les utilisateurs importés disposent d’une identité Clerk pour chaque requête authentifiée. Votre serveur doit associer cette identité à la ligne correspondante de votre table `users` — sinon, l’identifiant utilisateur Clerk ne correspondra à aucune de vos clés étrangères existantes (`orders.user_id`, `documents.owner_id`, etc.) et les données historiques sembleront perdues.

Clerk géré par Replit simplifie cette opération : lorsque vous importez un utilisateur en utilisant son identifiant existant comme `externalId` de l’utilisateur Clerk, cette valeur est automatiquement inscrite dans les claims de session sous `sessionClaims.userId`. Votre middleware doit simplement privilégier cette valeur plutôt que l’identifiant utilisateur Clerk brut :

```ts theme={null}
import { getAuth } from "@clerk/express";

const requireAuth = (req: any, res: any, next: any) => {
  const auth = getAuth(req);
  const userId = auth?.sessionClaims?.userId || auth?.userId;
  if (!userId) {
    return res.status(401).json({ error: "Unauthorized" });
  }
  req.userId = userId;
  next();
};
```

Avec ce modèle :

* Les **utilisateurs importés** sont associés à leur `users.id` existant via `sessionClaims.userId` — toutes leurs données historiques restent liées.
* Les **nouveaux utilisateurs** (qui se sont inscrits après la transition et n’ont pas d’`externalId`) utilisent `auth.userId`, qui correspond à leur ID utilisateur Clerk. Utilisez l’ID utilisateur Clerk comme clé primaire pour ces nouvelles lignes, ou créez une ligne lors de leur première connexion et associez-la.

<div id="isso">
  ## C’est tout
</div>

Tout le reste — faire fonctionner votre ancien système d’authentification en parallèle, effectuer un test avec de vrais comptes, surveiller la création de comptes en double après la transition, désactiver l’ancien système — relève des bonnes pratiques habituelles de migration et n’est pas spécifique à Clerk Auth.
