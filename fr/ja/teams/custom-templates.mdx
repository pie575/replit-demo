<div id="section">
  ## Introduction
</div>

Replit est un environnement de développement cloud qui vous permet d’écrire et d’exécuter n’importe quel framework ou stack. Pour créer un modèle personnalisé, deux approches sont recommandées :

1. **[Importer depuis un fournisseur Git](https://replit.com/import)** — Importez un stack de démarrage existant (ou celui de votre choix) depuis GitHub, GitLab ou Bitbucket.
2. **Forker le modèle Blank** — Forkez le [modèle Blank](https://replit.com/@replit/Nothing?v=1) pour partir de zéro dans un environnement de développement entièrement vide.

Nos clients ont créé avec succès des modèles pour Rust, Python, Java, C++ et bien d’autres stacks : si cela peut s’exécuter, cela peut s’exécuter sur Replit.

<Tip>
  Lors de la création de votre premier modèle, nous vous recommandons de collaborer avec l’**équipe d’ingénierie terrain** de Replit. Elle possède une vaste expérience de la configuration de modèles personnalisés pour de nombreux stacks et peut vous accompagner. Contactez votre responsable de compte pour être mis en relation.
</Tip>

Les modèles personnalisés permettent aux administrateurs Enterprise de créer des points de départ préconfigurés et de les afficher directement dans la zone de saisie d’Agent pour tous les membres de l’organisation. Lorsqu’un créateur sélectionne un modèle personnalisé, Agent le fork et utilise la configuration, les instructions et les compétences du modèle pour orienter toutes les tâches suivantes. Aucune configuration supplémentaire n’est requise.

<Note>
  Les modèles personnalisés sont disponibles uniquement avec le forfait **Enterprise**. Seuls les administrateurs de l’organisation peuvent épingler et gérer les modèles.
</Note>

<div id="section-2">
  ## Fonctionnement des modèles personnalisés
</div>

Les modèles personnalisés sont des Replit Apps standard de votre organisation, **épinglées dans la zone de saisie d’Agent**. Lorsqu’un créateur en sélectionne un :

1. Agent forke le modèle et crée une New App (tous les fichiers sont copiés)
2. Agent ignore la phase de planification et passe directement en mode Build
3. Le fichier `custom_instruction/instructions.md` du modèle est injecté dans le contexte d’Agent
4. Les [compétences](/fr/ja/features/agent/skills) personnalisées de `.agents/skills/` sont détectées et mises à disposition
5. Le fichier [`replit.md`](/fr/ja/features/project-setup/replit-dot-md) fournit un contexte de projet continu

Ainsi, les normes, pratiques et outils de votre organisation sont intégrés dès la première interaction.

<div id="section-3">
  ## Structure des fichiers du modèle
</div>

La mise en page recommandée pour les modèles personnalisés est la suivante :

```
my-template/
├── .replit                              # Configuration de l’App (commandes d’exécution, ports, modules)
├── replit.md                            # Mémoire d’Agent : vue d’ensemble et préférences du projet
├── custom_instruction/
│   └── instructions.md                  # Instructions de l’entreprise intégrées au prompt d’Agent
├── .agents/
│   └── skills/
│       └── my-skill/
│           └── SKILL.md                 # Compétences personnalisées qu’Agent peut utiliser à la demande
└── ...                                  # Le reste de la structure de votre dépôt
```

Chaque fichier a un rôle distinct. Les sections suivantes expliquent comment configurer chacun d’eux.

<div id="section-4">
  ## Configuration d&#39;un modèle personnalisé
</div>

<div id="app">
  ### Création d&#39;une App de base
</div>

Créez une nouvelle Replit App dans votre organisation. Configurez le projet avec tous les fichiers, dépendances et éléments de configuration dont les créateurs ont besoin pour démarrer. Cela inclut :

* L&#39;ossature du code source (composants, utilitaires et fichiers de configuration)
* Des dépendances préinstallées (`package.json`, `requirements.txt`, etc.)
* La configuration de l&#39;environnement dans le [fichier `.replit`](/fr/replit-app/configuration)

<div id="secret">
  ### Configuration des Secrets partagés
</div>

Si votre modèle nécessite des clés API, des jetons ou d&#39;autres informations d&#39;identification, ajoutez-les aux **Secrets** du modèle (dans le panneau d&#39;outils) avant de l&#39;épingler. Lorsqu&#39;un créateur crée une nouvelle App à partir du modèle, tous les Secrets sont automatiquement copiés dans la nouvelle App. Il peut ainsi commencer à travailler immédiatement sans avoir à configurer lui-même les informations d&#39;identification.

Documentez tous les Secrets dans `custom_instruction/instructions.md` (ou dans une compétence dédiée) afin que les créateurs sachent ce qui est disponible et à quoi sert chaque clé.

<Warning>
  Les Secrets sont copiés lors du fork et ne sont pas synchronisés dynamiquement. Si vous effectuez une rotation des clés du modèle ou ajoutez de nouveaux Secrets, les Apps existantes précédemment forkées ne seront pas mises à jour. Les créateurs devront ajouter ou mettre à jour manuellement les Secrets dans ces Apps.
</Warning>

<div id="instructions">
  ### Création d’instructions personnalisées
</div>

Créez un fichier à l’emplacement `custom_instruction/instructions.md` à la racine du projet. C’est le fichier le plus important du modèle : il indique à Agent comment votre organisation développe ses logiciels.

<Warning>
  Le nom du dossier est `custom_instruction` (au singulier), et non `custom_instructions`.
</Warning>

Agent injecte directement ce fichier dans son prompt système avec le Preamble et le présente comme des directives fournies par votre entreprise. Rédigez-le en Markdown et incluez les éléments suivants :

* **Modèles d’architecture** : comment structurer l’App
* **Normes de codage** : conventions de nommage, règles d’organisation des fichiers et exigences de linting
* **Utilisation des composants** : bibliothèques et composants à utiliser (et à éviter)
* **Modèles d’API** : comment appeler les services backend, gérer l’authentification et les erreurs
* **Exigences de test** : tests attendus et méthode d’exécution
* **Directives de déploiement** : paramètres spécifiques à l’environnement et flux de travail de déploiement

````markdown theme={null}
# Normes d’ingénierie de l’entreprise

## Architecture
Toutes les applications web utilisent React avec TypeScript. Utilisez exclusivement des composants fonctionnels
avec des hooks. La gestion de l’état utilise Zustand pour l’état local
et React Query pour l’état côté serveur.

## Bibliothèque de composants
Utilisez notre package interne de design system `@acme/ui`. N’utilisez jamais d’éléments HTML
bruts pour les boutons, les champs de saisie, les formulaires ou les fenêtres modales : utilisez toujours le
composant correspondant de `@acme/ui`.

Importez les composants comme suit :
```tsx
import { Button, TextField, Modal } from '@acme/ui';
```

## Intégration API
Tous les appels d’API passent par le package `@acme/api-client`. N’utilisez jamais
directement fetch ou axios. L’authentification est gérée automatiquement
par le client.

## Tests
Chaque composant doit avoir un fichier de test correspondant. Utilisez Vitest
pour les tests unitaires et Playwright pour les tests d’intégration.
````

**Limite de taille** : le contenu est soumis à une limite souple d’environ 25 Ko. Au-delà de cette limite, il peut être progressivement tronqué. Si vos Instructions deviennent volumineuses, déplacez les documents de référence détaillés vers les [compétences](/fr/ja/features/agent/skills) dans `.agents/skills/`, plutôt que de tout conserver dans `instructions.md`. Les compétences sont chargées à la demande lorsqu’elles sont pertinentes. Elles ne sont donc pas prises en compte dans la limite de taille des Instructions et vous permettent de réserver les Instructions principales aux règles générales.

<div id="section-5">
  ### Ajouter des compétences personnalisées
</div>

Créez des compétences dans le répertoire `.agents/skills/` pour les flux de travail spécialisés qu’Agent doit suivre. Chaque compétence est un dossier contenant un fichier `SKILL.md` avec un front matter YAML.

```
.agents/skills/
├── use-design-system/
│   └── SKILL.md
├── api-integration/
│   └── SKILL.md
└── run-tests/
    └── SKILL.md
```

Le frontmatter de chaque `SKILL.md` doit contenir `name` et `description` :

```markdown theme={null}
---
name: use-design-system
description: Use when building UI components. Provides component patterns, theming rules, and accessibility requirements for the Acme design system.
---

# Acme Design System

## Available components

- `Button` — Primary, secondary, and ghost variants
- `TextField` — Text input with validation support
- `Modal` — Dialog overlay with focus trapping
...
```

| Champ         | Obligatoire | Détails                                                                                          |
| ------------- | ----------- | ------------------------------------------------------------------------------------------------ |
| `name`        | Oui         | 64 caractères maximum. Uniquement des lettres minuscules, des chiffres et des traits d’union.    |
| `description` | Oui         | 1 024 caractères maximum. Décrit ce que fait la compétence et quand l’utiliser.                  |
| `enabled`     | Non         | La valeur par défaut est `true`. Définissez-le sur `false` pour la désactiver sans la supprimer. |

**Comment les compétences sont chargées** : Agent ne reconnaît que `name` et `description` dans le prompt. Lorsqu’une compétence est pertinente pour la tâche en cours, il charge à la demande l’intégralité du contenu de `SKILL.md`. Cela signifie que le champ `description` est important : rédigez-le de manière à ce qu’il corresponde aux scénarios dans lesquels Agent doit utiliser la compétence.

Les compétences peuvent également inclure des fichiers auxiliaires avec `SKILL.md` :

```
.agents/skills/use-design-system/
├── SKILL.md
├── references/
│   └── component-api.md
└── assets/
    └── theme-tokens.json
```

Pour en savoir plus sur les compétences, consultez [les compétences Agent](/fr/ja/features/agent/skills) et [l’utilisation des compétences](/fr/ja/build/use-agent-skills).

<div id="replitmd">
  ### Configuration de replit.md
</div>

Préremplissez le fichier `replit.md`, situé à la racine du projet, avec une présentation de l’architecture du modèle. Ce fichier est toujours chargé dans le contexte d’Agent et sert de mémoire persistante au projet.

Le fichier doit comporter les quatre sections suivantes :

```markdown theme={null}
# Vue d’ensemble
Application de gestion des tâches conçue avec React, TypeScript et le système de design Acme. Utilise un backend Express.js avec PostgreSQL.

# Préférences utilisateur
- Utiliser TypeScript pour tous les fichiers
- Privilégier les composants fonctionnels avec des hooks
- Respecter les standards de codage Acme

# Architecture du système
- Frontend : React + TypeScript + @acme/ui
- Backend : Express.js + TypeScript
- Base de données : PostgreSQL avec Drizzle ORM
- Auth : SSO Acme via @acme/auth

# Dépendances externes
- @acme/ui : Système de design interne
- @acme/api-client : Couche d’intégration API
- @acme/auth : SDK d’authentification
```

Agent met à jour `replit.md` à mesure que le projet évolue. Lorsque le fichier dépasse environ 4 000 tokens, Agent le résume automatiquement pour rester ciblé et utile.

Pour en savoir plus, consultez [replit.md](/fr/ja/features/project-setup/replit-dot-md).

<div id="section-6">
  ### Épingler un modèle à l’organisation
</div>

Une fois votre modèle prêt :

1. Accédez à l’App modèle de votre organisation
2. Ouvrez le menu d’actions de l’App (menu à trois points)
3. Sélectionnez **Épingler à la zone de saisie Agent**

<img src="/assets/mirror/custom-templates-pin-to-agent-b733d3eb9a80.png" alt="Menu d’actions de l’App montrant l’option Épingler à la zone de saisie Agent" width="984" height="856" data-path="images/teams/custom-templates-pin-to-agent.png" />

<Note>
  Seuls les administrateurs de l’organisation (membres disposant du rôle `system_admins`) peuvent épingler et désépingler des modèles.
</Note>

Définissez l’accès des membres sur **lecture seule** afin qu’ils puissent afficher et utiliser les modèles épinglés sans pouvoir les modifier.

<img src="/assets/mirror/custom-templates-members-read-only-cf6aa160c8ef.png" alt="Boîte de dialogue d’invitation montrant que l’accès des membres est défini sur lecture seule" width="954" height="1064" data-path="images/teams/custom-templates-members-read-only.png" />

Les modèles s’affichent sous forme de pastilles sélectionnables sous la zone de saisie Agent de tous les membres de l’organisation. Pour les retirer, ouvrez le même menu et sélectionnez **Désépingler de la zone de saisie Agent**.

<div id="section-7">
  ### Contrôler l’accès aux modèles
</div>

L’épinglage rend les modèles visibles par tous les membres de l’Org. Pour une distribution plus ciblée, utilisez le bouton **Invite** de l’App modèle pour la partager avec des [groupes ou des utilisateurs spécifiques](/fr/ja/teams/identity-and-access-management/groups-and-permissions). Vous pouvez ainsi limiter les équipes ou les personnes pouvant afficher et dupliquer le modèle, sans l’épingler dans la zone de saisie à l’échelle de l’Org.

<div id="section-8">
  ## Comportement lorsqu’un créateur sélectionne un modèle
</div>

<img src="/assets/mirror/custom-templates-input-box-553384ac7dd0.png" alt="Modèle affiché sous forme de pastille sélectionnable dans la zone de saisie d’Agent" width="1746" height="726" data-path="images/teams/custom-templates-input-box.png" />

Lorsqu’un membre de l’organisation sélectionne un modèle épinglé dans la zone de saisie d’Agent :

1. **Fork** : une New App est créée comme copie du modèle, avec tous ses fichiers
2. **Ignorer la planification** : Agent ignore la conversation de planification initiale et passe directement en Mode Build
3. **Chargement des instructions** : `custom_instruction/instructions.md` est chargé et injecté dans le prompt système d’Agent comme directives fournies par l’entreprise
4. **Détection des compétences** : les compétences présentes dans `.agents/skills/` sont détectées et répertoriées dans le contexte d’Agent pour être chargées à la demande
5. **Chargement du contexte du projet** : `replit.md` est chargé et injecté dans le contexte d’Agent (il est généré automatiquement s’il n’existe pas)
6. **Héritage de la configuration** : le fichier `.replit`, les dépendances et tous les fichiers du modèle sont transférés vers la New App

Le créateur peut immédiatement commencer à envoyer à Agent des prompts décrivant des exigences spécifiques, et Agent fonctionne dans le cadre des garde-fous établis par le modèle.

<div id="section-9">
  ## Comment les fichiers interagissent
</div>

Chaque fichier de configuration a un rôle distinct :

| Fichier                              | Objectif                                     | Quand Agent le lit                        | Agent peut le modifier                           |
| ------------------------------------ | -------------------------------------------- | ----------------------------------------- | ------------------------------------------------ |
| `custom_instruction/instructions.md` | Normes et règles de l’organisation           | Toujours (injecté dans le prompt système) | Non                                              |
| `.agents/skills/*/SKILL.md`          | Flux de travail et modèles spécialisés       | À la demande (lorsqu’ils sont pertinents) | Oui (Agent peut également créer des compétences) |
| `replit.md`                          | Présentation et configuration du projet      | Toujours (injecté dans le prompt système) | Oui (Agent le met à jour au fil du temps)        |
| `.replit`                            | Configuration de l’environnement d’exécution | Lors de la configuration d’une App        | Oui                                              |

**Distinction principale** : `custom_instruction/instructions.md` est la source de référence statique pour les normes de l’organisation. `replit.md` est un document évolutif qu’Agent met à jour à mesure que le projet évolue. Les compétences sont des ressources de référence à la demande pour des flux de travail spécifiques.

<div id="section-10">
  ## Bonnes pratiques
</div>

<div id="instructions-2">
  ### Gardez les Instructions ciblées
</div>

Rédigez `custom_instruction/instructions.md` pour les modèles les plus importants. Concentrez-vous sur :

* Les décisions difficiles à annuler (architecture, modèle de données)
* Les modèles qui doivent rester cohérents (utilisation des composants, conventions d’API)
* Les normes que les créateurs ne connaissent peut-être pas (bibliothèques internes, conventions d’équipe)

Évitez d’ajouter des changelogs, des détails d’implémentation ou des informations qui changent fréquemment.

<div id="description">
  ### Rédiger une description de compétence détectable
</div>

Le champ Description du frontmatter de `SKILL.md` indique à Agent quand charger une compétence. Rédigez une description qui correspond aux tâches pour lesquelles la compétence est pertinente :

```yaml theme={null}
# Bon exemple — indique quand l’utiliser
description: フォームのビルドやユーザー入力の処理時に使用します。Acmeデザインシステムのバリデーションパターン、エラー表示規約、アクセシブルなフォームレイアウトを提供します。

# Exemple moins efficace — trop vague
description: フォームのユーティリティとヘルパー。
```

<div id="section-11">
  ### Organiser les compétences par flux de travail
</div>

Regroupez les compétences par flux de travail plutôt que par catégories techniques :

| Approche                  | Exemples                                   |
| ------------------------- | ------------------------------------------ |
| **Par flux de travail**   | `build-a-form`、`connect-to-api`、`add-auth` |
| **Par domaine technique** | `react-utils`、`api-helpers`、`auth-config`  |

Cette approche permet à Agent de détecter les compétences au moment opportun.

<div id="section-12">
  ### Améliorer continuellement les modèles
</div>

Les modèles s’améliorent à l’usage. Une fois que votre équipe commence à développer à partir d’un modèle :

1. Repérez les erreurs récurrentes de l’Agent et ajoutez-les à `instructions.md`
2. Lorsque l’Agent résout efficacement un problème, créez une nouvelle compétence pour documenter la solution
3. Mettez à jour les dépendances de base et la configuration au fur et à mesure que votre stack évolue
4. Testez les modifications en créant une nouvelle App à partir du modèle afin de vérifier l’expérience

<div id="app-2">
  ### Mises à jour des modèles et App existantes
</div>

Les modifications apportées à un modèle App s’appliquent aux **nouvelles** App créées à partir de celui-ci. Les App existantes précédemment forkées à partir du modèle sont des copies indépendantes et ne reçoivent pas ces mises à jour.
