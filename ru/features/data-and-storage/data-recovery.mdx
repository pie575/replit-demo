Ошибки случаются: неудачное изменение схемы, удалённые строки или сессия Agent, которая пошла не по плану. Replit предлагает свой способ восстановления для каждой базы данных.

| База данных | Способ восстановления                                            | Доступность                                                                  |
| ----------- | ---------------------------------------------------------------- | ---------------------------------------------------------------------------- |
| Разработки  | Откат к чекпоинту                                               | Все тарифы                                                                   |
| Продакшен   | Восстановление на момент времени и резервные копии по расписанию | Core: до 7 дней истории. Pro и Enterprise: до 28 дней (по умолчанию 7 дней). |

<div id="restore-your-development-database">
  ## Восстановление базы данных разработки
</div>

Вы можете вернуть приложение и базу данных разработки к предыдущему состоянию с помощью [функции отката](/ru/features/version-control/checkpoints-and-rollbacks/). Так базу данных можно восстановить до любого чекпоинта, созданного Agent.

<Frame>
  <img src="/assets/mirror/checkpoint-rollback-476fde84864b.png" alt="Интерфейс отката к чекпоинту с параметрами отката" width="3154" height="2366" data-path="images/replitai/checkpoint-rollback.png" />
</Frame>

<Info>
  При откате к состоянию чекпоинта обязательно выберите «Database» в разделе «Additional rollback options». Тогда база данных вернётся к тому состоянию, в котором она была на момент создания чекпоинта.
</Info>

<div id="restore-your-production-database">
  ## Восстановление продакшен-базы данных
</div>

Для продакшен-баз данных доступно восстановление на конкретный момент времени (point-in-time restore).

<Frame>
  <img src="/assets/mirror/database-rollbacks-f13dd20874ae.jpg" alt="Интерфейс отката базы данных с параметрами отката" width="1082" height="708" data-path="images/databases/database-rollbacks.jpg" />
</Frame>

Глубина восстановления зависит от вашего тарифа и настроек хранения истории. Core хранит историю до 7 дней, а Pro и Enterprise — до 28 дней. На всех тарифах изначально установлено 7 дней, изменить этот период можно в настройках продакшен-базы данных. Чем больше период, тем больше расходуется хранилища, поэтому увеличение срока хранения повышает стоимость использования. При переходе с Pro на Core период хранения сокращается до 7 дней.

<Warning>
  Восстановление базы данных не восстанавливает код приложения, а откат
  приложения не восстанавливает базу данных. Чтобы вернуть и то, и другое к
  одному моменту: восстановите базу данных, затем [откатитесь к
  соответствующему чекпоинту](/ru/features/version-control/checkpoints-and-rollbacks/)
  и опубликуйте приложение заново.
</Warning>

<div id="schedule-production-database-backups">
  ## Настройка расписания резервного копирования продакшен-базы данных
</div>

Резервное копирование по расписанию ежедневно создаёт одну полную точку восстановления. Replit планирует его примерно на полночь по часовому поясу браузера, действующему на момент включения или изменения расписания.

1. Откройте инструмент **Database** и выберите продакшен-базу данных.
2. Откройте **Settings**, затем разверните **Scheduled backups** в разделе **Advanced**.
3. Чтобы включить резервное копирование по расписанию, выберите срок хранения в разделе **Keep backups for**.

Доступные сроки хранения зависят от вашего тарифного плана: Core — до 7 дней, Pro и Enterprise — до 28 дней.

<div id="storage-costs">
  ### Стоимость хранения
</div>

Replit тарифицирует каждую категорию хранения продакшен-базы данных отдельно:

| Категория хранения                                | Цена за ГиБ в месяц |
| ------------------------------------------------- | ------------------: |
| Логическое хранилище базы данных                  |               $0,35 |
| Хранилище восстановления на момент времени (PITR) |               $0,20 |
| Хранилище резервных копий по расписанию           |               $0,09 |

<Note>В настоящее время на хранение базы данных действует скидка 100%.</Note>

Плата $0,35 за логическое хранилище взимается независимо от того, используете ли вы PITR, резервные копии по расписанию или и то и другое. Хранение резервных копий по расписанию обходится дешевле за ГиБ, чем хранилище PITR. Если вам достаточно ежедневных точек восстановления, резервные копии по расписанию с более коротким окном PITR помогут снизить расходы на хранение данных для восстановления. Итоговая стоимость резервного копирования зависит от объёма сохранённых копий и срока их хранения.

PITR даёт больше точек восстановления в пределах своего окна. Резервные копии по расписанию дают одну точку восстановления в день, поэтому выбирайте тот способ восстановления, который отвечает вашим задачам.

<Note>
  В расписании используется ваше текущее смещение относительно UTC. Переход на
  летнее время может сдвинуть время резервного копирования на час, пока вы не
  обновите расписание. Для часовых поясов с дробным смещением используется
  ближайший час.
</Note>

<div id="restore-a-scheduled-backup">
  ### Восстановление запланированной резервной копии
</div>

1. Откройте раздел **Scheduled backups** в настройках продакшен-базы данных.
2. Выберите **View all backups**.
3. Нажмите **Restore** рядом с нужной точкой восстановления.
4. Введите `restore` и нажмите **Continue**.

При восстановлении база данных переключается на данные выбранной резервной копии. Текущие данные не удаляются, но подключённым сервисам может потребоваться кратковременное переподключение.

<div id="troubleshooting-publishing-failures">
  ## Устранение сбоев публикации
</div>

Если публикация завершается сбоем из-за проблем с базой данных:

1. **Проверьте логи публикации** — найдите конкретные сообщения об ошибках подключения к базе данных или о конфликтах схемы
2. **Просмотрите недавние изменения схемы** на предмет возможных конфликтов с существующим кодом приложения
3. **Протестируйте изменения в предварительном просмотре deployment**, прежде чем публиковать повторно
