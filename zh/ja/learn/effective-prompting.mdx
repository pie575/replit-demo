有效的提示词，就是向能干的助手清晰下达指令。只要善于引导 [**Agent**](/zh/ja/features/agent/overview)，就能快速将创意变成应用。

<div id="section">
  ## 快速示例
</div>

下面来看看模糊提示词与有效提示词之间的区别：

<AccordionGroup>
  <Accordion title="修复代码" icon="bug">
    **模糊：**“修复代码。”

    **有效：**“脚本在处理用户输入时出错。我怀疑问题出在验证函数上。能帮我调试 `validate_input` 部分吗？错误信息如下：[详细信息]”

    有效的提示词会指出问题所在、可疑函数，并提供上下文。
  </Accordion>

  <Accordion title="构建功能" icon="hammer">
    **模糊：**“创建一个网站。”

    **有效：**“请创建一个简单的作品集网站，包含主页、个人简介和联系表单。请使用简洁现代的设计风格和占位内容。”

    有效的提示词会明确目标、核心功能和期望的视觉风格。
  </Accordion>

  <Accordion title="提升性能" icon="gauge-high">
    **模糊：**“别让它变慢。”

    **有效：**“请重构数据处理函数，使其能够更高效地处理更大的输入。可以使用不同的算法或数据结构吗？”

    不要只给出否定性限制，应告诉 Agent *如何*改进。
  </Accordion>

  <Accordion title="更改界面" icon="paintbrush">
    **模糊：**“添加动画。”

    **有效：**“请让落地页主图在首次加载时以柔和的淡入动画呈现，营造欢迎的氛围。”

    明确说明具体元素、期望效果、时机和预期体验。
  </Accordion>

  <Accordion title="复杂系统" icon="server">
    **模糊：**“构建后端。”

    **有效：**“请设置服务器端逻辑。实现用户认证 (注册/登录) ，并创建能够安全获取用户个人资料数据的 API 端点。”

    将大型任务拆分为具体功能。
  </Accordion>
</AccordionGroup>

<div id="section-3">
  ### 先制定计划
</div>

<Tip>在编写提示词之前，先梳理应用的功能和用户流程。清晰的计划有助于写出更聚焦的提示词。</Tip>

像产品经理一样思考应用的结构。将整体目标拆解为逻辑清晰的步骤。

**不要这样：** “构建一个任务管理应用。”

**试试这样：** “1. 创建包含输入字段和任务列表的基本 HTML 结构。2. 添加用于新增任务的 JavaScript。3. 使用数据库保存任务。4. 添加将任务标记为已完成的功能。”

然后针对每个步骤向 Agent 提供提示词。

<div id="section-4">
  ### 逐步构建
</div>

每成功完成一个步骤后，都使用[**checkpoint**](/zh/ja/features/agent/overview#checkpoints)保存进度。如果出现问题，您可以回滚到正常运行的状态，并尝试其他方法。

**不要这样：** “构建一个完整的电商平台。”

**试试这样：** “请搭建一个基础的全栈电商网站项目，让用户能够通过 Replit Auth 注册和登录。”然后继续使用关于商品列表、购物车和结账的提示词。

<div id="section-5">
  ### 具体说明
</div>

明确界定你的需求：输出格式、约束条件和边界情况。

**不要这样写：** “添加一个联系表单。”

**试试这样写：** “请在 `/contact` 创建一个包含以下字段的联系表单页面：

* 姓名 (必填)
* 电子邮件 (必填，格式必须有效)
* 留言 (必填，至少 10 个字符)

提交时，请将表单数据发送至 `contact@mydomain.com`。”

<div id="section-6">
  ### 使用积极的语言
</div>

描述您*希望实现的效果*，而不是想要避免的情况。

**不要这样说：** “不要让用户个人资料页面显得杂乱。”

**试试这样说：** “设计一个简洁的用户个人资料页面。突出显示用户名，然后显示电子邮件地址和注册日期。请添加“编辑个人资料”按钮。”

<div id="section-7">
  ### 保持简洁
</div>

使用清晰直接的语言。将复杂的请求拆分成要点。

**不要这样写：**“实现必要的服务器端基础设施，以支持动态生成和获取用户生成的内容产物。”

**试试这样写：**“请创建后端功能，让用户提交博客文章。用户需要输入标题和正文内容。请将文章保存到数据库中。”

<div id="section-8">
  ## 利用上下文
</div>

<div id="section-9">
  ### 提供相关文件
</div>

不要附上整个项目，而应明确提及特定文件。

**不要这样：**  (附上所有内容) “根据设计系统实现用户资料页面。”

**试试这样：** “请创建一个用户资料页面，并从服务器端点获取用户数据。请按照 [设计文档 URL] 设置样式，并与以下模型图保持一致：[`profile_mockup.jpg` 已附上]。”

<Tip>切换到无关任务时，请新开一个聊天，以避免累积的上下文造成混淆。</Tip>

<div id="section-10">
  ### 提供示例
</div>

提供具体示例 (代码片段、示例数据、屏幕截图) ，以减少歧义。

**不要这样：** “让商品卡片看起来更美观。”

**试试这样：** “请重新设计商店页面的商品卡片。每张卡片应显示商品图片、名称、价格和“添加到购物车”按钮，并采用类似这样的布局：[附上屏幕截图]。请使用浅灰色边框。”

<div id="section-11">
  ## 有效调试
</div>

如果发生错误，请提供以下信息：

* **完整准确的**错误信息
* 相关代码片段
* 发生错误的文件名
* 你想实现的目标
* 已尝试过的步骤

**不要这样说：** “登录页面坏了。”

**试着这样说：** “使用正确的凭据在 `/login` 登录时，浏览器控制台显示‘未找到用户’错误。数据库查询似乎没有正常工作。以下是 `auth.js` 中处理登录的代码。”

<div id="section-12">
  ## 寻求建议
</div>

<Tip>开始构建前，先切换到 Plan 模式，了解可选方案。可以向 Agent 咨询相关库、实现方式及其取舍。</Tip>

**不要这样说：**“添加支付功能。”

**试试这样说：**“对于在 Replit 上构建的 Web 应用，有哪些适合接受信用卡付款的好方案？我需要能相对简单集成的方案。”

<div id="section-13">
  ## 反复优化提示词
</div>

最初的提示词不够完美很正常。如果生成结果不符合预期：

* 添加更多细节
* 提供示例
* 简化指令
* 尝试换一种描述方式

**初始提示词：** “创建一个网站页眉。”

**优化后：** “创建一个固定页眉组件，网站徽标位于左侧，导航链接 (首页、关于我们、联系我们) 位于右侧。”

<div id="section-14">
  ## 总结
</div>

编写有效提示词的要点：

* 在编写提示词前先**规划**
* 利用 checkpoint 分阶段**构建**
* **明确具体**地说明需求
* 通过示例和相关文件**提供上下文**
* 如果结果略有偏差，就**迭代改进**

掌握这些原则后，您就能使用 Agent 更快地构建应用。
