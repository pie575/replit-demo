La publication transforme votre projet en application publique. Si la publication échoue ou si l’URL publiée fonctionne différemment de l’aperçu, résolvez le problème étape par étape.

Cette page sert à la fois de guide de récupération de Build et de référence de dépannage des déploiements. Commençons par la question la plus simple : votre application fonctionne-t-elle dans l’aperçu ?

<div id="section">
  ## Ce que vous pourrez accomplir
</div>

À la fin de cette page, vous saurez déterminer si le problème vient de l’application elle-même, des paramètres de publication, des Secrets de production, du type de déploiement, de la configuration des ports ou de l’accès au réseau/DNS.

<div id="section-2">
  ## Commencer par aperçu
</div>

Avant de publier, vérifiez que votre application fonctionne correctement dans l’éditeur de projet.

Sélectionnez **Run** en haut de l’éditeur de projet pour ouvrir l’aperçu. Si votre application ne s’affiche pas dans l’aperçu à l’adresse `replit.dev`, corrigez-la avant de la publier.

Demandez d’abord à Agent de diagnostiquer l’aperçu :

<AiPrompt>
  Cette application ne fonctionne pas dans l’aperçu.<br />
  Vérifie la commande d’exécution, l’installation des dépendances, les erreurs de l’application, les ports et les Secrets manquants.<br />
  Corrige d’abord le problème le plus simple et indique-moi comment vérifier que l’aperçu fonctionne avant la publication.
</AiPrompt>

Si l’aperçu ne fonctionne pas, la publication ne résoudra pas le problème.

<div id="section-3">
  ## Si l’aperçu fonctionne, mais que la publication échoue
</div>

Si l’aperçu fonctionne, mais que la publication échoue, vérifiez les paramètres spécifiques à la publication.

<div id="section-4">
  ### Vérifier les logs
</div>

Ouvrez l’onglet **Logs** du panneau **Publishing**. Recherchez des traces de pile, des packages manquants, des échecs de commande, des variables d’environnement manquantes et des erreurs de démarrage.

Collez l’erreur pertinente dans Agent :

<AiPrompt>
  La publication a échoué avec cette sortie de log : [collez l’erreur].<br />
  Explique la cause probable.<br />
  Indique s’il s’agit d’une erreur de commande, de dépendance, de Secret, de port, de build ou d’application.<br />
  Recommande la correction la plus simple et explique comment la vérifier.
</AiPrompt>

<div id="section-5">
  ### Vérifier les commandes d’exécution et de compilation
</div>

Les erreurs courantes incluent les fautes de frappe, les indicateurs incorrects, un mauvais fichier d’entrée ou des commandes qui ne fonctionnent qu’en local.

Vérifiez les commandes dans le panneau **Publishing**. Si votre application nécessite à la fois une commande de compilation et une commande de démarrage, assurez-vous qu’elles sont toutes les deux correctes.

<div id="secrets">
  ### Vérifier les Secrets en production
</div>

Les Secrets configurés dans l’éditeur de projet ne sont pas automatiquement transférés vers les applications publiées. Ajoutez tous les Secrets et toutes les variables d’environnement nécessaires à la production dans le panneau **Publishing**.

L’absence de Secrets peut entraîner des erreurs liées à des valeurs non définies, des échecs d’appels API, des échecs de connexion à la base de données, des erreurs de connexion, des échecs de paiement, etc.

Consultez [Secrets](/fr/ja/core-concepts/project-editor/app-setup/secrets).

<div id="section-6">
  ### Vérifier le fonctionnement des processus de longue durée
</div>

Les applications publiées nécessitent que le programme continue de s’exécuter. Si le programme ne s’exécute qu’une seule fois puis s’arrête, la plateforme le redémarre automatiquement.

Assurez-vous que l’application démarre un processus de longue durée, comme un serveur web.

<div id="section-7">
  ### Vérifier les paramètres de l’hôte et du port
</div>

Si vous exécutez un serveur web, Deployments peut détecter automatiquement le port utilisé par le serveur, mais celui-ci doit écouter sur `0.0.0.0`. S’il écoute uniquement sur `localhost` ou `127.0.0.1`, l’application publiée ne fonctionnera pas.

[Si vous avez spécifié un port dans la configuration `.replit`](/fr/ja/features/project-setup/configuration), la détection automatique des ports est désactivée. Pour passer l’étape de promotion, vous devez spécifier un port avec `externalPort` défini sur `80`. Vérifiez que le serveur écoute sur le `localPort` indiqué.

Demandons à Agent de vérifier plus en détail :

<AiPrompt>
  Vérifie que cette application est correctement configurée pour la publication.<br />
  Vérifie que le serveur lance un processus de longue durée, écoute sur 0.0.0.0, utilise le port attendu et correspond à toute configuration de port dans .replit.<br />
  Ne modifie pas le comportement de l’application au-delà des corrections nécessaires à la publication.
</AiPrompt>

<div id="section-8">
  ### Vérifier le délai du contrôle d’intégrité
</div>

Avant de déclarer une application publiée comme étant en ligne, Replit lui envoie une requête HTTP. Si la page d’accueil met plus de 5 secondes à répondre, le contrôle d’intégrité peut expirer et la publication peut échouer à l’étape finale.

Si le démarrage est lent, demandez à Agent de réduire les traitements au démarrage, de reporter les traitements lourds après une action de l’utilisateur ou de mettre les données en cache aux endroits appropriés.

<div id="url">
  ## Si la publication a réussi, mais que l’URL publiée ne fonctionne pas
</div>

Si l’app fonctionne dans l’aperçu et que la publication a réussi, mais que l’URL publiée ne fonctionne pas, comparez le comportement de l’aperçu avec celui de l’environnement de production.

Points à vérifier :

* Les Secrets et les variables d’environnement de production.
* Les paramètres de connexion à la base de données.
* Les URL de rappel ou de redirection de connexion.
* Les webhooks de paiement ou les paramètres de redirection.
* Les listes d’autorisation d’API ou les paramètres CORS.
* Les fichiers écrits localement plutôt que dans une base de données ou un service de stockage.
* Les différences de mise en page entre mobile et navigateur.

Demandez à Agent de comparer les environnements :

<AiPrompt>
  L’app fonctionne dans l’aperçu, mais pas à l’URL publiée.<br />
  Aidez-moi à comparer le comportement de l’aperçu et de l’environnement de production.<br />
  Vérifiez les Secrets, les paramètres de la base de données, les appels d’API, les redirections de connexion, les redirections de paiement, la sortie de build et les logs.<br />
  Indiquez-moi la vérification la plus sûre à effectuer ensuite.
</AiPrompt>

<div id="section-9">
  ## Problèmes de déploiement statique
</div>

Les déploiements statiques servent des fichiers statiques tels que HTML, CSS et JavaScript.

Si votre application comprend un traitement côté serveur, des routes API, des rappels d’authentification, des appels de base de données depuis le serveur ou une logique back-end s’exécutant sur une longue durée, elle n’est peut-être pas adaptée à un déploiement statique. Modifiez plutôt le type de déploiement en Autoscale dans le panneau **Publishing**.

Les problèmes de déploiement statique sont souvent dus à une mauvaise configuration du répertoire public ou à la sélection de Static pour une application nécessitant un serveur.

<div id="section-10">
  ## Limites de taille et de fichiers
</div>

Les VM réservées et les déploiements Autoscale prennent en charge les Replit Apps jusqu’à 8 Go. Les déploiements statiques prennent en charge les Replit Apps jusqu’à 1 Go.

Pour réduire la taille de votre application, supprimez les fichiers inutiles, évitez de valider les fichiers générés ou utilisez un stockage externe pour les ressources volumineuses.

<Warning>
  Le système de fichiers d’une application publiée n’est pas persistant et est réinitialisé à chaque publication. Pour conserver vos données, utilisez une base de données telle que [SQL Database](/fr/ja/features/data-and-storage/sql-database).
</Warning>

Si des fichiers importés ou des données générées disparaissent après la publication, enregistrez-les dans une base de données ou un service de stockage plutôt que dans le système de fichiers de l’application.

<div id="replitappreplitdev-url">
  ## Problèmes d’accès aux URL `replit.app` et `replit.dev`
</div>

Si vous ne parvenez pas à accéder à une App sur les domaines `replit.app` ou `replit.dev`, cela peut être dû à des filtres Web ou à des restrictions réseau.

Essayez d’utiliser des résolveurs DNS publics, comme Google DNS (`8.8.8.8`) ou Cloudflare DNS (`1.1.1.1`).

<div id="dns">
  ### Modifier les paramètres DNS
</div>

<Tabs>
  <Tab title="Windows">
    1. Ouvrez le **Panneau de configuration**.
    2. Accédez au **Centre Réseau et partage**.
    3. Dans le volet de gauche, sélectionnez **Modifier les paramètres de la carte**.
    4. Cliquez avec le bouton droit sur votre connexion réseau active, puis sélectionnez **Propriétés**.
    5. Sélectionnez **Protocole Internet version 4 (TCP/IPv4)**, puis cliquez sur **Propriétés**.
    6. Sélectionnez **Utiliser l’adresse de serveur DNS suivante**.
    7. Saisissez l’adresse IP d’un serveur DNS public, telle que `8.8.8.8` pour Google DNS ou `1.1.1.1` pour Cloudflare DNS.
    8. Sélectionnez **OK** pour enregistrer vos modifications.

    Pour obtenir des instructions détaillées, consultez le [guide Microsoft de configuration DNS](https://support.microsoft.com/en-us/windows/change-tcp-ip-settings-bd0a07af-15f5-cd6a-363f-ca2b6f391ace).
  </Tab>

  <Tab title="macOS">
    1. Ouvrez les **Préférences Système**.
    2. Sélectionnez **Réseau**.
    3. Dans le volet de gauche, sélectionnez votre connexion réseau active.
    4. Sélectionnez **Avancé** en bas à droite.
    5. Accédez à l’onglet **DNS**.
    6. Sélectionnez le bouton **+** pour ajouter un serveur DNS.
    7. Saisissez l’adresse IP d’un serveur DNS public, telle que `8.8.8.8` pour Google DNS ou `1.1.1.1` pour Cloudflare DNS.
    8. Sélectionnez **OK**, puis cliquez sur **Appliquer**.

    Pour obtenir des instructions détaillées, consultez le [guide Apple de configuration DNS](https://support.apple.com/guide/mac-help/change-dns-settings-on-mac-mh14127/mac).
  </Tab>

  <Tab title="Linux">
    1. Modifiez le fichier `/etc/resolv.conf` pour ajouter des serveurs DNS publics. La méthode exacte varie selon votre distribution.
    2. Ajoutez les lignes suivantes :

    ```bash theme={null}
    nameserver 8.8.8.8
    nameserver 1.1.1.1
    ```

    Pour en savoir plus sur la configuration DNS des différentes distributions, consultez le [guide de configuration réseau du wiki Debian](https://wiki.debian.org/NetworkConfiguration#Defining_the_.28DNS.29_Nameservers).
  </Tab>
</Tabs>

<div id="dns-2">
  ### Vider le cache DNS
</div>

Après avoir modifié vos paramètres DNS, videz le cache DNS afin d’appliquer les nouveaux paramètres :

* **Windows** : exécutez `ipconfig /flushdns` dans l’invite de commandes.
* **macOS et Linux** : exécutez `sudo systemctl restart NetworkManager` dans le terminal. La commande exacte peut varier selon votre distribution.

<Note>
  Afin d’améliorer les performances et la stabilité dans chaque région, les URL `replit.dev`
  des Replit Apps peuvent changer lors des migrations de cluster. Une fois la migration terminée,
  elles restent stables pendant environ un an, sauf si vous demandez explicitement un changement de région.
</Note>

<div id="streamlit">
  ## Publier une application Streamlit
</div>

Les applications Streamlit s’exécutent via les déploiements Replit. Pour commencer simplement, utilisez le [modèle Streamlit](https://replit.com/@replit/Streamlit?v=1).

Vous pouvez également configurer la commande d’exécution pour le déploiement comme suit :

```bash theme={null}
streamlit run --server.address 0.0.0.0 --server.headless true --server.enableCORS=false --server.enableWebsocketCompression=false main.py
```

Si votre application utilise un autre fichier d’entrée, remplacez `main.py` par son nom.

<div id="section-11">
  ## Vérification finale
</div>

* L’aperçu fonctionne.
* La publication est terminée.
* L’URL publiée se charge.
* Le flux principal de l’application fonctionne sur l’URL publiée.
* Les Secrets et la configuration de production sont configurés.
* Les logs ne contiennent aucune erreur de démarrage masquée.
