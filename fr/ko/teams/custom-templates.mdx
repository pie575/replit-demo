<div id="section">
  ## Premiers pas
</div>

Replit est un environnement de développement cloud dans lequel vous pouvez écrire et exécuter n’importe quel framework ou stack. Deux approches sont recommandées pour créer des modèles personnalisés :

1. **[Importer depuis un fournisseur Git](https://replit.com/import)** — Importez une stack de démarrage existante (ou toute stack de votre choix) depuis GitHub, GitLab ou Bitbucket.
2. **Forker le modèle Blank** — Forkez le [modèle Blank](https://replit.com/@replit/Nothing?v=1) pour partir de zéro dans un environnement de développement entièrement vide.

Nos clients ont créé avec succès des modèles pour Rust, Python, Java, C++ et de nombreuses autres stacks. Tout ce qui peut s’exécuter peut s’exécuter sur Replit.

<Tip>
  Lors de la création de votre premier modèle, nous vous recommandons de collaborer avec l’**équipe Field Engineering** de Replit. Cette équipe possède une vaste expérience dans la configuration de modèles personnalisés pour différentes stacks et peut vous aider. Contactez votre responsable de compte pour être mis en relation.
</Tip>

Les modèles personnalisés permettent aux administrateurs Enterprise de créer des points de départ préconfigurés qui s’affichent directement dans le champ de saisie d’Agent pour tous les membres de l’organisation. Lorsqu’un builder sélectionne un modèle personnalisé, Agent en crée un fork et utilise la configuration, les instructions et les compétences du modèle pour orienter toutes les tâches suivantes. Aucune configuration supplémentaire n’est nécessaire.

<Note>
  Les modèles personnalisés sont disponibles uniquement avec le forfait **Enterprise**. Seuls les administrateurs de l’organisation peuvent épingler et gérer les modèles.
</Note>

<div id="section-2">
  ## Fonctionnement des modèles personnalisés
</div>

Les modèles personnalisés sont des Replit Apps standard de votre organisation, **épinglées dans le champ de saisie d’Agent**. Lorsqu’un builder en sélectionne un :

1. Agent forke le modèle pour créer une nouvelle application (tous les fichiers sont copiés)
2. Agent ignore l’étape de planification et passe directement à la création
3. Le fichier `custom_instruction/instructions.md` du modèle est injecté dans le contexte d’Agent
4. Les [compétences](/fr/ko/features/agent/skills) personnalisées de `.agents/skills/` sont détectées et deviennent disponibles
5. Le fichier [`replit.md`](/fr/ko/features/project-setup/replit-dot-md) fournit un contexte de projet persistant

Ainsi, les normes, modèles et outils de votre organisation sont intégrés dès la première interaction.

<div id="section-3">
  ## Structure des fichiers de modèle
</div>

La structure recommandée pour un modèle personnalisé est la suivante :

```
my-template/
├── .replit                              # Configuration de l’application (commande d’exécution, port, modules)
├── replit.md                            # Mémoire d’Agent : aperçu du projet et paramètres par défaut
├── custom_instruction/
│   └── instructions.md                  # Instructions de l’entreprise intégrées au prompt d’Agent
├── .agents/
│   └── skills/
│       └── my-skill/
│           └── SKILL.md                 # Compétence personnalisée qu’Agent peut utiliser si nécessaire
└── ...                                  # Reste de la structure du dépôt
```

Chaque fichier a un rôle spécifique. Les sections suivantes expliquent comment configurer chacun d’eux.

<div id="section-4">
  ## Configuration de modèles personnalisés
</div>

<div id="section-5">
  ### Créer une app de base
</div>

Créez une nouvelle Replit App dans votre organisation. Replit configure le projet avec tous les fichiers, dépendances et paramètres nécessaires pour vous permettre de démarrer. Cela inclut :

* Le squelette du code source (composants, utilitaires, fichiers de configuration)
* Les dépendances préinstallées (`package.json`, `requirements.txt`, etc.)
* La configuration de l’environnement dans le [fichier `.replit`](/fr/replit-app/configuration)

<div id="section-6">
  ### Configurer les Secrets partagés
</div>

Si votre modèle nécessite des clés API, des jetons ou d&#39;autres identifiants, ajoutez-les aux **Secrets** du modèle (dans le panneau d&#39;outils) avant de l&#39;épingler. Lorsqu&#39;un builder crée une application à partir de votre modèle, tous les secrets sont automatiquement copiés dans la nouvelle application, ce qui lui permet de commencer à travailler sans avoir à configurer lui-même les identifiants.

Documentez tous les secrets dans `custom_instruction/instructions.md` (ou dans une compétence dédiée) afin que les builders sachent lesquels sont disponibles et à quoi sert chaque clé.

<Warning>
  Les secrets sont copiés au moment du fork et ne sont pas synchronisés dynamiquement. Si vous remplacez une clé ou ajoutez un nouveau secret au modèle, les applications existantes précédemment forkées ne seront pas mises à jour. Les builders devront ajouter ou mettre à jour manuellement les secrets dans ces applications.
</Warning>

<div id="section-7">
  ### Rédiger des instructions personnalisées
</div>

Créez un fichier `custom_instruction/instructions.md` à la racine du projet. C’est le fichier le plus important du modèle : il indique à Agent comment votre organisation développe ses logiciels.

<Warning>
  Le nom du dossier doit être `custom_instruction` (au singulier), et non `custom_instructions` (au pluriel).
</Warning>

Agent injecte directement ce fichier dans le prompt système, précédé d’un préambule le présentant comme des instructions fournies par l’entreprise. Rédigez-le en Markdown et incluez les éléments suivants :

* **Modèles d’architecture** : la manière dont votre application est structurée
* **Normes de codage** : conventions de nommage, règles d’organisation des fichiers et exigences de linting
* **Utilisation des composants** : bibliothèques et composants à utiliser (et à éviter)
* **Modèles d’API** : appels aux services backend, gestion de l’authentification et des erreurs
* **Exigences de test** : tests attendus et manière de les exécuter
* **Instructions de déploiement** : configuration par environnement et flux de travail de déploiement

````markdown theme={null}
# Normes d'ingénierie de l'entreprise

## Architecture
Toutes les applications web utilisent React avec TypeScript. Utilisez uniquement
des composants fonctionnels avec des hooks. Pour la gestion de l'état, utilisez Zustand pour l'état local
et React Query pour l'état du serveur.

## Bibliothèque de composants
Utilisez le package du système de conception interne `@acme/ui`. N'utilisez jamais d'éléments HTML bruts
pour les boutons, les champs de saisie, les formulaires ou les modales ; utilisez toujours les composants correspondants
de `@acme/ui`.

Importez les composants comme suit :
```tsx
import { Button, TextField, Modal } from '@acme/ui';
```

## Intégration d'API
Tous les appels d'API sont effectués via le package `@acme/api-client`.
N'utilisez jamais directement de fetch brut ou d'axios. L'authentification est gérée
automatiquement par le client.

## Tests
Tous les composants doivent avoir un fichier de test correspondant. Utilisez Vitest
pour les tests unitaires et Playwright pour les tests d'intégration.
````

**Limite de taille** : le contenu est soumis à une limite souple d’environ 25 KB. Au-delà, il peut être progressivement tronqué. À mesure que vos instructions s’allongent, déplacez les documents de référence détaillés vers des [compétences](/fr/ko/features/agent/skills) dans `.agents/skills/` plutôt que de tout conserver dans `instructions.md`. Les compétences sont chargées à la demande lorsqu’elles sont pertinentes. Elles ne sont donc pas prises en compte dans la limite de taille des instructions et permettent de réserver les instructions principales aux règles générales.

<div id="section-8">
  ### Ajouter des compétences personnalisées
</div>

Créez des compétences dans le répertoire `.agents/skills/` pour définir des flux de travail spécifiques qu’Agent doit suivre. Chaque compétence est un répertoire contenant un fichier `SKILL.md` avec un front matter YAML.

```
.agents/skills/
├── use-design-system/
│   └── SKILL.md
├── api-integration/
│   └── SKILL.md
└── run-tests/
    └── SKILL.md
```

Chaque fichier `SKILL.md` doit contenir un `name` et une `description` dans son front matter :

```markdown theme={null}
---
name: use-design-system
description: Use when building UI components. Provides component patterns, theming rules, and accessibility requirements for the Acme design system.
---

# Acme Design System

## Available components

- `Button` — Primary, secondary, and ghost variants
- `TextField` — Text input with validation support
- `Modal` — Dialog overlay with focus trapping
...
```

| Champ         | Obligatoire | Détails                                                                                                  |
| ------------- | ----------- | -------------------------------------------------------------------------------------------------------- |
| `name`        | Oui         | Maximum 64 caractères. Seules les lettres minuscules, les chiffres et les traits d’union sont autorisés. |
| `description` | Oui         | Maximum 1 024 caractères. Décrit ce que fait la compétence et quand l’utiliser.                          |
| `enabled`     | Non         | La valeur par défaut est `true`. Définissez-la sur `false` pour la désactiver sans la supprimer.         |

**Chargement des compétences** : Agent ne voit que `name` et `description` dans le prompt. Il lit l’intégralité du contenu de `SKILL.md` si nécessaire lorsque la compétence est pertinente pour la tâche en cours. La `description` est donc très importante. Rédigez-la de sorte qu’elle corresponde aux scénarios dans lesquels Agent doit utiliser la compétence.

Les compétences peuvent également inclure des fichiers auxiliaires avec `SKILL.md` :

```
.agents/skills/use-design-system/
├── SKILL.md
├── references/
│   └── component-api.md
└── assets/
    └── theme-tokens.json
```

Pour en savoir plus sur les compétences, consultez [Compétences Agent](/fr/ko/features/agent/skills) et [Utilisation des compétences](/fr/ko/build/use-agent-skills).

<div id="replitmd">
  ### Configuration de replit.md
</div>

Préremplissez le fichier `replit.md`, à la racine du projet, avec une vue d’ensemble de l’architecture du modèle. Ce fichier est toujours chargé dans le contexte d’Agent et sert de mémoire persistante pour le projet.

Le fichier doit comporter les quatre sections suivantes :

```markdown theme={null}
# Vue d’ensemble
Application de gestion des tâches développée avec React, TypeScript et le système de design Acme. Utilise un backend Express.js avec PostgreSQL.

# Préférences utilisateur
- Utiliser TypeScript pour tous les fichiers
- Privilégier les composants fonctionnels avec des hooks
- Respecter les normes de codage Acme

# Architecture système
- Frontend : React + TypeScript + @acme/ui
- Backend : Express.js + TypeScript
- Base de données : PostgreSQL avec Drizzle ORM
- Auth : SSO Acme via @acme/auth

# Dépendances externes
- @acme/ui : Système de design interne
- @acme/api-client : Couche d’intégration d’API
- @acme/auth : SDK d’authentification
```

Agent met à jour `replit.md` à mesure que le projet évolue. Lorsque le fichier dépasse environ 4 000 jetons, Agent le résume automatiquement afin qu’il reste concis et utile.

Pour en savoir plus, consultez [replit.md](/fr/ko/features/project-setup/replit-dot-md).

<div id="section-9">
  ### Épingler un modèle dans votre organisation
</div>

Une fois votre modèle prêt :

1. Accédez à l’application de modèle de votre organisation
2. Ouvrez le menu d’actions de l’application (menu à trois points)
3. Sélectionnez **Épingler dans le champ de saisie d’Agent**

<img src="/assets/mirror/custom-templates-pin-to-agent-b733d3eb9a80.png" alt="Menu d’actions de l’application montrant l’option Épingler dans le champ de saisie d’Agent" width="984" height="856" data-path="images/teams/custom-templates-pin-to-agent.png" />

<Note>
  Seuls les administrateurs de l’organisation (membres ayant le rôle `system_admins`) peuvent épingler ou désépingler des modèles.
</Note>

Définissez l’accès des membres sur **lecture seule** afin qu’ils puissent consulter et utiliser le modèle épinglé sans le modifier.

<img src="/assets/mirror/custom-templates-members-read-only-cf6aa160c8ef.png" alt="Boîte de dialogue d’invitation avec l’accès des membres défini sur lecture seule" width="954" height="1064" data-path="images/teams/custom-templates-members-read-only.png" />

Le modèle s’affiche désormais sous forme de pastille sélectionnable sous le champ de saisie d’Agent pour tous les membres de votre organisation. Pour le retirer, ouvrez le même menu et sélectionnez **Désépingler du champ de saisie d’Agent**.

<div id="section-10">
  ### Contrôle d’accès aux modèles
</div>

L’épinglage rend un modèle visible par tous les membres de l’organisation. Pour une diffusion plus ciblée, utilisez le bouton **Inviter** de l’application modèle pour le partager avec des [groupes ou des utilisateurs spécifiques](/fr/ko/teams/identity-and-access-management/groups-and-permissions). Vous pouvez ainsi limiter les équipes ou les personnes autorisées à voir et à forker le modèle, sans l’épingler dans le champ de saisie de toute l’organisation.

<div id="section-11">
  ## Que se passe-t-il lorsqu’un builder sélectionne un modèle ?
</div>

<img src="/assets/mirror/custom-templates-input-box-553384ac7dd0.png" alt="Modèle affiché sous forme de pastille sélectionnable dans le champ de saisie d’Agent" width="1746" height="726" data-path="images/teams/custom-templates-input-box.png" />

Lorsqu’un membre de l’organisation sélectionne un modèle épinglé dans le champ de saisie d’Agent :

1. **Fork** : une nouvelle application est créée à partir d’une copie du modèle contenant tous les fichiers
2. **Ignorer la planification** : Agent ignore la conversation de planification initiale et passe directement en mode de création
3. **Chargement des instructions** : `custom_instruction/instructions.md` est lu et les instructions fournies par l’entreprise sont injectées dans le prompt système d’Agent
4. **Découverte des compétences** : les compétences de `.agents/skills/` sont identifiées et répertoriées dans le contexte d’Agent afin d’être chargées si nécessaire
5. **Chargement du contexte du projet** : `replit.md` est lu et injecté dans le contexte d’Agent (ou créé automatiquement s’il n’existe pas)
6. **Héritage de la configuration** : le fichier `.replit`, les dépendances et tous les fichiers du modèle sont transférés vers la nouvelle application

Les builders peuvent immédiatement soumettre à Agent un prompt précisant leurs besoins, et Agent opère dans le cadre des garde-fous définis par le modèle.

<div id="section-12">
  ## Comment les fichiers fonctionnent ensemble
</div>

Chaque fichier de configuration joue un rôle spécifique :

| Fichier                              | Objectif                                             | Quand Agent le lit                        | Agent peut le modifier                           |
| ------------------------------------ | ---------------------------------------------------- | ----------------------------------------- | ------------------------------------------------ |
| `custom_instruction/instructions.md` | Normes et règles de l’organisation                   | Toujours (injecté dans le prompt système) | Non                                              |
| `.agents/skills/*/SKILL.md`          | Flux de travail et modèles spécialisés               | Au besoin (si pertinent)                  | Oui (Agent peut également créer des compétences) |
| `replit.md`                          | Vue d’ensemble du projet et configuration par défaut | Toujours (injecté dans le prompt système) | Oui (Agent le met à jour au fil du temps)        |
| `.replit`                            | Configuration de l’environnement d’exécution         | Lors de la configuration de l’application | Oui                                              |

**Distinction essentielle** : `custom_instruction/instructions.md` est une source statique et de référence pour les normes de l’organisation. `replit.md` est un document vivant qu’Agent maintient à mesure que le projet évolue. Les compétences servent de références consultées au besoin pour des flux de travail spécifiques.

<div id="section-13">
  ## Bonnes pratiques
</div>

<div id="section-14">
  ### Gardez les instructions ciblées
</div>

Créez `custom_instruction/instructions.md` pour les conventions les plus importantes. Concentrez-vous sur :

* Les décisions difficiles à remettre en cause (architecture, modèle de données)
* Les conventions qui doivent rester cohérentes (utilisation des composants, conventions d’API)
* Les normes que les builders peuvent ne pas connaître (bibliothèques internes, règles des Teams)

N’incluez pas l’historique des modifications, les détails d’implémentation ou les informations qui changent fréquemment.

<div id="section-15">
  ### Rédiger des descriptions de compétences faciles à identifier
</div>

Le champ `description` dans le frontmatter de `SKILL.md` permet à Agent de déterminer quand charger une compétence. Rédigez des descriptions qui correspondent aux tâches pour lesquelles la compétence est pertinente :

```yaml theme={null}
# Bon — indique quand l’utiliser
description: À utiliser lors de la création de formulaires ou du traitement des saisies utilisateur. Fournit des modèles de validation, des conventions d’affichage des erreurs et des mises en page de formulaires accessibles.

# Moins efficace — trop vague
description: Utilitaires et aides pour les formulaires.
```

<div id="section-16">
  ### Organiser les compétences par flux de travail
</div>

Regroupez les compétences par flux de travail plutôt que par catégories techniques :

| Approche                  | Exemple                                      |
| ------------------------- | -------------------------------------------- |
| **Par flux de travail**   | `build-a-form`, `connect-to-api`, `add-auth` |
| **Par domaine technique** | `react-utils`, `api-helpers`, `auth-config`  |

Cette approche aide Agent à trouver les compétences au bon moment.

<div id="section-17">
  ### Améliorez les modèles de manière itérative
</div>

Les modèles s&#39;améliorent à l&#39;usage. Une fois que votre équipe commence à créer des applications à partir d&#39;un modèle :

1. Identifiez les schémas que Agent gère mal et ajoutez-les à `instructions.md`
2. Lorsque Agent résout efficacement un problème, créez une compétence pour consigner la solution
3. Mettez à jour les dépendances et la configuration par défaut à mesure que votre stack évolue
4. Testez les modifications en créant une application à partir du modèle afin de valider l&#39;expérience

<div id="section-18">
  ### Mises à jour des modèles et applications existantes
</div>

Les modifications apportées à une application modèle s’appliquent aux nouvelles applications créées. Les applications existantes précédemment forkées à partir du modèle sont des copies indépendantes et ne bénéficient pas de ces mises à jour.
