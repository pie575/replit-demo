Некоторые старые опубликованные приложения могут по-прежнему быть подключены к базе данных для разработки, которая изначально создавалась для другого приложения.

Такое случается со старыми приложениями, которые были форкнуты или ремикшированы на Replit. В прежней конфигурации на основе Neon форк мог и дальше использовать подключение к базе данных исходного приложения. В рамках перехода Replit к полной изоляции баз данных для разработки и продакшена старые общие базы данных для разработки удаляются, а опубликованные приложения должны перейти на собственные продакшен-базы данных.

Воспользуйтесь этим руководством, если ваше опубликованное приложение выдаёт ошибки подключения к базе данных или если `DATABASE_URL` на панели Secrets по-прежнему указывает на `neon.tech`.

<Warning>
  Старая общая база данных будет отключена **8 июня 2026 года**. Обновите
  опубликованное приложение до этой даты, чтобы избежать простоя или безвозвратной потери данных.
</Warning>

<div id="before-you-start">
  ## Прежде чем начать
</div>

Опубликованному приложению нужна собственная **продакшен-база данных**. Базу данных для разработки, которая отображается на панели **Database**, не следует использовать напрямую в опубликованных приложениях.

<Frame>
  <img src="/assets/mirror/dev-database-5c024a6c134e.png" alt="Панель Database с базой данных для разработки" width="955" height="767" data-path="images/databases/shared-database-migration/dev-database.png" />
</Frame>

Чтобы это исправить, сначала определите, какой случай ваш:

* **Случай 1:** нужные данные уже есть в базе данных, которая отображается на панели **Database** вашего приложения.
* **Случай 2:** на панели **Database** нужных данных нет, потому что опубликованное приложение по-прежнему использует старую общую базу данных для разработки.

<div id="how-to-tell-if-your-published-app-is-using-a-shared-database">
  ## Как понять, что ваше опубликованное приложение использует общую базу данных?
</div>

Проблема затрагивает ваше опубликованное приложение, если верно хотя бы одно из перечисленного:

* После обновления базы данных опубликованное приложение выдаёт ошибки подключения к базе данных
* Ваше приложение создано как ремикс другого приложения, у которого была база данных **до 9 января 2026 года**

<div id="how-to-check-if-your-published-app-is-using-the-shared-database-from-the-source-app">
  ## Как проверить, использует ли опубликованное приложение общую базу данных исходного приложения?
</div>

<div id="step-1-open-the-database-panel-in-the-source-app">
  ### Шаг 1. Откройте панель Database в исходном приложении
</div>

<Frame>
  <img src="/assets/mirror/secret-pane-showing-secrets-763dd4c4845f.png" alt="Панель Secrets со значением DATABASE_URL" width="792" height="418" data-path="images/databases/shared-database-migration/secret-pane-showing-secrets.png" />
</Frame>

Возьмите значение из `NEON_DATABASE_URL` либо из `DATABASE_URL`, если `NEON_DATABASE_URL` отсутствует.

<Info>
  Не в каждом затронутом приложении есть `NEON_DATABASE_URL`. Если его нет, это
  обычно означает, что следует использовать текущий `DATABASE_URL` из Secrets
  опубликованного приложения, если он по-прежнему указывает на `neon.tech`.
</Info>

<div id="step-2-open-the-publish-panel-in-the-published-app">
  ### Шаг 2: Откройте панель Publish в опубликованном приложении
</div>

<Frame>
  <img src="/assets/mirror/production-app-secrets-e4da45c53e36.png" alt="Secrets опубликованного приложения с DATABASE_URL" width="1385" height="1225" data-path="images/databases/shared-database-migration/production-app-secrets.png" />
</Frame>

Чтобы проверить URL базы данных опубликованного приложения:

1. Откройте приложение в Replit
2. Откройте панель **Publishing**
3. Перейдите в **Adjust Settings**
4. Откройте **Secrets**
5. Найдите `DATABASE_URL`

<div id="step-3-compare-the-database-url-from-the-source-app-in-step-1-and-the-remix-app-in-step-2">
  ### Шаг 3. Сравните URL базы данных исходного приложения из шага 1 и приложения-ремикса из шага 2
</div>

Если они совпадают, значит, ваше опубликованное приложение использует общую с исходным приложением базу данных Neon для разработки.

<div id="how-to-copy-data-from-source-app-to-the-published-app">
  ## Как скопировать данные из исходного приложения в опубликованное?
</div>

Убедившись, что опубликованное приложение использует общую базу данных разработки из исходного приложения, перейдите к следующему шагу — переносу необходимых данных в опубликованное приложение. Возможны два сценария:

* Случай 1: панель Database в опубликованном приложении уже содержит нужные данные.
* Случай 2: панель Database в опубликованном приложении не содержит нужных данных.

<div id="case-1-the-database-panel-already-shows-the-data-you-need">
  ### Случай 1: на панели Database уже отображаются нужные данные
</div>

Это самый простой вариант, если нужные данные уже видны на панели **Database** вашего приложения.

<div id="step-1-confirm-the-data-is-present">
  #### Шаг 1. Убедитесь, что данные на месте
</div>

<Frame>
  <img src="/assets/mirror/my-data-12834f2ebfd6.png" alt="Панель базы данных со строками моих данных" width="865" height="454" data-path="images/databases/shared-database-migration/my-data.png" />
</Frame>

Откройте панель **Database** в опубликованном приложении и проверьте, что нужные таблицы и данные на месте.

Если нужных данных в панели Database нет, остановитесь на этом шаге. Чтобы корректно перенести данные, выполните шаги из [случая 2](#case-2-the-database-panel-does-not-show-the-data-you-need).

<div id="step-2-publish-or-republish-with-a-production-database">
  #### Шаг 2: опубликуйте или переопубликуйте приложение с продакшен-базой данных
</div>

1. Откройте приложение в Project Editor
2. Выберите **Publish** или **Republish**
3. Включите параметр **Create production database**
4. Включите параметр **Set up your production database with your current development data**
5. Пройдите процесс публикации до конца

При публикации создаётся новая версия опубликованного приложения, а её переменная `DATABASE_URL` автоматически указывает на новую продакшен-базу данных. Обновлять этот секрет вручную при этом не требуется.

<Frame>
  <img src="/assets/mirror/production-database-settings-8855bf453da9.png" alt="Настройки публикации с параметрами создания продакшен-базы данных" width="1406" height="1207" data-path="images/databases/shared-database-migration/production-database-settings.png" />
</Frame>

<Warning>
  Копирование в рабочую среду перезаписывает все имеющиеся там данные. Подробнее о восстановлении продакшен-базы данных и управлении ею см. в разделе [Продакшен-базы данных](/ru/features/data-and-storage/development-and-production).
</Warning>

<div id="step-3-verify-the-published-app">
  #### Шаг 3. Проверьте опубликованное приложение
</div>

Откройте опубликованное приложение и убедитесь, что данные доступны, а приложение работает корректно.

<div id="case-2-the-database-panel-in-the-published-app-does-not-show-the-data-you-need">
  ### Случай 2: панель Database в опубликованном приложении не показывает нужные данные
</div>

Если на панели **Database** опубликованного приложения нет нужных данных, экспортируйте их, выполнив следующие шаги.

Если ваше опубликованное приложение всё ещё подключено к базе данных другого приложения, на панели Database появится предупреждение «external database detected».

<Frame>
  <img src="/assets/mirror/external-database-detected-489d99632e74.png" alt="Панель Database с предупреждением об обнаружении внешней базы данных" width="1403" height="1208" data-path="images/databases/shared-database-migration/external-database-detected.png" />
</Frame>

<Warning>
  Если пользователи продолжают работать с приложением и сохранять новые данные,
  запланируйте короткое техническое окно перед экспортом данных.
</Warning>

<div id="step-1-export-the-data-from-the-old-database">
  #### Шаг 1: Экспортируйте данные из старой базы данных
</div>

<Frame>
  <img src="/assets/mirror/pg-dump-example-54c6c790ccb1.png" alt="pg_dump example" width="1252" height="450" data-path="images/databases/shared-database-migration/pg-dump-example.png" />
</Frame>

Откройте **Shell** в Project Editor и выполните:

```bash theme={null}
pg_dump -Fc "database_url" --no-owner --no-privileges -f backup.dump
```

`database_url` — это URL базы данных, полученный в разделе [Шаг 1: откройте панель Database в исходном приложении](#step-1-open-the-database-panel-in-the-source-app).

<div id="step-2-remove-the-old-database_url-from-your-apps-secrets">
  ### Шаг 2. Удалите старый `DATABASE_URL` из Secrets вашего приложения
</div>

<Frame>
  <img src="/assets/mirror/secret-pane-eb253120f8a6.png" alt="пример панели секретов" width="1410" height="1184" data-path="images/databases/shared-database-migration/secret-pane.png" />
</Frame>

1. Откройте инструмент **Secrets** в Project Editor
2. Найдите старый `DATABASE_URL`
3. Удалите его
4. Обновите страницу или заново откройте панель **Database**

После этого приложение перестанет обращаться к старой общей базе данных и снова будет использовать свою текущую базу данных для разработки.

<div id="step-3-import-the-data-into-your-apps-current-development-database">
  ### Шаг 3. Импортируйте данные в текущую базу данных разработки вашего приложения
</div>

<Frame>
  <img src="/assets/mirror/pg-restore-example-409ae4d7bf09.png" alt="пример pg_restore" width="802" height="426" data-path="images/databases/shared-database-migration/pg-restore-example.png" />
</Frame>

После удаления старого секрета `DATABASE_URL` текущая база данных разработки вашего приложения снова будет доступна в Project Editor как `$DATABASE_URL`.

Вернитесь в **Shell** в Project Editor и выполните:

```bash theme={null}
pg_restore --clean --if-exists --single-transaction --no-owner --no-privileges --exit-on-error -d "$DATABASE_URL" backup.dump
```

Экспортированные данные будут загружены в текущую базу данных разработки вашего приложения.

<div id="step-5-follow-case-1-to-publish-or-republish-with-a-production-database">
  ### Шаг 5. Выполните действия из случая 1, чтобы опубликовать или повторно опубликовать приложение с продакшен-базой данных
</div>

Когда на панели **Database** отобразятся нужные данные, выполните действия из [случая 1](#case-1-the-database-panel-already-shows-the-data-you-need), чтобы опубликовать или повторно опубликовать приложение с параметром **Create production database** и скопировать эти данные в продакшен.

<div id="step-6-verify-the-published-app">
  ### Шаг 6. Проверьте опубликованное приложение
</div>

<Frame>
  <img src="/assets/mirror/successful-export-bfb997304cc1.png" alt="успешный экспорт" width="965" height="554" data-path="images/databases/shared-database-migration/successful-export.png" />
</Frame>

Откройте опубликованное приложение и убедитесь, что данные доступны, а само приложение работает корректно.

<div id="troubleshooting">
  ## Устранение неполадок
</div>

<div id="the-import-fails-because-tables-already-exist">
  ### Импорт завершается ошибкой, так как таблицы уже существуют
</div>

Приведённая выше команда `pg_restore --clean --if-exists` перед восстановлением удаляет и заново создаёт объекты из дампа, совпадающие с существующими.

<div id="the-import-fails-with-role-or-policy-errors">
  ### Импорт завершается ошибками, связанными с ролями или политиками
</div>

Если в вашей базе данных используются пользовательские роли PostgreSQL или политики на основе ролей, импорт может завершиться ошибкой, поскольку этих ролей ещё нет в новой базе данных.

Автоматическая миграция Helium в Replit пытается воссоздать заглушки ролей перед восстановлением, а описанный выше ручной процесс — нет. Если во время выполнения `pg_restore` возникают ошибки, связанные с ролями, [обратитесь за помощью в службу поддержки](https://replit.com/support).

<div id="i-already-fixed-the-app">
  ### Я уже исправил приложение
</div>

Если у вашего опубликованного приложения уже есть собственная продакшен-база данных и оно работает корректно, больше ничего делать не нужно.
