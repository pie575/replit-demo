예전에 게시된 일부 앱은 다른 앱용으로 생성된 development database에 여전히 연결되어 있을 수 있습니다.

이런 상황은 Replit에서 fork하거나 remix한 오래된 앱에서 발생할 수 있습니다. 기존 Neon 환경에서는 fork한 앱이 원본 앱의 데이터베이스 연결을 그대로 사용할 수 있었기 때문입니다. Replit은 development database와 production database를 완전히 분리하는 작업을 진행 중이며, 이에 따라 오래된 공유 development database는 제거되고 게시된 앱은 각자의 production database로 이전해야 합니다.

게시된 앱에 데이터베이스 연결 오류가 나타나거나 Secrets 패널의 `DATABASE_URL`이 여전히 `neon.tech`를 가리키고 있다면 이 가이드를 따르세요.

<Warning>
  기존 공유 데이터베이스는 **2026년 6월 8일**에 종료됩니다. 다운타임이나 영구적인
  데이터 손실을 방지하려면 그전에 게시된 앱을 업데이트하세요.
</Warning>

<div id="before-you-start">
  ## 시작하기 전에
</div>

게시된 앱에는 자체 **production database**가 필요합니다. **Database** 패널에 표시되는 development database는 게시된 앱에서 직접 사용하면 안 됩니다.

<Frame>
  <img src="/assets/mirror/dev-database-5c024a6c134e.png" alt="Development database를 보여주는 Database 패널" width="955" height="767" data-path="images/databases/shared-database-migration/dev-database.png" />
</Frame>

이 문제를 해결하려면 먼저 다음 중 어떤 상황에 해당하는지 확인하세요.

* **사례 1:** 필요한 데이터가 앱의 **Database** 패널에 표시되는 database에 이미 들어 있는 경우
* **사례 2:** 게시된 앱이 여전히 이전의 공유 development database를 사용하고 있어 **Database** 패널에 필요한 데이터가 표시되지 않는 경우

<div id="how-to-tell-if-your-published-app-is-using-a-shared-database">
  ## 게시된 앱이 공유 database를 사용 중인지 확인하는 방법
</div>

다음 중 하나라도 해당되면 게시된 앱이 영향을 받습니다.

* database 업그레이드 후 게시된 앱에서 database 연결 오류가 발생하는 경우
* **2026년 1월 9일 이전에** database가 있던 다른 app을 remix하여 만든 app인 경우

<div id="how-to-check-if-your-published-app-is-using-the-shared-database-from-the-source-app">
  ## 게시된 앱이 소스 앱의 공유 데이터베이스를 사용하고 있는지 확인하는 방법
</div>

<div id="step-1-open-the-database-panel-in-the-source-app">
  ### 1단계: 소스 앱에서 Database 패널 열기
</div>

<Frame>
  <img src="/assets/mirror/secret-pane-showing-secrets-763dd4c4845f.png" alt="DATABASE_URL이 표시된 Secret 패널" width="792" height="418" data-path="images/databases/shared-database-migration/secret-pane-showing-secrets.png" />
</Frame>

`NEON_DATABASE_URL`의 값을 가져오세요. `NEON_DATABASE_URL`이 없다면 `DATABASE_URL`의 값을 사용하세요.

<Info>
  영향을 받는 모든 앱에 `NEON_DATABASE_URL`이 있는 것은 아닙니다. 이 값이 없다면, 게시된
  앱의 Secrets에 있는 현재 `DATABASE_URL`이 여전히 `neon.tech`를 가리키고 있을 경우
  해당 값을 사용하면 됩니다.
</Info>

<div id="step-2-open-the-publish-panel-in-the-published-app">
  ### 2단계: 게시된 앱에서 Publish 패널 열기
</div>

<Frame>
  <img src="/assets/mirror/production-app-secrets-e4da45c53e36.png" alt="DATABASE_URL이 표시된 게시된 앱의 secrets" width="1385" height="1225" data-path="images/databases/shared-database-migration/production-app-secrets.png" />
</Frame>

게시된 앱의 데이터베이스 URL을 확인하려면 다음 단계를 따르세요.

1. Replit에서 앱을 엽니다
2. **Publishing** 패널을 엽니다
3. **Adjust Settings**를 엽니다
4. **Secrets**를 엽니다
5. `DATABASE_URL`을 찾습니다

<div id="step-3-compare-the-database-url-from-the-source-app-in-step-1-and-the-remix-app-in-step-2">
  ### 3단계: 1단계에서 확인한 소스 앱의 database url과 2단계에서 확인한 remix 앱의 database url 비교
</div>

두 값이 같다면 게시된 앱이 소스 앱의 Neon development database를 공유해서 사용하고 있는 것입니다.

<div id="how-to-copy-data-from-source-app-to-the-published-app">
  ## 소스 앱의 데이터를 게시된 앱으로 복사하는 방법
</div>

게시된 앱이 소스 앱의 공유된 development database를 사용 중인지 확인했다면, 이제 필요한 데이터를 게시된 앱으로 옮길 차례입니다. 고려해야 할 시나리오는 두 가지입니다.

* 사례 1: 게시된 앱의 Database 패널에 이미 필요한 데이터가 있는 경우
* 사례 2: 게시된 앱의 Database 패널에 필요한 데이터가 없는 경우

<div id="case-1-the-database-panel-already-shows-the-data-you-need">
  ### 사례 1: Database 패널에 필요한 데이터가 이미 표시되는 경우
</div>

필요한 데이터가 앱의 **Database** 패널에 이미 표시되고 있다면 이 방법이 가장 간단합니다.

<div id="step-1-confirm-the-data-is-present">
  #### 1단계: 데이터가 있는지 확인하기
</div>

<Frame>
  <img src="/assets/mirror/my-data-12834f2ebfd6.png" alt="내 데이터 행을 보여주는 Database 패널" width="865" height="454" data-path="images/databases/shared-database-migration/my-data.png" />
</Frame>

게시된 앱에서 **Database** 패널을 열고 필요한 테이블과 데이터가 있는지 확인하세요.

Database 패널에 필요한 데이터가 보이지 않는다면 여기서 잠시 멈추세요. [사례 2](#case-2-the-database-panel-does-not-show-the-data-you-need)의 단계를 따라 데이터를 올바르게 마이그레이션해야 합니다.

<div id="step-2-publish-or-republish-with-a-production-database">
  #### 2단계: production database로 Publish 또는 Republish하기
</div>

1. Project Editor에서 앱을 엽니다
2. **Publish** 또는 **Republish**를 선택합니다
3. **Create production database**를 켭니다
4. **Set up your production database with your current development data**를 켭니다
5. publish flow를 완료합니다

Publish하면 게시된 앱의 새 버전이 생성되고 해당 `DATABASE_URL`이 새 production database로 자동 설정됩니다. 이 flow 중에 해당 secret을 직접 업데이트할 필요는 없습니다.

<Frame>
  <img src="/assets/mirror/production-database-settings-8855bf453da9.png" alt="Create production database 옵션이 표시된 Publish 설정" width="1406" height="1207" data-path="images/databases/shared-database-migration/production-database-settings.png" />
</Frame>

<Warning>
  production으로 복사하면 기존 production data를 덮어씁니다. production database의 복원 또는 관리에 대한 자세한 내용은 [Production
  Databases](/ko/features/data-and-storage/development-and-production)를
  참조하세요.
</Warning>

<div id="step-3-verify-the-published-app">
  #### 3단계: 게시된 앱 확인하기
</div>

게시된 앱을 열어 데이터에 접근할 수 있는지, 앱이 정상적으로 작동하는지 확인하세요.

<div id="case-2-the-database-panel-in-the-published-app-does-not-show-the-data-you-need">
  ### 사례 2: 게시된 앱의 Database 패널에 필요한 데이터가 표시되지 않는 경우
</div>

게시된 앱의 **Database** 패널에서 필요한 데이터가 보이지 않는다면 다음 단계에 따라 데이터를 내보내세요.

게시된 앱이 여전히 다른 앱의 database에 연결되어 있으면 Database 패널에 &quot;external database detected&quot; 경고가 표시됩니다.

<Frame>
  <img src="/assets/mirror/external-database-detected-489d99632e74.png" alt="외부 데이터베이스가 감지되었음을 보여주는 Database 패널" width="1403" height="1208" data-path="images/databases/shared-database-migration/external-database-detected.png" />
</Frame>

<Warning>
  사용자가 여전히 앱을 사용하며 새 데이터를 저장하고 있다면, 데이터를 내보내기 전에
  짧은 유지보수 시간을 계획하세요.
</Warning>

<div id="step-1-export-the-data-from-the-old-database">
  #### 1단계: 기존 데이터베이스에서 데이터 내보내기
</div>

<Frame>
  <img src="/assets/mirror/pg-dump-example-54c6c790ccb1.png" alt="pg_dump example" width="1252" height="450" data-path="images/databases/shared-database-migration/pg-dump-example.png" />
</Frame>

Project Editor에서 **Shell**을 열고 다음 명령어를 실행하세요:

```bash theme={null}
pg_dump -Fc "database_url" --no-owner --no-privileges -f backup.dump
```

`database_url`은 [1단계: 소스 앱에서 Database 패널 열기](#step-1-open-the-database-panel-in-the-source-app)에서 확인한 데이터베이스 URL입니다.

<div id="step-2-remove-the-old-database_url-from-your-apps-secrets">
  ### 2단계: 앱의 Secrets에서 기존 `DATABASE_URL` 제거
</div>

<Frame>
  <img src="/assets/mirror/secret-pane-eb253120f8a6.png" alt="secret pane example" width="1410" height="1184" data-path="images/databases/shared-database-migration/secret-pane.png" />
</Frame>

1. Project Editor에서 **Secrets** 도구를 엽니다
2. 기존 `DATABASE_URL`을 찾습니다
3. 삭제합니다
4. 페이지를 새로 고치거나 **Database** 패널을 다시 엽니다

이렇게 하면 앱이 더 이상 기존 공유 database를 바라보지 않고 현재 development database를 다시 사용하게 됩니다.

<div id="step-3-import-the-data-into-your-apps-current-development-database">
  ### 3단계: 앱의 현재 development database로 데이터 import하기
</div>

<Frame>
  <img src="/assets/mirror/pg-restore-example-409ae4d7bf09.png" alt="pg_restore example" width="802" height="426" data-path="images/databases/shared-database-migration/pg-restore-example.png" />
</Frame>

기존 `DATABASE_URL` secret을 제거하면 Project Editor에서 앱의 현재 development database를 다시 `$DATABASE_URL`로 사용할 수 있습니다.

Project Editor의 **Shell**로 돌아가 다음을 실행하세요.

```bash theme={null}
pg_restore --clean --if-exists --single-transaction --no-owner --no-privileges --exit-on-error -d "$DATABASE_URL" backup.dump
```

이렇게 하면 내보낸 데이터가 앱의 현재 개발 데이터베이스로 import됩니다.

<div id="step-5-follow-case-1-to-publish-or-republish-with-a-production-database">
  ### 5단계: 사례 1에 따라 production database로 Publish 또는 Republish하기
</div>

**Database** 패널에 올바른 데이터가 표시되면, [사례 1](#case-1-the-database-panel-already-shows-the-data-you-need)에 따라 **Create production database** 옵션으로 Publish 또는 Republish하여 해당 데이터를 production으로 복사하세요.

<div id="step-6-verify-the-published-app">
  ### 6단계: 게시된 앱 확인
</div>

<Frame>
  <img src="/assets/mirror/successful-export-bfb997304cc1.png" alt="successful export" width="965" height="554" data-path="images/databases/shared-database-migration/successful-export.png" />
</Frame>

게시된 앱을 열어 데이터에 정상적으로 접근할 수 있는지, 앱이 제대로 작동하는지 확인하세요.

<div id="troubleshooting">
  ## 문제 해결
</div>

<div id="the-import-fails-because-tables-already-exist">
  ### 테이블이 이미 존재하여 import가 실패하는 경우
</div>

위의 `pg_restore --clean --if-exists` 명령은 복원하기 전에 덤프에 있는 객체와 일치하는 기존 객체를 삭제하고 다시 생성합니다.

<div id="the-import-fails-with-role-or-policy-errors">
  ### 역할 또는 정책 오류로 import가 실패하는 경우
</div>

database에서 사용자 지정 PostgreSQL 역할이나 역할 기반 정책을 사용한다면, 새 database에 해당 역할이 아직 없기 때문에 import가 실패할 수 있습니다.

Replit의 자동 Helium migration은 복원 전에 역할 스텁을 다시 생성하려고 시도하지만, 위의 수동 절차에는 이 과정이 없습니다. `pg_restore` 실행 중 역할 관련 오류가 발생하면 [지원팀에 문의](https://replit.com/support)하세요.

<div id="i-already-fixed-the-app">
  ### 이미 앱을 수정했습니다
</div>

게시된 앱에 이미 자체 production database가 있고 정상적으로 작동한다면, 추가로 조치할 사항은 없습니다.
