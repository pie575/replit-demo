高效的 提示词，本质上就是向一位得力助手清晰地下达指令。把 [**Agent**](/zh/features/agent/overview) 引导好，你就能快速从创意走向成品应用。

<div id="quick-examples">
  ## 快速示例
</div>

对比一下模糊的提示词和有效的提示词：

<AccordionGroup>
  <Accordion title="修复代码" icon="bug">
    **模糊：**&quot;修复我的代码。&quot;

    **有效：**&quot;我的脚本在处理用户输入时报错。问题似乎出在验证函数里。能帮我调试 `validate_input` 这部分吗？错误信息如下：[详情]&quot;

    有效的提示词指明了问题范围和可疑的函数，并提供了上下文。
  </Accordion>

  <Accordion title="构建功能" icon="hammer">
    **模糊：**&quot;做一个网站。&quot;

    **有效：**&quot;创建一个简单的作品集网站，包含首页、关于我和联系表单几个板块。采用简洁、现代的设计主题，并使用占位内容。&quot;

    有效的提示词明确了用途、核心功能和期望的视觉风格。
  </Accordion>

  <Accordion title="性能优化" icon="gauge-high">
    **模糊：**&quot;别让它变慢。&quot;

    **有效：**&quot;重构数据处理函数，让它能更高效地处理更大的输入。是否可以换一种算法或数据结构？&quot;

    告诉 Agent 该*如何*改进，而不是用否定式的限制。
  </Accordion>

  <Accordion title="界面调整" icon="paintbrush">
    **模糊：**&quot;加个动画。&quot;

    **有效：**&quot;为 landing page 上的主图添加动画，让它在页面首次加载时缓缓淡入，营造出迎宾般的效果。&quot;

    指明具体的元素、期望的效果、触发时机以及想要达成的体验。
  </Accordion>

  <Accordion title="复杂系统" icon="server">
    **模糊：**&quot;构建 backend。&quot;

    **有效：**&quot;搭建服务端逻辑。实现用户身份验证 (注册/登录) ，并创建一个 API 端点，用于安全地获取用户资料数据。&quot;

    把大任务拆分成具体的功能点。
  </Accordion>
</AccordionGroup>

<div id="plan-first">
  ### 先制定计划
</div>

<Tip>输入提示词前，先梳理 App 的功能和用户流程。清晰的计划能让提示词更聚焦。</Tip>

像产品经理一样思考应用的结构，将整体目标拆分为合理的阶段。

**不要这样：**“Build 一个任务管理 App。”

**试试这样：**“1. 创建包含输入字段和任务清单的基础 HTML 结构。2. 添加用于新增任务的 JavaScript。3. 使用数据库存储任务。4. 添加将任务标记为已完成的功能。”

然后针对每个步骤向 Agent 输入提示词。

<div id="build-incrementally">
  ### 逐步构建
</div>

使用 [**Checkpoints**](/zh/features/agent/overview#checkpoints) 在每一步成功完成后保存进度。如果出现问题，你可以回滚到可正常运行的状态，换一种思路重试。

**不要这样写：**“构建一个完整的电商平台。”

**可以这样写：**“为电商网站搭建一个基础的 full-stack project，并使用 Replit Auth 实现用户注册和登录。”随后再用后续提示词逐步添加商品列表、购物车和结账流程。

<div id="be-specific">
  ### 具体明确
</div>

明确定义你的需求：输出格式、约束条件、边界情况。

**不要这样写：** &quot;添加一个联系表单。&quot;

**试试这样写：** &quot;在 `/contact` 创建一个联系表单页面，包含以下字段：

* 姓名 (必填)
* 邮箱 (必填，须为有效格式)
* 留言 (必填，至少 10 个字符)

提交后，将表单数据发送至 `contact@mydomain.com`。&quot;

<div id="use-positive-language">
  ### 使用正面表述
</div>

说明你*想要*什么，而不是要避免什么。

**不要这样写：**“别把用户资料页做得很混乱。”

**试试这样写：**“设计一个简洁的用户资料页。突出显示用户名，下方依次是邮箱和注册日期。加入一个&quot;编辑资料&quot;按钮。”

<div id="keep-it-simple">
  ### 保持简单
</div>

使用清晰、直白的语言。把复杂的需求拆分成要点列表。

**不要这样写：**&quot;实现必要的服务器端基础设施，以便动态生成和检索用户生成内容的构建产物。&quot;

**试试这样写：**&quot;创建后端功能，让用户可以提交博客文章。用户需要输入标题和正文内容。将文章存储到数据库中。&quot;

<div id="working-with-context">
  ## 使用上下文
</div>

<div id="provide-relevant-files">
  ### 提供相关文件
</div>

请提及具体文件，而不是附上整个 project。

**不要这样：** (附上所有内容) “根据我们的设计系统实现用户个人资料页面。”

**试试这样：**“创建用户个人资料页面。从服务器端点获取用户数据。按照 [设计文档 URL] 设置样式，并与此模型图保持一致：[附上 `profile_mockup.jpg`]。”

<Tip>切换到不相关的 task 时，请新开一个 Chat，避免累积的上下文造成混淆。</Tip>

<div id="show-examples">
  ### 提供示例
</div>

提供代码片段、示例数据或截图等具体示例，减少歧义。

**不要这样写：** “把产品卡片做得好看一些。”

**试试这样写：** “重新设计商店页面上的产品卡片。每张卡片应显示产品图片、名称、价格，以及一个“Add to Cart”按钮，布局参考：[附上截图]。使用浅灰色边框。”

<div id="debugging-effectively">
  ## 高效调试
</div>

出现错误时，请提供：

* **完整准确**的错误信息
* 相关代码片段
* 报错所在的文件名
* 你想要实现的目标
* 你已经尝试过的步骤

**不要这样说：**“我的登录页面坏了。”

**试试这样说：**“我在 `/login` 用正确的凭据登录时，浏览器控制台报出 &#39;User not found&#39; 错误。数据库校验似乎没有生效。这是 `auth.js` 中的登录处理代码。”

<div id="ask-for-guidance">
  ## 寻求建议
</div>

<Tip>切换到 Plan 模式，在动手构建前先探索各种方案。可以向 Agent 咨询有哪些库、实现思路，以及各自的利弊取舍。</Tip>

**不要这样问：**“添加支付功能。”

**试试这样问：**“在基于 Replit 构建的 web app 中，接受信用卡支付有哪些不错的方案？我需要集成起来相对简单的。”

<div id="iterate-on-your-prompts">
  ## 不断迭代你的提示词
</div>

第一次写的提示词可能并不完美——这很正常。如果结果不理想，可以：

* 补充更多细节
* 提供一个示例
* 简化指令
* 换一种表述方式

**初始版本：**“为我的网站创建一个页头。”

**改进版本：**“创建一个吸顶页头组件，左侧放置站点徽标，右侧放置导航链接 (首页、关于、联系我们) 。”

<div id="summary">
  ## 小结
</div>

高效 提示词 的关键在于：

* 在写 提示词 之前先做好**规划**
* 借助 checkpoint **循序渐进地构建**
* 把需求描述得**足够具体**
* 通过示例和相关文件**提供上下文**
* 结果不理想时反复**迭代**

掌握这些原则，你就能借助 Agent 更快地构建应用。
