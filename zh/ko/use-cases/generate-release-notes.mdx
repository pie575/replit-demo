每周从 GitHub 和 Linear 汇总变更，按新增、改进和修复分类，
生成面向客户的发布说明并发布到 Notion。跳过内部事项，标记疑似破坏性
变更的内容，让产品、支持团队和客户定期围绕同一信息保持一致。

* 需要与客户掌握相同信息的产品营销和支持团队

<div id="agent">
  ## 向 Agent 发出请求
</div>

<AiPrompt>
  请创建一个每周一上午 9 点运行的例程。从 GitHub 和 Linear 获取上周的
  变更，为客户生成按新增、改进和修复分类的发布说明，
  并发布到 Notion。跳过内部工作。标记看似存在破坏性
  变更的项目。
</AiPrompt>

<div id="section-4">
  ## 预期结果
</div>

Agent 会根据拉取请求和议题起草上周更新说明的草稿，然后创建 Notion 页面。
在发送给客户前，请调整措辞。跳过看似仅供内部使用的条目，并将破坏性变更置于最前。
发布前，请将上周已合并的拉取请求与页面进行比对。

<div id="section-5">
  ## 按需调整
</div>

<AiPrompt>
  请撰写两个版本：一个面向客户，另一个用于内部更新日志。
  请保留在同一个 Notion 页面中。
</AiPrompt>

<AiPrompt>
  请将包含 Notion 页面链接和 3 个亮点的 Slack 帖子发布到 #ship。
</AiPrompt>

<div id="section-6">
  ## 故障排查
</div>

* **发布说明中出现内部事项：** 告诉 Agent 正确的仓库和 Linear 团队，并再次要求它跳过不会发布给客户的事项。
* **破坏性变更不够显眼：** 告诉 Agent 哪些内容属于“破坏性变更” (如登录、支付、必要的迁移) ，并要求它突出标记这些项目并置于顶部。
* **Notion 页面有误：** 提供准确的页面或数据库链接，并说明是覆盖上周的页面，还是每次创建新页面。
