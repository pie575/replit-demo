Ces réponses concernent les erreurs susceptibles d&#39;apparaître sur une application publiée. Pour un dépannage plus général, consultez [Dépannage des déploiements](/fr/build/troubleshooting).

<AccordionGroup>
  <Accordion title="Mon application publiée renvoie des erreurs 403 Forbidden : comment les résoudre ?">
    Une erreur 403 sur une App publiée est généralement due à l&#39;une des causes suivantes :

    * **En-têtes de requête trop volumineux**—un trop grand nombre de cookies peut rendre les en-têtes suffisamment volumineux pour qu&#39;ils soient rejetés en périphérie. Effacez les cookies de votre navigateur pour ce domaine et réessayez.
    * **Authentification manquante**—la requête n&#39;inclut pas le jeton de connexion ou la session requis.
    * **Restriction d&#39;accès**—votre App est peut-être configurée pour bloquer une partie du trafic. Consultez les [déploiements privés](/fr/features/publishing/private-deployments) et les [jetons d&#39;accès externes](/fr/features/deployment-customization/external-access-tokens).

    Pour un diagnostic détaillé, collez les logs de votre déploiement dans un nouveau chat Agent.
  </Accordion>

  <Accordion title="Mon app affiche « Application failed to respond » : qu’est-ce que cela signifie ?">
    Le processus de votre App n&#39;écoute pas sur le port attendu par Replit. Replit transmet le bon port via la variable d&#39;environnement `PORT` : utilisez-la plutôt qu&#39;une valeur codée en dur :

    ```js theme={null}
    const PORT = process.env.PORT || 3000;
    ```

    ```python theme={null}
    port = int(os.environ.get("PORT", 3000))
    ```

    Votre app a peut-être aussi planté avant de se lier au port : consultez les logs de votre déploiement pour détecter les erreurs de démarrage. Avec les [déploiements Autoscale](/fr/features/publishing/deployment-types#autoscale), la première requête après une période d&#39;inactivité peut prendre quelques secondes (démarrage à froid), ce qui est normal.
  </Accordion>

  <Accordion title="Comment corriger les erreurs CORS dans mon app Replit publiée ?">
    Une erreur CORS signifie que votre frontend et votre backend se trouvent sur des origines différentes et que le backend n&#39;a pas été configuré pour l&#39;autoriser. S&#39;ils font partie de la même app, utilisez des URL relatives comme `/api/endpoint` pour éviter complètement le CORS.

    Sinon, configurez votre backend afin d&#39;autoriser l&#39;origine de votre frontend. Par exemple, pour Express :

    ```js theme={null}
    const cors = require("cors");
    app.use(cors({ origin: "https://your-frontend.replit.app" }));
    ```

    Avant de publier, autorisez uniquement les origines dont vous avez réellement besoin. Consultez [Dépannage des déploiements](/fr/build/troubleshooting).
  </Accordion>

  <Accordion title="Mon application fonctionne en local, mais renvoie des erreurs réseau une fois publiée">
    Les apps déployées échouent lorsque l&#39;environnement de production diffère de votre configuration locale. Vérifiez trois points :

    1. **URL localhost codées en dur** — remplacez `localhost:3000` ou `127.0.0.1` par des chemins relatifs ou des URL basées sur l&#39;environnement, puis redéployez.
    2. **Secrets de production manquants** — vérifiez que chaque clé requise est bien définie dans vos deployment secrets. Consultez [Secrets](/fr/core-concepts/project-editor/app-setup/secrets).
    3. **Migrations non exécutées en production** — exécutez les migrations en attente sur la production database avant de publier.

    Si les erreurs persistent, [contactez l&#39;assistance Replit](https://replit.com/support) en précisant votre message d&#39;erreur et les étapes déjà tentées.
  </Accordion>

  <Accordion title="Comment déboguer une erreur 502 Bad Gateway sur mon app publiée ?">
    Une erreur 502 signifie généralement que le processus de votre app a planté ou a renvoyé une sortie inutilisable par le serveur. Consultez les logs de votre deployment pour y repérer des erreurs de plantage survenues juste avant l&#39;apparition des 502 : les rejets de promesses non gérés et les exceptions non interceptées peuvent faire planter un processus Node.js silencieusement.

    Ajoutez un gestionnaire pour faire remonter les plantages :

    ```js theme={null}
    process.on("uncaughtException", (err) => console.error("Uncaught:", err));
    ```

    Une fois que vous avez identifié l&#39;erreur sous-jacente dans vos logs, collez-la dans un nouveau chat Agent pour obtenir de l&#39;aide et la corriger.
  </Accordion>

  <Accordion title="Mon app ne parvient pas à envoyer des requêtes à des API externes : que dois-je vérifier ?">
    Vérifiez d’abord si la requête est bloquée plutôt qu’en échec à cause de votre code. Ouvrez les logs de votre deployment et recherchez les messages indiquant que des requêtes sortantes sont bloquées ou redirigées.

    Causes fréquentes et solutions :

    * **URL autoréférentielles**—si votre backend appelle sa propre URL publique (par exemple `fetch("https://myapp.replit.app/api/...")`), utilisez plutôt un chemin relatif comme `fetch("/api/...")`.
    * **Requêtes pendant la phase de build**—effectuez les appels sortants à l’exécution, et non pendant le build.
    * **Restrictions réseau**—sur un réseau d’entreprise ou scolaire, les connexions sortantes peuvent être bloquées ; renseignez-vous auprès de votre administrateur réseau.

    Si aucun de ces cas ne s’applique et que les requêtes restent bloquées, [contactez le support Replit](https://replit.com/support) en fournissant les lignes de log pertinentes.
  </Accordion>

  <Accordion title="L’URL de mon application a changé après une nouvelle publication : puis-je récupérer mon ancien sous-domaine ?">
    Le sous-domaine `.replit.app` est dérivé du nom de votre projet et n&#39;est pas garanti de rester le même après avoir annulé sa publication puis l&#39;avoir republié, en particulier si le projet a été renommé.

    La solution permanente consiste à utiliser un [domaine personnalisé](/fr/features/publishing/custom-domains), qui reste le même après les redéploiements. Pour tenter de restaurer l&#39;ancien sous-domaine, assurez-vous que le nom de votre projet correspond au nom d&#39;origine (renommez-le si nécessaire), puis republiez-le — Replit ne peut pas réattribuer manuellement un sous-domaine libéré. Consultez [Project geography](/fr/features/publishing/project-geography).
  </Accordion>
</AccordionGroup>
