---
title: "更新使用共享数据库的已发布应用"
description: "分步指导你更新仍在使用最初为其他应用创建的数据库的已发布应用。"
---

一些较早发布的应用可能仍连接到最初为其他应用创建的开发数据库。

这种情况可能出现在 Replit 中分叉或混编的旧应用中。在旧版 Neon 配置中，分叉应用可能会继续使用原始应用的数据库连接。随着 Replit 全面分离开发数据库和生产数据库，旧的共享开发数据库将被移除，已发布应用必须迁移到自己的生产数据库。

如果已发布应用出现数据库连接错误，或 Secrets 面板中的 `DATABASE_URL` 仍指向 `neon.tech`，请参考本指南。

<Warning>
  旧的共享数据库计划于 **2026 年 6 月 8 日**停止服务。为避免停机或
  永久性数据丢失，请在此之前更新已发布应用。
</Warning>

<div id="section">
  ## 开始之前
</div>

已发布应用需要使用独立的**生产数据库**。**Database** 面板中显示的开发数据库不应直接用于已发布应用。

<Frame>
  <img src="/assets/mirror/dev-database-5c024a6c134e.png" alt="显示开发数据库的数据库面板" width="955" height="767" data-path="images/databases/shared-database-migration/dev-database.png" />
</Frame>

要解决此问题，请先确定您属于以下哪种情况。

* **情况 1：**所需数据已存在于应用的 **Database** 面板中。
* **情况 2：**已发布应用仍在使用旧的共享开发数据库，因此 **Database** 面板中未显示所需数据。

<div id="section-2">
  ## 如何判断已发布应用是否使用共享数据库？
</div>

如果符合以下任一情况，说明你的已发布应用受到了影响。

* 数据库升级后，已发布应用出现数据库连接错误
* 该应用是在 **2026 年 1 月 9 日之前** 从另一个包含数据库的应用 Remix 而来

<div id="section-3">
  ## 如何确认已发布应用是否使用源应用的共享数据库
</div>

<div id="1-database">
  ### 第 1 步：在源应用中打开 Database 面板
</div>

<Frame>
  <img src="/assets/mirror/secret-pane-showing-secrets-763dd4c4845f.png" alt="显示 DATABASE_URL 的 Secret 面板" width="792" height="418" data-path="images/databases/shared-database-migration/secret-pane-showing-secrets.png" />
</Frame>

获取 `NEON_DATABASE_URL` 的值；如果没有 `NEON_DATABASE_URL`，则获取 `DATABASE_URL` 的值。

<Info>
  并非所有受影响的应用都有 `NEON_DATABASE_URL`。如果没有该值，
  通常表示你需要在已发布应用的 Secrets 中确认当前的 `DATABASE_URL` 是否仍然
  指向 `neon.tech`。
</Info>

<div id="2-publish">
  ### 第 2 步：在已发布应用中打开 Publish 面板
</div>

<Frame>
  <img src="/assets/mirror/production-app-secrets-e4da45c53e36.png" alt="显示 DATABASE_URL 的已发布应用 Secrets" width="1385" height="1225" data-path="images/databases/shared-database-migration/production-app-secrets.png" />
</Frame>

要查看已发布应用的数据库 URL：

1. 在 Replit 中打开应用
2. 打开 **Publishing** 面板
3. 选择 **Adjust Settings**
4. 打开 **Secrets**
5. 找到 `DATABASE_URL`

<div id="3-1-url-2">
  ### 第 3 步：比较第 1 步中源应用的数据库 URL 与第 2 步中 Remix 应用的数据库 URL
</div>

如果两个 URL 相同，说明已发布应用正在使用源应用共享的 Neon 开发数据库。

<div id="section-4">
  ## 如何将数据从源应用复制到已发布应用
</div>

确认已发布应用正在使用源应用的共享开发数据库后，下一步是将所需数据传输到已发布应用。需要考虑以下两种情况：

* 情况 1：已发布应用的 Database 面板中已有所需数据。
* 情况 2：已发布应用的 Database 面板中没有所需数据。

<div id="1-database-2">
  ### 情况 1：Database 面板中已显示所需数据
</div>

如果所需数据已显示在应用的 **Database** 面板中，这是最简单的方法。

<div id="1">
  #### 第 1 步：确认数据是否存在
</div>

<Frame>
  <img src="/assets/mirror/my-data-12834f2ebfd6.png" alt="显示“my data”行的数据库面板" width="865" height="454" data-path="images/databases/shared-database-migration/my-data.png" />
</Frame>

在已发布应用中打开 **Database** 面板，确认其中是否包含所需的表和数据。

如果 Database 面板中未显示所需数据，请在此停止。要正确迁移数据，请按照[情况 2](#case-2-the-database-panel-does-not-show-the-data-you-need)中的步骤操作。

<div id="2">
  #### 第 2 步：使用生产数据库发布或重新发布
</div>

1. 在 Project Editor 中打开应用
2. 选择 **Publish** 或 **重新发布**
3. 开启 **Create production database**
4. 开启 **Set up your production database with your current development data**
5. 完成发布流程

发布后，系统会创建已发布应用的新版本，并自动将 `DATABASE_URL` 设置为新的生产数据库。无需手动更新该 Secret。

<Frame>
  <img src="/assets/mirror/production-database-settings-8855bf453da9.png" alt="显示 Create production database 选项的发布设置" width="1406" height="1207" data-path="images/databases/shared-database-migration/production-database-settings.png" />
</Frame>

<Warning>
  复制到生产环境会覆盖现有的生产数据。有关如何恢复或管理生产
  数据库的详细信息，请参阅[生产
  数据库](/zh/ko/features/data-and-storage/development-and-production)。
</Warning>

<div id="3">
  #### 第 3 步：验证已发布应用
</div>

打开已发布应用，确认能否访问数据，以及应用是否正常运行。

<div id="2-database">
  ### 情况 2：已发布应用的 Database 面板未显示所需数据
</div>

如果已发布应用的 **Database** 面板中看不到所需数据，请按以下步骤导出数据。

如果已发布应用仍连接到其他应用的数据库，Database 面板会显示“external database detected”警告。

<Frame>
  <img src="/assets/mirror/external-database-detected-489d99632e74.png" alt="显示 external database detected 的数据库面板" width="1403" height="1208" data-path="images/databases/shared-database-migration/external-database-detected.png" />
</Frame>

<Warning>
  如果用户仍在使用应用并保存新数据，请在导出数据前安排
  短暂的维护窗口。
</Warning>

<div id="1-2">
  #### 第 1 步：从原数据库导出数据
</div>

<Frame>
  <img src="/assets/mirror/pg-dump-example-54c6c790ccb1.png" alt="pg_dump 示例" width="1252" height="450" data-path="images/databases/shared-database-migration/pg-dump-example.png" />
</Frame>

在 Project Editor 中打开 **Shell**，然后运行以下命令。

```bash theme={null}
pg_dump -Fc "database_url" --no-owner --no-privileges -f backup.dump
```

`database_url` 是在[第 1 步：在源 App 中打开 Database 面板](#step-1-open-the-database-panel-in-the-source-app)中获取的数据库 URL。

<div id="2-secrets-database_url">
  ### 第 2 步：从应用的 Secrets 中删除旧的 `DATABASE_URL`
</div>

<Frame>
  <img src="/assets/mirror/secret-pane-eb253120f8a6.png" alt="Secrets 面板示例" width="1410" height="1184" data-path="images/databases/shared-database-migration/secret-pane.png" />
</Frame>

1. 在 Project Editor 中打开 **Secrets** 工具
2. 找到旧的 `DATABASE_URL`
3. 将其删除
4. 刷新页面或重新打开 **Database** 面板

完成后，应用将不再指向旧的共享数据库，并会重新使用当前的开发数据库。

<div id="3-2">
  ### 第 3 步：将数据导入应用当前的开发数据库
</div>

<Frame>
  <img src="/assets/mirror/pg-restore-example-409ae4d7bf09.png" alt="pg_restore 示例" width="802" height="426" data-path="images/databases/shared-database-migration/pg-restore-example.png" />
</Frame>

移除旧的 `DATABASE_URL` Secret 后，应用当前的开发数据库会再次在 Project Editor 中以 `$DATABASE_URL` 的形式可用。

返回 Project Editor 中的 **Shell**，然后运行以下命令。

```bash theme={null}
pg_restore --clean --if-exists --single-transaction --no-owner --no-privileges --exit-on-error -d "$DATABASE_URL" backup.dump
```

这样，导出的数据就会导入应用当前的开发数据库。

<div id="5-1">
  ### 第 5 步：按照案例 1 使用生产数据库发布或重新发布
</div>

如果 **Database** 面板显示了正确的数据，请按照[案例 1](#case-1-the-database-panel-already-shows-the-data-you-need)操作，选择 **Create production database** 发布或重新发布，并将这些数据复制到生产环境。

<div id="6">
  ### 第 6 步：验证已发布应用
</div>

<Frame>
  <img src="/assets/mirror/successful-export-bfb997304cc1.png" alt="成功导出" width="965" height="554" data-path="images/databases/shared-database-migration/successful-export.png" />
</Frame>

打开已发布应用，确认可以访问数据且应用运行正常。

<div id="section-5">
  ## 故障排查
</div>

<div id="section-6">
  ### 表已存在，导致导入失败
</div>

上述 `pg_restore --clean --if-exists` 命令会在恢复前删除转储文件中对应的对象，然后重新创建它们。

<div id="role-policy">
  ### 因角色或策略错误导致导入失败
</div>

如果数据库使用自定义 PostgreSQL 角色或基于角色的策略，由于新数据库中尚不存在这些角色，导入可能会失败。

Replit 的自动 Helium 迁移会尝试在恢复前重新创建角色存根，但上述手动流程不会这样做。如果在执行 `pg_restore` 时遇到与角色相关的错误，请[联系支持团队](https://replit.com/support)。

<div id="section-7">
  ### 已修改应用
</div>

如果已发布应用已有自己的生产数据库且运行正常，则无需进行其他操作。

<div id="section-8">
  ## 还需要更多帮助吗？
</div>

如果您不确定自己的应用属于哪种情况，或在迁移过程中遇到问题，请[联系支持团队](https://replit.com/support)。
