---
title: "Mettre à jour une application publiée utilisant une base de données partagée"
description: "Guide étape par étape pour mettre à jour une application publiée qui utilise encore une base de données créée à l’origine pour une autre application."
---

Certaines anciennes applications publiées peuvent encore être connectées à une base de données de développement créée à l’origine pour une autre application.

Cela peut se produire avec d’anciennes applications forkées ou remixées sur Replit. Dans les anciennes configurations Neon, un fork pouvait continuer à utiliser la connexion à la base de données de l’application d’origine. Alors que Replit évolue vers une séparation complète des bases de données de développement et de production, les anciennes bases de données de développement partagées sont supprimées et les applications publiées doivent migrer vers leur propre base de données de production.

Utilisez ce guide si des erreurs de connexion à la base de données s’affichent dans votre application publiée ou si `DATABASE_URL` dans le panneau Secrets pointe encore vers `neon.tech`.

<Warning>
  Les anciennes bases de données partagées seront mises hors service le **8 juin 2026**. Pour éviter toute indisponibilité ou
  perte de données permanente, mettez à jour vos applications publiées avant cette date.
</Warning>

<div id="section">
  ## Avant de commencer
</div>

Les applications publiées nécessitent leur propre **base de données de production**. La base de données de développement affichée dans le panneau **Database** ne doit pas être utilisée directement par une application publiée.

<Frame>
  <img src="/assets/mirror/dev-database-5c024a6c134e.png" alt="Panneau Base de données affichant la base de données de développement" width="955" height="767" data-path="images/databases/shared-database-migration/dev-database.png" />
</Frame>

Pour résoudre ce problème, commencez par identifier la situation qui s’applique.

* **Cas 1 :** les données nécessaires sont déjà présentes dans le panneau Base de données de l’application.
* **Cas 2 :** l’application publiée utilise encore l’ancienne base de données de développement partagée. Les données nécessaires ne s’affichent donc pas dans le panneau Base de données.

<div id="section-2">
  ## Comment savoir si une application publiée utilise une base de données partagée ?
</div>

Si l&#39;un des cas suivants s&#39;applique, votre application publiée est concernée.

* Des erreurs de connexion à la base de données s&#39;affichent dans l&#39;application publiée après une mise à niveau de la base de données
* L&#39;application a été remixée à partir d&#39;une autre application qui disposait d&#39;une base de données **avant le 9 janvier 2026**

<div id="section-3">
  ## Vérifier si l’application publiée utilise la base de données partagée de l’application source
</div>

<div id="1-database">
  ### Étape 1 : ouvrez le panneau Base de données dans l’application source
</div>

<Frame>
  <img src="/assets/mirror/secret-pane-showing-secrets-763dd4c4845f.png" alt="Panneau Secrets affichant DATABASE_URL" width="792" height="418" data-path="images/databases/shared-database-migration/secret-pane-showing-secrets.png" />
</Frame>

Récupérez la valeur de `NEON_DATABASE_URL` ou, si `NEON_DATABASE_URL` n’existe pas, celle de `DATABASE_URL`.

<Info>
  Toutes les applications concernées ne disposent pas de `NEON_DATABASE_URL`. Si cette valeur
  n’existe pas, cela signifie généralement que vous devez vérifier si le `DATABASE_URL` actuel dans les Secrets
  de l’application publiée pointe toujours vers `neon.tech`.
</Info>

<div id="2-publish">
  ### Étape 2 : ouvrez le panneau Publishing de l’application publiée
</div>

<Frame>
  <img src="/assets/mirror/production-app-secrets-e4da45c53e36.png" alt="Secrets de l’application publiée affichant DATABASE_URL" width="1385" height="1225" data-path="images/databases/shared-database-migration/production-app-secrets.png" />
</Frame>

Pour vérifier l’URL de la base de données de l’application publiée :

1. Ouvrez l’application dans Replit
2. Ouvrez le panneau **Publishing**
3. Ouvrez **Ajuster les paramètres**
4. Ouvrez **Secrets**
5. Recherchez `DATABASE_URL`

<div id="3-1-url-2">
  ### Étape 3 : comparer l’URL de la base de données de l’application source à l’étape 1 avec celle de l’application remixée à l’étape 2
</div>

Si les deux URL sont identiques, l’application publiée utilise la base de données de développement Neon partagée de l’application source.

<div id="section-4">
  ## Comment copier des données de l’application source vers l’application publiée
</div>

Après avoir vérifié que votre application publiée utilise la base de données de développement partagée de l’application source, l’étape suivante consiste à transférer les données nécessaires vers l’application publiée. Deux scénarios sont à envisager.

* Cas 1 : les données nécessaires sont déjà présentes dans le panneau Base de données de l’application publiée.
* Cas 2 : les données nécessaires ne sont pas présentes dans le panneau Base de données de l’application publiée.

<div id="1-database-2">
  ### Cas 1 : les données nécessaires sont déjà affichées dans le panneau Base de données
</div>

C’est la méthode la plus simple si les données dont vous avez besoin sont déjà visibles dans le panneau Base de données de l’application.

<div id="1">
  #### Étape 1 : vérifier la présence des données
</div>

<Frame>
  <img src="/assets/mirror/my-data-12834f2ebfd6.png" alt="panneau Base de données affichant la ligne my data" width="865" height="454" data-path="images/databases/shared-database-migration/my-data.png" />
</Frame>

Dans l’application publiée, ouvrez le panneau **Base de données** et vérifiez que les tables et les données requises sont présentes.

Si les données requises ne s’affichent pas dans le panneau Base de données, arrêtez-vous ici. Pour migrer correctement vos données, suivez les étapes du [cas 2](#case-2-the-database-panel-does-not-show-the-data-you-need).

<div id="2">
  #### Étape 2 : Publier ou republier avec une base de données de production
</div>

1. Ouvrez l’application dans le Project Editor
2. Sélectionnez **Publier** ou **Republier**
3. Activez **Créer une base de données de production**
4. Activez **Configurer votre base de données de production avec vos données de développement actuelles**
5. Terminez la procédure de publication

La publication crée une nouvelle version de l’application publiée et définit automatiquement `DATABASE_URL` sur la nouvelle base de données de production. Vous n’avez pas besoin de mettre à jour ce secret manuellement.

<Frame>
  <img src="/assets/mirror/production-database-settings-8855bf453da9.png" alt="Paramètres de publication affichant l’option Créer une base de données de production" width="1406" height="1207" data-path="images/databases/shared-database-migration/production-database-settings.png" />
</Frame>

<Warning>
  La copie vers l’environnement de production écrase les données de production existantes. Pour en savoir
  plus sur la restauration ou la gestion de votre base de données de production, consultez
  [Base de données de production](/fr/ko/features/data-and-storage/development-and-production).
</Warning>

<div id="3">
  #### Étape 3 : Vérifier l’application publiée
</div>

Ouvrez l’application publiée et vérifiez que vous pouvez accéder aux données et qu’elle fonctionne correctement.

<div id="2-database">
  ### Cas 2 : les données requises ne s’affichent pas dans le panneau Base de données de l’application publiée
</div>

Si les données requises ne s’affichent pas dans le panneau **Base de données** de l’application publiée, suivez les étapes ci-dessous pour les exporter.

Si l’application publiée est toujours connectée à la base de données d’une autre application, l’avertissement « external database detected » s’affiche dans le panneau Base de données.

<Frame>
  <img src="/assets/mirror/external-database-detected-489d99632e74.png" alt="Panneau Base de données affichant « external database detected »" width="1403" height="1208" data-path="images/databases/shared-database-migration/external-database-detected.png" />
</Frame>

<Warning>
  Si des personnes utilisent encore l’application et y enregistrent de nouvelles données, prévoyez une
  courte période de maintenance avant de les exporter.
</Warning>

<div id="1-2">
  #### Étape 1 : Exportez les données de l’ancienne base de données
</div>

<Frame>
  <img src="/assets/mirror/pg-dump-example-54c6c790ccb1.png" alt="Exemple de pg_dump" width="1252" height="450" data-path="images/databases/shared-database-migration/pg-dump-example.png" />
</Frame>

Dans le Project Editor, ouvrez le **Shell** et exécutez la commande suivante.

```bash theme={null}
pg_dump -Fc "database_url" --no-owner --no-privileges -f backup.dump
```

`database_url` est l’URL de la base de données obtenue à l’[étape 1 : ouvrir le panneau Database dans l’application source](#step-1-open-the-database-panel-in-the-source-app).

<div id="2-secrets-database_url">
  ### Étape 2 : supprimer l’ancien `DATABASE_URL` des Secrets de l’application
</div>

<Frame>
  <img src="/assets/mirror/secret-pane-eb253120f8a6.png" alt="exemple de panneau Secrets" width="1410" height="1184" data-path="images/databases/shared-database-migration/secret-pane.png" />
</Frame>

1. Ouvrez l’outil **Secrets** dans le Project Editor
2. Recherchez l’ancien `DATABASE_URL`
3. Supprimez-le
4. Actualisez la page ou rouvrez le panneau Base de données

Après cette opération, l’application n’utilisera plus l’ancienne base de données partagée et utilisera à nouveau la base de données de développement actuelle.

<div id="3-2">
  ### Étape 3 : Importer les données dans la base de données de développement actuelle de l’application
</div>

<Frame>
  <img src="/assets/mirror/pg-restore-example-409ae4d7bf09.png" alt="Exemple de pg_restore" width="802" height="426" data-path="images/databases/shared-database-migration/pg-restore-example.png" />
</Frame>

Une fois l’ancien secret `DATABASE_URL` supprimé, la base de données de développement actuelle de l’application redevient accessible via `$DATABASE_URL` dans Project Editor.

Revenez dans le **Shell** de Project Editor et exécutez la commande suivante.

```bash theme={null}
pg_restore --clean --if-exists --single-transaction --no-owner --no-privileges --exit-on-error -d "$DATABASE_URL" backup.dump
```

Les données exportées sont ainsi chargées dans la base de données de développement actuelle de l’application.

<div id="5-1">
  ### Étape 5 : publier ou republier avec une base de données de production en suivant le cas 1
</div>

Si le panneau Base de données affiche les données correctes, suivez le [cas 1](#case-1-the-database-panel-already-shows-the-data-you-need) pour publier ou republier avec **Create production database** et copier ces données dans la base de données de production.

<div id="6">
  ### Étape 6 : Vérifier l&#39;application publiée
</div>

<Frame>
  <img src="/assets/mirror/successful-export-bfb997304cc1.png" alt="Exportation réussie" width="965" height="554" data-path="images/databases/shared-database-migration/successful-export.png" />
</Frame>

Ouvrez l&#39;application publiée et vérifiez que vous pouvez accéder aux données et qu&#39;elle fonctionne correctement.

<div id="section-5">
  ## Résolution des problèmes
</div>

<div id="section-6">
  ### L’importation échoue, car la table existe déjà
</div>

La commande `pg_restore --clean --if-exists` ci-dessus supprime les objets correspondants du dump avant de les restaurer, puis les recrée.

<div id="role-policy">
  ### L’importation échoue en raison d’erreurs de rôles ou de stratégies
</div>

Si votre base de données utilise des rôles PostgreSQL personnalisés ou des stratégies basées sur les rôles, l’importation peut échouer, car ces rôles n’existent pas encore dans la nouvelle base de données.

La migration Helium automatique de Replit tente de recréer des stubs de rôles avant la restauration, mais ce n’est pas le cas du processus manuel ci-dessus. Si vous rencontrez des erreurs liées aux rôles lors de l’exécution de `pg_restore`, [contactez l’assistance](https://replit.com/support).

<div id="section-7">
  ### Vous avez déjà modifié l’application
</div>

Si votre application publiée dispose déjà de sa propre base de données de production et fonctionne correctement, vous n’avez rien d’autre à faire.

<div id="section-8">
  ## Besoin d&#39;aide supplémentaire ?
</div>

Si vous ne savez pas quel cas s&#39;applique à votre application ou si vous rencontrez des problèmes lors de la migration, [contactez l&#39;assistance](https://replit.com/support).
