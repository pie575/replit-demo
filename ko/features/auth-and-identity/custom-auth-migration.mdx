---

앱에 자체 인증 시스템, 사용자 저장소, 또는 세션 로직이 있다면 이 페이지를 사용하세요. [Clerk Auth](/ko/features/auth-and-identity/clerk-auth)로 이전하는 것은 단순한 코드 변경이 아니라 데이터와 신원 마이그레이션입니다. 계획이 없으면 기존 사용자가 자신의 기존 데이터에 대한 접근 권한을 잃은 것처럼 보일 수 있습니다.

<Note>
  **Replit Auth를 사용 중인가요?** 자동화된 마이그레이션 흐름은 해당되는 Replit Auth 앱에만 제공됩니다. 대신 [Replit Auth에서 Clerk로 마이그레이션하기](/ko/features/auth-and-identity/migrate-auth-to-clerk)를 따르세요.

  Replit은 커스텀 인증 시스템을 자동으로 마이그레이션하지 않습니다. 이 페이지는 자동화된 가져오기 절차가 아니라 계획 및 검증 가이드를 제공합니다.
</Note>

## 신원 연속성 계획하기

* 오늘날 사람과 앱 데이터를 연결하는 안정적인 값을 식별하세요. 사용자 ID, 이메일 주소, 사용자 이름, 또는 별도의 계정 레코드일 수 있습니다.
* 소유권, 권한, 구독, 환경 설정, 감사 기록을 포함하여 해당 값에 의존하는 모든 테이블과 서비스를 목록화하세요.
* 로그인 동작을 변경하기 전에 새 신원 시스템이 각 기존 로컬 레코드를 어떻게 해석할지 결정하세요.
* 전환 이후 완전히 새로운 사용자가 로컬 레코드에 어떻게 할당되고 연결될지 정의하세요.

<Warning>
  제공자의 사용자 ID, 이메일 주소, 또는 첫 로그인 시 생성되는 새 계정이 기존 레코드와 일치할 것이라고 가정하지 마세요. 전환 전에 대표 계정으로 매핑을 검증하세요.
</Warning>

## 계정 자격 증명 및 세션

* 비밀번호 해시, OAuth 신원, MFA 요소, 인증 상태, 활성 세션을 개별적으로 목록화하세요. 이들은 서로 다른 이식성 및 보안 요구 사항을 가질 수 있습니다.
* 실제 계정을 처리하기 전에 선택한 제공자의 최신 문서에 따라 비밀번호 마이그레이션을 검증하세요. 자격 증명을 안전하게 마이그레이션할 수 없다면 비밀번호 재설정 또는 계정 연결 흐름을 계획하세요.
* OAuth 신원이나 활성 세션이 자동으로 이전될 것이라고 가정하지 마세요. 기존 사용자가 어떻게 다시 로그인할지, 그리고 중복 계정을 어떻게 방지할지 계획하세요.
* 명시적으로 대체 방안을 계획하지 않은 한, 권한 부여 및 앱별 데이터는 로컬 데이터 모델에 유지하세요. 인증과 권한 부여는 종종 별도의 마이그레이션 작업이 필요합니다.

## 전환 전 테스트하기

* 대표성 있는 민감하지 않은 계정과 데이터로 비프로덕션 환경에서 테스트하세요.
* 기존 계정으로 로그인한 다음, 대시보드, 프로필, 저장된 항목 등 사용자별 데이터를 읽는 페이지를 열어보세요.
* 권한 부여 규칙, 계정 복구, 로그아웃, 신규 계정 흐름을 검증하세요.
* 전환 중에 중복 레코드와 접근 실패를 모니터링하세요. 검증이 완료될 때까지 롤백 계획을 유지하세요.

## 도움 받기

* 커스텀 인증 시스템을 Replit이 관리하는 Clerk Auth로 마이그레이션해야 한다면, 프로덕션 계정 데이터를 변경하기 전에 [Replit 지원팀에 문의](https://replit.com/support)하세요.
* 다른 제공자로 인증을 관리한다면, 해당 제공자의 최신 마이그레이션 문서를 사용하고 전환 전에 신원 매핑을 검증하세요.
