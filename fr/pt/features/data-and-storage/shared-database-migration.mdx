---
title: "Corriger une app publiée qui utilise une base de données partagée"
description: "Instructions étape par étape pour mettre à jour une app publiée qui utilise encore une base de données créée à l'origine pour une autre app."
---

Certaines apps publiées plus anciennes peuvent encore être connectées à une base de données de développement créée à l&#39;origine pour une autre app.

Ce cas concerne les apps plus anciennes qui ont été forkées ou remixées sur Replit. Dans l&#39;ancien système de Neon, un fork pouvait continuer à utiliser la connexion à la base de données de l&#39;app d&#39;origine. Dans le cadre de la transition de Replit vers une isolation complète des bases de données de développement et de production, les anciennes bases de données de développement partagées sont progressivement supprimées et les apps publiées doivent migrer vers leur propre base de données de production.

Suivez ce guide si votre app publiée affiche des erreurs de connexion à la base de données, ou si `DATABASE_URL` dans le panneau Secrets pointe encore vers `neon.tech`.

<Warning>
  L&#39;ancienne base de données partagée sera désactivée le **8 juin 2026**. Mettez à jour votre
  app publiée avant cette date pour éviter toute interruption de service ou perte définitive de données.
</Warning>

<div id="antes-de-comear">
  ## Avant de commencer
</div>

Votre app publiée a besoin de sa propre **base de données de production**. La base de données de développement affichée dans le panneau **Database** ne doit pas être utilisée directement par les apps publiées.

<Frame>
  <img src="/assets/mirror/dev-database-5c024a6c134e.png" alt="Panneau de base de données affichant la base de données de développement" width="955" height="767" data-path="images/databases/shared-database-migration/dev-database.png" />
</Frame>

Pour y remédier, commencez par identifier votre situation :

* **Cas 1 :** les données souhaitées figurent déjà dans la base de données affichée dans le panneau **Database** de votre app.
* **Cas 2 :** le panneau **Database** n&#39;affiche pas les données dont vous avez besoin, car votre app publiée utilise encore l&#39;ancienne base de données de développement partagée.

<div id="como-saber-se-o-seu-app-publicado-est-usando-um-banco-de-dados-compartilhado">
  ## Comment savoir si votre App publiée utilise une base de données partagée ?
</div>

Votre App publiée est concernée si l&#39;une des situations suivantes s&#39;applique :

* Votre App publiée affiche des erreurs de connexion à la base de données après la mise à jour de celle-ci
* Votre App a été remixée à partir d&#39;une autre App disposant d&#39;une base de données **avant le 9 janvier 2026**

<div id="como-verificar-se-o-seu-app-publicado-est-usando-o-banco-de-dados-compartilhado-do-app-de-origem">
  ## Comment vérifier si votre app publiée utilise la base de données partagée de l&#39;app d&#39;origine ?
</div>

<div id="passo-1-abra-o-painel-database-no-app-de-origem">
  ### Étape 1 : ouvrez le panneau Database dans l&#39;app source
</div>

<Frame>
  <img src="/assets/mirror/secret-pane-showing-secrets-763dd4c4845f.png" alt="Panneau des secrets affichant DATABASE_URL" width="792" height="418" data-path="images/databases/shared-database-migration/secret-pane-showing-secrets.png" />
</Frame>

Récupérez la valeur de `NEON_DATABASE_URL`, ou celle de `DATABASE_URL` si `NEON_DATABASE_URL` n&#39;existe pas.

<Info>
  Les apps concernées ne disposent pas toutes d&#39;une variable `NEON_DATABASE_URL`. Si elle est absente, cela
  signifie généralement que vous devez utiliser le `DATABASE_URL` actuel des Secrets de l&#39;app
  publiée, s&#39;il pointe toujours vers `neon.tech`.
</Info>

<div id="passo-2-abra-o-painel-publish-no-app-publicado">
  ### Étape 2 : ouvrez le panneau Publish dans l&#39;app publiée
</div>

<Frame>
  <img src="/assets/mirror/production-app-secrets-e4da45c53e36.png" alt="Secrets de l'app publiée affichant DATABASE_URL" width="1385" height="1225" data-path="images/databases/shared-database-migration/production-app-secrets.png" />
</Frame>

Pour vérifier l&#39;URL de la base de données de votre app publiée :

1. Ouvrez votre app dans Replit
2. Ouvrez le panneau **Publishing**
3. Ouvrez **Adjust Settings**
4. Ouvrez **Secrets**
5. Recherchez `DATABASE_URL`

<div id="passo-3-compare-a-url-do-banco-de-dados-do-app-de-origem-no-passo-1-com-a-do-app-remixado-no-passo-2">
  ### Étape 3 : comparez l&#39;URL de la base de données de l&#39;app d&#39;origine obtenue à l&#39;étape 1 avec celle de l&#39;app remixée obtenue à l&#39;étape 2
</div>

Si elles sont identiques, votre app publiée utilise une base de données de développement Neon partagée avec l&#39;app d&#39;origine.

<div id="como-copiar-dados-do-app-de-origem-para-o-app-publicado">
  ## Comment copier les données de l&#39;app d’origine vers l&#39;app publiée ?
</div>

Une fois que vous avez confirmé que votre app publiée utilise bien la base de données de développement partagée de l&#39;app d’origine, l&#39;étape suivante consiste à transférer les données nécessaires vers l&#39;app publiée. Deux cas de figure sont possibles :

* Cas 1 : le panneau Database de l&#39;app publiée contient déjà les données nécessaires.
* Cas 2 : le panneau Database de l&#39;app publiée ne contient pas les données nécessaires.

<div id="caso-1-o-painel-database-j-mostra-os-dados-que-voc-precisa">
  ### Cas 1 : le panneau Database affiche déjà les données dont vous avez besoin
</div>

C&#39;est la méthode la plus simple si les données qu&#39;il vous faut sont déjà visibles dans le panneau **Database** de votre App.

<div id="passo-1-confirme-que-os-dados-esto-presentes">
  #### Étape 1 : Vérifiez que les données sont présentes
</div>

<Frame>
  <img src="/assets/mirror/my-data-12834f2ebfd6.png" alt="Panneau de base de données affichant des lignes dans my data" width="865" height="454" data-path="images/databases/shared-database-migration/my-data.png" />
</Frame>

Ouvrez le panneau **Database** dans l&#39;App publiée et vérifiez que les tables et les données dont vous avez besoin s&#39;y trouvent.

Si vous n&#39;y voyez pas les données dont vous avez besoin, arrêtez-vous ici. Vous devrez suivre les étapes du [Cas 2](#caso-2-o-painel-database-no-app-publicado-não-mostra-os-dados-que-você-precisa) pour migrer correctement vos données.

<div id="passo-2-publique-ou-republique-com-um-banco-de-dados-de-produo">
  #### Étape 2 : publiez ou republiez avec une base de données de production
</div>

1. Ouvrez votre app dans le Project Editor
2. Sélectionnez **Publish** ou **Republish**
3. Activez **Create production database**
4. Activez **Set up your production database with your current development data**
5. Terminez le processus de publication

La publication crée une nouvelle version de votre app publiée et fait automatiquement pointer son `DATABASE_URL` vers la nouvelle base de données de production. Vous n&#39;avez pas besoin de mettre à jour ce secret manuellement au cours de ce processus.

<Frame>
  <img src="/assets/mirror/production-database-settings-8855bf453da9.png" alt="Paramètres de publication affichant les options Create production database" width="1406" height="1207" data-path="images/databases/shared-database-migration/production-database-settings.png" />
</Frame>

<Warning>
  La copie vers la production écrase toutes les données de production existantes. Consultez [Production
  Databases](/fr/pt/features/data-and-storage/development-and-production) pour
  plus de détails sur la restauration ou la gestion de votre base de données de production.
</Warning>

<div id="passo-3-verifique-o-app-publicado">
  #### Étape 3 : Vérifiez l&#39;App publiée
</div>

Ouvrez votre App publiée et vérifiez que vos données sont accessibles et que l&#39;App fonctionne correctement.

<div id="caso-2-o-painel-database-no-app-publicado-no-mostra-os-dados-que-voc-precisa">
  ### Cas 2 : le panneau Database de l&#39;app publiée n&#39;affiche pas les données dont vous avez besoin
</div>

Si vous ne trouvez pas les données nécessaires dans le panneau **Database** de votre app publiée, suivez ces étapes pour les exporter.

Si votre app publiée est encore connectée à la base de données d&#39;une autre app, un avertissement « external database detected » s&#39;affiche dans le panneau Database.

<Frame>
  <img src="/assets/mirror/external-database-detected-489d99632e74.png" alt="Panneau de base de données affichant external database detected" width="1403" height="1208" data-path="images/databases/shared-database-migration/external-database-detected.png" />
</Frame>

<Warning>
  Si des personnes utilisent encore votre app et y enregistrent de nouvelles données, prévoyez une
  brève fenêtre de maintenance avant d&#39;exporter les données.
</Warning>

<div id="passo-1-exporte-os-dados-do-banco-de-dados-antigo">
  #### Étape 1 : exportez les données de l&#39;ancienne base de données
</div>

<Frame>
  <img src="/assets/mirror/pg-dump-example-54c6c790ccb1.png" alt="Exemple de pg_dump" width="1252" height="450" data-path="images/databases/shared-database-migration/pg-dump-example.png" />
</Frame>

Ouvrez le **Shell** dans le Project Editor et exécutez :

```bash theme={null}
pg_dump -Fc "database_url" --no-owner --no-privileges -f backup.dump
```

`database_url` est l&#39;URL de la base de données obtenue à l&#39;[Étape 1 : Ouvrez le panneau Database dans l&#39;app d’origine](#passo-1-abra-o-painel-database-no-app-de-origem).

<div id="passo-2-remova-o-database_url-antigo-dos-secrets-do-seu-app">
  ### Étape 2 : supprimez l&#39;ancien `DATABASE_URL` des Secrets de votre app
</div>

<Frame>
  <img src="/assets/mirror/secret-pane-eb253120f8a6.png" alt="Exemple de panneau de secrets" width="1410" height="1184" data-path="images/databases/shared-database-migration/secret-pane.png" />
</Frame>

1. Ouvrez l&#39;outil **Secrets** dans le Project Editor
2. Repérez l&#39;ancien `DATABASE_URL`
3. Supprimez-le
4. Actualisez la page ou rouvrez le panneau **Database**

Votre app ne devrait alors plus pointer vers l&#39;ancienne base de données partagée, mais utiliser de nouveau votre base de données de développement actuelle.

<div id="passo-3-importe-os-dados-para-o-banco-de-dados-de-desenvolvimento-atual-do-seu-app">
  ### Étape 3 : importez les données dans la base de données de développement actuelle de votre app
</div>

<Frame>
  <img src="/assets/mirror/pg-restore-example-409ae4d7bf09.png" alt="Exemple de pg_restore" width="802" height="426" data-path="images/databases/shared-database-migration/pg-restore-example.png" />
</Frame>

Une fois l&#39;ancien secret `DATABASE_URL` supprimé, la base de données de développement actuelle de votre app devrait à nouveau être disponible sous `$DATABASE_URL` dans le Project Editor.

Retournez dans le **Shell** du Project Editor et exécutez :

```bash theme={null}
pg_restore --clean --if-exists --single-transaction --no-owner --no-privileges --exit-on-error -d "$DATABASE_URL" backup.dump
```

Cette opération charge les données exportées dans la base de données de développement actuelle de votre app.

<div id="passo-5-siga-o-caso-1-para-publicar-ou-republicar-com-um-banco-de-dados-de-produo">
  ### Étape 5 : suivez le cas 1 pour publier ou republier avec une base de données de production
</div>

Une fois que le panneau **Database** affiche les bonnes données, suivez le [cas 1](#caso-1-o-painel-database-já-mostra-os-dados-que-você-precisa) pour publier ou republier avec **Create production database** et copier ces données en production.

<div id="passo-6-verifique-o-app-publicado">
  ### Étape 6 : Vérifiez l&#39;App publiée
</div>

<Frame>
  <img src="/assets/mirror/successful-export-bfb997304cc1.png" alt="exportation réussie" width="965" height="554" data-path="images/databases/shared-database-migration/successful-export.png" />
</Frame>

Ouvrez votre App publiée et vérifiez que vos données sont accessibles et que l&#39;App fonctionne correctement.

<div id="soluo-de-problemas">
  ## Dépannage
</div>

<div id="a-importao-falha-porque-as-tabelas-j-existem">
  ### L&#39;importation échoue car les tables existent déjà
</div>

La commande `pg_restore --clean --if-exists` ci-dessus supprime puis recrée les objets correspondants du dump avant de les restaurer.

<div id="a-importao-falha-com-erros-de-funo-role-ou-poltica">
  ### L&#39;importation échoue avec des erreurs de rôle ou de politique
</div>

Si votre base de données utilise des rôles PostgreSQL personnalisés ou des politiques basées sur les rôles, l&#39;importation peut échouer, car ces rôles n&#39;existent pas encore dans la nouvelle base de données.

La migration automatique de Replit vers Helium tente de recréer des stubs de rôles avant la restauration, mais la procédure manuelle décrite ci-dessus ne le fait pas. Si vous rencontrez des erreurs liées aux rôles lors du `pg_restore`, [contactez l&#39;assistance](https://replit.com/support) pour obtenir de l&#39;aide.

<div id="eu-j-corrigi-o-app">
  ### J&#39;ai déjà corrigé l&#39;App
</div>

Si votre App publiée dispose déjà de sa propre base de données de production et fonctionne correctement, vous n&#39;avez rien de plus à faire.

<div id="precisa-de-mais-ajuda">
  ## Besoin d&#39;aide supplémentaire ?
</div>

Si vous ne savez pas quel cas s&#39;applique à votre app, ou si vous rencontrez des difficultés pendant la migration, [contactez l’assistance](https://replit.com/support).
