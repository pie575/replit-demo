能够同时处理多项工作，是区分优秀构建者与卓越构建者的关键技能之一。本页将介绍如何安全地同时构建多项功能，即使你此前从未以这种方式工作过。

<div id="agent">
  ## 与 Agent 的全新协作方式
</div>

此前，你可能一直像与坐在身旁的伙伴一样和 Agent 协作：提问、观察、回应。并行构建则是一种不同的协作方式。将功能作为**任务**交给 Agent 后，Agent 会在后台进行构建，你可以同时处理其他事情。

其实，你在日常生活中早已习惯这种工作方式。你不会一直站在洗衣机前等它洗完。启动洗衣机后，你会去做饭。任务也是如此：启动一个任务后，在它运行期间，你可以启动另一个任务、审核其他任务，或继续在主对话中与 Agent 聊天。

这会改变你的角色。你不再是守着一次构建过程的乘客，而是统筹多个构建过程的导演。

<div id="section">
  ## 任务运行期间，应用依然安全
</div>

大家最常问的问题是：*趁你不注意时，后台任务会不会弄坏应用？*

不会，完全不用担心。每项任务都会在项目的独立**副本**中进行操作。除非你审核并选择应用任务所做的更改，否则应用不会发生任何变化。

每项任务都有自己的 Agent，并继承项目的完整上下文，因此无需重复说明相同的信息。任务彼此独立，所以即使第一个任务仍在运行，你也可以立即启动下一个任务。

<div id="3">
  ## 示例：同时构建三个功能
</div>

假设你有一个已经支持预约和登录的租车应用，现在想添加三个功能：

* 活动页面
* 活动报名
* 联系表单

如果按顺序逐个构建，每个功能约需 5 分钟，总共需要 15 分钟。并行构建则只需约 5 分钟。

为每个功能创建一个任务。任务会以 Plan 模式启动，因此你会在构建前看到各自的方案。批准方案后，活动页面和联系表单会立即开始构建，但活动报名会等待，因为活动页面尚未创建时，访客无法报名参加活动。Agent 会自动识别这种依赖关系，像项目经理一样，在依赖任务完成后再执行该任务。

<div id="section-2">
  ## 将工作拆分为小任务
</div>

要让并行构建顺利进行，关键在于将功能拆分为小型且相互独立的任务。小任务完成得更快、更易于审核，也不太可能相互干扰。

一个实用原则：**如果任务描述中出现“和”，请考虑将其拆分。**

* 好的示例：“添加活动页面”“添加联系表单”
* 过大的示例：“添加活动、注册、电子邮件通知和管理面板”

较大的版本并没有错，但这会让一个 Agent 按顺序完成所有工作。将其拆分为四个小任务后，Agent 可以同时执行它们。

亲自试试看。以下哪些任务可以并行执行？

1. 添加深色模式切换功能
2. 添加客户评价部分
3. 让客户能够回复评价
4. 将应用翻译成法语

<Accordion title="答案">
  任务 1、2 和 4 相互独立，可以同时执行。任务 3 依赖于任务 2：如果没有评价，就没有可回复的内容。你无需自行判断这一点。Agent 会检测依赖关系，并自动安排这两个任务的执行顺序。
</Accordion>

<div id="section-3">
  ## 为什么要在应用前更新
</div>

这是唯一容易让人困惑的地方，所以我们慢慢说明。

假设两位朋友各自带了一份同一场派对邀请函的副本回家修改。一位加上地图，另一位重写日程安排。当你采用第一位朋友的版本后，它就成了正式的邀请函。这时，第二位朋友的副本就出现了问题：其改写所依据的邀请函已经不复存在。在采用第二位朋友的工作之前，需要让他们基于最新版本重新完成。

任务的工作方式完全相同。每个任务开始时都会复制一份项目。当你应用一个任务的更改时，其他所有任务的副本都会落后一个版本。对于互不相关的功能，这通常不会有问题，但由于你无法阅读代码，无法确定两个任务是否修改了同一处内容。

<Tip>
  在应用任务的更改之前，请先**更新**该任务。更新会让任务与应用的最新版本同步并解决冲突，从而让任务的更改能够层层叠加，而不是互相覆盖。
</Tip>

<div id="section-4">
  ## 以经理的视角进行审核
</div>

进行并行构建时，你就成了经理。经理常犯的典型错误是：批准自己尚未检查过的工作。你需要遵循一个简单的循环：每次只处理一个任务：

<Steps>
  <Step title="测试任务成果">
    打开已完成的任务并试用其功能。像用户一样点击和操作。
  </Step>

  <Step title="应用">
    确认没有问题后，将更改应用到主应用。
  </Step>

  <Step title="更新下一个任务">
    在处理下一个已完成的任务之前，先更新该任务，使其与刚刚更改的版本同步。
  </Step>

  <Step title="重复">
    重复测试、应用和更新，直到所有任务都已纳入。
  </Step>
</Steps>

<Frame>
  <img src="/assets/mirror/task-review-apply-3ef379c7e976.png" alt="显示 Agent 工作日志、测试结果和应用更改按钮的任务审核界面" width="3456" height="1984" data-path="images/replitai/task-review-apply.png" />
</Frame>

绝对不要一次性全部批准。一次应用三个尚未审核的功能后，如果出了问题，你就得从三个可疑对象中排查。

<div id="section-5">
  ## 需要按顺序推进的情况
</div>

并行构建是一种工具，而非规则。遇到以下情况时，请在主对话中一次处理一项：

* **两个想法涉及同一界面时。** “重新设计主页”和“修改导航”会相互冲突。请按顺序进行。
* **处于探索阶段时。** 在设计过程中，一次尝试的结果会改变你接下来想做的事。探索是对话，而不是工作指令。
* **无法用一句话描述任务时。** 如果无法简明地表达出来，说明你还没准备好将其委派出去。

<div id="section-6">
  ## 找到自己的极限
</div>

决定并行构建上限的不是 Replit，而是你的注意力。每次切换任务都会消耗一点专注力，而每个人的注意力预算各不相同。

先从两个任务开始。如果你觉得审核起来轻松自如，再尝试三个任务。Agent 的构建能力已足够强，你无需监控每一步；对大多数构建者来说，速度提升足以弥补切换成本。不过，这不是一项启用即可生效的设置，而是一项需要通过练习掌握的技能。
