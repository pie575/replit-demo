Ce guide propose une liste de contrôle complète pour garantir que vos applications créées par vibe coding respectent les bonnes pratiques de sécurité.

Bien que Replit propose de nombreuses fonctionnalités de sécurité [par défaut](/fr/ko/features/security/overview), il est important de comprendre et de mettre en œuvre des mesures de sécurité supplémentaires adaptées aux exigences spécifiques de votre application.

<div id="section">
  ## Prérequis
</div>

* Un compte Replit
* Des connaissances de base dans le langage de programmation de votre choix
* Une bonne connaissance du Project Editor
* Une application en cours de développement sur Replit

<div id="section-2">
  ## Sécurité du front-end
</div>

<AccordionGroup>
  <Accordion title="Utiliser HTTPS partout" icon="lock">
    Replit utilise HTTPS par défaut pour toutes les applications. Vous n&#39;avez rien à craindre !
  </Accordion>

  <Accordion title="Valider et nettoyer les entrées" icon="shield-check">
    Pour prévenir les attaques par cross-site scripting (XSS), validez et nettoyez toujours les entrées utilisateur :

    ```javascript theme={null}
    // Mauvais exemple : utilisation directe de l'entrée utilisateur
    element.innerHTML = userInput;

    // Bon exemple : nettoyer l'entrée avant de l'utiliser
    import { sanitize } from 'some-sanitizer-library';
    element.innerHTML = sanitize(userInput);
    ```

    Demandez à Agent :

    ```
    Aidez-moi à valider et nettoyer les entrées afin de me protéger contre les attaques XSS
    ```
  </Accordion>

  <Accordion title="Ne pas exposer les données sensibles dans le navigateur" icon="eye-slash">
    Utilisez les secrets Replit pour stocker des informations sensibles telles que des clés API.

    Ne transmettez ni ne stockez de secrets aux emplacements suivants :

    * Stockage local
    * Stockage de session
    * JavaScript côté client
    * Cookies sans attributs de sécurité appropriés

    Demandez à Agent :

    ```
    Aidez-moi à ne pas exposer les données sensibles dans le navigateur. Est-ce que je m'y prends correctement ?
    ```
  </Accordion>

  <Accordion title="protection contre les CSRF" icon="shield">
    Mettez en place une protection contre les attaques de falsification de requête intersites (CSRF) dans vos formulaires :

    ```javascript theme={null}
    // Exemple d'implémentation d'un jeton CSRF
    const csrfToken = generateToken();
    session.csrfToken = csrfToken;
    ```

    Demandez à Agent :

    ```
    Aidez-moi à implémenter des jetons CSRF dans mes formulaires
    ```
  </Accordion>
</AccordionGroup>

<div id="section-3">
  ## Sécurité du backend
</div>

<AccordionGroup>
  <Accordion title="Principes de base de l’authentification" icon="key">
    Lors de la mise en place de l’authentification :

    * Utilisez Replit Auth lorsque c’est possible
    * Si vous mettez en place une authentification personnalisée, utilisez des bibliothèques éprouvées
    * Ne stockez jamais les mots de passe en clair

    Demandez à Agent :

    ```
    Aidez-moi à mettre en place l’authentification de mon application avec Replit Auth
    ```
  </Accordion>

  <Accordion title="Vérification des autorisations" icon="user-lock">
    Vérifiez toujours les autorisations avant d’effectuer une action :

    ```javascript theme={null}
    // Exemple de vérification des autorisations
    if (!user.canAccess(resource)) {
      return res.status(403).send('Access denied');
    }
    ```

    Demandez à Agent :

    ```
    Aidez-moi à mettre en place des vérifications d’autorisation dans mon application
    ```
  </Accordion>

  <Accordion title="Protection des points de terminaison API" icon="shield">
    Sécurisez vos points de terminaison API :

    * Ajoutez une authentification aux points de terminaison sensibles
    * Configurez correctement CORS
    * Envisagez de limiter le débit des requêtes

    Demandez à Agent :

    ```
    Comment authentifier correctement les points de terminaison de mon application ?
    ```
  </Accordion>

  <Accordion title="Prévention des injections SQL" icon="database">
    Agent utilise des ORM par défaut pour prévenir les injections SQL. Si vous écrivez des requêtes de base de données personnalisées :

    ```javascript theme={null}
    // Mauvais exemple : concaténation de chaînes dans une requête
    db.query(`SELECT * FROM users WHERE username = '${username}'`);

    // Bon exemple : requête paramétrée utilisant un ORM
    db.query('SELECT * FROM users WHERE username = ?', [username]);
    ```
  </Accordion>

  <Accordion title="En-têtes de sécurité" icon="code">
    Ajoutez des en-têtes de sécurité importants à votre application :

    ```html theme={null}
    <!-- Via index.html ou le backend -->
    <meta http-equiv="X-Frame-Options" content="DENY">
    <meta http-equiv="X-Content-Type-Options" content="nosniff">
    <meta http-equiv="Content-Security-Policy" content="default-src 'self'">
    ```

    Analysez votre site sur [securityheaders.com](https://securityheaders.com) pour obtenir des recommandations.

    Demandez à Agent :

    ```
    Pouvez-vous ajouter des en-têtes de sécurité à mon application ?
    ```
  </Accordion>
</AccordionGroup>

<div id="section-4">
  ## Bonnes pratiques de sécurité continues
</div>

<AccordionGroup>
  <Accordion title="Maintenir les dépendances à jour" icon="arrow-rotate-right">
    Vérifiez régulièrement les paquets obsolètes susceptibles de contenir des vulnérabilités :

    ```bash theme={null}
    npm audit
    ```
  </Accordion>

  <Accordion title="Gestion appropriée des erreurs" icon="exclamation">
    N&#39;exposez pas d&#39;informations sensibles dans les messages d&#39;erreur :

    ```javascript theme={null}
    // Mauvais exemple : exposition de détails sensibles
    catch (err) {
      res.status(500).send(`Database error: ${err.message}`);
    }

    // Bon exemple : message d'erreur générique
    catch (err) {
      console.error(err); // Journalisation en interne
      res.status(500).send('An error occurred');
    }
    ```

    Demandez à Agent :

    ```
    Aidez-moi à mettre en œuvre une gestion appropriée des erreurs dans mon application
    ```
  </Accordion>

  <Accordion title="Cookies sécurisés" icon="cookie">
    Lorsque vous utilisez des cookies :

    * Définissez l&#39;indicateur HttpOnly pour empêcher l&#39;accès via JavaScript
    * Utilisez l&#39;attribut Secure pour exiger HTTPS
    * Utilisez l&#39;attribut SameSite pour prévenir les attaques CSRF

    Demandez à Agent :

    ```
    Aidez-moi à sécuriser les cookies de mon application
    ```
  </Accordion>

  <Accordion title="Sécurité du téléversement de fichiers" icon="upload">
    Si votre application autorise le téléversement de fichiers :

    * Limitez les types et la taille des fichiers
    * Analysez les fichiers à la recherche de logiciels malveillants lorsque possible
    * Stockez les fichiers dans le stockage d&#39;objets de Replit
    * Générez de nouveaux noms de fichiers au lieu d&#39;utiliser les noms fournis par les utilisateurs

    Demandez à Agent :

    ```
    Aidez-moi à sécuriser les téléversements de fichiers de mon application
    ```
  </Accordion>

  <Accordion title="Limitation du débit" icon="clock">
    Mettez en œuvre une limitation du débit, en particulier pour les points de terminaison d&#39;API liés à l&#39;authentification :

    ```javascript theme={null}
    // Exemple de middleware de limitation du débit
    const rateLimit = require('express-rate-limit');

    const limiter = rateLimit({
      windowMs: 15 * 60 * 1000, // 15 minutes
      max: 100 // Limite chaque IP à 100 requêtes par windowMs
    });

    app.use('/api/', limiter);
    ```

    Demandez à Agent :

    ```
    Aidez-moi à mettre en œuvre une limitation du débit dans mon application
    ```
  </Accordion>
</AccordionGroup>

<div id="section-5">
  ## Liste de contrôle
</div>

Nous avons résumé les éléments ci-dessus sous forme de liste de contrôle pour vous aider à adopter de bonnes pratiques de sécurité.

<div id="section-6">
  ## Sécurité du front-end
</div>

|   | Mesure de sécurité                                     | Description                                                                                    |
| - | ------------------------------------------------------ | ---------------------------------------------------------------------------------------------- |
| ☐ | Utiliser HTTPS partout                                 | Prévenir l&#39;écoute clandestine et les attaques de l&#39;homme du milieu                     |
| ☐ | Valider et nettoyer les entrées                        | Valider toutes les entrées utilisateur pour prévenir les attaques XSS                          |
| ☐ | Ne pas stocker de données sensibles dans le navigateur | Aucun secret dans le stockage local ou le code côté client                                     |
| ☐ | Protection contre les CSRF                             | Mettre en œuvre des jetons anti-CSRF pour les formulaires et les requêtes modifiant l&#39;état |
| ☐ | Ne pas exposer les clés API dans le front-end          | Toujours conserver les identifiants API côté serveur                                           |

<div id="section-7">
  ## Sécurité du backend
</div>

|   | Mesure de sécurité                       | Description                                                                                       |
| - | ---------------------------------------- | ------------------------------------------------------------------------------------------------- |
| ☐ | Principes de base de l’authentification  | Utiliser des bibliothèques éprouvées et stocker correctement les mots de passe (hachage + salage) |
| ☐ | Vérification des autorisations           | Toujours vérifier les autorisations avant d’effectuer une opération                               |
| ☐ | Protection des points de terminaison API | Mettre en place une authentification appropriée pour tous les points de terminaison API           |
| ☐ | Prévention des injections SQL            | Utiliser des requêtes paramétrées ou un ORM ; interdire le SQL brut avec des entrées utilisateur  |
| ☐ | En-têtes de sécurité de base             | Mettre en place X-Frame-Options, X-Content-Type-Options et HSTS                                   |
| ☐ | Protection contre les attaques DDoS      | Utiliser un CDN ou un service cloud doté de fonctionnalités d’atténuation des attaques DDoS       |

<div id="section-8">
  ## Bonnes pratiques de sécurité
</div>

|   | Mesure de sécurité                     | Description                                                                                               |
| - | -------------------------------------- | --------------------------------------------------------------------------------------------------------- |
| ☐ | Maintenir les dépendances à jour       | La plupart des vulnérabilités proviennent de bibliothèques obsolètes                                      |
| ☐ | Gestion appropriée des erreurs         | Ne pas exposer d’informations sensibles dans les messages d’erreur                                        |
| ☐ | Cookies sécurisés                      | Configurer les attributs HttpOnly, Secure et SameSite                                                     |
| ☐ | sécurité du téléversement de fichiers | Valider le type et la taille des fichiers, et analyser les contenus malveillants                          |
| ☐ | Limitation du débit                    | À mettre en place sur tous les points de terminaison d’API, en particulier ceux liés à l’authentification |
