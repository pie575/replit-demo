Publishing은 project를 공개 앱으로 전환하는 기능입니다. publishing이 실패하거나 public URL이 Preview와 다르게 동작한다면, 아래 순서대로 문제를 짚어 나가세요.

이 페이지는 Build 복구 가이드이자 deployment 문제 해결 참고 자료입니다. 가장 단순한 질문부터 시작해 보세요. 앱이 Preview에서는 정상적으로 작동하나요?

<div id="what-youll-achieve">
  ## 이 페이지에서 얻을 수 있는 것
</div>

이 페이지를 끝까지 읽고 나면 문제의 원인이 앱, Publishing 설정, production Secrets, deployment type, 포트 config, 네트워크/DNS 접근 중 어디에 있는지 판단할 수 있습니다.

<div id="start-with-preview">
  ## Preview부터 시작하기
</div>

publishing 전에 Project Editor에서 앱이 제대로 실행되는지 확인하세요.

Project Editor 상단의 **Run**을 선택한 후 Preview를 엽니다. Preview에 `replit.dev` URL로 앱이 표시되지 않으면 publishing 전에 앱을 먼저 수정하세요.

Agent에게 Preview 문제부터 진단해 달라고 요청해 보세요.

<AiPrompt>
  이 앱이 Preview에서 동작하지 않습니다.<br />
  run command, dependency 설치, 앱 오류, 포트, 누락된 Secrets를 확인해 주세요.<br />
  가장 사소한 문제부터 수정하고, publishing 전에 Preview가 정상 동작하는지 확인하는 방법을 알려주세요.
</AiPrompt>

Preview가 정상 동작하지 않는 상태라면 publishing한다고 해서 해결되지 않습니다.

<div id="if-preview-works-but-publishing-fails">
  ## Preview는 정상 작동하지만 게시에 실패하는 경우
</div>

Preview는 정상적으로 작동하는데 게시에 실패한다면 게시 관련 설정을 확인하세요.

<div id="check-logs">
  ### 로그 확인
</div>

**Publishing** pane에서 **Logs** tab을 엽니다. 스택 트레이스, 누락된 packages, 실패한 명령, 누락된 environment variables, 시작 오류가 있는지 살펴보세요.

관련 오류 내용을 Agent에 붙여넣으세요:

<AiPrompt>
  다음과 같은 로그 출력과 함께 publishing이 실패했습니다: [오류 붙여넣기].<br />
  예상되는 원인을 설명해 주세요.<br />
  이것이 명령, dependency, Secret, 포트, build, 앱 중 어떤 오류인지 알려주세요.<br />
  가장 간단한 해결 방법과 이를 검증하는 방법을 알려주세요.
</AiPrompt>

<div id="check-run-and-build-commands">
  ### 실행 및 빌드 명령어 확인
</div>

오타, 잘못된 플래그, 잘못된 진입 파일, 로컬에서만 작동하는 명령어 등이 흔한 실수입니다.

**Publishing** 창에서 명령어를 검토하세요. 앱에 빌드 명령어와 시작 명령어가 모두 필요하다면, 두 명령어가 모두 올바른지 확인하세요.

<div id="check-production-secrets">
  ### production Secrets 확인
</div>

Project Editor에서 설정한 Secrets는 published app에 자동으로 적용되지 않습니다. **Publishing** pane에서 production에 필요한 Secrets와 environment variables를 모두 추가하세요.

Secrets가 누락되면 값이 정의되지 않았다는 오류, API 호출 실패, database 연결 실패, login 오류, 결제 실패 등이 발생할 수 있습니다.

자세한 내용은 [Secrets](/ko/core-concepts/project-editor/app-setup/secrets)를 참고하세요.

<div id="check-long-running-process-behavior">
  ### 장시간 실행 프로세스 동작 확인
</div>

게시된 앱은 프로그램이 계속 실행되는 것을 전제로 합니다. 프로그램이 한 번 실행된 후 종료되면 플랫폼이 자동으로 다시 시작합니다.

애플리케이션이 웹 서버와 같은 장시간 실행 프로세스를 시작하는지 확인하세요.

<div id="check-host-and-port-configuration">
  ### 호스트 및 포트 구성 확인
</div>

웹 서버를 실행 중이라면 Deployments가 서버에서 사용하는 포트를 자동으로 감지할 수 있지만, 서버는 반드시 `0.0.0.0`에서 수신 대기해야 합니다. `localhost` 또는 `127.0.0.1`에서만 수신 대기하면 published app에서는 동작하지 않습니다.

[`.replit` config에 포트를 지정](/ko/features/project-setup/configuration)한 경우에는 자동 포트 감지가 비활성화됩니다. 승격 단계를 통과하려면 `externalPort`가 `80`으로 설정된 포트를 지정해야 합니다. 서버가 지정한 `localPort`에서 수신 대기하는지 확인하세요.

Agent에게 다음과 같이 꼼꼼히 확인해 달라고 요청하세요.

<AiPrompt>
  이 앱이 publishing에 맞게 올바르게 구성되어 있는지 확인해 줘.<br />
  서버가 장시간 실행되는 프로세스를 시작하는지, 0.0.0.0에서 수신 대기하는지, 예상한 포트를 사용하는지, .replit 포트 구성과 일치하는지 검증해 줘.<br />
  publishing 수정에 필요한 범위를 넘어서 앱 동작을 변경하지는 마.
</AiPrompt>

<div id="check-health-check-timing">
  ### 헬스 체크 시간 확인
</div>

Replit은 published app을 라이브 상태로 표시하기 전에 앱에 HTTP 요청을 보냅니다. 홈페이지 응답에 5초 이상 걸리면 헬스 체크가 시간 초과되어 마지막 단계에서 publishing이 실패할 수 있습니다.

시작이 느리다면 Agent에게 시작 시 수행하는 작업을 줄이거나, 부담이 큰 작업을 사용자 동작 이후로 미루거나, 필요한 경우 데이터를 cache하도록 요청하세요.

<div id="if-publishing-succeeds-but-the-public-url-is-broken">
  ## Publishing은 성공했지만 public URL이 작동하지 않는 경우
</div>

Preview에서는 정상 작동하고 publishing도 성공했는데 public URL이 작동하지 않는다면, Preview와 production의 동작을 비교해 보세요.

확인할 항목:

* Production Secrets 및 environment variables
* Database 연결 설정
* Login 콜백 또는 리디렉션 URL
* 결제 webhook 또는 리디렉션 설정
* API 허용 목록 또는 CORS 설정
* database나 스토리지 서비스에 저장하지 않고 로컬에 기록한 파일
* 모바일 layout 및 브라우저 차이

Agent에게 environments 비교를 요청해 보세요:

<AiPrompt>
  앱이 Preview에서는 작동하지만 게시된 URL에서는 작동하지 않습니다.<br />
  Preview와 production의 동작을 비교하도록 도와주세요.<br />
  Secrets, database 설정, API 호출, login 리디렉션, 결제 리디렉션, 빌드 출력, logs를 확인해 주세요.<br />
  가장 안전한 다음 확인 단계를 알려주세요.
</AiPrompt>

<div id="static-deployment-issues">
  ## Static deployment 문제
</div>

Static Deployments는 HTML, CSS, JavaScript 같은 정적 파일을 제공합니다.

앱에 서버 측 동작, API 라우트, authentication 콜백, 서버에서 실행되는 database 호출, 장시간 실행되는 backend 로직이 포함되어 있다면 Static Deployments에는 적합하지 않을 수 있습니다. 이런 경우에는 **Publishing** pane에서 deployment type을 Autoscale로 변경하세요.

Static deployment 문제는 public 디렉터리를 잘못 지정했거나, 서버가 필요한 앱에 Static을 선택한 경우에 주로 발생합니다.

<div id="file-and-size-limits">
  ## 파일 및 용량 제한
</div>

Reserved VM과 Autoscale Deployments는 최대 8GB 크기의 Replit App을 지원하며, Static Deployments는 최대 1GB까지 지원합니다.

앱 용량을 줄이려면 불필요한 파일을 삭제하고, 생성된 출력물은 커밋하지 말고, 대용량 asset은 외부 스토리지에 보관하세요.

<Warning>
  published app의 파일 시스템은 영구적으로 유지되지 않으며 publish할 때마다 초기화됩니다. 데이터를 영구적으로 보관하려면 [SQL Database](/ko/features/data-and-storage/sql-database)와 같은 database를 사용하세요.
</Warning>

업로드한 파일이나 생성된 데이터가 publish 후 사라진다면, 앱 파일 시스템 대신 database나 스토리지 서비스에 저장하세요.

<div id="access-issues-with-replitapp-and-replitdev-urls">
  ## `replit.app` 및 `replit.dev` URL 접속 문제
</div>

`replit.app` 또는 `replit.dev` 도메인으로 앱에 접속하는 데 문제가 있다면 웹 필터나 네트워크 제한이 원인일 수 있습니다.

Google DNS(`8.8.8.8`)나 Cloudflare DNS(`1.1.1.1`) 같은 공용 DNS 리졸버를 사용해 보세요.

<div id="change-dns-settings">
  ### DNS 설정 변경
</div>

<Tabs>
  <Tab title="Windows">
    1. **제어판**을 엽니다.
    2. **네트워크 및 공유 센터**로 이동합니다.
    3. 왼쪽에서 **어댑터 설정 변경**을 선택합니다.
    4. 사용 중인 네트워크 연결을 마우스 오른쪽 버튼으로 클릭하고 **속성**을 선택합니다.
    5. **인터넷 프로토콜 버전 4(TCP/IPv4)**를 선택한 다음 **속성**을 선택합니다.
    6. **다음 DNS 서버 주소 사용**을 선택합니다.
    7. Google DNS의 `8.8.8.8` 또는 Cloudflare DNS의 `1.1.1.1`과 같은 공용 DNS 서버 IP 주소를 입력합니다.
    8. **확인**을 선택해 변경 사항을 저장합니다.

    자세한 안내는 [Microsoft DNS 구성 가이드](https://support.microsoft.com/en-us/windows/change-tcp-ip-settings-bd0a07af-15f5-cd6a-363f-ca2b6f391ace)를 참고하세요.
  </Tab>

  <Tab title="macOS">
    1. **시스템 환경설정**을 엽니다.
    2. **네트워크**를 선택합니다.
    3. 왼쪽에서 사용 중인 네트워크 연결을 선택합니다.
    4. 오른쪽 아래에서 **고급**을 선택합니다.
    5. **DNS** 탭으로 이동합니다.
    6. **+** 버튼을 선택해 DNS 서버를 추가합니다.
    7. Google DNS의 `8.8.8.8` 또는 Cloudflare DNS의 `1.1.1.1`과 같은 공용 DNS 서버 IP 주소를 입력합니다.
    8. **확인**을 선택한 다음 **적용**을 선택합니다.

    자세한 안내는 [Apple DNS 구성 가이드](https://support.apple.com/guide/mac-help/change-dns-settings-on-mac-mh14127/mac)를 참고하세요.
  </Tab>

  <Tab title="Linux">
    1. `/etc/resolv.conf` 파일을 편집해 공용 DNS 서버를 추가합니다. 구체적인 방법은 배포판에 따라 다릅니다.
    2. 다음 줄을 추가합니다.

    ```bash theme={null}
    nameserver 8.8.8.8
    nameserver 1.1.1.1
    ```

    배포판별 DNS 구성 방법에 대한 자세한 내용은 [Debian Wiki 네트워크 구성 가이드](https://wiki.debian.org/NetworkConfiguration#Defining_the_.28DNS.29_Nameservers)를 참고하세요.
  </Tab>
</Tabs>

<div id="clear-dns-cache">
  ### DNS 캐시 지우기
</div>

DNS 설정을 변경한 후에는 새 구성을 적용하기 위해 DNS 캐시를 지우세요.

* **Windows**: 명령 프롬프트에서 `ipconfig /flushdns`를 실행합니다.
* **macOS 및 Linux**: 터미널에서 `sudo systemctl restart NetworkManager`를 실행합니다. 정확한 명령어는 배포판에 따라 다를 수 있습니다.

<Note>
  지역별 성능과 안정성을 높이기 위해 Replit Apps의 `replit.dev` URL은 클러스터
  마이그레이션 과정에서 간혹 변경될 수 있습니다. 마이그레이션이 완료되면 위치 변경을
  명시적으로 요청하지 않는 한 URL은 약 1년 동안 그대로 유지됩니다.
</Note>

<div id="publish-a-streamlit-application">
  ## Streamlit 애플리케이션 게시하기
</div>

Streamlit 애플리케이션은 Replit Deployments에서 사용할 수 있습니다. 가장 쉽게 시작하는 방법은 [Streamlit 템플릿](https://replit.com/@replit/Streamlit?v=1)을 사용하는 것입니다.

또는 게시에 사용할 실행 명령을 다음과 같이 설정하세요:

```bash theme={null}
streamlit run --server.address 0.0.0.0 --server.headless true --server.enableCORS=false --server.enableWebsocketCompression=false main.py
```

애플리케이션에서 다른 진입 파일을 사용하는 경우 `main.py`를 해당 파일 이름으로 바꾸세요.

<div id="youre-done-when">
  ## 완료 기준
</div>

* Preview가 정상적으로 작동합니다.
* Publishing이 완료됩니다.
* public URL이 정상적으로 열립니다.
* public URL에서 앱의 주요 flow가 작동합니다.
* Production Secrets와 설정이 모두 구성되어 있습니다.
* logs에 드러나지 않은 시작 오류가 없습니다.
