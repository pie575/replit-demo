氛围编程是一种把想法快速变成软件的方式。你不必从写代码开始，而是先描述你想要什么，再借助 AI 把这个方向具象化，变成一个可以测试和改进的可运行应用。

Replit 正是为这个循环而生。你可以描述想法、预览结果、给出反馈、进行修改，并在同一个地方发布。

本页介绍氛围编程背后的理念。下一页[使用 Agent 构建](/zh/ja/learn/build-with-agent)将介绍如何使用 Agent 的各项工具，[高效提示](/zh/ja/learn/effective-prompting)则会介绍如何写出更清晰的指令。

<div id="section">
  ## 软件曾经是一个团队循环
</div>

软件通常由团队来构建。

产品经理或创始人定义要做什么、为什么做。设计师塑造体验。开发者把想法变成可运行的软件。团队成员负责测试、给出反馈、发现缺陷，并判断哪些内容已经可以发布。

这种协作之所以强大，是因为每个角色带来的判断力各不相同：产品决定什么才重要，设计决定它该给人什么感受，工程决定它该如何运作，测试则验证它是否真的做到了。

但这个循环往往很慢。每一次改动都要经过层层交接：讲清想法、设计流程、编写代码、评审结果、测试并修改。

氛围编程压缩了这个循环。

有了 Replit，你可以独自推进产品构建流程中更多的环节：定义目标、生成第一个版本、测试、给出反馈并加以改进，无需等待每一步在不同的人和工具之间来回流转。

<div id="section-2">
  ## 你的角色将发生转变
</div>

无需成为开发者，也能开始构建。

在氛围编程 (vibe coding) 中，你的角色更接近产品负责人：由你决定该做什么、为谁而做、什么最重要，以及结果是否足够好。

Agent 负责协助实现，但主导工作的是你。

你带来的是：

* 目标
* 受众
* 品味
* 约束条件
* 反馈
* 决定发布什么

Agent 提供的支持：

* 把想法变成可运行的软件
* 进行修改
* 讲解运行原理
* 调试问题
* 让应用持续迭代改进

你主导得越好，Agent 就能构建得越好。

<div id="5">
  ## 五项原则
</div>

氛围编程 (vibe coding) 遵循以下五项简单原则时效果最佳：

1. 从目标出发。
2. 小步快跑，分片构建。
3. 管理好上下文。
4. 审查并测试。
5. 根据反馈迭代改进。

第一条原则确定方向，其余四条构成一个循环：构建一个切片，提供合适的上下文，进行审查，加以改进，然后构建下一个切片。

这些原则比写出完美的第一条提示词更重要。最终的应用几乎不可能一步到位,目标是让这个循环清晰、持续地运转下去。

<div id="section-3">
  ## 从目标出发
</div>

一次好的氛围编程 (vibe coding) 会话，开场就像一场出色的产品讨论：

为谁而做？它应该能做什么？是什么让它变得有用？

在让 Replit 动手构建之前，先描述你想要的结果。

<AiPrompt>
  请为一家本地面包店搭建一个简洁的网站。让顾客可以查看今日特色、了解餐饮服务，并提交餐饮服务需求。整体风格要温暖、精致，并且在移动端易于使用。
</AiPrompt>

这样做之所以有效，是因为你给 Replit 的不只是一项任务，而是一个产品目标。你描述清楚了受众、核心操作，以及第一个版本应有的调性。

此时你还不需要知道技术实现细节。先想清楚&quot;应用跑起来之后，什么应该成立&quot;。

<div id="section-4">
  ## 以小切片方式构建
</div>

切片是指产品中足够完整、可以拿来试用的一小部分。

以面包店网站为例，第一个切片可能包括：

* 展示今日特惠的主页
* 餐饮服务预订表单
* 适配移动端的布局

这些已经足以验证你的想法。你可以打开页面、点击试用，再决定接下来改进什么。

不要一次性要求做出整个产品。请求越大，越难审查，也越容易被误解。小切片能让你在不失去掌控的前提下稳步推进。

第一个切片跑通后，再添加下一个切片。

<AiPrompt>
  请在提交餐饮服务预订表单后添加一条确认信息。页面的其余部分请勿改动。
</AiPrompt>

这条指令简短、明确，而且可以测试。

<div id="section-5">
  ## 管理上下文
</div>

上下文就是 Replit 用来理解你需求的信息。

好的上下文包括：

* 应用面向谁
* 解决什么问题
* 现在应该包含什么
* 什么可以稍后再做
* 什么不要改动
* 示例、截图、草图、文件或数据
* 关于语气、风格或品牌的说明

管理上下文，就是在合适的时机提供合适的信息。

如果你还在做同一个功能，就留在同一个对话里，这样 Replit 能沿用之前的决定。如果你要开始另一个功能，或者对话已经变得杂乱，不妨用一段简短的要点摘要重新开始。

例如：

<AiPrompt>
  上下文：这个面包店网站面向订购生日蛋糕的忙碌家长。请让表单简短、取货信息清晰易懂，并避免任何显得过于企业化的内容。本次改动只需改进餐饮预订请求部分。
</AiPrompt>

你不只是在堆砌文字，而是在帮助 Replit 聚焦。

<div id="section-6">
  ## 审查与测试
</div>

Agent 可以帮你构建，但结果是否可用，由你来判断。

每次有实质性改动后，都要打开应用，以目标用户的身份实际用一遍。不要只看 Agent 说自己改了什么，要亲自走一遍流程。

问问自己：

* 别人能否顺利完成主要操作？
* 页面内容是否讲得通？
* 在移动端能否正常使用？
* 有没有重要功能被弄坏？
* Replit 是否改动了本不该动的地方？
* 目前的成果是否足以支撑继续往下构建？

审查与测试正是最考验你产品判断力的环节。你要确认的是:这个软件是否符合你的本意。

<div id="section-7">
  ## 通过反馈不断改进
</div>

切片的第一个版本只是草稿，这很正常。

氛围编程靠反馈来打磨。告诉 Replit 保留什么、修改什么、删除什么，以及接下来尝试什么。

不要使用以下提示词：

<AiPrompt>
  请做得更好一些。
</AiPrompt>

不妨试试这样：

<AiPrompt>
  请让餐饮服务预订表单更易于快速浏览。保持字段不变，改进间距、标签和提交按钮。不要改动特色菜区域。
</AiPrompt>

好的反馈是具体的：在保护已经正常运作的部分的同时，只改进应用的某一处。

某个切片跑通后，就回到循环中，继续构建下一个小切片。

如果某次改动走偏了，就把范围收窄。

<AiPrompt>
  改动太多了。保留新的按钮样式，但恢复原来的布局，只更新餐饮表单。
</AiPrompt>

通过反馈不断改进，能让你在不失去掌控的前提下持续推进产品。

<div id="section-8">
  ## 良好氛围编程的感觉
</div>

出现以下情况时，说明你走在正确的方向上：

* 你能用平实的语言讲清目标
* 每次变更都足够小，便于审查
* 你知道 Agent 构建完成后该测试什么
* 你会主动提供上下文，而不是猜测 Agent 知道些什么
* 你不仅告诉 Agent 要改什么，也告诉它要保留什么
* 应用每迭代一轮就更好用一分

氛围编程并不是抛出一个想法就撒手不管，而是拉近想法、软件、反馈与改进之间的距离。
