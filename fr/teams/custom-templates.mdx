<div id="getting-started">
  ## Premiers pas
</div>

Replit est un environnement de développement cloud capable d&#39;écrire et d&#39;exécuter n&#39;importe quel framework ou stack. Pour créer un template personnalisé, deux approches sont recommandées :

1. **[Importer](https://replit.com/import) depuis un fournisseur Git** — Importez votre stack de départ existante (ou celle qui correspond à vos préférences) depuis GitHub, GitLab ou Bitbucket.
2. **Forker le template Blank** — Forkez le [template Blank](https://replit.com/@replit/Nothing?v=1) pour partir de zéro avec un environnement de développement entièrement vide.

Des clients ont créé avec succès des templates pour Rust, Python, Java, C++ et bien d&#39;autres stacks : si cela peut s&#39;exécuter, cela peut s&#39;exécuter sur Replit.

<Tip>
  Nous vous recommandons de travailler avec l&#39;**équipe Field Engineering** de Replit lors de la création de vos premiers templates. Elle possède une vaste expérience de la configuration de templates personnalisés pour un large éventail de stacks et peut vous aider. Contactez votre responsable de compte pour être mis en relation.
</Tip>

Les templates personnalisés permettent aux administrateurs Enterprise de créer des points de départ préconfigurés qui apparaissent directement dans la zone de saisie d’Agent pour chaque membre de votre organisation. Lorsqu&#39;un créateur sélectionne un template personnalisé, Agent le fork et utilise sa configuration, ses instructions et ses compétences pour guider tous les travaux ultérieurs. Aucune configuration supplémentaire n&#39;est nécessaire.

<Note>
  Les templates personnalisés sont disponibles exclusivement avec le forfait **Enterprise**. Seuls les administrateurs de l&#39;organisation peuvent épingler et gérer des templates.
</Note>

<div id="how-custom-templates-work">
  ## Fonctionnement des templates personnalisés
</div>

Un template personnalisé est une Replit App standard de votre organisation **épinglée à la zone de saisie d’Agent**. Lorsqu’un créateur le sélectionne :

1. Agent crée une nouvelle app en dupliquant le template (tous les fichiers sont copiés)
2. Agent ignore l’étape de planification et passe directement à la création
3. Le fichier `custom_instruction/instructions.md` du template est injecté dans le contexte d’Agent
4. Les [compétences](/fr/features/agent/skills) personnalisées de `.agents/skills/` sont détectées et mises à disposition
5. Le fichier [`replit.md`](/fr/features/project-setup/replit-dot-md) fournit un contexte continu pour le projet

Ainsi, les normes, modèles et outils de votre organisation sont intégrés dès la première interaction.

<div id="template-file-structure">
  ## Structure des fichiers d’un template
</div>

Voici la structure recommandée pour un template personnalisé :

```
my-template/
├── .replit                              # Configuration de l’App (commandes d’exécution, ports, modules)
├── replit.md                            # Mémoire d’Agent : aperçu et préférences du projet
├── custom_instruction/
│   └── instructions.md                  # Instructions de l’entreprise injectées dans le prompt d’Agent
├── .agents/
│   └── skills/
│       └── my-skill/
│           └── SKILL.md                 # Compétences personnalisées qu’Agent peut utiliser à la demande
└── ...                                  # Le reste de la structure de votre dépôt
```

Chaque fichier a un rôle distinct. Les sections ci-dessous expliquent comment configurer chacun d’eux.

<div id="set-up-a-custom-template">
  ## Configurer un template personnalisé
</div>

<div id="create-the-base-app">
  ### Créer l’application de base
</div>

Créez une Replit App dans votre organisation. Configurez le projet avec tous les fichiers, dépendances et paramètres dont vos créateurs ont besoin pour démarrer. Cela comprend :

* Squelette du code source (composants, utilitaires, fichiers de configuration)
* Dépendances préinstallées (`package.json`, `requirements.txt`, etc.)
* Configuration de l’environnement dans le [fichier `.replit`](/fr/replit-app/configuration)

<div id="configure-shared-secrets">
  ### Configurer les Secrets partagés
</div>

Si votre template utilise des clés API, des jetons ou d&#39;autres identifiants, ajoutez-les aux **Secrets** du template (dans le volet Tools) avant de l&#39;épingler. Lorsqu&#39;un créateur crée une nouvelle app à partir du template, tous les secrets sont automatiquement copiés dans celle-ci, ce qui lui permet de commencer à travailler sans avoir à configurer lui-même les identifiants.

Documentez chaque secret dans `custom_instruction/instructions.md` (ou dans une compétence dédiée) afin que les créateurs sachent ce qui est disponible et à quoi sert chaque clé.

<Warning>
  Les Secrets sont copiés au moment du fork et ne sont pas synchronisés dynamiquement. Si vous renouvelez une clé ou ajoutez un nouveau secret au template, les apps existantes précédemment forkées ne sont pas mises à jour. Les créateurs doivent ajouter ou mettre à jour manuellement les secrets dans ces apps.
</Warning>

<div id="write-custom-instructions">
  ### Rédiger des instructions personnalisées
</div>

Créez un fichier à l’emplacement `custom_instruction/instructions.md`, à la racine du projet. Il s’agit du fichier le plus important de votre template : il indique à Agent comment votre organisation développe ses logiciels.

<Warning>
  Le nom du dossier doit être `custom_instruction` (au singulier), et non `custom_instructions`.
</Warning>

Agent injecte ce fichier directement dans son prompt système, précédé d’un préambule qui le présente comme des directives fournies par l’entreprise. Rédigez-le en Markdown et incluez :

* **Modèles d’architecture** : Structure à adopter pour vos applications
* **Normes de codage** : Conventions de nommage, règles d’organisation des fichiers et exigences de linting
* **Utilisation des composants** : Bibliothèques et composants à utiliser (et à éviter)
* **Modèles d’API** : Méthodes d’appel de vos services backend, gestion de l’authentification et des erreurs
* **Exigences de test** : Tests attendus et manière de les exécuter
* **Consignes de déploiement** : Configuration propre à chaque environnement et workflows de déploiement

````markdown theme={null}
# Company Engineering Standards

## Architecture
All web applications use React with TypeScript. Use functional components
with hooks exclusively. State management uses Zustand for local state
and React Query for server state.

## Component Library
Use our internal design system package `@acme/ui`. Never use raw HTML
elements for buttons, inputs, forms, or modals — always use the
corresponding component from `@acme/ui`.

Import components like this:
```tsx
import { Button, TextField, Modal } from '@acme/ui';
```

## API Integration
All API calls go through the `@acme/api-client` package. Never use
raw fetch or axios directly. Authentication is handled automatically
by the client.

## Testing
Every component must have a corresponding test file. Use Vitest
for unit tests and Playwright for integration tests.
````

**Limite de taille** : le contenu est soumis à une limite souple d’environ 25 Ko. Au-delà de cette limite, il peut être progressivement tronqué. À mesure que vos instructions s’allongent, placez la documentation de référence détaillée dans les [compétences](/fr/features/agent/skills) de `.agents/skills/` plutôt que de tout conserver dans `instructions.md`. Les compétences sont chargées à la demande lorsqu’elles sont pertinentes ; elles ne sont donc pas prises en compte dans la limite de taille des instructions et permettent de garder vos instructions principales axées sur des règles générales.

<div id="add-custom-skills">
  ### Ajouter des compétences personnalisées
</div>

Créez des compétences dans le répertoire `.agents/skills/` pour les workflows spécialisés qu’Agent doit suivre. Chaque compétence est un répertoire contenant un fichier `SKILL.md` avec un en-tête YAML.

```
.agents/skills/
├── use-design-system/
│   └── SKILL.md
├── api-integration/
│   └── SKILL.md
└── run-tests/
    └── SKILL.md
```

Chaque `SKILL.md` doit inclure un `name` et une `description` dans son frontmatter :

```markdown theme={null}
---
name: use-design-system
description: Use when building UI components. Provides component patterns, theming rules, and accessibility requirements for the Acme design system.
---

# Acme Design System

## Available components

- `Button` — Primary, secondary, and ghost variants
- `TextField` — Text input with validation support
- `Modal` — Dialog overlay with focus trapping
...
```

| Champ         | Obligatoire | Détails                                                                                          |
| ------------- | ----------- | ------------------------------------------------------------------------------------------------ |
| `name`        | Oui         | 64 caractères maximum. Lettres minuscules, chiffres et traits d’union uniquement.                |
| `description` | Oui         | 1 024 caractères maximum. Décrit le rôle de la compétence et quand l’utiliser.                   |
| `enabled`     | Non         | La valeur par défaut est `true`. Définissez-la sur `false` pour la désactiver sans la supprimer. |

**Chargement des compétences** : Agent ne voit que le `name` et la `description` dans son prompt. Il lit l’intégralité du contenu de `SKILL.md` à la demande lorsque la compétence est pertinente pour la tâche en cours. La `description` est donc essentielle : rédigez-la de façon à ce qu’elle corresponde aux cas où Agent doit utiliser la compétence.

Les compétences peuvent également inclure des fichiers complémentaires à côté de `SKILL.md` :

```
.agents/skills/use-design-system/
├── SKILL.md
├── references/
│   └── component-api.md
└── assets/
    └── theme-tokens.json
```

Pour en savoir plus sur les compétences, consultez [Compétences Agent](/fr/features/agent/skills) et [Utiliser une compétence](/fr/build/use-agent-skills).

<div id="configure-replitmd">
  ### Configurez replit.md
</div>

Préremplissez `replit.md` à la racine du projet avec une présentation de l’architecture de votre template. Ce fichier est toujours chargé dans le contexte d’Agent et sert de mémoire du projet.

Le fichier doit comporter les quatre sections suivantes :

```markdown theme={null}
# Vue d’ensemble
Application de gestion de tâches développée avec React, TypeScript et le système
de design Acme. Utilise un backend Express.js avec PostgreSQL.

# Préférences utilisateur
- Utiliser TypeScript pour tous les fichiers
- Privilégier les composants fonctionnels avec des hooks
- Respecter les normes de codage Acme

# Architecture système
- Frontend : React + TypeScript + @acme/ui
- Backend : Express.js + TypeScript
- Base de données : PostgreSQL avec Drizzle ORM
- Auth : Acme SSO via @acme/auth

# Dépendances externes
- @acme/ui : Système de design interne
- @acme/api-client : Couche d’intégration d’API
- @acme/auth : SDK d’authentification
```

Agent met à jour `replit.md` au fur et à mesure que le projet évolue. Si le fichier dépasse environ 4 000 jetons, Agent le résume automatiquement pour qu’il reste concis et utile.

Pour en savoir plus, consultez [replit.md](/fr/features/project-setup/replit-dot-md).

<div id="pin-the-template-to-your-organization">
  ### Épinglez le template à votre organisation
</div>

Une fois votre template prêt :

1. Accédez à l’App de template de votre organisation.
2. Ouvrez le menu d’actions de l’App (menu à trois points).
3. Sélectionnez **Épingler à la zone de saisie de l’Agent**.

<img src="/assets/mirror/custom-templates-pin-to-agent-b733d3eb9a80.png" alt="Menu d’actions de l’App affichant l’option Épingler à la zone de saisie de l’Agent" width="984" height="856" data-path="images/teams/custom-templates-pin-to-agent.png" />

<Note>
  Seuls les administrateurs de l’organisation (membres du rôle `system_admins`) peuvent épingler ou désépingler des templates.
</Note>

Définissez l’accès des membres sur **Lecture seule** afin qu’ils puissent voir et utiliser le template épinglé sans pouvoir le modifier.

<img src="/assets/mirror/custom-templates-members-read-only-cf6aa160c8ef.png" alt="Boîte de dialogue d’invitation indiquant que l’accès des membres est défini sur Lecture seule" width="954" height="1064" data-path="images/teams/custom-templates-members-read-only.png" />

Le template apparaît désormais sous la forme d’une pastille sélectionnable sous la zone de saisie de l’Agent pour tous les membres de votre organisation. Pour le retirer, ouvrez le même menu et sélectionnez **Désépingler de la zone de saisie de l’Agent**.

<div id="control-template-access">
  ### Contrôler l&#39;accès au template
</div>

L&#39;épinglage rend un template visible par tous les membres de l&#39;organisation. Pour une diffusion plus ciblée, utilisez le bouton **Inviter** de l&#39;App du template afin de le partager avec des [groupes ou des utilisateurs individuels](/fr/teams/identity-and-access-management/groups-and-permissions) spécifiques. Vous pouvez ainsi limiter les équipes ou les personnes qui peuvent voir et dupliquer le template, tout en le laissant non épinglé dans le champ de saisie de l&#39;organisation.

<div id="what-happens-when-a-builder-selects-a-template">
  ## Ce qui se passe lorsqu’un créateur sélectionne un template
</div>

<img src="/assets/mirror/custom-templates-input-box-553384ac7dd0.png" alt="Template affiché sous forme de pastille sélectionnable dans la zone de saisie d’Agent" width="1746" height="726" data-path="images/teams/custom-templates-input-box.png" />

Lorsqu’un membre de l’organisation choisit un template épinglé dans la zone de saisie d’Agent :

1. **Fork** : une nouvelle app est créée en tant que copie du template, avec tous ses fichiers
2. **Ignorer la planification** : Agent ignore la conversation de planification initiale et passe directement en mode Build
3. **Charger les instructions** : `custom_instruction/instructions.md` est lu et injecté dans le prompt système d’Agent en tant que directives fournies par l’entreprise
4. **Découvrir les compétences** : les compétences présentes dans `.agents/skills/` sont identifiées et répertoriées dans le contexte d’Agent pour être chargées à la demande
5. **Charger le contexte du projet** : `replit.md` est lu et injecté dans le contexte d’Agent (ou généré automatiquement s’il est absent)
6. **Hériter de la configuration** : le fichier `.replit`, les dépendances et tous les fichiers du template sont conservés dans la nouvelle app

Le créateur peut immédiatement commencer à envoyer à Agent des prompts correspondant à ses exigences spécifiques, et Agent fonctionne dans le cadre défini par le template.

<div id="how-files-work-together">
  ## Comment les fichiers fonctionnent ensemble
</div>

Chaque fichier de configuration remplit un rôle distinct :

| Fichier                              | Objectif                                     | Quand Agent le lit                        | Modifiable par Agent                      |
| ------------------------------------ | -------------------------------------------- | ----------------------------------------- | ----------------------------------------- |
| `custom_instruction/instructions.md` | Normes et règles de l’organisation           | Toujours (injecté dans le prompt système) | Non                                       |
| `.agents/skills/*/SKILL.md`          | Workflows et modèles spécialisés             | À la demande (si pertinent)               | Oui (Agent peut aussi créer des compétences)   |
| `replit.md`                          | Vue d’ensemble et préférences du projet     | Toujours (injecté dans le prompt système) | Oui (Agent le met à jour au fil du temps) |
| `.replit`                            | Configuration de l’environnement d’exécution | Lors de la configuration de l’app         | Oui                                       |

**Distinction essentielle** : `custom_instruction/instructions.md` est votre référence statique et faisant autorité pour les normes de l’organisation. `replit.md` est le document vivant qu’Agent maintient à mesure que le projet évolue. Les compétences constituent des ressources de référence à la demande pour des workflows spécifiques.

<div id="best-practices">
  ## Bonnes pratiques
</div>

<div id="keep-instructions-focused">
  ### Gardez des instructions ciblées
</div>

Rédigez `custom_instruction/instructions.md` pour les pratiques les plus importantes. Concentrez-vous sur :

* Les décisions difficiles à modifier ultérieurement (architecture, modèles de données)
* Les pratiques qui doivent rester cohérentes (utilisation des composants, conventions d’API)
* Les normes que le créateur pourrait ne pas connaître (bibliothèques internes, conventions de l’équipe)

Évitez d’inclure des changelogs, des détails d’implémentation ou des informations qui changent fréquemment.

<div id="write-discoverable-skill-descriptions">
  ### Rédiger des descriptions de compétences faciles à identifier
</div>

Agent utilise le champ `description` du frontmatter de `SKILL.md` pour déterminer quand charger une compétence. Rédigez des descriptions correspondant aux tâches pour lesquelles la compétence est pertinente :

```yaml theme={null}
# Bon — indique quand l’utiliser
description: Use when building forms or handling user input. Provides validation patterns, error display conventions, and accessible form layouts.

# Moins efficace — trop vague
description: Form utilities and helpers.
```

<div id="organize-skills-by-workflow">
  ### Organisez les compétences par workflow
</div>

Regroupez les compétences par workflow plutôt que par catégorie technique :

| Approche                  | Exemple                                      |
| ------------------------- | -------------------------------------------- |
| **Par workflow**          | `build-a-form`, `connect-to-api`, `add-auth` |
| **Par domaine technique** | `react-utils`, `api-helpers`, `auth-config`  |

Cette approche aide Agent à trouver les compétences au bon moment.

<div id="iterate-on-your-template">
  ### Faites évoluer votre template
</div>

Les templates s&#39;améliorent à l&#39;usage. Une fois que votre équipe commence à utiliser un template :

1. Repérez les schémas qu’Agent interprète mal et ajoutez-les à `instructions.md`
2. Créez de nouvelles compétences lorsqu’Agent résout efficacement un problème — consignez la solution
3. Mettez à jour les dépendances et configurations de base à mesure que votre stack évolue
4. Testez les modifications en créant une nouvelle app à partir du template afin de vérifier l’expérience

<div id="template-updates-and-existing-apps">
  ### Mises à jour du template et apps existantes
</div>

Les modifications apportées à l’app template s’appliquent aux **nouvelles** apps créées à partir de celui-ci. Les apps existantes précédemment forkées à partir du template sont des copies indépendantes et ne reçoivent pas ces mises à jour.
