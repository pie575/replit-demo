Ce guide vous accompagne pas à pas dans la copie manuelle d&#39;une application vers un autre workspace ou compte. Vous copiez le code, configurez la nouvelle application, copiez vos données, puis redirigez vos utilisateurs vers la nouvelle application.

Rien n&#39;est déplacé ni supprimé. L&#39;ancien project reste exactement où il est, et les deux copies ne sont pas synchronisées entre elles. À la fin, c&#39;est à vous de décider si vous conservez l&#39;ancien ou si vous le supprimez.

<Note>
  Vous cherchez plutôt le transfert intégré en un clic ? Consultez [Transférer une application vers Teams](/fr/teams/identity-and-access-management/transfer-app-to-teams). Suivez ce guide lorsque cette option n&#39;est pas disponible ou lorsque vous devez copier d&#39;un compte à un autre.
</Note>

<div id="before-you-start">
  ## Avant de commencer
</div>

Vous avez besoin :

* d&#39;un accès à la fois à l&#39;ancien project et au nouveau workspace ou compte ;
* d&#39;environ une heure de disponibilité sans interruption pour le basculement final. Les étapes préalables peuvent s&#39;étaler sur plusieurs jours ;
* si votre App dispose d&#39;une adresse web personnalisée, d&#39;un accès à l&#39;endroit où vous gérez ce domaine.

Deux éléments ne sont pas copiés automatiquement et prennent le plus de temps : votre **base de données** et votre **adresse web**. Ce guide traite les deux.

<Note>
  Si l&#39;administrateur de votre workspace a activé le paramètre [exportation du code source](/fr/teams/enterprise-privacy-settings#ban-source-code-export), vous ne pouvez pas télécharger le project sous forme de fichier zip. Contactez-le avant de commencer : il pourra vous confirmer si une copie manuelle est autorisée et comment déplacer le code et la base de données.
</Note>

<div id="plan-for-downtime">
  ## Prévoir l&#39;interruption de service
</div>

C&#39;est comme ouvrir une seconde boutique avant de fermer la première : il y a un court moment où l&#39;ancienne est fermée et où la nouvelle n&#39;a pas encore ouvert. Pendant ce laps de temps, personne ne peut utiliser votre app.

**Combien de temps l&#39;app reste-t-elle hors ligne ?** En général de 15 à 60 minutes. Cela dépend du volume de données de votre base de données et de la rapidité de mise à jour de votre adresse web.

**Vais-je perdre des données ?** Uniquement si quelqu&#39;un ajoute des données à l&#39;ancienne app après la copie de la base de données. Pour l&#39;éviter, mettez l&#39;ancienne app hors ligne *avant* de réaliser la copie finale. Ce guide suit cet ordre.

**Puis-je revenir en arrière ?** Oui. L&#39;ancien project n&#39;est pas supprimé. En cas de problème, publiez à nouveau l&#39;ancienne app : elle fonctionnera exactement comme avant.

**Quand dois-je le faire ?** Choisissez un moment où peu de personnes utilisent votre app, et prévenez vos utilisateurs à l&#39;avance si possible.

<div id="step-1-copy-the-code-to-a-new-project">
  ## Étape 1 : copier le code dans un nouveau projet
</div>

Choisissez une méthode. L&#39;ancienne app reste en ligne pendant cette étape. Les deux méthodes transfèrent votre code. GitHub conserve toujours l&#39;historique de vos commits, tandis qu&#39;un fichier zip ne le conserve que s&#39;il inclut le dossier `.git` :

|                              | Via GitHub                                                            | Via un fichier zip                                                                                                                     |
| ---------------------------- | --------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------- |
| **Fichiers de code**         | Uniquement les fichiers que vous committez et poussez                 | Tout ce qui se trouve sur le disque, y compris les modifications non committées                                                        |
| **Historique des commits**   | Historique complet sur le dépôt distant                               | Historique complet si le zip inclut le dossier `.git`. Aucun historique si vous excluez `.git` pour rester sous la limite d&#39;import |
| **Dossiers de dépendances**  | Suit votre `.gitignore`                                               | Exclus (`node_modules`, `.venv`, `build`, etc.) ; réinstallés à l&#39;import                                                           |
| **Exigences**                | Un compte GitHub connecté aux deux comptes Replit                     | Aucune                                                                                                                                 |
| **Synchronisation continue** | Les deux copies peuvent pousser et tirer sur le même dépôt            | Aucune — instantané ponctuel                                                                                                           |
| **Idéal pour**               | Les projets que vous souhaitez sauvegarder dans Git sur le long terme | Les copies ponctuelles rapides                                                                                                         |

<div id="via-github">
  ### Via GitHub
</div>

<Steps>
  <Step title="Envoyer l'ancien project vers GitHub">
    Dans l&#39;ancien project, ouvrez le [Git Pane](/fr/features/workspace-tools/git-interface), connectez un dépôt GitHub, puis effectuez un commit et un push. Utilisez un dépôt privé, sauf si vous souhaitez rendre le code public.
  </Step>

  <Step title="Accorder l'accès au nouveau compte">
    Si le nouveau workspace appartient à un autre compte Replit, son compte GitHub doit disposer d&#39;un accès au dépôt. Pour un dépôt privé, ajoutez ce compte GitHub comme collaborateur ou utilisez une organisation GitHub partagée.
  </Step>

  <Step title="Importer dans le nouveau workspace">
    Connectez-vous au nouveau compte, ouvrez [replit.com/import](https://replit.com/import), sélectionnez **GitHub**, connectez le compte GitHub et choisissez le dépôt. Consultez [Importer depuis un provider](/fr/build/import-from-providers) pour le dépannage.
  </Step>

  <Step title="Vérifier la copie">
    Ouvrez le nouveau project et vérifiez que les fichiers et l&#39;historique des commits sont bien présents. Replit installe les dependencies et configure les Run commands pendant l&#39;import.
  </Step>
</Steps>

<Warning>
  GitHub ne reçoit que ce que vous avez commité et poussé. Les fichiers correspondant à `.gitignore` et les modifications non commitées ne sont pas transférés. Ne commitez jamais de valeurs secrètes ni de dumps de base de données dans le dépôt.
</Warning>

<div id="via-zip-file">
  ### Via un fichier zip
</div>

<Steps>
  <Step title="Télécharger l'ancien project">
    Dans l&#39;ancien project, sélectionnez le menu à trois points en haut de l&#39;arborescence des fichiers et choisissez **Download as zip**.

    Si le téléchargement fonctionne et que le fichier fait moins de 200 Mo, passez à l&#39;étape suivante.

    Un fichier zip de plus de 200 Mo peut se télécharger sans problème. En revanche, l&#39;[import ZIP](/fr/build/import-from-providers#limitations) rejette les fichiers de plus de 200 Mo : Replit ne peut donc pas s&#39;en servir pour créer le nouveau project. Si le téléchargement échoue ou si le zip dépasse 200 Mo, créez-en un plus petit :

    1. Dans l&#39;ancien project, ouvrez l&#39;outil **Shell**.

    2. Collez cette commande et appuyez sur Entrée. Elle crée un fichier nommé `project.zip` et exclut les dossiers que Replit peut reconstruire lui-même :

       ```bash theme={null}
       zip -r project.zip . -x ".cache/*" "node_modules/*" ".venv/*" "venv/*" ".pythonlibs/*" "build/*" "target/*" ".next/*" "__pycache__/*"
       ```

    3. Vérifiez la taille. Collez cette commande et appuyez sur Entrée. Elle affiche la taille en Mo, par exemple `150M` pour 150 Mo :

       ```bash theme={null}
       du -h project.zip
       ```

    4. Si la taille dépasse 200 Mo, réduisez le fichier en excluant votre historique de modifications. Collez les deux lignes et appuyez sur Entrée :

       ```bash theme={null}
       rm project.zip
       zip -r project.zip . -x ".cache/*" ".local/*" ".git/*" "node_modules/*" ".venv/*" "venv/*" ".pythonlibs/*" "build/*" "target/*" ".next/*" "__pycache__/*"
       ```

       N&#39;excluez `.local` et `.git` que si vous devez ramener le zip sous les 200 Mo. Ces exclusions ne suppriment aucun des deux dossiers de l&#39;ancien project. En revanche, un zip sans `.git` ne contient pas l&#39;historique des commits du project. Utilisez la méthode GitHub si vous devez conserver cet historique.

    5. Repérez `project.zip` dans l&#39;arborescence des fichiers, sélectionnez le menu à trois points situé à côté, puis choisissez **Download**.

    Le dossier `.cache` contient l&#39;état interne de Replit, y compris les valeurs de secrets mises en cache. Excluez-le toujours des fichiers zip que vous créez manuellement. Si votre project comporte d&#39;autres dossiers générés volumineux, ajoutez-les à la liste d&#39;exclusion.
  </Step>

  <Step title="Importer dans le nouveau workspace">
    Connectez-vous au nouveau compte, ouvrez [replit.com/import](https://replit.com/import), sélectionnez **ZIP**, puis téléversez le fichier.
  </Step>

  <Step title="Vérifier la copie">
    Ouvrez le nouveau project et vérifiez que vos fichiers sont bien présents. Si le zip inclut le dossier `.git`, votre historique de commits a suivi. Si vous avez utilisé la commande d&#39;archive réduite, le nouveau project démarre sans historique de commits. Replit réinstalle les dependencies exclues pendant l&#39;import.
  </Step>
</Steps>

<div id="step-2-set-up-the-new-app">
  ## Étape 2 : configurer la nouvelle app
</div>

L&#39;ancienne app est toujours en ligne. Au cours de cette étape, vous rendez la nouvelle app pleinement fonctionnelle avec une *copie de test* de vos données, afin que le basculement final soit rapide.

<Steps>
  <Step title="Ajoutez vos Secrets">
    Les valeurs des secrets (clés API, mots de passe) ne quittent jamais l&#39;ancien projet. Ouvrez l&#39;outil [Secrets](/fr/core-concepts/project-editor/app-setup/secrets) dans les deux projets et recopiez chaque valeur manuellement. N&#39;oubliez pas les secrets de déploiement.
  </Step>

  <Step title="Reconnectez les Connectors et les autres services">
    Reconnectez chaque intégration depuis **Tools → Connectors** dans le nouveau projet. Consultez [Recréer ce qui n&#39;est pas copié](#re-create-what-doesnt-copy-over) pour App Storage, les collaborateurs et tout le reste.
  </Step>

  <Step title="Publiez la nouvelle app">
    [Publiez](/fr/features/publishing/overview) le nouveau projet. Il reçoit sa propre adresse web `replit.app` ainsi que sa propre base de données de production, vide. Ne connectez pas encore votre domaine personnalisé.
  </Step>

  <Step>
    Suivez la section [Copier la base de données](#copy-the-database) ci-dessous, en prenant pour cible la base de données de **production** du nouveau projet. Vous disposez ainsi de données réelles pour vos tests. L&#39;étape 3 remplacera cette copie par vos données les plus récentes.
  </Step>

  <Step>
    Ouvrez la nouvelle app à son adresse `replit.app` et utilisez-la comme le feraient vos utilisateurs. Corrigez tout ce qui ne fonctionne pas avant de poursuivre. Vos utilisateurs ne sont pas encore affectés.
  </Step>
</Steps>

<div id="step-3-switch-your-users-to-the-new-app">
  ## Étape 3 : basculer vos utilisateurs vers la nouvelle app
</div>

C&#39;est l&#39;étape qui implique une interruption de service. Réalisez-la d&#39;une traite.

<Steps>
  <Step title="Mettre l'ancienne app hors ligne">
    Dans l&#39;ancien project, ouvrez l&#39;outil **Publishing** et sélectionnez **Unpublish**. Votre app est désormais hors ligne. Personne ne peut plus ajouter de données à partir de ce moment : la copie que vous réalisez ensuite sera donc complète.
  </Step>

  <Step title="Copier la base de données une dernière fois">
    Suivez [Copier la base de données](#copy-the-database) ci-dessous, en utilisant la base de données **production** du nouveau project comme cible. Cette copie contient vos données les plus récentes.
  </Step>

  <Step title="Faire pointer votre adresse web vers la nouvelle app">
    Si votre app utilise un domaine personnalisé : dans l&#39;ancien project, ouvrez **Publishing → Domains** et déconnectez le domaine. Dans le nouveau project, ouvrez **Publishing → Domains** et [connectez-le](/fr/features/publishing/custom-domains#connect-a-domain-you-already-own). Mettez à jour les enregistrements chez votre provider de domaine (par exemple GoDaddy ou Namecheap) si Replit vous le demande.

    La nouvelle adresse peut mettre de quelques minutes à quelques heures avant d&#39;être opérationnelle pour tout le monde. Entre-temps, certains visiteurs peuvent voir une erreur.

    Si votre app utilise uniquement une adresse `replit.app`, communiquez plutôt la nouvelle adresse à vos utilisateurs.
  </Step>

  <Step title="Vérifier que la nouvelle app est en ligne">
    Ouvrez votre adresse web et vérifiez que la nouvelle app se charge avec vos données. Votre app est de nouveau en ligne.
  </Step>
</Steps>

<div id="copy-the-database">
  ## Copier la base de données
</div>

La copie du code ne touche pas à votre base de données. Copiez les données avec les outils `pg_dump` et `pg_restore` de PostgreSQL, disponibles dans le Shell des deux projets. Les étapes 2 et 3 renvoient toutes deux ici. Les commandes sont identiques à chaque fois. Seule la *cible* change.

<Warning>
  Les données écrites après l&#39;exécution de `pg_dump` ne sont pas incluses dans la copie. Pour la copie finale de l&#39;étape 3, mettez d&#39;abord l&#39;ancienne app hors ligne.
</Warning>

<Steps>
  <Step title="Exporter les données de l'ancien projet">
    Ouvrez l&#39;outil **Shell** dans l&#39;ancien projet. Collez cette commande et appuyez sur Entrée. Elle crée un fichier nommé `backup.dump` dans votre arborescence de fichiers :

    ```bash theme={null}
    pg_dump -Fc "$DATABASE_URL" --no-owner --no-privileges -f backup.dump
    ```

    Cette commande exporte la base de données de **développement**. Or, vos données en production se trouvent généralement dans la base de données de **production**. Pour l&#39;exporter :

    1. Ouvrez l&#39;outil **Database**, sélectionnez la base de données de production et ouvrez les **paramètres**.
    2. Copiez la chaîne de connexion.
    3. Dans la commande ci-dessus, remplacez `"$DATABASE_URL"` par la chaîne de connexion, en conservant les guillemets.

    Consultez [Connection details](/fr/features/data-and-storage/connection-details) si vous ne la trouvez pas.
  </Step>

  <Step title="Déplacer le fichier de sauvegarde vers le nouveau projet">
    Dans l&#39;arborescence de fichiers de l&#39;ancien projet, ouvrez le menu à trois points à côté de `backup.dump` et téléchargez le fichier. Téléversez-le ensuite dans le nouveau projet à l&#39;aide de l&#39;option **Upload files** de l&#39;arborescence de fichiers.

    Si vous avez copié le code via GitHub, ne validez pas le fichier de sauvegarde. Déplacez-le séparément pour que vos données ne se retrouvent jamais dans le dépôt.
  </Step>

  <Step title="Importer les données dans le nouveau projet">
    Ouvrez l&#39;outil **Shell** dans le nouveau projet. Collez cette commande et appuyez sur Entrée :

    ```bash theme={null}
    pg_restore --clean --if-exists --single-transaction --no-owner --no-privileges --exit-on-error -d "$DATABASE_URL" backup.dump
    ```

    Telle quelle, cette commande importe les données dans la base de données de **développement** du nouveau projet. C&#39;est bien ce que vous voulez à l&#39;étape 2.

    Pour la copie finale de l&#39;étape 3, c&#39;est la base de données de **production** qu&#39;il faut viser. Dans le nouveau projet, ouvrez l&#39;outil **Database**, sélectionnez la base de données de production, ouvrez les **paramètres**, copiez la chaîne de connexion et utilisez-la à la place de `"$DATABASE_URL"`.

    Cette commande supprime les objets correspondants dans la base de données cible, puis charge les données. Si elle se termine sans rien afficher, c&#39;est qu&#39;elle a fonctionné.
  </Step>
</Steps>

<Note>
  Si `pg_restore` échoue avec des erreurs de rôle ou de politique, c&#39;est que votre base de données utilise des rôles PostgreSQL personnalisés qui n&#39;existent pas encore dans le nouveau projet. [Contactez le support](https://replit.com/support) pour obtenir de l&#39;aide.
</Note>

<Note>
  Si le nouveau projet utilise une [base de données de développement Neon héritée](/fr/features/data-and-storage/development-and-production#legacy-development-database), le flux de publication propose l&#39;option **Set up your production database with your current development data**. Celle-ci copie le contenu de la base de données de développement tel qu&#39;il est au moment de la publication. C&#39;est suffisant pour des tests, mais pour la bascule finale, suivez plutôt les étapes ci-dessus afin d&#39;obtenir les données les plus récentes.
</Note>

<div id="re-create-what-doesnt-copy-over">
  ## Recréer ce qui n&#39;est pas copié
</div>

Le reste de la configuration du project se trouve en dehors du système de fichiers. Recréez chaque élément dans le nouveau project :

| Élément                       | Que faire                                                                                                                                                                                                                                                                                |
| ----------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Secrets**                   | Les valeurs des secrets ne quittent jamais l&#39;ancien project. Ajoutez-les de nouveau dans l&#39;outil [Secrets](/fr/core-concepts/project-editor/app-setup/secrets) du nouveau project, sans oublier les deployment secrets.                                                             |
| **Account Secrets**           | [Liez-les](/fr/core-concepts/project-editor/app-setup/secrets#manage-account-secrets) dans le nouveau project. Si le nouveau project relève d&#39;un autre compte, ajoutez-les d&#39;abord à ce compte.                                                                                     |
| **App Storage**               | Les buckets ne sont pas transférés. Au sein d&#39;un même compte, [ajoutez le bucket existant](/fr/features/data-and-storage/object-storage#bucket-access-management) au nouveau project. D&#39;un compte à l&#39;autre, téléchargez les objets puis téléversez-les dans un nouveau bucket. |
| **Connectors**                | Reconnectez chaque integration depuis **Tools → Connectors** dans le nouveau project. Consultez la [présentation des integrations](/fr/features/integrations/overview).                                                                                                                     |
| **Deployments**               | La copie n&#39;est pas publiée. [Publiez](/fr/features/publishing/overview)-la depuis le nouveau workspace, comme à l&#39;[étape 2](#step-2-set-up-the-new-app).                                                                                                                            |
| **Custom Domains**            | Retirez le domaine de l&#39;ancien deployment, associez-le au nouveau et mettez à jour vos enregistrements DNS. Voir l&#39;[étape 3](#step-3-switch-your-users-to-the-new-app).                                                                                                          |
| **Collaborateurs**            | Invitez de nouveau les collaborateurs et configurez les [accès](/fr/teams/identity-and-access-management/groups-and-permissions) dans le nouveau workspace.                                                                                                                                 |
| **Historique de l&#39;Agent** | Les conversations avec l&#39;Agent et les retours en arrière par [checkpoint](/fr/features/version-control/checkpoints-and-rollbacks) restent attachés à l&#39;ancien project. Les commits de checkpoint suivent votre historique Git, mais vous ne pouvez pas y revenir depuis la copie.   |

<div id="if-something-goes-wrong">
  ## En cas de problème
</div>

L&#39;ancien project est toujours là. Pour revenir en arrière :

1. Dans l&#39;ancien project, ouvrez l&#39;outil **Publishing** et sélectionnez **Publier**.
2. Si vous avez déplacé un domaine personnalisé, replacez-le de la même manière.

Votre App est de nouveau en ligne avec les données qu&#39;elle contenait au moment de sa mise hors ligne. Rien n&#39;a été perdu.

<div id="clean-up">
  ## Nettoyage
</div>

Attendez environ une semaine pour vous assurer que la nouvelle app fonctionne correctement. Ensuite :

* Supprimez `backup.dump` des deux projets ainsi que de votre appareil. Chaque copie contient un export complet de vos données.
* Si vous le souhaitez, supprimez l&#39;ancien projet.
