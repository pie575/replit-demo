Vous trouverez ici les réponses aux questions fréquentes sur les erreurs pouvant survenir dans les apps publiées. Pour un dépannage plus général, consultez [Dépannage des déploiements](/fr/ja/build/troubleshooting).

<AccordionGroup>
  <Accordion title="Mon application publiée renvoie une erreur 403 Forbidden : comment la corriger ?">
    Les erreurs 403 sur les applications publiées sont généralement dues à l’une des causes suivantes :

    * **Les en-têtes de requête sont trop volumineux**—un trop grand nombre de cookies peut alourdir les en-têtes au point qu’ils soient rejetés à la périphérie. Effacez les cookies du navigateur associés au domaine, puis réessayez.
    * **Informations d’authentification manquantes**—la requête ne contient pas le jeton de connexion ou la session requis.
    * **Restrictions d’accès**—l’application est peut-être configurée pour bloquer une partie du trafic. Consultez les [déploiements privés](/fr/ja/features/publishing/private-deployments) et les [jetons d’accès externes](/fr/ja/features/deployment-customization/external-access-tokens).

    Pour un diagnostic détaillé, collez les journaux de déploiement dans une nouvelle conversation avec Agent.
  </Accordion>

  <Accordion title="L’App affiche « Application failed to respond » : qu’est-ce que cela signifie ?">
    Le processus de votre application n&#39;écoute pas le port attendu par Replit. Replit transmet le bon port via la variable d&#39;environnement `PORT` : utilisez donc cette variable pour la liaison plutôt qu&#39;une valeur codée en dur :

    ```js theme={null}
    const PORT = process.env.PORT || 3000;
    ```

    ```python theme={null}
    port = int(os.environ.get("PORT", 3000))
    ```

    L’application peut aussi planter avant de s’associer au port : vérifiez les erreurs de démarrage dans les journaux de déploiement. Avec les [déploiements Autoscale](/fr/ja/features/publishing/deployment-types#autoscale), la première requête après une période d’inactivité peut prendre quelques secondes (démarrage à froid) : ce comportement est normal.
  </Accordion>

  <Accordion title="Comment corriger les erreurs CORS dans les applications Replit publiées ?">
    Les erreurs CORS signifient que le front-end et le back-end ont des origines différentes et que le back-end n&#39;est pas configuré pour les autoriser. S&#39;ils font partie de la même application, vous pouvez complètement éviter les problèmes de CORS en utilisant des URL relatives telles que `/api/endpoint`.

    Sinon, configurez le back-end pour autoriser l&#39;origine du front-end. Par exemple, avec Express :

    ```js theme={null}
    const cors = require("cors");
    app.use(cors({ origin: "https://your-frontend.replit.app" }));
    ```

    Avant la mise en ligne, n’autorisez que les origines nécessaires. Consultez le [guide de dépannage des déploiements](/fr/ja/build/troubleshooting).
  </Accordion>

  <Accordion title="L’application fonctionne en local, mais renvoie une erreur réseau une fois publiée">
    Si l&#39;environnement de production diffère de votre configuration locale, l&#39;application déployée échoue. Vérifiez les 3 points suivants :

    1. **URL localhost codées en dur** — remplacez `localhost:3000` ou `127.0.0.1` par des chemins relatifs ou des URL basées sur l&#39;environnement, puis redéployez.
    2. **Secrets de production manquants** — assurez-vous que toutes les clés nécessaires sont définies dans les secrets de déploiement. Consultez [Secrets](/fr/ja/core-concepts/project-editor/app-setup/secrets).
    3. **Migrations non exécutées en production** — exécutez les migrations en attente sur la base de données de production avant la publication.

    Si l&#39;erreur persiste, [contactez le support Replit](https://replit.com/support) en indiquant le message d&#39;erreur et les étapes que vous avez suivies.
  </Accordion>

  <Accordion title="Comment déboguer une erreur 502 Bad Gateway sur une application publiée ?">
    Une erreur 502 signifie généralement que le processus de l’application a planté ou que le serveur a renvoyé une réponse qu’il ne peut pas traiter. Consultez les journaux de déploiement pour identifier l’erreur ayant provoqué le plantage juste avant l’erreur 502 : des rejets de Promise non gérés et des exceptions non interceptées peuvent faire planter silencieusement le processus Node.js.

    Ajoutez un gestionnaire pour faire remonter les plantages :

    ```js theme={null}
    process.on("uncaughtException", (err) => console.error("Uncaught:", err));
    ```

    Une fois l&#39;erreur sous-jacente identifiée dans les journaux, collez-la dans une nouvelle conversation avec Agent et demandez de l&#39;aide pour la corriger.
  </Accordion>

  <Accordion title="L’application ne peut pas envoyer de requêtes à une API externe : que vérifier ?">
    Commencez par vérifier s&#39;il s&#39;agit bien de requêtes bloquées et non d&#39;un problème de code. Ouvrez les journaux de déploiement et recherchez des messages indiquant que des requêtes sortantes sont bloquées ou redirigées.

    Causes fréquentes et solutions :

    * **URL autoréférentielle** — si votre backend appelle sa propre URL publique (par exemple `fetch("https://myapp.replit.app/api/...")`), utilisez plutôt un chemin relatif comme `fetch("/api/...")`.
    * **Requêtes pendant la phase de build** — effectuez les appels sortants au moment de l&#39;exécution, et non pendant le build.
    * **Restrictions réseau** — les réseaux d&#39;entreprise ou d&#39;établissement scolaire bloquent parfois les connexions sortantes. Renseignez-vous auprès de votre administrateur réseau.

    Si aucun de ces cas ne s&#39;applique et que vos requêtes restent bloquées, [contactez l&#39;assistance Replit](https://replit.com/support) en joignant les lignes de journal concernées.
  </Accordion>

  <Accordion title="L’URL de mon application a changé après sa republication : puis-je récupérer mon ancien sous-domaine ?">
    Le sous-domaine `.replit.app` est dérivé du nom du projet et peut ne pas être conservé après avoir rendu le projet privé puis l’avoir republié, notamment si son nom a été modifié.

    La solution permanente consiste à utiliser un [domaine personnalisé](/fr/ja/features/publishing/custom-domains). Il ne changera pas lors des redéploiements. Pour tenter de restaurer un ancien sous-domaine, assurez-vous que le nom du projet correspond au nom d’origine (rétablissez-le si nécessaire), puis republiez-le : Replit ne peut pas réattribuer manuellement les sous-domaines libérés. Consultez la page [géographie du projet](/fr/ja/features/publishing/project-geography).
  </Accordion>
</AccordionGroup>
