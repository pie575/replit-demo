Здесь собраны ответы на часто задаваемые вопросы об ошибках, которые могут возникать в опубликованных приложениях. Более подробную информацию см. в разделе [Устранение неполадок деплоя](/ru/ja/build/troubleshooting).

<AccordionGroup>
  <Accordion title="Опубликованное приложение возвращает ошибку 403 Forbidden — как её исправить?">
    Ошибка 403 в опубликованном приложении обычно возникает по одной из следующих причин:

    * **Слишком большой размер заголовков запроса**—из-за большого количества файлов cookie заголовки могут стать слишком большими и быть отклонены на периферийных серверах. Очистите файлы cookie браузера для этого домена и повторите проверку.
    * **Отсутствуют учетные данные**—запрос не содержит необходимого токена входа или сеанса.
    * **Ограничения доступа**—возможно, приложение настроено на блокировку части трафика. См. [приватные деплои](/ru/ja/features/publishing/private-deployments) и [токены внешнего доступа](/ru/ja/features/deployment-customization/external-access-tokens).

    Для более подробной диагностики вставьте логи деплоя в новый чат Agent.
  </Accordion>

  <Accordion title="В App отображается сообщение «Application failed to respond» — что это означает?">
    Процесс приложения не прослушивает порт, который ожидает Replit. Replit передаёт нужный порт через переменную окружения `PORT`, поэтому используйте её вместо жёстко заданного значения:

    ```js theme={null}
    const PORT = process.env.PORT || 3000;
    ```

    ```python theme={null}
    port = int(os.environ.get("PORT", 3000))
    ```

    Возможно, приложение аварийно завершает работу ещё до привязки — проверьте логи деплоя на наличие ошибок запуска. В [деплоях Autoscale](/ru/ja/features/publishing/deployment-types#autoscale) первый запрос после периода бездействия может выполняться несколько секунд (холодный старт) — это нормально.
  </Accordion>

  <Accordion title="Как исправить ошибку CORS в опубликованном приложении Replit?">
    Ошибка CORS означает, что фронтенд и бэкенд имеют разные источники, а бэкенд не настроен на разрешение запросов с фронтенда. Если они являются частями одного приложения, CORS можно полностью избежать, используя относительные URL, например `/api/endpoint`.

    В противном случае настройте бэкенд так, чтобы он разрешал запросы с источника фронтенда. Например, для Express:

    ```js theme={null}
    const cors = require("cors");
    app.use(cors({ origin: "https://your-frontend.replit.app" }));
    ```

    Перед публикацией разрешите только необходимые источники. См. [устранение неполадок при деплое](/ru/ja/build/troubleshooting).
  </Accordion>

  <Accordion title="Приложение работает локально, но после публикации возникает сетевая ошибка">
    Если продакшен-среда отличается от локальной, развёрнутое приложение завершится с ошибкой. Проверьте следующие 3 пункта:

    1. **Жёстко заданные URL localhost**—замените `localhost:3000` или `127.0.0.1` относительными путями или URL на основе переменных окружения, затем повторно выполните деплой.
    2. **Отсутствуют секреты для продакшена**—убедитесь, что все необходимые ключи указаны в Secrets деплоя. См. [Secrets](/ru/ja/core-concepts/project-editor/app-setup/secrets).
    3. **Миграции не выполнены в продакшен-среде**—перед публикацией выполните все ожидающие миграции для продакшен-базы данных.

    Если ошибка сохраняется, [обратитесь в поддержку Replit](https://replit.com/support), указав сообщение об ошибке и предпринятые действия.
  </Accordion>

  <Accordion title="Как устранить ошибку 502 Bad Gateway в опубликованном приложении?">
    Ошибка 502 обычно означает, что процесс приложения аварийно завершился или сервер вернул ответ, который не может обработать. Проверьте лог деплоя на ошибки, возникшие непосредственно перед появлением 502: необработанные отклонения Promise или неперехваченные исключения могут незаметно приводить к сбою процесса Node.js.

    Добавьте обработчик, чтобы такие сбои не оставались незамеченными:

    ```js theme={null}
    process.on("uncaughtException", (err) => console.error("Uncaught:", err));
    ```

    Определив основную ошибку в логе, вставьте её в новый чат Agent и попросите помочь её исправить.
  </Accordion>

  <Accordion title="Приложение не может отправлять запросы к внешнему API — что проверить?">
    Сначала проверьте, не блокируется ли запрос, а не ищите проблему в коде. Откройте логи деплоя и убедитесь, что в них нет сообщений о блокировке или перенаправлении исходящих запросов.

    Распространённые причины и способы устранения:

    * **Самоссылочный URL** — если бэкенд вызывает собственный публичный URL (например, `fetch("https://myapp.replit.app/api/...")`), используйте относительный путь, например `fetch("/api/...")`.
    * **Запросы на этапе сборки** — выполняйте исходящие вызовы во время работы приложения, а не во время сборки.
    * **Сетевые ограничения** — в корпоративных или школьных сетях исходящие подключения могут блокироваться. Обратитесь к сетевому администратору.

    Если ни одна из этих причин не подходит, но запросы по-прежнему блокируются, [обратитесь в поддержку Replit](https://replit.com/support), приложив соответствующие строки логов.
  </Accordion>

  <Accordion title="После повторной публикации URL приложения изменился — можно ли вернуть прежний поддомен?">
    Поддомен `.replit.app` формируется на основе имени проекта, поэтому при отмене публикации и повторной публикации он не всегда сохраняется, особенно если имя проекта было изменено.

    Постоянное решение — использовать [собственный домен](/ru/ja/features/publishing/custom-domains). Он не изменится при повторном развёртывании. Чтобы попытаться восстановить прежний поддомен, убедитесь, что имя проекта совпадает с исходным (при необходимости верните прежнее имя), и опубликуйте его снова — Replit не может вручную переназначать освобождённые поддомены. См. [регион проекта](/ru/ja/features/publishing/project-geography).
  </Accordion>
</AccordionGroup>
