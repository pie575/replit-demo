<div id="section">
  ## Ajouter des en-têtes de réponse
</div>

Les **en-têtes de réponse** personnalisés vous permettent d&#39;ajouter des directives d&#39;en-tête HTTP aux requêtes correspondant à un chemin donné.
Un en-tête de réponse est une paire nom-valeur qui indique au navigateur comment interagir avec le contenu demandé.

Par exemple, vous pouvez définir l&#39;en-tête `Access-Control-Allow-Origin` pour indiquer au navigateur quels domaines sont autorisés à accéder à la page.
Pour créer cette entrée, ajoutez ce qui suit au fichier `.replit` situé à la racine de votre Replit App.

```
[[deployment.responseHeaders]]
path = "/*"
name = "Access-Control-Allow-Origin"
value = "origin"
```

Cet en-tête de réponse contient les paramètres suivants :

* **path** : le modèle de chemin d&#39;URL correspondant à la ressource demandée
* **name** : le nom de l&#39;en-tête HTTP
* **value** : la valeur de l&#39;en-tête HTTP

Vous pouvez ajouter plusieurs entrées `deployment.responseHeaders` dans le fichier `.replit`.

Pour appliquer les modifications de configuration, republiez votre Replit App.

<div id="404">
  ## Créer une page 404 personnalisée
</div>

Une page 404 personnalisée s&#39;affiche lorsqu&#39;un utilisateur demande un chemin d&#39;URL qui ne correspond à aucun fichier ni à aucune règle de votre app publiée.

Pour ajouter une page 404 personnalisée, créez un fichier nommé `404.html` à la racine de votre Replit App, puis rédigez-en le contenu.

Lorsqu&#39;un utilisateur tente d&#39;accéder à un chemin d&#39;URL inexistant, le code HTML de votre page 404 personnalisée s&#39;affiche.

<div id="url">
  ## Définir des réécritures de chemin d&#39;URL
</div>

Vous pouvez définir des réécritures d’URL qui modifient le chemin d&#39;URL d&#39;une requête avant que votre Replit App ne la traite.
L&#39;URL d&#39;origine reste affichée dans le navigateur, mais le serveur charge la ressource définie dans la règle de réécriture.

Par exemple, vous pouvez faire en sorte que toutes les requêtes commençant par `/app` chargent le contenu du fichier `/app/index.html`.
Pour créer cette entrée, ajoutez ce qui suit au fichier `.replit` situé à la racine de votre Replit App.

```
[[deployment.rewrites]]
from = "/app/*"
to = "/app/index.html"
```

* **from** : modèle de chemin d&#39;URL correspondant à la ressource demandée
* **to** : chemin réécrit correspondant à un fichier du Static Deployment

Vous pouvez ajouter plusieurs entrées `deployment.rewrites` dans le fichier `.replit`.
Le serveur interprète les entrées dans leur ordre d&#39;apparition et ignore les doublons.

Pour appliquer les modifications de configuration, vous devez republier la Replit App.

Les sections suivantes décrivent les limitations des règles de réécriture d’URL.

<div id="section-3">
  ### Correspondance de chemins
</div>

Les paramètres `from` et `to` d&#39;une règle de réécriture sont soumis aux contraintes suivantes :

* En l&#39;absence de `*`, la correspondance doit être exacte
* `*` correspond au reste du chemin
* `*` n&#39;est valide qu&#39;en fin de chemin
* Si vous incluez `*` dans le paramètre `from`, vous pouvez également l&#39;inclure dans le paramètre `to` pour représenter la portion correspondante du chemin

Par exemple, supposons que votre fichier `.replit` contienne la réécriture suivante.

```
[[deployment.rewrites]]
from = "/v1/*"
to = "/v2/*"
```

Lorsqu&#39;un utilisateur accède au chemin `/v1/about-us.html`, la règle de réécriture renvoie le fichier situé à `/v2/about-us.html`.

<div id="section-4">
  ### Masquage
</div>

Le masquage se produit lorsqu&#39;une règle de réécriture correspond à un chemin d&#39;URL qui correspond également à un fichier présent dans le Static Deployment.
Dans ce cas, le serveur cloud ignore la règle de réécriture et sert directement le fichier concerné.

Par exemple, supposons que l&#39;application publiée contienne les fichiers suivants :

* `index.html`
* `about.html`

Le fichier `.replit` contient la réécriture suivante :

```
[[deployment.rewrites]]
from = "/*"
to = "/index.html"
```

Lorsqu&#39;un utilisateur consulte `/register.html`, le serveur réécrit la requête vers `/index.html` et sert ce fichier.
En revanche, s&#39;il consulte `/about.html`, comme ce fichier existe dans le Static Deployment, le serveur ignore la règle de réécriture et sert le fichier `about.html`.

<div id="section-5">
  ### Restrictions de domaine
</div>

Les réécritures ne fonctionnent que pour les requêtes adressées au domaine par défaut du Static Deployment, et elles ne peuvent rediriger que vers des fichiers contenus dans ce Static Deployment.
