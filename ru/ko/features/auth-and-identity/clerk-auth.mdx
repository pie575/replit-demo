Clerk Auth предоставляет вашему приложению выделенную систему аутентификации на базе [Clerk](https://clerk.com). В отличие от [Replit Auth](/ru/ko/features/auth-and-identity/authentication), использующего систему входа Replit и учетные записи Replit, Clerk Auth выделяет для вашего приложения **отдельный тенант Clerk**. Пользователи вашего приложения создают учетные записи непосредственно в нем, а не в Replit, а вы получаете полный контроль над брендингом, способами и процессом входа.

<Note>
  **Сравнение Clerk Auth и Replit Auth** — с **Clerk Auth** (эта страница) ваше приложение получает выделенный тенант аутентификации с полностью настраиваемым брендингом и учетными записями пользователей, независимыми от Replit. С **[Replit Auth](/ru/ko/features/auth-and-identity/authentication)** пользователи входят с учетными записями Replit и видят страницу входа с брендингом Replit. Выберите Clerk Auth, если хотите использовать собственный бренд при входе или вам нужны учетные записи пользователей, независимые от Replit.
</Note>

<div id="clerk-auth-replit-auth">
  ## Сравнение Clerk Auth и Replit Auth
</div>

|                                  | Clerk Auth                                                                            | Replit Auth                                                          |
| -------------------------------- | ------------------------------------------------------------------------------------- | -------------------------------------------------------------------- |
| **Учётные записи пользователей** | Пользователи создают учётные записи в приложении (учётная запись Replit не требуется) | Пользователи входят с учётной записью Replit                         |
| **Брендинг**                     | Полная кастомизация — название приложения, значок, цвета                              | Страница входа в стиле Replit                                        |
| **Учётные данные SSO**           | Собственные учётные данные OAuth для каждого провайдера                               | Общее OAuth-приложение Replit                                        |
| **Среды**                        | Отдельные среды Development и Production                                              | Единая среда                                                         |
| **Рефералы**                     | Нет интеграции с Replit Referrals                                                     | Регистрации учитываются в Replit Referrals                           |
| **Подходит для**                 | Приложений с индивидуальным брендингом, профессиональных и коммерческих продуктов     | Быстрой настройки и приложений, для которых допустим брендинг Replit |

<div id="section">
  ## Начало работы
</div>

Чтобы добавить Clerk Auth в приложение, укажите это в промпте для Agent.

```
Создайте приложение [идея вашего приложения] с поддержкой Clerk Auth.
```

Agent берет на себя всё: создание тенанта Clerk, сохранение учетных данных, настройку маршрутов, добавление middleware и многое другое. Учетная запись Clerk и ручная настройка не требуются.

<div id="clerk-auth-replit">
  ## Как Clerk Auth работает с Replit
</div>

Когда Agent настраивает Clerk Auth в вашем приложении, он выполняет следующие действия:

1. **Создаёт выделенный тенант Clerk** — ваше приложение получает собственное приложение Clerk с отдельными средами Development и Production
2. **Настраивает учётные данные** — ключи API и секреты сохраняются в переменных среды
3. **Настраивает прокси** — аутентификация без сбоев работает на опубликованном домене
4. **Настраивает маршруты входа и регистрации** — в приложение добавляются готовые React-компоненты Clerk
5. **Добавляет серверное ПО промежуточного уровня** — маршруты API защищаются промежуточным ПО Express от Clerk

<Note>
  Вам не нужно создавать учётную запись Clerk или управлять инфраструктурой. Replit автоматически управляет всем.
</Note>

<div id="section-2">
  ## Функции
</div>

<div id="section-3">
  ### Поддерживаемые возможности
</div>

Clerk Auth предоставляет вашему App следующее:

* **Независимые учётные записи пользователей** — пользователи вашего App не являются пользователями Replit и существуют только в тенанте Clerk этого App
* **Полностью брендированные страницы входа** — название App, логотип, цвета, шрифты и текст на страницах входа и регистрации настраиваются в коде App
* **SSO под вашим брендом** — если вы укажете собственные учётные данные OAuth для каждого провайдера, на экране согласия OAuth вместо стандартных значений будут отображаться название и брендинг вашего App
* **Аутентификация по электронной почте и паролю** — встроенная регистрация и вход с подтверждением электронной почты
* **Вход через социальные сети (SSO)** — пользователи могут входить через Google, GitHub, Apple и X (Twitter)
* **Управление пользователями** — просмотр, поиск и управление пользователями на панели Auth
* **Управление сеансами** — защищённые токены сеансов, управляемые автоматически
* **Среды Development и Production** — тестирование аутентификации в среде разработки перед развёртыванием в Production

<Note>
  Большинством настроек Clerk Auth можно управлять в инструменте **Auth** в Project Editor — учётная запись Clerk и работа с панелью управления Clerk не требуются.
</Note>

<div id="section-4">
  ### Неподдерживаемые функции
</div>

Следующие функции пока недоступны в Clerk Auth по сравнению с внешним приложением Clerk, настроенным самостоятельно. Полное сравнение см. [в этом FAQ](#how-does-clerk-auth-compare-to-external-clerk).

* **Вход по номеру телефона** — вход и аутентификация по SMS
* **Поддержка MFA** — многофакторная аутентификация для конечных пользователей
* **Поддержка всех провайдеров SSO** — пока поддерживаются только Google, GitHub, Apple и X
* **Тенанты организаций** — функции Clerk для организаций и членства в командах

<div id="development-production">
  ## Среды разработки и Production
</div>

Все приложения с Clerk Auth получают две полностью изолированные среды Clerk: среду **Development** для приложения разработки/предпросмотра во время сборки и среду **Production** для опубликованного приложения. Эти среды намеренно разделены — у каждой собственные API-ключи и отдельное хранилище пользователей.

<div id="api">
  ### Отдельные API-ключи
</div>

У каждой среды есть собственные публичный и секретный API-ключи. Ключи, доступные приложению, автоматически переключаются в зависимости от того, запущено ли оно в среде разработки или Production.

* В Secrets рабочего пространства значения `CLERK_PUBLISHABLE_KEY` и `CLERK_SECRET_KEY` содержат **тестовые ключи** (`pk_test...` и `sk_test...`), указывающие на среду Development.

<Frame>
  <img src="/assets/mirror/clerk-check-dev-keys-5a23f6b7dd0c.png" alt="CLERK_SECRET_KEY и CLERK_PUBLISHABLE_KEY с префиксами sk_test_ и pk_test_ в инструменте Secrets рабочего пространства" width="1946" height="402" data-path="images/workspace/auth/clerk-check-dev-keys.png" />
</Frame>

* После публикации приложения опубликованный деплой запускается с **боевыми ключами** (`pk_live...` и `sk_live...`), указывающими на среду Production. Чтобы проверить префиксы, откройте **Publishing → Overview → Adjust settings** и проверьте `CLERK_PUBLISHABLE_KEY` и `CLERK_SECRET_KEY`.

<Frame>
  <img src="/assets/mirror/clerk-check-prod-keys-acccd7f68da1.png" alt="Секреты Production-приложения в Publishing Overview с CLERK_SECRET_KEY и CLERK_PUBLISHABLE_KEY, использующими префиксы sk_live_ и pk_live_" width="1924" height="1664" data-path="images/workspace/auth/clerk-check-prod-keys.png" />
</Frame>

<Note>
  Для переключения между средами ничего дополнительно делать не нужно — Replit автоматически управляет ключами и для Development, и для Production. Просто разрабатывайте, тестируйте и публикуйте.
</Note>

<Warning>
  Не заменяйте тестовые ключи боевыми, не редактируйте их в панели Secrets и не изменяйте настройки напрямую в панели Clerk. Это нарушит автоматическое переключение между Development и Production и не поддерживается для Clerk Auth, управляемого Replit.
</Warning>

<div id="section-5">
  ### Отдельные хранилища пользователей
</div>

В каждой среде есть собственное хранилище пользователей. Учётные записи, зарегистрированные в среде Development, **не** существуют в среде Production, и наоборот.

* Пользователи, зарегистрировавшиеся при тестировании приложения для разработки или предварительного просмотра, создаются только в хранилище Development.
* Пользователи, зарегистрировавшиеся в опубликованном приложении, создаются только в хранилище Production.
* Сеансы, метаданные пользователей и любые данные, использующие `userId` Clerk в качестве ключа, также доступны только в среде, где была создана учётная запись.

Это ожидаемое поведение. Чтобы просмотреть пользователей в каждой среде, откройте в Workspace **панель Auth** и с помощью переключателя среды на вкладке **Users** переходите между Development и Production.

<Note>
  Development — это пространство для экспериментов и разработки, а Production — среда для обслуживания реальных пользователей приложения. Они намеренно разделены, поэтому учётные записи и данные, созданные в Development, не отображаются в Production.
</Note>

<div id="section-6">
  ## Управление пользователями
</div>

Панель **Auth** в Project Editor позволяет просматривать всех аутентифицированных пользователей. Clerk Auth создаёт отдельное хранилище пользователей для вашего приложения, поэтому перечисленные здесь пользователи — это учётные записи приложения, а не учётные записи Replit.

<Frame>
  <img src="/assets/mirror/clerk-users-4940ed365605.png" alt="Вкладка Clerk Auth Users с аутентифицированными пользователями на панели Auth" width="2136" height="794" data-path="images/workspace/auth/clerk-users.png" />
</Frame>

На вкладке **Users** можно:

* **Просматривать всех пользователей** и их данные, включая адрес электронной почты, имя, время последнего входа и дату создания учётной записи
* **Искать и фильтровать пользователей**, чтобы найти нужного
* **Блокировать и разблокировать пользователей**, чтобы управлять доступом к приложению
* **Сортировать пользователей** по различным критериям
* **Переключать среды** — между Development и Production, чтобы управлять пользователями в каждой из них

<div id="section-7">
  ## Настройка страницы входа
</div>

Визуальный брендинг страниц входа и регистрации — название приложения, логотип, цвета, шрифты и текст — задаётся в коде приложения, а не в панели Auth. Чтобы внести изменения, обратитесь к Agent.

```
Измени заголовок страницы входа на [название приложения], используй [описание логотипа]
и оформи её в соответствии с цветовой гаммой сайта.
```

Внутренне это реализовано с помощью свойств `appearance` и `localization`, передаваемых в `<ClerkProvider>`, а также файла логотипа в каталоге `public/` приложения. Agent поддерживает их синхронизацию с остальной темой приложения.

<Note>
  **Собственный экран согласия Google, Apple, GitHub, X** (экран, который появляется после того, как пользователь нажимает &quot;Sign in with Google&quot; и т. п.) отображает отдельное название приложения — оно берётся из OAuth-приложения, зарегистрированного у соответствующего провайдера, и **не изменяется** при редактировании кода страницы входа. Чтобы изменить его, настройте [пользовательские учётные данные OAuth](#configuring-oauth-credentials-for-an-sso-provider) для соответствующего провайдера.
</Note>

<div id="section-8">
  ## Настройка провайдеров входа
</div>

Clerk Auth поддерживает Google, GitHub, Apple и X в качестве провайдеров для входа через социальные сети. На вкладке **Configure** панели Auth можно выбрать, какие провайдеры будут отображаться на странице входа, а также — в среде Production — будут ли они использовать OAuth-учетные данные, управляемые Replit, или собственные пользовательские учетные данные для брендированного входа.

<Frame>
  <img src="/assets/mirror/clerk-configure-60169c473d64.png" alt="Вкладка Configure с провайдерами SSO на боковой панели, выбранной средой Production, списком провайдеров, переключателями активации и действием Edit" width="923" height="378" data-path="images/workspace/auth/clerk-configure.png" />
</Frame>

Откройте вкладку **Configure**. В разделе **SSO providers** на боковой панели выберите **Development** или **Production**: **Development** используется для приложений в разработке и предварительном просмотре в Workspace, а **Production** — для опубликованных приложений. Для каждой среды на основной панели отображается отдельный список. Здесь можно выполнить следующие действия:

* **Включить или отключить провайдера** — используйте переключатель, чтобы управлять отображением провайдера на странице входа. Отключенные провайдеры не видны пользователям.
* **Настроить пользовательские OAuth-учетные данные (только для Production)** — см. раздел [Настройка OAuth-учетных данных для провайдера SSO](#configuring-oauth-credentials-for-an-sso-provider) ниже.

<div id="sso-oauth">
  ### Настройка учетных данных OAuth для SSO-провайдера
</div>

По умолчанию провайдеры используют **учетные данные, управляемые Replit** — вход работает сразу, без дополнительной настройки, но на экране согласия OAuth отображается брендинг Replit. Чтобы использовать собственный OAuth-клиент, созданный в консоли разработчика провайдера, переключитесь на **Custom credentials** — тогда на экране согласия будут отображаться название и брендинг вашего приложения.

1. В Project Editor откройте **панель Auth**. Перейдите на вкладку **Configure**, затем на боковой панели в разделе **SSO providers** выберите **Production**.

<Frame>
  <img src="/assets/mirror/clerk-configure-60169c473d64.png" width="923" height="378" data-path="images/workspace/auth/clerk-configure.png" />
</Frame>

2. Выберите значок **Edit** рядом с провайдером, который хотите настроить. По умолчанию выбраны **Replit-managed credentials**.

<Frame>
  <img src="/assets/mirror/clerk-sso-default-credentials-525090775408.png" alt="Панель редактирования провайдера с вариантами Replit-managed credentials и Custom credentials" width="1468" height="960" data-path="images/workspace/auth/clerk-sso-default-credentials.png" />
</Frame>

3. Выберите **Custom credentials**. Панель развернется и отобразит поля учетных данных, а также контрольный список **Provider setup** со значениями, которые необходимо зарегистрировать у провайдера.

<Frame>
  <img src="/assets/mirror/clerk-sso-custom-credentials-f24112a5cf07.png" alt="Панель Custom credentials с полями идентификатора OAuth-клиента и секрета, а также контрольным списком Provider setup с URL обратного вызова перенаправления и источником JavaScript" width="1468" height="2246" data-path="images/workspace/auth/clerk-sso-custom-credentials.png" />
</Frame>

4. Следуйте инструкциям, чтобы завершить настройку. В них есть ссылки для перехода прямо в консоль и к соответствующей справочной документации. Эту документацию также можно найти в разделе [Дополнительные ресурсы](#additional-resources) для нужного провайдера.
5. Введите все необходимые значения учетных данных.
6. В консоли разработчика провайдера зарегистрируйте в его портале разработчика все элементы из контрольного списка **Provider setup**. Используйте значок копирования, чтобы точно скопировать каждое значение, затем отметьте выполненные элементы или по завершении выберите **Mark all as done**.
7. Выберите **Save changes**.

<div id="section-9">
  ### Повторная проверка настроек после изменения домена
</div>

Действия, связанные с доменом, например подключение нового внешнего домена или [покупка домена через Replit](/ru/ko/build/domain-purchasing), могут изменить URL-адреса обратного вызова для перенаправления и источники JavaScript вашего приложения. В таких случаях провайдерам, настроенным с пользовательскими учетными данными, может потребоваться повторно зарегистрировать новые значения в консоли разработчика.

После изменения домена вернитесь на вкладку **Configure**. Подсказки по настройке отображаются на вкладке, боковой панели и в виде значка предупреждения рядом с провайдером в списке **SSO providers**. Если рядом с провайдером отображаются значок предупреждения и текст **setup steps remaining**, это означает, что в чек-листе **Provider setup** этого провайдера появились новые пункты, которые необходимо выполнить.

<Frame>
  <img src="/assets/mirror/clerk-sso-setup-reminders-a5b092846006.png" alt="Вкладка Configure и боковая панель с предупреждениями о настройке, а также список SSO providers со значком предупреждения и текстом «setup steps remaining» после изменения домена" width="923" height="378" data-path="images/workspace/auth/clerk-sso-setup-reminders.png" />
</Frame>

Откройте панель редактирования провайдера, скопируйте обновлённые значения из раздела **Provider setup** и зарегистрируйте их в консоли разработчика провайдера, затем выберите **Mark all as done**.

<div id="section-10">
  ## Настройка домена для подтверждения электронной почты
</div>

Если ваше приложение поддерживает **регистрацию по электронной почте и паролю**, Clerk отправляет код подтверждения в почтовый ящик нового пользователя. Настройте домен для отправки писем, чтобы коды приходили от имени URL вашего приложения без задержек и не блокировались спам-фильтрами.

<div id="section-11">
  ### Когда нужна эта настройка
</div>

Настраивать DNS-записи нужно только в том случае, если к вашему App подключён **внешний домен** (например, домен, зарегистрированный у Cloudflare, GoDaddy, Namecheap или другого провайдера).

Настройка не требуется, если ваш App доступен по одному из следующих адресов:

* поддомену `.replit.app`
* домену, [приобретённому через Replit](/ru/ko/build/domain-purchasing)

В обоих случаях DNS-записями управляет Replit.

<div id="dns">
  ### Добавление DNS-записей для отправки электронных писем
</div>

Чтобы разрешить приложению отправлять письма с подтверждением с внешнего домена, добавьте набор DNS-записей у своего провайдера домена.

1. Откройте **Publishing** в Project Editor.
2. Выберите **Domains**.
3. Найдите подключённый внешний домен и выберите **Manage**.
4. В разделе **Authentication DNS setup required** скопируйте CNAME-записи, отображаемые Replit — они необходимы Clerk для отправки писем с подтверждением с вашего домена.
5. Войдите в панель своего DNS-провайдера (Cloudflare, GoDaddy, Namecheap и т. д.) и добавьте каждую запись в точности, как указано.

<Frame>
  <img src="/assets/mirror/clerk-domain-8797ea9f41fc.png" alt="Панель управления доменом с разделом Authentication DNS setup required, содержащим CNAME-записи для отправки писем Clerk" width="1156" height="1524" data-path="images/workspace/auth/clerk-domain.png" />
</Frame>

Распространение изменений DNS может занять до 48 часов. После применения записей при регистрации по электронной почте и паролю коды аутентификации будут автоматически отправляться с вашего домена — дополнительных действий в панели Auth не требуется.

<div id="section-12">
  ### Устранение неполадок
</div>

* **Письмо с подтверждением не приходит** — убедитесь, что все записи добавлены в точности так, как указано на панели Manage, включая завершающую точку (trailing dot), если её требует ваш DNS-провайдер. Также проверьте папку «Спам» получателя.
* **Записи по-прежнему не обнаружены** — дождитесь распространения DNS-записей (это может занять до 48 часов), затем ещё раз проверьте панель Manage: возможно, некоторые записи всё ещё отмечены как отсутствующие.

<div id="section-13">
  ## Рекомендации по безопасности
</div>

* **Всегда выполняйте проверку на стороне сервера** — проверяйте аутентификацию не только в UI, но и в API-маршрутах
* **Используйте переменные окружения** — не храните ключи или секреты непосредственно в коде
* **Сначала подключайте прокси-промежуточное ПО** — прокси Clerk должен быть подключён в приложении Express до body parser
* **Не перенаправляйте главную страницу на экран входа** — оставьте лендинг доступным для неаутентифицированных посетителей

<div id="faq">
  ## Часто задаваемые вопросы
</div>

<div id="clerk-auth-clerk">
  ### Нужна ли учётная запись Clerk, чтобы использовать Clerk Auth?
</div>

Нет. Когда Agent настраивает ваше приложение, Replit автоматически создаёт и управляет тенантом Clerk, который обеспечивает работу Clerk Auth. Вам не нужно регистрироваться в Clerk или самостоятельно управлять его инфраструктурой.

<div id="replit-clerk-clerk">
  ### Можно ли получить доступ к панели управления Clerk для экземпляра Clerk, управляемого Replit?
</div>

Нет. Экземпляры Clerk, управляемые Replit, не отображаются в панели управления Clerk. Вместо этого управляйте ими с помощью инструмента **Auth** в Project Editor: здесь можно настраивать провайдеров, просматривать пользователей и переключаться между средами Development и Production.

<div id="clerk-publishable-pk_test">
  ### Публичный ключ Clerk начинается с `pk_test`. Как перейти на рабочий ключ?
</div>

Переходить не нужно. Ключи `pk_test...` и `sk_test...`, отображаемые в панели Secrets Workspace, относятся к среде **Development** Clerk вашего приложения и используются во время разработки. При публикации приложения деплой автоматически выполняется с ключами `pk_live...` и `sk_live...` для среды Production. Чтобы убедиться в этом, в Workspace откройте **Publishing → Overview → Adjust settings** и проверьте значение `CLERK_PUBLISHABLE_KEY` опубликованного приложения — оно будет начинаться с `pk_live`. Не редактируйте эти ключи вручную. Подробнее см. в разделе [Среды Development и Production](#development-and-production-environments).

<div id="section-14">
  ### Почему я не могу войти в опубликованное приложение с учётной записью, созданной во время разработки?
</div>

Среды **Development** и **Production** в Clerk Auth используют отдельные хранилища пользователей. Учётные записи, созданные в приложении для разработки или предварительного просмотра, существуют только в среде Development и не переносятся в Production при публикации — в опубликованном приложении нужно зарегистрироваться заново. То же касается всех данных, где Clerk `userId` используется в качестве ключа. Откройте **панель Auth** в Workspace и с помощью переключателя среды на вкладке **Users** просмотрите пользователей в каждой среде. Подробнее см. в разделе [Отдельные хранилища пользователей](#separate-user-stores).

<div id="clerk-auth">
  ### Clerk Auth бесплатен?
</div>

Сейчас Clerk Auth предоставляется бесплатно. Как и для других сервисов Replit с оплатой по мере использования, в будущем может быть введена плата за использование. Любые будущие платежи будут включены в текущий счёт Replit — отдельный счёт Clerk или способ оплаты не потребуются.

<div id="clerk-auth-clerk-mau">
  ### Есть ли в Clerk Auth ограничение по MAU, как во внешних тарифах Clerk?
</div>

Нет. В отличие от внешних тарифов Clerk с ограничениями по MAU в зависимости от уровня, в Clerk Auth нет ограничений на количество ежемесячно активных пользователей (MAU).

<div id="clerk-auth-clerk-2">
  ### Чем Clerk Auth отличается от внешнего Clerk?
</div>

Управляемый Replit тенант Clerk, лежащий в основе Clerk Auth, отличается от приложения Clerk, которое вы самостоятельно создаёте в своей учётной записи Clerk (**внешний Clerk**). В таблице ниже приведены текущие различия между ними. Она отражает текущее состояние Clerk Auth; набор поддерживаемых функций будет расширяться.

|                                         | Clerk Auth                                                                             | Внешний Clerk                             |
| --------------------------------------- | -------------------------------------------------------------------------------------- | ----------------------------------------- |
| **Настройка**                           | Автоматически предоставляется Replit                                                   | Настраивается вручную                     |
| **Владение тенантом Clerk**             | Управляется Replit и принадлежит приложению                                            | Принадлежит учётной записи Clerk          |
| **Модель ценообразования**              | Сейчас бесплатно (в будущем — оплата на основе использования)                          | Подписка + оплата на основе использования |
| **Выставление счетов**                  | Через Replit (сейчас бесплатно)                                                        | Через учётную запись Clerk                |
| **Лимиты MAU**                          | Без ограничений                                                                        | Лимиты зависят от тарифа                  |
| **Настройка прокси и доменов**          | Автоматически для replit.app и приобретённых доменов, вручную для подключённых доменов | Вручную                                   |
| **Провайдер SSO**                       | Поддерживаются только отдельные провайдеры: Google, Apple, GitHub, X                   | Поддерживается больше провайдеров         |
| **Интерфейс управления пользователями** | Инструмент Auth в Project Editor                                                       | Панель управления приложения Clerk        |
| **SMS**                                 | Не поддерживается                                                                      | Поддерживается                            |
| **MFA**                                 | Не поддерживается                                                                      | Поддерживается                            |
| **Тенанты организаций**                 | Не поддерживаются                                                                      | Поддерживаются                            |

<div id="clerk-auth-2">
  ### Какие распространённые настройки Clerk Auth необходимо выполнить вручную?
</div>

Большинство настроек Clerk Auth автоматизировано, но некоторые из них требуют действий вне инструмента **Auth**.

* **Пользовательские учётные данные OAuth для SSO-провайдера** — если вы хотите, чтобы на экране согласия провайдера отображались название и брендинг вашего приложения вместо значений Replit по умолчанию, зарегистрируйте OAuth-приложение в консоли разработчика провайдера и введите учётные данные в панели Auth. См. [Настройка учётных данных OAuth для SSO-провайдера](#configuring-oauth-credentials-for-an-sso-provider).
* **DNS-записи для подтверждения электронной почты на внешнем домене** — если ваше приложение подключает внешний домен, управляемый другим провайдером, добавьте DNS-записи, чтобы письма с подтверждением отправлялись с этого домена. См. [Настройка домена для подтверждения электронной почты](#domain-setup-for-email-verification).

<div id="replit-clerk-clerk-2">
  ### Можно ли использовать собственное приложение Clerk вместо приложения Clerk, управляемого Replit?
</div>

Да. Если для вашего приложения уже создано приложение Clerk, управляемое Replit, сначала удалите его, прежде чем подключать собственное внешнее приложение Clerk.

1. Откройте панель **Auth** в Project Editor.
2. Перейдите на вкладку **Configure**.
3. Прокрутите страницу до конца и нажмите **Delete Clerk app**.

При удалении приложения Clerk удаляются управляемый Replit тенант Clerk и связанный с ним домен. После этого вы сможете подключить собственное приложение Clerk и повторно использовать этот домен. Если в вашем приложении ещё нет приложения Clerk, управляемого Replit, пропустите этот шаг и сразу интегрируйте внешнее приложение Clerk.
