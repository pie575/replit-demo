Clerk Auth предоставляет вашему приложению выделенную систему аутентификации на базе [Clerk](https://clerk.com). В отличие от [Replit Auth](/ru/ja/features/auth-and-identity/authentication), использующего систему входа Replit и учётные записи Replit, Clerk Auth создаёт **отдельный тенант Clerk** специально для вашего приложения. Пользователи вашего приложения создают учётные записи непосредственно в нём, а не используют учётные записи Replit. Вы получаете полный контроль над брендингом, способами входа и процессом авторизации.

<Note>
  **Clerk Auth и Replit Auth** — **Clerk Auth** (на этой странице) предоставляет вашему приложению собственный тенант аутентификации с полностью настраиваемым брендингом и независимыми от Replit учётными записями пользователей. **[Replit Auth](/ru/ja/features/auth-and-identity/authentication)** позволяет пользователям входить с учётными записями Replit и отображает страницу входа в стиле Replit. Выберите Clerk Auth, если хотите использовать собственный брендинг при входе или вам нужны независимые от Replit учётные записи пользователей.
</Note>

<div id="clerk-auth-vs-replit-auth">
  ## Сравнение Clerk Auth и Replit Auth
</div>

|                                  | Clerk Auth                                                                     | Replit Auth                                                   |
| -------------------------------- | ------------------------------------------------------------------------------ | ------------------------------------------------------------- |
| **Учётные записи пользователей** | Пользователи создают учётные записи в App (учётная запись Replit не требуется) | Пользователи входят с учётной записью Replit                  |
| **Брендинг**                     | Полностью настраиваемый — название App, значок и цвета                         | Страница входа в стиле Replit                                 |
| **Учётные данные SSO**           | Собственные учётные данные OAuth для каждого провайдера                        | Общее OAuth-приложение Replit                                 |
| **Среды**                        | Отдельные среды разработки и продакшена                                        | Единая среда                                                  |
| **Реферальная программа**        | Без интеграции с Replit Referrals                                              | Регистрации учитываются в Replit Referrals                    |
| **Оптимально для**               | App с индивидуальным брендингом и профессиональных/коммерческих продуктов      | Быстрой настройки и App, для которых приемлем брендинг Replit |

<div id="section">
  ## Начало работы
</div>

Добавьте Clerk Auth в App, указав его в промпте для Agent:

```
Помоги мне создать App для [ваша идея приложения] с Clerk Auth.
```

Agent всё сделает сам: создаст tenant Clerk, сохранит учётные данные, настроит маршруты и добавит middleware. Учётная запись Clerk и ручная настройка не понадобятся.

<div id="clerk-authreplit">
  ## Как Clerk Auth работает в Replit
</div>

Когда Agent настраивает Clerk Auth в вашем App, происходит следующее:

1. **Создаётся выделенный тенант Clerk** — ваш App получает собственное приложение Clerk с отдельными средами разработки и продакшен-средой
2. **Настраиваются учётные данные** — API-ключи и секреты сохраняются в переменных окружения
3. **Настраивается прокси** — аутентификация беспрепятственно работает на опубликованном домене
4. **Настраиваются маршруты входа и регистрации** — в ваш App добавляются готовые React-компоненты Clerk
5. **Добавляется серверное промежуточное ПО** — API-маршруты защищаются промежуточным ПО Clerk для Express

<Note>
  Вам не нужно создавать учётную запись Clerk или управлять инфраструктурой. Replit автоматически управляет всем.
</Note>

<div id="section-2">
  ## Возможности
</div>

<div id="section-3">
  ### Поддерживаемые возможности
</div>

Clerk Auth предоставляет вашему App следующее:

* **Отдельные учётные записи пользователей** — пользователи вашего App не являются пользователями Replit и существуют только в тенанте Clerk вашего App
* **Полностью брендированные страницы входа** — настройте название App, логотип, цвета, шрифты и текст в коде вашего App
* **SSO с собственным брендингом** — предоставьте собственный OAuth-клиент для каждого провайдера, чтобы на странице согласия OAuth отображались название и брендинг вашего App, а не значения по умолчанию
* **Аутентификация по электронной почте и паролю** — встроенные регистрация и вход, включая подтверждение адреса электронной почты
* **Вход через социальные сети (SSO)** — разрешите вход через Google, GitHub, Apple и X (Twitter)
* **Управление пользователями** — просматривайте, ищите и модерируйте пользователей на панели Auth
* **Управление сеансами** — безопасные токены сеансов с автоматическим управлением
* **Среды разработки и продакшена** — тестируйте аутентификацию в среде разработки перед публикацией

<Note>
  Большинством настроек Clerk Auth можно управлять с помощью инструмента Auth в Project Editor. Учётная запись Clerk не требуется, и вам не нужно работать с панелью мониторинга Clerk.
</Note>

<div id="section-4">
  ### Неподдерживаемые функции
</div>

В настоящее время Clerk Auth не поддерживает следующие функции (в отличие от внешнего приложения Clerk, которое вы настраиваете самостоятельно). Подробнее см. [в этом FAQ](#how-does-clerk-auth-compare-to-external-clerk).

* **Вход по номеру телефона** — вход и аутентификация с помощью SMS
* **Поддержка MFA** — многофакторная аутентификация для конечных пользователей
* **Полная поддержка провайдеров SSO** — сейчас поддерживаются только Google, GitHub, Apple и X
* **Организационные тенанты** — функции организаций и членства в командах Clerk

<div id="section-5">
  ## Среды разработки и продакшена
</div>

Все App, использующие Clerk Auth, получают две полностью изолированные среды Clerk: **среду разработки** для создаваемых и предварительно просматриваемых App и **продакшен-среду** для опубликованных App. Эти среды изолированы по своей архитектуре: у них отдельные API-ключи и хранилища пользователей.

<div id="api">
  ### Отдельные API-ключи
</div>

Для каждой среды предусмотрены отдельные публикуемый и секретный API-ключи. Ключи, доступные приложению, автоматически переключаются в зависимости от того, работает ли оно в среде разработки или в production-среде:

* В рабочем пространстве Secrets `CLERK_PUBLISHABLE_KEY` и `CLERK_SECRET_KEY` содержат **тестовые ключи** (`pk_test...` и `sk_test...`), указывающие на среду разработки.

<Frame>
  <img src="/assets/mirror/clerk-check-dev-keys-5a23f6b7dd0c.png" alt="Инструмент Secrets в рабочем пространстве с CLERK_SECRET_KEY и CLERK_PUBLISHABLE_KEY с префиксами sk_test_ и pk_test_" width="1946" height="402" data-path="images/workspace/auth/clerk-check-dev-keys.png" />
</Frame>

* После публикации приложения опубликованный деплой использует **боевые ключи** (`pk_live...` и `sk_live...`), указывающие на production-среду. Чтобы проверить префиксы, откройте **Publishing → Overview → Adjust settings** и проверьте `CLERK_PUBLISHABLE_KEY` и `CLERK_SECRET_KEY`.

<Frame>
  <img src="/assets/mirror/clerk-check-prod-keys-acccd7f68da1.png" alt="Секреты Production app в Publishing Overview с CLERK_SECRET_KEY и CLERK_PUBLISHABLE_KEY с префиксами sk_live_ и pk_live_" width="1924" height="1664" data-path="images/workspace/auth/clerk-check-prod-keys.png" />
</Frame>

<Note>
  Вам не нужно ничего делать для переключения между средами. Replit автоматически управляет ключами как для разработки, так и для production-среды. Просто разрабатывайте, тестируйте и публикуйте.
</Note>

<Warning>
  Не заменяйте тестовые ключи боевыми, не редактируйте их в панели Secrets и не настраивайте вручную на панели мониторинга Clerk. Это нарушит автоматическое переключение между средой разработки и production-средой, и Clerk Auth под управлением Replit больше не будет поддерживаться.
</Warning>

<div id="section-6">
  ### Отдельные хранилища пользователей
</div>

В каждой среде используется собственное хранилище пользователей. Аккаунты, зарегистрированные в среде разработки, **не существуют** в продакшен-среде, и наоборот:

* Пользователи, зарегистрировавшиеся при тестировании приложения для разработки или предпросмотра, создаются только в хранилище разработки.
* Пользователи, зарегистрировавшиеся в опубликованном приложении, создаются только в рабочем хранилище.
* Сессии, метаданные пользователей и данные, связанные с `userId` Clerk, также привязаны к среде, в которой был создан аккаунт.

Это ожидаемое поведение. Чтобы просмотреть пользователей в каждой среде, откройте **панель Auth** в рабочем пространстве и с помощью переключателя среды на вкладке **Users** переключайтесь между средой разработки и продакшен-средой.

<Note>
  Среда разработки предназначена для экспериментов и создания приложений. Продакшен-среда обслуживает реальных пользователей опубликованного приложения. Эти среды намеренно разделены: аккаунты и данные, созданные в среде разработки, не отображаются в продакшен-среде.
</Note>

<div id="section-7">
  ## Управление пользователями
</div>

Панель Auth в Project Editor предоставляет полный обзор пользователей, прошедших аутентификацию. Clerk Auth создаёт отдельное хранилище пользователей для приложения, поэтому перечисленные здесь пользователи — это аккаунты приложения, а не учётные записи Replit.

<Frame>
  <img src="/assets/mirror/clerk-users-4940ed365605.png" alt="Вкладка Users в Clerk Auth со списком пользователей, прошедших аутентификацию, на панели Auth" width="2136" height="794" data-path="images/workspace/auth/clerk-users.png" />
</Frame>

На вкладке **Users** можно:

* **Просматривать всех пользователей** со сведениями, включая электронную почту, имя, дату последнего входа и дату создания аккаунта
* **Искать и фильтровать пользователей**, чтобы найти нужного пользователя
* **Блокировать и разблокировать пользователей**, чтобы управлять доступом к приложению
* **Сортировать пользователей** по различным критериям
* **Переключать окружения** — между разработкой и продакшеном, чтобы управлять пользователями в каждом из них

<div id="section-8">
  ## Настройка страницы входа
</div>

Визуальное оформление страниц входа и регистрации (название приложения, логотип, цвета, шрифты и текст) настраивается в коде приложения, а не на панели Auth. Чтобы внести изменения, попросите Agent:

```
Обновите страницу входа: используйте в качестве заголовка [your app name], добавьте [describe your logo] и подберите цвета в соответствии с цветовой схемой сайта.
```

Внутренне это управляется свойствами `appearance` и `localization`, передаваемыми в `<ClerkProvider>`, а также файлом логотипа в каталоге `public/` приложения. Agent синхронизирует их с темой приложения.

<Note>
  Название приложения, отображаемое на **экранах согласия OAuth Google, Apple, GitHub и X** (которые появляются после того, как пользователь нажимает «Войти через Google» и т. п.), отличается. Оно берётся из OAuth-приложения, зарегистрированного у провайдера, и **не изменится**, если вы отредактируете код страницы входа. Чтобы изменить его, настройте [пользовательские учетные данные OAuth для провайдера SSO](#configuring-oauth-credentials-for-an-sso-provider).
</Note>

<div id="section-9">
  ## Настройка провайдеров входа
</div>

Clerk Auth поддерживает Google, GitHub, Apple и X в качестве провайдеров SSO. На вкладке Configure панели Auth можно выбирать, какие провайдеры будут отображаться на странице входа. В Production также можно указать, будет ли каждый провайдер использовать учетные данные OAuth, управляемые Replit, или собственные учетные данные для брендированного входа.

<Frame>
  <img src="/assets/mirror/clerk-configure-60169c473d64.png" alt="Боковая панель с провайдерами SSO, выбранным Production и вкладкой Configure со списком провайдеров, переключателями включения и действиями Edit" width="923" height="378" data-path="images/workspace/auth/clerk-configure.png" />
</Frame>

Откройте вкладку **Configure**. На боковой панели **SSO providers** выберите **Development** или **Production**. **Development** используется для App, находящихся в разработке или предварительном просмотре в рабочем пространстве, а **Production** — для опубликованных App. Список провайдеров для каждой среды отображается на основной панели. Здесь можно:

* **Включать или отключать провайдеры** — с помощью переключателя укажите, отображается ли провайдер на странице входа. Отключённые провайдеры не видны пользователям.
* **Настраивать собственные учетные данные OAuth (только для Production)** — см. раздел [Настройка учетных данных OAuth для провайдера SSO](#configuring-oauth-credentials-for-an-sso-provider) ниже.

<div id="ssooauth">
  ### Настройка учётных данных OAuth для провайдеров SSO
</div>

По умолчанию провайдеры используют **учётные данные, управляемые Replit**. Вход будет доступен сразу, но на экране согласия OAuth будет отображаться брендинг Replit. Переключившись на **Custom credentials**, вы сможете использовать собственный OAuth-клиент из консоли разработчика провайдера, и на экране согласия вместо стандартных будут отображаться название и брендинг вашего приложения.

1. Откройте панель Auth в Project Editor. Перейдите на вкладку Configure и выберите **Production** в разделе **SSO providers** на боковой панели.

<Frame>
  <img src="/assets/mirror/clerk-configure-60169c473d64.png" width="923" height="378" data-path="images/workspace/auth/clerk-configure.png" />
</Frame>

2. Выберите значок **Edit** рядом с провайдером, который хотите настроить. По умолчанию выбраны **Replit-managed credentials**.

<Frame>
  <img src="/assets/mirror/clerk-sso-default-credentials-525090775408.png" alt="Панель редактирования провайдера с вариантами учётных данных, управляемых Replit, и пользовательских учётных данных" width="1468" height="960" data-path="images/workspace/auth/clerk-sso-default-credentials.png" />
</Frame>

3. Выберите **Custom credentials**. Панель развернётся и отобразит поля учётных данных, а также контрольный список **Provider setup** со значениями, которые необходимо зарегистрировать у провайдера.

<Frame>
  <img src="/assets/mirror/clerk-sso-custom-credentials-f24112a5cf07.png" alt="Панель Custom credentials с полями идентификатора и секрета OAuth-клиента, а также контрольным списком Provider setup с URL обратного вызова перенаправления и источниками JavaScript" width="1468" height="2246" data-path="images/workspace/auth/clerk-sso-custom-credentials.png" />
</Frame>

4. Следуйте инструкциям, чтобы завершить настройку. Они содержат прямые ссылки на консоль и соответствующую справочную документацию. Дополнительную справочную документацию для провайдера можно найти в разделе [Additional resources](#additional-resources).
5. Введите все необходимые значения учётных данных.
6. В портале разработчика провайдера зарегистрируйте все значения из контрольного списка **Provider setup**. Используйте значок копирования, чтобы точно скопировать каждое значение, и отмечайте пункты по завершении либо выберите **Mark all as done**, когда всё будет готово.
7. Выберите **Save changes**.

<div id="section-10">
  ### Повторная проверка настройки после изменения домена
</div>

Операции с доменами, например привязка нового внешнего домена или [покупка домена через Replit](/ru/ja/build/domain-purchasing), могут изменить URL-адрес обратного вызова перенаправления и источник JavaScript вашего приложения. В таком случае для провайдеров, настроенных с пользовательскими учётными данными, необходимо зарегистрировать новые значения в консоли разработчика.

После изменения домена вернитесь на вкладку **Configure**. Напоминания о настройке отображаются в виде значков предупреждения на вкладке, боковой панели и рядом с провайдерами в списке **SSO providers**. Если рядом с провайдером отображаются значок предупреждения и **setup steps remaining**, это означает, что в его списке **Provider setup** появились новые пункты, которые необходимо выполнить.

<Frame>
  <img src="/assets/mirror/clerk-sso-setup-reminders-a5b092846006.png" alt="Вкладка Configure и боковая панель с предупреждениями о настройке, а также список SSO providers со значком предупреждения и setup steps remaining рядом с провайдером после изменения домена" width="923" height="378" data-path="images/workspace/auth/clerk-sso-setup-reminders.png" />
</Frame>

Откройте панель редактирования провайдера, скопируйте обновлённые значения из **Provider setup**, зарегистрируйте их в консоли разработчика провайдера, а затем выберите **Mark all as done**.

<div id="section-11">
  ## Настройка домена для аутентификации по электронной почте
</div>

Если ваше App поддерживает **регистрацию с помощью электронной почты и пароля**, Clerk отправляет код подтверждения на почту каждому новому пользователю. Настроив домен для отправки писем, вы обеспечите доставку кодов с URL вашего App без задержек и блокировки спам-фильтрами.

<div id="section-12">
  ### Когда нужна эта настройка
</div>

Настроить эти DNS-записи нужно, только если к вашему App привязан **внешний домен, управляемый другим провайдером** (например, домен, зарегистрированный через Cloudflare, GoDaddy, Namecheap или аналогичный сервис).

Настройка не требуется в следующих случаях:

* Если App размещено на поддомене `.replit.app`
* Для доменов, [приобретённых через Replit](/ru/ja/build/domain-purchasing)

В обоих случаях DNS-записями управляет Replit.

<div id="dns">
  ### Добавление DNS-записей для отправки писем
</div>

Чтобы разрешить приложению отправлять письма для аутентификации с внешнего домена, добавьте у своего регистратора домена набор DNS-записей.

1. Откройте **Publishing** в Project Editor.
2. Выберите **Domains**.
3. Найдите привязанный внешний домен и выберите **Manage**.
4. В разделе **Authentication DNS setup required** скопируйте CNAME-записи, отображаемые Replit. Они необходимы Clerk для отправки писем для аутентификации с вашего домена.
5. Войдите в систему у своего DNS-провайдера (например, Cloudflare, GoDaddy или Namecheap) и добавьте каждую запись в точности так, как показано.

<Frame>
  <img src="/assets/mirror/clerk-domain-8797ea9f41fc.png" alt="Панель управления доменом с разделом Authentication DNS setup required, содержащим CNAME-записи для отправки писем Clerk" width="1156" height="1524" data-path="images/workspace/auth/clerk-domain.png" />
</Frame>

Распространение изменений DNS может занять до 48 часов. Когда записи станут активны, при регистрации с помощью электронной почты и пароля коды аутентификации будут автоматически отправляться с вашего домена. Дополнительные действия на панели Auth не требуются.

<div id="section-13">
  ### Устранение неполадок
</div>

* **Письмо для подтверждения не приходит** — Убедитесь, что все записи добавлены в точности так, как указано на панели Manage. Добавьте завершающую точку, если её требует ваш DNS-провайдер. Проверьте папку «Спам» получателя.
* **Записи всё ещё не обнаружены** — Подождите распространения изменений DNS (до 48 часов), затем ещё раз проверьте записи, отмеченные на панели Manage как отсутствующие.

<div id="section-14">
  ## Лучшие практики безопасности
</div>

* **Всегда проверяйте на стороне сервера** — проверяйте аутентификацию в API-маршрутах, а не только в UI
* **Используйте переменные окружения** — не храните ключи и секреты непосредственно в коде
* **Подключайте прокси-промежуточное ПО первым** — в приложениях Express прокси Clerk необходимо подключать перед парсерами тела запроса
* **Не перенаправляйте главную страницу на страницу входа** — неаутентифицированные посетители должны иметь доступ к целевой странице

<div id="faq">
  ## Часто задаваемые вопросы
</div>

<div id="clerk-authclerk">
  ### Нужна ли учётная запись Clerk для использования Clerk Auth?
</div>

Нет. Тенант Clerk для Clerk Auth автоматически создаётся и управляется Replit, когда Agent настраивает App. Вам не нужно регистрироваться в Clerk или самостоятельно управлять инфраструктурой Clerk.

<div id="replitclerkclerk">
  ### Можно ли получить доступ к панели мониторинга Clerk для экземпляров Clerk, управляемых Replit?
</div>

Нет. Экземпляры Clerk, управляемые Replit, недоступны через панель мониторинга Clerk. Вместо этого управляйте ими с помощью инструмента Auth в Project Editor. Там можно настраивать провайдеров, просматривать пользователей и переключаться между средами разработки и продакшена.

<div id="clerkpk_test">
  ### Публичный ключ Clerk начинается с `pk_test`. Как переключиться на ключ для продакшен-среды?
</div>

Переключаться не нужно. Ключи `pk_test...` и `sk_test...`, отображаемые на панели Secrets в рабочем пространстве, относятся к **среде разработки** Clerk, используемой вашим App при сборке. При публикации App деплой автоматически использует ключи `pk_live...` и `sk_live...` для продакшен-среды. Чтобы проверить это, в рабочем пространстве откройте **Publishing → Overview → Adjust settings** и проверьте значение `CLERK_PUBLISHABLE_KEY` опубликованного App. Оно должно начинаться с `pk_live`. Не изменяйте эти ключи вручную. Подробнее см. в разделе [Среды разработки и продакшен-среды](#development-and-production-environments).

<div id="section-15">
  ### Почему я не могу войти в опубликованное App, используя аккаунт, созданный при разработке?
</div>

Среды **разработки** и **продакшена** Clerk Auth используют разные хранилища пользователей. Аккаунты, созданные в приложении для разработки или предварительного просмотра, существуют только в среде разработки и не копируются в продакшен при публикации. В опубликованном App необходимо зарегистрироваться заново. То же касается данных, связанных с `userId` Clerk. Откройте **панель Auth** в рабочем пространстве и с помощью переключателя среды на вкладке **Users** просмотрите пользователей в каждой среде. Подробнее см. в разделе [Раздельные хранилища пользователей](#separate-user-stores).

<div id="clerk-auth">
  ### Можно ли пользоваться Clerk Auth бесплатно?
</div>

Сейчас Clerk Auth предоставляется бесплатно. Как и в случае с другими сервисами Replit с оплатой по мере использования, в будущем может быть введена такая тарификация. Будущие платежи будут выставляться через существующий биллинг Replit. Отдельные счета или способы оплаты Clerk не потребуются.

<div id="clerk-authmau">
  ### Есть ли у Clerk Auth ограничение на количество ежемесячно активных пользователей (MAU)?
</div>

Нет. В отличие от внешних тарифов Clerk, где лимит MAU зависит от тарифа, Clerk Auth не ограничивает количество MAU.

<div id="clerk-authexternal-clerk">
  ### Чем Clerk Auth отличается от External Clerk?
</div>

Управляемый Replit тенант Clerk, используемый в Clerk Auth, отличается от приложений Clerk (**External Clerk**), созданных в учётной записи Clerk. В таблице ниже приведены текущие различия. Она отражает текущее состояние Clerk Auth; список поддерживаемых функций будет расширяться.

|                                         | Clerk Auth                                                                                | External Clerk                          |
| --------------------------------------- | ----------------------------------------------------------------------------------------- | --------------------------------------- |
| **Настройка**                           | Автоматически подготавливается Replit                                                     | Настраивается самостоятельно            |
| **Владение тенантом Clerk**             | Управляется Replit, принадлежит App                                                       | Принадлежит учётной записи Clerk        |
| **Модель ценообразования**              | Сейчас бесплатно (в будущем — оплата по мере использования)                               | Подписка + оплата по мере использования |
| **Биллинг**                             | Биллинг Replit (сейчас бесплатно)                                                         | Биллинг через учётную запись Clerk      |
| **Ограничения MAU**                     | Без ограничений                                                                           | Зависят от тарифа                       |
| **Настройка прокси и доменов**          | replit.app и приобретённые домены настраиваются автоматически, связанные домены — вручную | Вручную                                 |
| **Провайдеры SSO**                      | Поддерживаются только определённые провайдеры: Google, Apple, GitHub, X                   | Поддерживается больше провайдеров       |
| **Интерфейс управления пользователями** | Инструмент Auth в Project Editor                                                          | Панель мониторинга приложения Clerk     |
| **SMS**                                 | Не поддерживается                                                                         | Поддерживается                          |
| **MFA**                                 | Не поддерживается                                                                         | Поддерживается                          |
| **Тенанты организаций**                 | Не поддерживается                                                                         | Поддерживается                          |

<div id="clerk-auth-2">
  ### Какие настройки Clerk Auth нужно выполнить вручную?
</div>

Большая часть настроек Clerk Auth автоматизирована, но некоторые из них необходимо выполнить за пределами инструмента Auth:

* **Пользовательские учетные данные OAuth для SSO-провайдера** — если вы хотите, чтобы на экране согласия провайдера отображались название и брендинг вашего приложения, а не данные Replit по умолчанию, зарегистрируйте OAuth-приложение в консоли разработчика провайдера и вставьте учетные данные на панели Auth. См. [Настройка учетных данных OAuth для SSO-провайдера](#configuring-oauth-credentials-for-an-sso-provider).
* **DNS-записи для подтверждения электронной почты на внешнем домене** — если ваше приложение связано с внешним доменом, управляемым другим провайдером, добавьте DNS-записи, чтобы письма для подтверждения отправлялись с этого домена. См. [Настройка домена для подтверждения электронной почты](#domain-setup-for-email-verification).

<div id="replitclerkclerk-2">
  ### Можно ли использовать собственное приложение Clerk вместо приложения Clerk, управляемого Replit?
</div>

Да. Если для вашего приложения уже создано приложение Clerk, управляемое Replit, сначала удалите его, прежде чем подключать собственное внешнее приложение Clerk:

1. Откройте панель Auth в Project Editor.
2. Перейдите на вкладку Configure.
3. Прокрутите страницу до конца и нажмите **Delete Clerk app**.

При удалении приложения Clerk удаляются тенант Clerk, управляемый Replit, и связанные с ним домены. Затем вы сможете подключить собственное приложение Clerk и повторно использовать эти домены. Если для вашего приложения ещё не создано приложение Clerk, управляемое Replit, пропустите этот шаг и сразу подключите внешнее приложение Clerk.
