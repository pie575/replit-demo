Les erreurs arrivent : une mauvaise modification de schéma, des lignes supprimées ou une session Agent qui a mal tourné. Replit vous offre une solution de récupération pour chaque base de données.

| Base de données | Méthode de récupération                                         | Disponibilité                                                                                   |
| --------------- | --------------------------------------------------------------- | ----------------------------------------------------------------------------------------------- |
| Développement   | Rollback vers un point de contrôle                              | Tous les forfaits                                                                               |
| Production      | Restauration à un point dans le temps et sauvegardes planifiées | Core : jusqu'à 7 jours d'historique. Pro et Enterprise : jusqu'à 28 jours (7 jours par défaut). |

## Restaurer votre base de données de développement

Vous pouvez ramener votre application et votre base de données de développement à un état précédent grâce à la [fonctionnalité de rollback](/fr/features/version-control/checkpoints-and-rollbacks/). Cela restaure votre base de données à n'importe quel point de contrôle créé par Agent.

<Frame>
  <img src="/assets/mirror/checkpoint-rollback-476fde84864b.png" alt="Interface de rollback de point de contrôle affichant les options de rollback" width="3154" height="2366" data-path="images/replitai/checkpoint-rollback.png" />
</Frame>

<Info>
  Assurez-vous de sélectionner « Database » sous « Additional rollback options » lors de la restauration à l'état d'un point de contrôle. Cela restaurera votre base de données à l'état qu'elle avait au moment du point de contrôle.
</Info>

## Restaurer votre base de données de production

Pour les bases de données de production, vous pouvez restaurer à un moment précis à l'aide de la restauration à un point dans le temps.

<Frame>
  <img src="/assets/mirror/database-rollbacks-f13dd20874ae.jpg" alt="Interface de rollback de base de données montrant les options de rollback" width="1082" height="708" data-path="images/databases/database-rollbacks.jpg" />
</Frame>

La durée de restauration disponible dépend de votre forfait et de votre paramètre de rétention. Le forfait Core conserve jusqu'à 7 jours d'historique, tandis que les forfaits Pro et Enterprise conservent jusqu'à 28 jours. Tous les forfaits commencent avec une fenêtre de 7 jours, que vous pouvez modifier dans les paramètres de votre base de données de production. Des fenêtres plus longues utilisent davantage de stockage, ce qui augmente vos coûts d'utilisation si vous étendez la rétention. Si vous rétrogradez de Pro à Core, votre fenêtre de rétention est réduite à 7 jours.

<Warning>
  La restauration de votre base de données ne restaure pas le code de votre application, et l'annulation (rollback) de votre application ne restaure pas votre base de données. Pour ramener les deux au même moment : restaurez la base de données, puis [effectuez un rollback vers le point de contrôle correspondant](/fr/features/version-control/checkpoints-and-rollbacks/) et republiez votre application.
</Warning>

## Planifier les sauvegardes de la base de données de production

Les sauvegardes planifiées créent un point de restauration complet chaque jour. Replit planifie la sauvegarde à proximité de minuit dans le fuseau horaire actuel de votre navigateur lorsque vous activez ou mettez à jour la planification.

1. Ouvrez l'outil **Database** et sélectionnez la base de données de production.
2. Ouvrez **Settings**, puis développez **Scheduled backups** sous **Advanced**.
3. Pour activer les sauvegardes planifiées, sélectionnez une période de rétention sous **Keep backups for**.

Les périodes de rétention disponibles dépendent de votre forfait. Core prend en charge jusqu'à 7 jours. Pro et Enterprise prennent en charge jusqu'à 28 jours.

### Coûts de stockage

Replit facture séparément chaque catégorie de stockage de la base de données de production :

| Catégorie de stockage                                    | Prix par Gio par mois |
| -------------------------------------------------------- | --------------------: |
| Stockage de la base de données logique                   |               0,35 \$ |
| Stockage de restauration à un point dans le temps (PITR) |               0,20 \$ |
| Stockage des sauvegardes planifiées                      |               0,09 \$ |

<Note>Les coûts de stockage de base de données sont actuellement réduits de 100 %.</Note>

Les frais de stockage logique de 0,35 \$ s'appliquent que vous utilisiez le PITR, les sauvegardes planifiées, ou les deux. Le stockage des sauvegardes planifiées coûte moins cher par Gio que le stockage PITR. Si des points de restauration quotidiens suffisent à vos besoins, combiner des sauvegardes planifiées avec une fenêtre PITR plus courte peut réduire les coûts de stockage de récupération. Votre coût total de sauvegarde dépend du volume de sauvegarde stocké et de la période de rétention.

Le PITR offre davantage de points de restauration au sein de sa fenêtre. Les sauvegardes planifiées offrent un point de restauration par jour ; choisissez donc la méthode de récupération qui correspond à vos besoins.

<Note>
  La planification utilise votre décalage UTC actuel. Un changement d'heure d'été ou d'hiver peut décaler l'heure de sauvegarde d'une heure jusqu'à ce que vous mettiez à jour la planification. Les fuseaux horaires à décalage fractionnaire utilisent l'heure la plus proche.
</Note>

### Restaurer une sauvegarde planifiée

1. Ouvrez **Scheduled backups** dans les paramètres de la base de données de production.
2. Sélectionnez **View all backups**.
3. Sélectionnez **Restore** pour le point de restauration souhaité.
4. Saisissez `restore`, puis sélectionnez **Continue**.

La restauration fait basculer votre base de données vers les données de la sauvegarde sélectionnée. Les données actuelles ne sont pas supprimées, mais les services connectés peuvent se reconnecter brièvement.

## Résolution des échecs de publication

Si la publication échoue en raison de problèmes de base de données :

1. **Vérifiez les journaux de publication** pour des messages d'erreur spécifiques concernant la connectivité de la base de données ou les conflits de schéma
2. **Examinez les modifications de schéma récentes** pour détecter des conflits potentiels avec le code d'application existant
3. **Testez vos modifications dans un environnement de prévisualisation de déploiement** avant de tenter de republier
