氛围编程让你能更快地将想法变成软件。你不必从编写代码开始，而是先描述你想要实现的内容，再借助 AI 将这一构想转化为可查看、测试和改进的功能完善的 App。

Replit 正是为这种迭代循环而设计的。你可以描述想法、预览结果、提供反馈、进行修改，并在同一平台完成发布。

本页面介绍氛围编程背后的思维方式。下一页[使用 Agent 构建](/zh/pt/learn/build-with-agent)将介绍如何使用 Agent 工具。[有效提示词](/zh/pt/learn/effective-prompting)将介绍如何编写更清晰的指令。

<div id="o-software-costumava-ser-um-loop-de-equipe">
  ## 软件开发曾是一个团队协作闭环
</div>

软件通常由团队共同开发。

产品经理或创始人决定要构建什么，以及为什么要构建。设计师塑造用户体验。开发者将想法转化为可运行的软件。团队成员负责测试、提供反馈、发现漏洞，并决定哪些内容已准备好发布。

这种协作很有价值，因为每个角色都能带来不同的判断。产品决定什么最重要。设计决定它应该呈现什么样子。工程决定它应该如何运行。测试决定它是否真的可用。

但这个闭环可能很慢。每次变更都必须经历交接：解释想法、设计流程、编写代码、审查结果、测试，然后再修改。

氛围编程缩短了这个闭环。

借助 Replit，你可以独自完成更多产品构建流程。你可以设定目标、生成初始版本、进行测试、提供反馈并持续改进，无需等待每个步骤在不同人员和工具之间流转。

<div id="seu-papel-muda">
  ## 你的角色变了
</div>

你无需成为开发者，也能开始构建。

在氛围编程中，你的角色更接近产品负责人。你决定要做什么、面向谁、什么最重要，以及结果是否足够好。

Agent 协助实现，但你仍然主导整个过程。

你带来：

* 目标
* 受众
* 品味
* 约束条件
* 反馈
* 决定发布什么

Agent 可以帮助你：

* 将想法转化为可用的软件
* 做出修改
* 解释行为
* 调试问题
* 持续改进 App

你领导得越好，Agent 就能构建得越好。

<div id="os-cinco-princpios">
  ## 五项原则
</div>

遵循以下五项简单原则，vibe coding 能发挥更好的效果：

1. 从目标出发。
2. 分小步构建。
3. 管理上下文。
4. 审查并测试。
5. 根据反馈改进。

第一项原则确定方向。接下来的四项会循环往复：构建一小步，提供恰当的上下文，审查并改进，然后再构建下一小步。

这些原则比写好第一个完美的提示词更重要。你很少能一步到位就获得最终的 App。关键是保持清晰的迭代节奏，不断推进。

<div id="comece-com-o-objetivo">
  ## 从目标出发
</div>

一次好的氛围编程会话，就像一次好的产品沟通：

这是为谁做的？他们应该能够做什么？怎样才能让它真正有用？

在让 Replit 开始构建之前，先描述你想要达成的结果。

<AiPrompt>
  为一家本地面包店创建一个简单的网站。顾客应能查看每日特惠、了解餐饮服务，并提交餐饮服务请求。让它温馨、精致，并且方便在手机上使用。
</AiPrompt>

之所以有效，是因为它为 Replit 提供了产品目标，而不只是一项任务。它明确了目标用户、核心操作，以及首个版本应具备的体验。

你暂时不需要了解技术实现。先从 App 正常运行时应达到什么效果开始。

<div id="construa-em-pequenas-fatias">
  ## 分阶段构建
</div>

每个阶段都是产品中一个足够完整、可以试用的小部分。

对于面包店网站，第一个阶段可以包括：

* 一个展示当日特价商品的首页
* 一个自助餐预订表单
* 一个适配手机的布局

这已经足够用来验证这个想法。你可以打开并浏览它，再决定下一步需要改进什么。

避免一次性要求构建整个产品。大型请求更难审查，也更容易被误解。分阶段构建能帮助你稳步推进，同时保持掌控。

第一个阶段完成后，再添加下一个。

<AiPrompt>
  在有人提交自助餐预订表单后添加一条确认消息。保持页面其余部分不变。
</AiPrompt>

这条指令简短、清晰且可验证。

<div id="gerencie-o-contexto">
  ## 管理上下文
</div>

上下文是 Replit 用来理解你需求的信息。

良好的上下文可以包括：

* App 面向哪些人
* 它要解决什么问题
* 当前应包含哪些内容
* 哪些内容应留到以后处理
* 哪些内容不应更改
* 示例、截图、草图、文件或数据
* 关于语气、风格或品牌的说明

管理上下文意味着在恰当的时机提供恰当的信息。

如果你正在继续开发同一项功能，请留在同一个对话中，以便 Replit 可以利用之前做出的决定。如果你要开始开发另一项功能，或者对话内容变得混乱，最好重新开始，并简要说明重要信息。

例如：

<AiPrompt>
  上下文：这个面包店网站面向为生日蛋糕下单的忙碌家长。请保持表单简洁，让取货信息一目了然，并避免任何企业化的感觉。这次只需改进餐饮服务咨询部分。
</AiPrompt>

你不只是添加更多文字，而是在帮助 Replit 聚焦。

<div id="revise-e-teste">
  ## 审查和测试
</div>

Agent 可以构建，但是否真正可用由你决定。

每次做出重大更改后，都要打开 App，像目标用户一样亲自使用。不要只看 Agent 所说的改动。实际体验整个流程。

问问自己：

* 用户能否完成主要操作？
* 页面是否合理？
* 在手机上能否正常使用？
* 是否有重要功能损坏？
* Replit 是否改动了本应保持不变的内容？
* 是否已经足够好，可以继续构建？

审查和测试是最需要发挥产品判断力的环节。你需要确认软件是否符合最初的意图。

<div id="melhore-com-feedback">
  ## 根据反馈改进
</div>

一个功能切片的初始版本只是草稿。这很正常。

Vibe coding 会通过反馈不断改进。告诉 Replit 哪些内容要保留、修改、移除，以及接下来要尝试什么。

不要这样说：

<AiPrompt>
  改进这个。
</AiPrompt>

试试这样说：

<AiPrompt>
  让自助餐申请表更便于快速浏览。保留现有字段，但改进间距、标签和提交按钮。不要更改特价菜部分。
</AiPrompt>

好的反馈应当具体明确。它能在改进 App 某个部分的同时，保留已经有效的内容。

当这个功能切片可以正常运行后，回到循环中，构建下一个小功能切片。

如果某项更改偏离了正确方向，请缩小改动范围。

<AiPrompt>
  这改动太大了。保留新的按钮样式，但恢复原始布局，并且只更新自助餐表单。
</AiPrompt>

根据反馈改进，能让产品持续推进，同时保持掌控。

<div id="como-parece-um-bom-vibe-coding">
  ## 良好的 vibe coding 是什么样的
</div>

出现以下情况时，说明你方向对了：

* 你能用简单的语言说明目标
* 每次改动都足够小，便于审查
* Agent 完成构建后，你知道接下来要测试什么
* 你会提供上下文，而不是猜测 Agent 知道什么
* 你会告诉 Agent 哪些内容需要保留，而不只是说明要改什么
* 每一轮之后，App 都会变得更实用

vibe coding 并不意味着提出一个想法后就撒手不管。它意味着缩短想法、软件、反馈和改进之间的距离。
