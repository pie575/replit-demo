Les compétences confèrent de nouvelles capacités à Agent. En partageant votre expertise, vos modèles préférés et vos connaissances spécialisées avec Agent, vous lui permettez de produire des résultats meilleurs et plus cohérents.

<div id="section">
  ## Pourquoi les compétences sont importantes
</div>

Chaque fois que vous développez avec Agent, vous créez un contexte utile : solutions à des problèmes, choix de conception, préférences de frameworks. Mais ce contexte disparaît à la fin de la conversation. Les compétences le préservent.

Une compétence d’animation GSAP apprend à Agent à utiliser correctement une bibliothèque spécifique. Une compétence de système de design garantit l’application exacte des règles de couleur et d’espacement. Une compétence de correction de bugs consigne les solutions afin qu’Agent ne répète pas les mêmes erreurs. Des tâches autrefois peu cohérentes deviennent fiables.

Les compétences constituent également une [norme ouverte](https://agentskills.io/specification). Elles fonctionnent avec n’importe quel agent, y compris Replit Agent, ce qui vous permet de les utiliser d’un outil à l’autre.

<div id="vs">
  ## Compétences proactives ou réactives
</div>

Un cadre pour déterminer quand et comment créer des compétences. Comprendre ces deux approches vous permettra de gagner en efficacité.

<div id="section-2">
  ### Compétences proactives
</div>

Les compétences proactives sont celles que vous ajoutez *avant de* commencer à créer votre application. Recherchez les bibliothèques et les modèles que vous souhaitez utiliser, trouvez ou créez les compétences correspondantes, puis saisissez votre prompt.

**Exemple :** Avant de créer un site portfolio avec des animations SVG imitant le dessin à la main, recherchez des bibliothèques d’animation et choisissez GSAP. Installez la compétence GSAP React, puis demandez à Agent de créer les animations. Agent dispose dès le départ de l’expertise nécessaire : il comprend l’API de la bibliothèque, les bonnes pratiques et les modèles courants. Sans cette compétence, il risque de générer quelque chose de générique ou d’imprécis.

Ce modèle est efficace lorsque :

* Vous utilisez une bibliothèque populaire, mais avec des modèles spécifiques qu’Agent ne maîtrise pas seul
* Vous souhaitez faire des choix de conception cohérents dans l’ensemble de votre projet (typographie, espacement, style d’animation)
* Vous démarrez un projet et connaissez déjà votre orientation technique

<div id="section-3">
  ### Compétences réactives
</div>

Les compétences réactives sont créées *après* avoir résolu un problème. Vous rencontrez un problème, le déboguez avec Agent, le corrigez, puis consignez la solution pour éviter qu’il ne se reproduise.

**Exemple :** Lors de la création d’un canevas pour une application mobile, vous remarquez des contours d’image crénelés qui s’aggravent à mesure que vous zoomez. Le débogage avec Agent révèle qu’il s’agit d’aliasing de minification — un problème de rendu qui, paradoxalement, s’aggrave à mesure que l’image rétrécit. Après avoir appliqué le correctif, vous demandez à Agent de créer une compétence :

<AiPrompt>
  Crée une compétence qui consigne ce que nous venons d’apprendre sur la correction de l’aliasing de minification. Inclus la cause racine, la solution et les situations dans lesquelles ce problème se produit généralement afin de pouvoir l’éviter à l’avenir.
</AiPrompt>

Agent utilise l’historique de la conversation pour rédiger une compétence propre au projet. La prochaine fois que ce problème se produit, il vous suffit de montrer la compétence à Agent pour éviter de reprendre le débogage depuis le début.

Ce modèle est efficace lorsque :

* Vous avez corrigé un bug difficile à identifier et souhaitez éviter qu’il ne se reproduise
* Vous avez appris quelque chose sur l’architecture de votre application pendant une session de débogage
* Vous souhaitez consigner une solution dont la découverte a demandé beaucoup d’efforts

<div id="section-4">
  ## Utiliser les compétences avec discernement
</div>

Les compétences sont comme les indications que vous donneriez à un ami pour se rendre chez vous. Une liste d’instructions ciblées fonctionne. Un classeur de documentation, non : personne n’a le temps de le lire et des détails importants risquent de passer inaperçus.

Il en va de même pour Agent. Si vous ajoutez trop de compétences, Agent risque de s’y perdre. Choisissez soigneusement les compétences à activer pour un projet donné et supprimez celles dont vous n’avez plus besoin.

<Note>
  Les compétences sont plus efficaces lorsqu’elles capturent des modèles spécifiques et reproductibles plutôt que des conseils généraux. Concentrez-vous sur des flux de travail précis, des conventions établies et des solutions éprouvées.
</Note>

<div id="section-5">
  ## Bien concevoir des compétences
</div>

Les compétences peuvent devenir complexes et sophistiquées. Voici quelques principes pour qu&#39;elles restent efficaces :

* **Décrivez le scénario nominal.** Indiquez à Agent la bonne marche à suivre. Si vous vous surprenez à dresser une liste de choses à ne pas faire, c&#39;est le signe qu&#39;il faut repenser l&#39;approche dans son ensemble.
* **Utilisez des scripts autant que possible.** Les scripts déterministes réduisent la charge de raisonnement d&#39;Agent et sont plus fiables que de le faire réfléchir aux mêmes étapes à chaque fois.
* **Créez des renvois.** Structurez les compétences comme des pointeurs vers d&#39;autres fichiers Markdown afin qu&#39;Agent ne charge que ce dont il a besoin pour la tâche en cours.
* **Évaluez-les régulièrement.** C&#39;est le seul moyen de vérifier que vos compétences fonctionnent réellement.
* **Rédigez-les vous-même.** L&#39;objectif est de fournir un contexte concis et intentionnel, ce que vous pouvez faire en rédigeant les compétences à la main plutôt qu&#39;en les générant en bloc. Vous pouvez demander à Agent de vous aider à préparer un brouillon, mais peaufinez-le vous-même afin que chaque ligne ait une raison d&#39;être.
* **Gardez-les sur mesure.** Ne créez pas de compétences génériques pour la propreté du code ou la sécurité : elles sont déjà intégrées à Agent. Les compétences doivent capturer ce qui est propre à vous ou à votre organisation.

Les échecs des compétences suivent des schémas faciles à diagnostiquer :

* **Une compétence se déclenche alors qu&#39;elle ne devrait pas.** Sa description est trop large. Affinez-la et précisez les cas où elle ne doit pas être utilisée : les instructions négatives telles que « Ne pas utiliser pour les articles de blog ou la documentation d&#39;aide » sont souvent plus utiles que les instructions positives.
* **Une compétence se déclenche, mais le résultat est incohérent.** Les instructions sont trop génériques. Remplacez les conseils vagues comme « Rendez cela professionnel » par des règles concrètes (noms précis, exigences spécifiques et éléments à éviter explicitement).
* **Deux compétences entrent en conflit.** Modifiez les descriptions afin qu&#39;elles ne se déclenchent pas toutes les deux pour la même tâche. Les conflits sont presque toujours un problème de périmètre, et non d&#39;instructions.

Les compétences vieillissent. Traitez-les comme des documents que vous entretenez réellement.

<div id="section-6">
  ## Appliquer des compétences à l’ensemble de l’espace de travail
</div>

Tout ce qui précède s’applique aux compétences d’un seul projet. Les équipes peuvent également personnaliser Agent à l’échelle de l’espace de travail afin que chacun parte des mêmes conventions. La personnalisation de l’espace de travail comporte deux éléments :

* **Instructions personnalisées** — Règles toujours actives injectées dans le contexte d’Agent avant que quiconque ne saisisse un prompt, pour tous les projets et tous les messages. Réservez-les aux règles véritablement universelles, telles que « Ne stockez pas les identifiants en clair ». Elles sont chargées à chaque tour : chaque mot utilise donc une partie du budget de contexte d’Agent. Restez concis.
* **Compétences d’espace de travail** — Les mêmes compétences décrites ci-dessus, disponibles pour tous les membres de l’espace de travail et gérées de manière centralisée. Elles ne coûtent presque rien tant qu’une tâche pertinente ne les sollicite pas, ce qui vous permet d’en proposer beaucoup sans dégrader les résultats.

Pour décider simplement où placer chaque élément : les règles à respecter, quel que soit ce que chacun construit, vont dans les instructions personnalisées ; celles qui ne concernent qu’un type de tâche spécifique vont dans les compétences.

Pour savoir comment configurer les instructions personnalisées et les compétences d’espace de travail, ainsi que qui peut les gérer, consultez [Personnalisation d’Agent](/fr/ja/features/agent/agent-customization).

<div id="section-7">
  ## À propos de la sécurité
</div>

Les compétences du panneau Skills de Replit ont fait l&#39;objet d&#39;un contrôle de sécurité. Toutefois, vous pouvez installer des compétences depuis n&#39;importe où : elles proviennent d&#39;un [dépôt open source](https://github.com/vercel-labs/skills) auquel chacun peut contribuer.

Les compétences sont des instructions que suit Agent. Une compétence malveillante pourrait donc demander à Agent d&#39;exfiltrer des données sensibles de votre projet. Avant d&#39;installer une compétence depuis une source externe :

1. **Ouvrez les fichiers.** Les compétences ne sont que du Markdown. Lisez le contenu de `/.agents/skills/` avant de les utiliser.
2. **Vérifiez la source.** Assurez-vous que la compétence provient d&#39;un dépôt ou d&#39;un auteur de confiance.
3. **Examinez les instructions.** Assurez-vous que la compétence ne renvoie pas vers des URL externes suspectes et ne demande pas d&#39;informations sensibles.

<Warning>
  Vérifiez toujours les compétences provenant de sources externes avant de les installer. Les compétences du panneau Skills de Replit ont fait l&#39;objet d&#39;un contrôle de sécurité, mais ce n&#39;est pas le cas de celles installées via la CLI ou copiées depuis Internet.
</Warning>

<div id="vs-mcp">
  ## Compétences vs serveurs MCP
</div>

Les compétences et les serveurs MCP sont les deux principaux moyens d’étendre les agents, chacun répondant à des besoins différents.

**Les compétences** sont économes en contexte. Seule une brève description est chargée jusqu’à ce qu’une compétence soit appelée. Utilisez des compétences pour :

* Les flux de travail et les conventions (« Comment déployer », « Checklist de revue de code »)
* Les documents de référence (modèles d’API, guides de style, systèmes de design)
* Les prompts réutilisables et les connaissances spécialisées (bibliothèques d’animation, modèles de framework)

**Les serveurs MCP** sont gourmands en contexte. Toutes les descriptions des outils sont chargées dès le départ ; en ajouter trop peut donc réduire la qualité des résultats. Utilisez des serveurs MCP pour :

* Vous connecter à des services externes (Notion, Linear, Figma)
* Les actions nécessitant un accès à une API
* Les outils qui *font réellement quelque chose* plutôt que de simplement vous guider

La différence essentielle : les compétences définissent *comment* Agent doit fonctionner. Les serveurs MCP définissent *à quoi* Agent peut accéder. Les deux fonctionnent aussi bien avec des agents de code comme Replit Agent qu’avec les agents que vous créez vous-même.
