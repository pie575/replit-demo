Ces réponses portent sur la publication et les déploiements. Pour un dépannage étape par étape, consultez [Dépannage des déploiements](/fr/build/troubleshooting). Pour en savoir plus sur les types de déploiement et la surveillance, consultez [Déploiements Autoscale](/fr/features/publishing/deployment-types#autoscale) et [Surveiller un déploiement](/fr/features/publishing/monitoring-a-deployment).

<AccordionGroup>
  <Accordion title="Ma publication échoue à l’étape « Creating Autoscale service » : comment résoudre ce problème ?">
    La plupart des échecs de publication Autoscale peuvent être résolus en consultant les logs de déploiement :

    1. Ouvrez **Publishing** et recherchez le déploiement ayant échoué.
    2. Sélectionnez le menu à trois points à côté de celui-ci pour ouvrir les logs.
    3. Copiez la sortie des logs, ouvrez un nouveau chat Agent, collez-la, puis demandez ce qui ne va pas et comment y remédier.

    Si l’erreur `No run command configured` s’affiche alors que vous avez configuré une commande d’exécution, ouvrez les paramètres de votre déploiement, dissociez la commande d’exécution, ajoutez-la à nouveau, puis enregistrez et republiez. Consultez [Résoudre les problèmes de déploiement](/fr/build/troubleshooting).
  </Accordion>

  <Accordion title="Mon app affiche une erreur interne du serveur après sa publication : que se passe-t-il ?">
    Si la publication a réussi, mais que l’application en ligne renvoie une erreur 500, le problème vient du code de votre application et non de l’infrastructure de Replit :

    1. Ouvrez **Publishing**, consultez les logs et copiez l’intégralité du message d’erreur.
    2. Ouvrez un nouveau chat Agent, collez les logs et demandez ce qui provoque l’erreur.
    3. Appliquez le correctif et republiez.

    Si Agent ne parvient pas à identifier le problème, ouvrez **Publishing → History**, trouvez la dernière version fonctionnelle et redéployez-la. Consultez [Résolution des problèmes de déploiement](/fr/build/troubleshooting).
  </Accordion>

  <Accordion title="Mon déploiement est bloqué lors de la compilation ou de la migration : que faire ?">
    1. Ouvrez la palette de commandes avec `Cmd+K` (Mac) ou `Ctrl+K` (Windows), recherchez **Restart compute**, puis sélectionnez cette option.
    2. Ouvrez **Publishing** et sélectionnez **Publish** pour déclencher un nouveau déploiement.
    3. En cas de nouvel échec, ouvrez les logs du déploiement ayant échoué via le menu à trois points, copiez le log de build et collez-le dans un nouveau chat Agent pour obtenir un diagnostic.

    Si le déploiement reste bloqué, [contactez l’assistance Replit](https://replit.com/support) en joignant vos logs de build complets. Consultez [Résolution des problèmes de déploiement](/fr/build/troubleshooting).
  </Accordion>

  <Accordion title="Mon app est en ligne, mais elle est lente ou expire : que dois-je vérifier ?">
    1. Consultez les logs de votre déploiement pour repérer des messages récurrents de délai d’expiration ou de mémoire insuffisante.
    2. Vérifiez les limites de processeur ou de mémoire des ressources de votre déploiement ; consultez [Surveiller un déploiement](/fr/features/publishing/monitoring-a-deployment).
    3. Ouvrez un nouveau chat Agent, collez les logs récents et demandez à Agent d’identifier les goulots d’étranglement.

    Les causes fréquentes incluent les requêtes de base de données sans index, les opérations synchrones bloquantes et les fuites de mémoire. Avec les [déploiements Autoscale](/fr/features/publishing/deployment-types#autoscale), la première requête après une mise à l’échelle à zéro peut prendre quelques secondes : il s’agit d’un démarrage à froid normal.
  </Accordion>

  <Accordion title="Mon historique de déploiements affiche des builds échoués : comment savoir ce qui ne va pas ?">
    Ouvrez **Publishing → Historique**, sélectionnez le déploiement ayant échoué et consultez les
    logs de build. Repérez la première ligne marquée `ERROR` ou `FAILED` : c&#39;est généralement la
    cause racine, et les lignes qui suivent en sont les conséquences. Copiez cette section
    dans un nouveau chat Agent pour obtenir un diagnostic. La plupart des échecs de build sont dus à
    des dépendances manquantes, à une commande d’exécution incorrecte ou à l’échec d’une migration de base de données. Consultez
    [Surveiller un déploiement](/fr/features/publishing/monitoring-a-deployment).
  </Accordion>

  <Accordion title="Pourquoi mon app fonctionne-t-elle dans l’aperçu de l’éditeur, mais pas une fois publiée ?">
    Il s’agit presque toujours d’une différence de configuration entre les environnements. Vérifiez les points suivants :

    * Chaque clé du volet [Secrets](/fr/core-concepts/project-editor/app-setup/secrets) de votre environnement de développement est également définie dans les secrets de votre deployment : ces environnements sont distincts.
    * Votre `DATABASE_URL` pointe vers la base de données de production, et non vers celle de développement.
    * Aucune référence à `localhost` ou à `127.0.0.1` n’est codée en dur ; utilisez plutôt des chemins relatifs ou des URL basées sur l’environnement.

    Consultez ensuite les logs de votre deployment pour identifier les erreurs spécifiques à la production. Consultez [Résoudre les problèmes de deployment](/fr/build/troubleshooting).
  </Accordion>

  <Accordion title="Mon déploiement Autoscale redémarre sans cesse : que signifient SIGTERM et le code de sortie 1 ?">
    Les [déploiements Autoscale](/fr/features/publishing/deployment-types#autoscale) redémarrent régulièrement par conception. Un `SIGTERM` dans vos logs signifie que le processus a été arrêté proprement — c’est normal. `Exit code 1` signifie que le processus s’est arrêté de manière inattendue ; vérifiez les lignes juste avant pour identifier l’erreur réelle.

    Si les redémarrages sont assez fréquents pour affecter les utilisateurs, recherchez des rejets de promesses non gérés, des erreurs de mémoire insuffisante ou des variables d’environnement manquantes empêchant le démarrage.
  </Accordion>

  <Accordion title="J’ai mis à jour mes variables d’environnement, mais mon application publiée ne les utilise pas : pourquoi ?">
    Replit stocke les secrets de développement et de production séparément : modifier l’un ne met pas l’autre à jour. Le panneau [Secrets de développement](/fr/core-concepts/project-editor/app-setup/secrets) est disponible uniquement dans l’éditeur ; votre application publiée utilise vos secrets de déploiement.

    Pour mettre à jour une variable dans votre application en ligne, définissez-la dans vos secrets de déploiement, puis ouvrez **Publishing** et sélectionnez **Publish** pour la republier. Les nouvelles valeurs prennent effet au démarrage du nouveau déploiement. Consultez [Résolution des problèmes de déploiement](/fr/build/troubleshooting).
  </Accordion>

  <Accordion title="Comment redéployer sans modifier mon code ?">
    Ouvrez **Publishing** et sélectionnez **Publish**. Replit génère et publie votre code actuel, même si rien n’a changé — pratique après avoir mis à jour un secret, réactivé une base de données ou pour prendre en compte une mise à jour de dépendance.

    Si votre app ne répond plus et qu’un redéploiement complet vous semble trop lourd, ouvrez la palette de commandes avec `Cmd+K` (Mac) ou `Ctrl+K` (Windows), recherchez **Restart compute**, puis sélectionnez cette option.
  </Accordion>

  <Accordion title="Puis-je modifier la région de déploiement de mon application après sa publication ?">
    Non. Vous ne pouvez pas modifier la zone géographique de Publishing après avoir publié une app. Pour déplacer l’app, remixez-la et publiez le remix dans la nouvelle région. Consultez [Project geography](/fr/features/publishing/project-geography).

    Vous ne pouvez pas non plus modifier directement la région de la base de données. L’app remixée peut recevoir un sous-domaine `.replit.app` différent. Si vous avez besoin d’une URL stable, connectez donc d’abord un [domaine personnalisé](/fr/features/publishing/custom-domains), puis ajoutez à nouveau les Secrets de deployment.
  </Accordion>

  <Accordion title="Pourquoi un scan PCI ou de sécurité signale-t-il le cookie GAESA sur mon app publiée ?">
    L’infrastructure de diffusion de Google ajoute le cookie `GAESA` (affinité de session Google App Engine) aux Apps Replit publiées afin d’acheminer les requêtes vers l’instance appropriée. Sa valeur est un identifiant de routage opaque et ne contient aucune donnée sensible ni donnée applicative.

    Certains analyseurs de sécurité signalent `GAESA` car il ne définit pas les attributs `Secure` ou `HttpOnly`. Votre App ne crée pas ce cookie et vous ne pouvez ni le modifier ni le désactiver pour une App publiée.

    Si une analyse de conformité PCI ou de sécurité signale ce cookie, contestez ce résultat auprès du fournisseur d’analyse en le qualifiant de faux positif. Indiquez le nom du cookie et expliquez que l’infrastructure de Google le définit pour acheminer les requêtes. Votre App publiée ne peut ni le lire, ni le modifier, ni le désactiver, et ce cookie ne contient aucune donnée sensible.

    La conformité de l’App que vous créez relève de votre responsabilité. Consultez le [modèle de responsabilité partagée](/fr/features/security/shared-responsibility-model). Si votre fournisseur d’analyse a besoin de plus de détails, [contactez l’assistance Replit](https://replit.com/support).
  </Accordion>

  <Accordion title="Comment mettre mon app hors ligne ou la dépublier ?">
    Ouvrez **Publishing**, sélectionnez l’option permettant d’arrêter votre deployment, puis confirmez. Votre app passe hors ligne et cesse d’engendrer des frais de deployment. Les fichiers, le code et la base de données de votre project ne sont pas supprimés : seul le deployment en ligne s’arrête. Les connexions de domaine personnalisé associées à ce deployment sont supprimées ; ajoutez-les de nouveau si vous republiez.

    Si votre préoccupation est le coût, notez que les [deployments Autoscale](/fr/features/publishing/deployment-types#autoscale) passent à zéro en l’absence de trafic ; vous n’aurez peut-être pas besoin de les arrêter.
  </Accordion>
