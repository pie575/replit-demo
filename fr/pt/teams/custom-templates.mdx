<div id="primeiros-passos">
  ## Premiers pas
</div>

Replit est un environnement de développement dans le cloud capable d&#39;écrire et d&#39;exécuter n&#39;importe quel framework ou stack. Pour créer un template personnalisé, deux approches sont recommandées :

1. **[Importer](https://replit.com/import) depuis un fournisseur Git** — Importez votre stack de départ existante (ou une stack correspondant à vos préférences) depuis GitHub, GitLab ou Bitbucket.
2. **Forker le template vierge** — Forkez le [template vierge](https://replit.com/@replit/Nothing?v=1) pour partir de zéro avec un environnement de développement entièrement vide.

Des clients ont créé avec succès des templates pour Rust, Python, Java, C++ et bien d&#39;autres stacks — si cela fonctionne quelque part, cela peut fonctionner sur Replit.

<Tip>
  Nous vous recommandons de collaborer avec l&#39;équipe **Field Engineering de Replit** lors de la création de vos premiers templates. Elle possède une solide expérience de la configuration de templates personnalisés sur une grande variété de stacks et se tient à votre disposition. Contactez votre chargé de compte pour entrer en relation avec elle.
</Tip>

Les templates personnalisés permettent aux administrateurs Enterprise de créer des points de départ préconfigurés qui apparaissent directement dans la boîte de réception de l&#39;Agent pour tous les membres de votre organisation. Lorsqu&#39;un développeur sélectionne un template personnalisé, l&#39;Agent le forke et s&#39;appuie sur la configuration, les instructions et les compétences du template pour guider tout le travail qui suit. Aucune configuration supplémentaire n&#39;est nécessaire.

<Note>
  Les templates personnalisés sont disponibles exclusivement dans le forfait **Enterprise**. Seuls les administrateurs de l&#39;organisation peuvent épingler et gérer les templates.
</Note>

<div id="como-os-templates-personalizados-funcionam">
  ## Comment fonctionnent les templates personnalisés
</div>

Un template personnalisé est une Replit App standard de votre organisation qui a été **épinglée dans la boîte de réception d&#39;Agent**. Lorsqu&#39;un développeur le sélectionne :

1. Agent crée une nouvelle app en effectuant un fork du template (tous les fichiers sont copiés)
2. Agent ignore la phase de planification et passe directement en mode construction
3. Le fichier `custom_instruction/instructions.md` du template est injecté dans le contexte d&#39;Agent
4. Les [compétences](/fr/pt/features/agent/skills) personnalisées de `.agents/skills/` sont détectées et rendues disponibles
5. Le fichier [`replit.md`](/fr/pt/features/project-setup/replit-dot-md) fournit un contexte continu du projet

Les standards, conventions et outils de votre organisation sont ainsi pris en compte dès la première interaction.

<div id="estrutura-de-arquivos-do-template">
  ## Structure de fichiers du template
</div>

Voici la disposition recommandée pour un template personnalisé :

```
meu-template/
├── .replit                              # Configuration de l’application (commandes d’exécution, ports, modules)
├── replit.md                            # Mémoire de l’Agent : vue d’ensemble et préférences du projet
├── custom_instruction/
│   └── instructions.md                  # Instructions de l’entreprise injectées dans le prompt de l’Agent
├── .agents/
│   └── skills/
│       └── minha-skill/
│           └── SKILL.md                 # Compétences personnalisées que l’Agent peut utiliser à la demande
└── ...                                  # Le reste de la structure de votre dépôt
```

Chaque fichier remplit un rôle distinct. Les sections ci-dessous expliquent comment configurer chacun d&#39;eux.

<div id="configurar-um-template-personalizado">
  ## Configurer un template personnalisé
</div>

<div id="criar-o-app-base">
  ### Créer l&#39;app de base
</div>

Créez une nouvelle Replit App dans votre organisation. Configurez le projet avec tous les fichiers, dépendances et paramètres dont vos développeurs ont besoin comme point de départ. Cela comprend :

* La structure du code source (composants, utilitaires, fichiers de configuration)
* Les dépendances préinstallées (`package.json`, `requirements.txt`, etc.)
* La configuration de l&#39;environnement dans le [fichier `.replit`](/fr/replit-app/configuration)

<div id="configurar-secrets-compartilhados">
  ### Configurer les Secrets partagés
</div>

Si votre template dépend de clés d&#39;API, de jetons ou d&#39;autres identifiants, ajoutez-les aux **Secrets** du template (dans le panneau Outils) avant de l&#39;épingler. Lorsqu&#39;un développeur crée une nouvelle app à partir du template, tous les Secrets sont automatiquement copiés dans la nouvelle app : les développeurs peuvent ainsi se mettre au travail sans avoir à configurer d&#39;identifiants.

Documentez chaque Secret dans `custom_instruction/instructions.md` (ou dans une compétence dédiée) afin que les développeurs sachent ce qui est disponible et à quoi sert chaque clé.

<Warning>
  Les Secrets sont copiés au moment du fork, et non synchronisés dynamiquement. Si vous effectuez la rotation d&#39;une clé ou ajoutez un nouveau Secret au template, les apps déjà forkées ne sont pas mises à jour. Les développeurs doivent y ajouter ou y mettre à jour les Secrets manuellement.
</Warning>

<div id="escrever-instrues-personalizadas">
  ### Écrire des instructions personnalisées
</div>

Créez un fichier `custom_instruction/instructions.md` à la racine du projet. C&#39;est le fichier le plus important de votre template : il indique à Agent comment votre organisation développe ses logiciels.

<Warning>
  Le nom du dossier doit être `custom_instruction` (au singulier), et non `custom_instructions`.
</Warning>

Agent injecte ce fichier directement dans son prompt système, avec un préambule qui le présente comme une consigne fournie par l&#39;entreprise. Rédigez-le en Markdown et incluez-y :

* **Modèles d&#39;architecture** : comment structurer vos apps
* **Standards de code** : conventions de nommage, règles d&#39;organisation des fichiers, attentes en matière de linting
* **Utilisation des composants** : quelles bibliothèques et quels composants utiliser (et lesquels éviter)
* **Modèles d&#39;API** : comment appeler vos services backend, gérer l&#39;authentification et traiter les erreurs
* **Exigences de tests** : quels tests sont attendus et comment les exécuter
* **Directives de déploiement** : configuration propre à l&#39;environnement et flux de déploiement

````markdown theme={null}
# Standards d'ingénierie de l'entreprise

## Architecture
Toutes les applications web utilisent React avec TypeScript. Utilisez exclusivement
des composants fonctionnels avec des hooks. La gestion d'état repose sur Zustand pour
l'état local et sur React Query pour l'état serveur.

## Bibliothèque de composants
Utilisez notre paquet de système de design interne `@acme/ui`. N'utilisez jamais
d'éléments HTML bruts pour les boutons, les champs de saisie, les formulaires ou les
modales : utilisez toujours le composant correspondant de `@acme/ui`.

Importez les composants ainsi :
```tsx
import { Button, TextField, Modal } from '@acme/ui';
```

## Intégration d'API
Tous les appels d'API passent par le paquet `@acme/api-client`. N'utilisez jamais
fetch brut ni axios directement. L'authentification est gérée automatiquement
par le client.

## Tests
Chaque composant doit avoir un fichier de test correspondant. Utilisez Vitest
pour les tests unitaires et Playwright pour les tests d'intégration.
````

**Limite de taille** : le contenu est limité à environ 25 KB. Le contenu dépassant cette limite peut être progressivement tronqué. À mesure que vos instructions s’étoffent, déplacez la documentation de référence détaillée vers les [compétences](/fr/pt/features/agent/skills) dans `.agents/skills/` plutôt que de tout conserver dans `instructions.md`. Les compétences sont chargées à la demande lorsqu’elles sont pertinentes ; elles ne comptent donc pas dans la limite de taille des instructions et permettent à vos instructions principales de rester axées sur des règles générales.

<div id="adicionar-skills-personalizadas">
  ### Ajouter des compétences personnalisées
</div>

Créez des compétences dans le répertoire `.agents/skills/` pour les flux de travail spécialisés que l’Agent doit suivre. Chaque compétence est un répertoire contenant un fichier `SKILL.md` avec un frontmatter YAML.

```
.agents/skills/
├── usar-sistema-de-design/
│   └── SKILL.md
├── integracao-de-api/
│   └── SKILL.md
└── executar-testes/
    └── SKILL.md
```

Chaque `SKILL.md` doit comporter un `name` et une `description` dans son frontmatter :

```markdown theme={null}
---
name: use-design-system
description: Use when building UI components. Provides component patterns, theming rules, and accessibility requirements for the Acme design system.
---

# Sistema de Design Acme

## Componentes disponíveis

- `Button` — Variantes primária, secundária e ghost
- `TextField` — Input de texto com suporte à validação
- `Modal` — Overlay de diálogo com captura de foco
...
```

| Champ         | Obligatoire | Détails                                                                                          |
| ------------- | ----------- | ------------------------------------------------------------------------------------------------ |
| `name`        | Oui         | Maximum de 64 caractères. Uniquement des lettres minuscules, des chiffres et des traits d’union. |
| `description` | Oui         | Maximum de 1 024 caractères. Décrit ce que fait la compétence et quand l’utiliser.               |
| `enabled`     | Non         | Valeur par défaut : `true`. Définissez-la sur `false` pour désactiver sans supprimer.            |

**Chargement des compétences** : Agent ne voit que le `name` et la `description` dans son prompt. Il lit le contenu complet de `SKILL.md` à la demande lorsqu’une compétence est pertinente pour la tâche en cours. La `description` est donc essentielle : rédigez-la de façon à couvrir les scénarios dans lesquels Agent doit utiliser la compétence.

Les compétences peuvent également inclure des fichiers auxiliaires avec `SKILL.md` :

```
.agents/skills/usar-sistema-de-design/
├── SKILL.md
├── references/
│   └── component-api.md
└── assets/
    └── theme-tokens.json
```

Pour en savoir plus sur les compétences, consultez [Compétences Agent](/fr/pt/features/agent/skills) et [Utiliser une compétence](/fr/pt/build/use-agent-skills).

<div id="configurar-replitmd">
  ### Configurer replit.md
</div>

Préremplissez le fichier `replit.md` à la racine du projet avec une vue d&#39;ensemble de l&#39;architecture de votre template. Ce fichier est toujours chargé dans le contexte de l&#39;Agent et sert de mémoire persistante du projet.

Le fichier doit comporter les quatre sections suivantes :

```markdown theme={null}
# Vue d’ensemble
Application de gestion des tâches conçue avec React, TypeScript et le système
de design Acme. Utilise un backend Express.js avec PostgreSQL.

# Préférences utilisateur
- Utiliser TypeScript pour tous les fichiers
- Privilégier les composants fonctionnels avec des hooks
- Suivre les conventions de code Acme

# Architecture du système
- Frontend : React + TypeScript + @acme/ui
- Backend : Express.js + TypeScript
- Base de données : PostgreSQL avec Drizzle ORM
- Authentification : Acme SSO via @acme/auth

# Dépendances externes
- @acme/ui : Système de design interne
- @acme/api-client : Couche d’intégration d’API
- @acme/auth : SDK d’authentification
```

L’Agent met à jour le `replit.md` au fur et à mesure que le projet évolue. Si le fichier dépasse environ 4 000 tokens, l’Agent le résume automatiquement afin de le maintenir concis et utile.

Pour plus de détails, consultez [replit.md](/fr/pt/features/project-setup/replit-dot-md).

<div id="fixe-o-template-na-sua-organizao">
  ### Épinglez le template à votre organisation
</div>

Une fois votre template prêt :

1. Accédez à l’app du template dans votre organisation
2. Ouvrez le menu d’actions de l’app (menu à trois points)
3. Sélectionnez **Épingler dans la boîte de réception d’Agent**

<img src="/assets/mirror/custom-templates-pin-to-agent-b733d3eb9a80.png" alt="Menu d’actions de l’app affichant l’option Épingler dans la boîte de réception d’Agent" width="984" height="856" data-path="images/teams/custom-templates-pin-to-agent.png" />

<Note>
  Seuls les administrateurs de l’organisation (membres du rôle `system_admins`) peuvent épingler et désépingler des templates.
</Note>

Définissez l’accès des membres sur **Lecture seule** afin qu’ils puissent consulter et utiliser le template épinglé sans pouvoir le modifier.

<img src="/assets/mirror/custom-templates-members-read-only-cf6aa160c8ef.png" alt="Boîte de dialogue d’invitation affichant l’accès des membres défini sur Lecture seule" width="954" height="1064" data-path="images/teams/custom-templates-members-read-only.png" />

Le template apparaît désormais sous forme de pastille sélectionnable sous la boîte de réception d’Agent pour tous les membres de votre organisation. Pour le retirer, ouvrez le même menu et sélectionnez **Désépingler de la boîte de réception d’Agent**.

<div id="controlar-o-acesso-ao-template">
  ### Contrôler l&#39;accès au template
</div>

L&#39;épinglage rend un template visible par tous les membres de l&#39;organisation. Pour une diffusion plus ciblée, utilisez le bouton **Inviter** dans l&#39;app du template afin de le partager avec des [Groupes ou des utilisateurs individuels](/fr/pt/teams/identity-and-access-management/groups-and-permissions) spécifiques. Vous pouvez ainsi limiter les Teams ou les personnes autorisées à voir et à forker le template, tout en le laissant désépinglé de la boîte de réception globale de l&#39;organisation.

<div id="o-que-acontece-quando-um-desenvolvedor-seleciona-um-template">
  ## Ce qui se passe lorsqu&#39;un développeur sélectionne un template
</div>

<img src="/assets/mirror/custom-templates-input-box-553384ac7dd0.png" alt="Template affiché sous forme de pastille sélectionnable dans la boîte de réception de l'Agent" width="1746" height="726" data-path="images/teams/custom-templates-input-box.png" />

Lorsqu&#39;un membre de l&#39;organisation choisit un template épinglé dans la boîte de réception de l&#39;Agent :

1. **Fork** : un nouvel App est créé sous forme de copie du template, avec tous ses fichiers
2. **Ignorer la planification** : l&#39;Agent saute la conversation de planification initiale et passe directement en mode construction
3. **Charger les instructions** : `custom_instruction/instructions.md` est lu et injecté dans le prompt système de l&#39;Agent comme consignes fournies par l&#39;entreprise
4. **Découvrir les compétences** : les compétences présentes dans `.agents/skills/` sont identifiées et répertoriées dans le contexte de l&#39;Agent pour un chargement à la demande
5. **Charger le contexte du projet** : `replit.md` est lu et injecté dans le contexte de l&#39;Agent (ou généré automatiquement s&#39;il est absent)
6. **Hériter de la configuration** : le fichier `.replit`, les dépendances et tous les fichiers du template sont transférés vers le nouvel App

Le développeur peut aussitôt commencer à envoyer des prompts à l&#39;Agent avec ses exigences spécifiques, et l&#39;Agent travaille dans le cadre des directives définies par le template.

<div id="como-os-arquivos-funcionam-juntos">
  ## Comment les fichiers fonctionnent ensemble
</div>

Chaque fichier de configuration a un rôle distinct :

| Fichier                              | Objectif                                     | Quand Agent le lit                        | Modifiable par Agent                             |
| ------------------------------------ | -------------------------------------------- | ----------------------------------------- | ------------------------------------------------ |
| `custom_instruction/instructions.md` | Normes et règles de l’organisation           | Toujours (injecté dans le prompt système) | Non                                              |
| `.agents/skills/*/SKILL.md`          | Flux de travail et normes spécialisés        | À la demande (lorsque pertinent)          | Oui (Agent peut également créer des compétences) |
| `replit.md`                          | Vue d’ensemble et préférences du projet      | Toujours (injecté dans le prompt système) | Oui (Agent le met à jour au fil du temps)        |
| `.replit`                            | Configuration de l’environnement d’exécution | Lors de la configuration de l’application | Oui                                              |

**Distinction fondamentale** : `custom_instruction/instructions.md` est votre source statique de référence pour les normes organisationnelles. `replit.md` est le document évolutif qu’Agent maintient au fur et à mesure que le projet évolue. Les compétences constituent des ressources de référence à la demande pour des flux de travail spécifiques.

<div id="melhores-prticas">
  ## Bonnes pratiques
</div>

<div id="mantenha-as-instrues-focadas">
  ### Gardez des instructions ciblées
</div>

Rédigez `custom_instruction/instructions.md` en vous concentrant sur les standards les plus importants. Privilégiez :

* Les décisions difficiles à revenir sur (architecture, modèles de données)
* Les standards qui doivent rester cohérents (utilisation des composants, conventions d&#39;API)
* Les standards que le développeur pourrait ignorer (bibliothèques internes, conventions d&#39;équipe)

Évitez d&#39;inclure des changelogs, des détails d&#39;implémentation ou des informations qui changent fréquemment.

<div id="escreva-descries-de-skills-descobrveis">
  ### Rédigez des descriptions de compétences facilement repérables
</div>

Le champ `description` du frontmatter de `SKILL.md` est ce sur quoi Agent s&#39;appuie pour déterminer quand charger une compétence. Rédigez des descriptions qui correspondent aux tâches pour lesquelles la compétence est pertinente :

```yaml theme={null}
# Bon — indique quand l’utiliser
description: Use when building forms or handling user input. Provides validation patterns, error display conventions, and accessible form layouts.

# Moins efficace — trop vague
description: Form utilities and helpers.
```

<div id="organize-skills-por-fluxo-de-trabalho">
  ### Organisez les compétences par flux de travail
</div>

Regroupez les compétences autour des flux de travail plutôt que par catégories techniques :

| Approche                  | Exemple                                      |
| ------------------------- | -------------------------------------------- |
| **Par flux de travail**   | `build-a-form`, `connect-to-api`, `add-auth` |
| **Par domaine technique** | `react-utils`, `api-helpers`, `auth-config`  |

L&#39;approche par flux de travail permet à Agent de trouver les compétences au bon moment.

<div id="itere-no-seu-template">
  ### Faites évoluer votre template
</div>

Les templates s’améliorent à l’usage. Lorsque votre équipe commence à développer avec un template :

1. Identifiez les erreurs récurrentes de l’Agent et ajoutez-les à `instructions.md`
2. Créez de nouvelles compétences lorsque l’Agent résout bien un problème — consignez la solution
3. Mettez à jour les dépendances et les configurations de base à mesure que votre stack évolue
4. Testez les modifications en créant une nouvelle App à partir du template afin de vérifier l’expérience

<div id="atualizaes-de-templates-e-apps-existentes">
  ### Mises à jour des templates et des apps existantes
</div>

Les modifications apportées à l’app du template sont appliquées aux **nouvelles** apps créées à partir de ce template. Les apps existantes précédemment forkées à partir du template sont des copies indépendantes et ne reçoivent pas ces mises à jour.
