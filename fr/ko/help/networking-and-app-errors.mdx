---
title: "Erreurs de réseau et d'app"
description: "Réponses aux erreurs courantes des apps déployées : 403 Forbidden, Application failed to respond, CORS, 502 Bad Gateway et problèmes de requêtes sortantes."
---

Ces réponses portent sur les erreurs qui peuvent survenir dans vos apps déployées. Pour un dépannage plus large, consultez [Dépannage des déploiements](/fr/ko/build/troubleshooting).

<AccordionGroup>
  <Accordion title="L’application déployée renvoie une erreur 403 Forbidden : comment la résoudre ?">
    Les erreurs 403 sur une application déployée proviennent généralement de l&#39;une des causes suivantes :

    * **En-têtes de requête trop volumineux** — un trop grand nombre de cookies peut alourdir les en-têtes au point qu&#39;ils soient rejetés en périphérie. Effacez les cookies du navigateur pour ce domaine, puis réessayez.
    * **Authentification manquante** — la requête ne contient pas le jeton de connexion ou la session requis.
    * **Restrictions d&#39;accès** — l&#39;application est peut-être configurée pour bloquer une partie du trafic. Consultez [Déploiements privés](/fr/ko/features/publishing/private-deployments) et [Jetons d&#39;accès externe](/fr/ko/features/deployment-customization/external-access-tokens).

    Pour un diagnostic détaillé, collez les journaux de déploiement dans un nouveau chat Agent.
  </Accordion>

  <Accordion title="L’application affiche « Application failed to respond » : qu’est-ce que cela signifie ?">
    Le processus de votre application n&#39;écoute pas sur le port attendu par Replit. Replit transmet le bon port via la variable d&#39;environnement `PORT` : utilisez-la pour la liaison plutôt qu&#39;une valeur codée en dur :

    ```js theme={null}
    const PORT = process.env.PORT || 3000;
    ```

    ```python theme={null}
    port = int(os.environ.get("PORT", 3000))
    ```

    Il se peut que l&#39;application ait planté avant la liaison — vérifiez les erreurs de démarrage dans les journaux de deployment. Sur les [deployments Autoscale](/fr/ko/features/publishing/deployment-types#autoscale), la première requête suivant une période d&#39;inactivité peut prendre quelques secondes (démarrage à froid). C&#39;est normal.
  </Accordion>

  <Accordion title="Comment corriger les erreurs CORS dans une application Replit déployée ?">
    Une erreur CORS signifie que le frontend et le backend se trouvent sur des origines différentes et que le backend n&#39;est pas configuré pour l&#39;autoriser. S&#39;ils font partie de la même application, utilisez des URL relatives (par exemple `/api/endpoint`) pour éviter complètement le CORS.

    Sinon, configurez le backend afin qu&#39;il autorise l&#39;origine du frontend. Avec Express, par exemple :

    ```js theme={null}
    const cors = require("cors");
    app.use(cors({ origin: "https://your-frontend.replit.app" }));
    ```

    Avant la publication, n&#39;autorisez que les origines spécifiques dont vous avez besoin. Consultez [Dépannage des déploiements](/fr/ko/build/troubleshooting).
  </Accordion>

  <Accordion title="L’application fonctionne en local, mais une erreur réseau se produit après le déploiement.">
    L’application déployée échoue lorsque l’environnement de production diffère de la configuration locale. Vérifiez les trois points suivants :

    1. **URL localhost codées en dur**—remplacez `localhost:3000` ou `127.0.0.1` par des chemins relatifs ou des URL dépendant de l’environnement, puis redéployez.
    2. **Secrets de production manquants**—assurez-vous que toutes les clés requises sont définies dans les Secrets de déploiement. Consultez [Secrets](/fr/ko/core-concepts/project-editor/app-setup/secrets).
    3. **Migrations non exécutées en production**—exécutez les migrations en attente sur la base de données de production avant la publication.

    Si l’erreur persiste, [contactez l’assistance Replit](https://replit.com/support) en indiquant le message d’erreur et les étapes déjà suivies.
  </Accordion>

  <Accordion title="Comment déboguer une erreur 502 Bad Gateway dans une application déployée ?">
    Une erreur 502 signifie généralement que le processus de l&#39;application a planté ou que le serveur a renvoyé une sortie inutilisable. Consultez les journaux de déploiement à la recherche d&#39;erreurs de plantage survenues juste avant l&#39;erreur 502 — les rejets de promesses non gérés et les exceptions non interceptées peuvent faire planter automatiquement le processus Node.js.

    Ajoutez des gestionnaires qui font remonter les plantages :

    ```js theme={null}
    process.on("uncaughtException", (err) => console.error("Uncaught:", err));
    ```

    Si vous parvenez à identifier l&#39;erreur sous-jacente dans les journaux, collez-la dans un nouveau chat Agent pour obtenir de l&#39;aide à la corriger.
  </Accordion>

  <Accordion title="L’application ne peut pas envoyer de requêtes à une API externe — que dois-je vérifier ?">
    Commencez par vérifier si la requête est bloquée plutôt que si elle échoue dans votre code. Ouvrez les journaux de déploiement et recherchez les messages concernant des requêtes sortantes bloquées ou redirigées.

    Causes fréquentes et correctifs :

    * **URL autoréférentielle**—si votre backend appelle sa propre URL publique (par exemple, `fetch("https://myapp.replit.app/api/...")`), utilisez plutôt un chemin relatif : `fetch("/api/...")`.
    * **Requêtes lors de l’étape de build**—effectuez les appels sortants à l’exécution, et non pendant le build.
    * **Restrictions réseau**—les réseaux d’entreprise ou scolaires peuvent bloquer les connexions sortantes. Vérifiez auprès de votre administrateur réseau.

    Si aucun de ces cas ne s’applique et que la requête est toujours bloquée, [contactez l’assistance Replit](https://replit.com/support) en incluant les lignes de journal pertinentes.
  </Accordion>

  <Accordion title="Après avoir republié l’application, son URL a changé : puis-je récupérer l’ancien sous-domaine ?">
    Le sous-domaine `.replit.app` est dérivé du nom du projet et rien ne garantit qu&#39;il reste identique après une annulation de publication suivie d&#39;une nouvelle publication, en particulier si le nom du projet a changé.

    La solution pérenne est un [domaine personnalisé](/fr/ko/features/publishing/custom-domains), qui reste identique d&#39;un redéploiement à l&#39;autre. Pour récupérer l&#39;ancien sous-domaine, vérifiez que le nom du projet correspond bien au nom d&#39;origine (rétablissez-le si nécessaire), puis republiez — Replit ne peut pas réattribuer manuellement un sous-domaine libéré. Consultez [Géographie du projet](/fr/ko/features/publishing/project-geography).
  </Accordion>
</AccordionGroup>
