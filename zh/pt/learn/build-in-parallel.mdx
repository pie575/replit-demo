同时处理多项工作，是区分优秀构建者和卓越构建者的关键能力之一。本页面将教你如何安全地同时构建多项功能，即使你此前从未尝试过这种工作方式。

<div id="uma-nova-forma-de-trabalhar-com-o-agent">
  ## 一种与 Agent 协作的新方式
</div>

到目前为止，你可能一直把 Agent 当作坐在身边的伙伴：你提问、观察、回应。并行构建则是一种不同的协作方式。你将一个功能作为一项**task**交给 Agent，它会在后台完成构建，而你可以同时处理其他事情。

你在日常生活中也是这样做的。你不会一直站在洗衣机前等它洗完。你把衣服放进洗衣机，然后去做饭。task也是如此：启动一项task后，在它运行期间，你可以启动另一项task、审查其他内容，或者继续在主对话中与 Agent 交流。

这会改变你的角色。你不再是旁观单项构建的乘客，而是统筹多项构建的负责人。

<div id="seu-app-fica-seguro-enquanto-as-tarefas-rodam">
  ## task运行期间，你的应用始终安全
</div>

大家最常问的问题是：*在我没有查看时，后台task会不会弄坏我的应用？*

不会。每项task都在你项目的独立**副本**中运行。只有当你审核task完成的工作并选择应用后，你的应用才会发生变化。

每项task也都有自己的 Agent，并继承你项目的全部上下文，因此你无需重复说明。task彼此独立：第一项task开始运行后，你可以立即启动下一项。

<div id="um-exemplo-prtico-trs-recursos-ao-mesmo-tempo">
  ## 实战示例：同时构建三项功能
</div>

假设你有一个已支持预订和登录的汽车租赁 App，想要添加三项功能：

* 活动页面
* 活动报名
* 联系表单

如果依次构建，每项大约需要五分钟，总共十五分钟；如果并行构建，则只需大约五分钟。

为每项功能创建一个 task。task会以 Plan 模式启动，因此每项task都会先显示计划，然后才开始构建。批准计划后，看看会发生什么：活动页面和联系表单会立即开始构建，但活动报名会等待。活动页面尚未创建时，访客无法报名参加活动。Agent 会自行识别这种依赖关系，像项目经理一样安排工作，并在其依赖的task完成后执行该task。

<div id="divida-seu-trabalho-em-partes-pequenas">
  ## 将工作拆分为小task
</div>

实现并行构建的关键在于，将功能拆分为小型且可独立完成的task。小task完成得更快，更易于审核，也不易相互干扰。

一条实用规则：**如果task描述中出现“和”，就考虑将其拆分。**

* 好：“添加活动页面”“添加联系表单”
* 过大：“添加活动、报名、电子邮件通知和管理员视图”

较大的task并没有错，但会迫使一个 Agent 按顺序完成所有工作。四个小task则让 Agent 有机会同时执行。

考考自己：以下哪些task可以并行运行？

1. 添加深色模式切换开关
2. 添加客户评价版块
3. 允许客户回复评价
4. 将应用翻译成法语

<Accordion title="答案">
  task 1、2 和 4 相互独立，可以同时运行。task 3 依赖于task 2：在有评价之前，没有可回复的内容。你无需自己判断这一点。Agent 会检测依赖关系，并为你按顺序安排这两个task。
</Accordion>

<div id="por-que-voc-atualiza-antes-de-aplicar">
  ## 为什么要在应用更改前更新
</div>

这是唯一容易让人困惑的概念，所以我们慢慢说。

两位朋友各自带了一份相同的派对邀请函副本回家修改。一个人添加了地图，另一个人重写了日程安排。你接受了第一位朋友的版本，它成了正式邀请函。现在，第二位朋友的副本就出现了问题：他的重写基于一份已经不存在的邀请函。在接受他的修改之前，他需要先根据最新版本重新完成。

task的工作方式完全相同。每个task开始时都会复制你的项目。当你应用一个task的更改时，其他所有task的副本都会落后一个版本。对于不相关的功能，这通常不是问题；但由于你不会查看代码，无法确定两个task是否修改了同一处内容。

<Tip>
  在应用task的更改之前，先**更新**该task。更新会将task与 App 的最新版本同步，并解决所有冲突，使各项task能在彼此的基础上继续构建，而不是相互覆盖。
</Tip>

<div id="revise-como-um-gerente">
  ## 像经理一样审查
</div>

并行构建会让你扮演经理的角色，而经理最常犯的错误就是批准未经核查的工作。遵循一个简单的循环：一次处理一个 task。

<Steps>
  <Step title="测试 task 的成果">
    打开已完成的 task，亲自试用该功能。像用户一样逐一点击和操作。
  </Step>

  <Step title="应用">
    满意吗？将更改应用到你的主 App。
  </Step>

  <Step title="更新下一个 task">
    在处理下一个已完成的 task 前，先更新它，使其与你刚刚修改的版本保持同步。
  </Step>

  <Step title="重复">
    测试、应用、更新，直到所有 task 都已合并。
  </Step>
</Steps>

  <img src="/assets/mirror/task-review-apply-3ef379c7e976.png" alt="任务审查界面，显示 Agent 的工作记录、测试结果以及“应用更改”按钮" width="3456" height="1984" data-path="images/replitai/task-review-apply.png" />

切勿批量批准。一次应用三个未经审查的功能后，一旦出现问题，就会有三个排查对象。

<div id="quando-permanecer-sequencial">
  ## 何时应按顺序进行
</div>

并行构建是一种工具，而非规则。遇到以下情况时，请留在主对话中，一次处理一件事：

* **两个想法涉及同一个界面。**“重新设计首页”和“更改导航”会相互冲突。请按顺序处理。
* **你正在探索。**在设计工作中，一次尝试的结果会影响你接下来想做什么。探索是一场对话，而不是一张工单。
* **你无法用一句话描述任务。**如果你无法清楚地说明它，就还没准备好将其委派出去。

<div id="encontre-seu-limite">
  ## 找到自己的上限
</div>

限制并行构建的不是 Replit，而是你的注意力。每次在task之间切换，都会消耗一点专注力，而每个人能投入的注意力各不相同。

先从两个task开始。如果能轻松审阅，再试试三个。Agent 的构建能力已经足够强，无需你监督每一步，因此大多数构建者认为，这样的速度提升值得付出切换上下文的代价。不过，这是一项需要练习的技能，而不是打开某项设置就能获得的能力。
