Publishing transforme votre projet en application publique. Si la publication échoue ou si l’URL publique se comporte différemment dans Preview, examinez le problème étape par étape.

Cette page sert à la fois de guide de récupération Build et de référence pour le dépannage des déploiements. Commencez par la question la plus simple : l’application fonctionne-t-elle dans Preview ?

<div id="what-youll-achieve">
  ## Ce que vous saurez faire
</div>

À la fin de cette page, vous devriez savoir si le problème vient de votre app, de votre configuration de publication, de vos Secrets de production, de votre type de déploiement, de votre configuration de port ou de votre accès au réseau/DNS.

<div id="start-with-preview">
  ## Commencer par Preview
</div>

Avant de publier, vérifiez que l&#39;application fonctionne correctement dans le Project Editor.

Sélectionnez **Run** en haut du Project Editor, puis ouvrez Preview. Si Preview n&#39;affiche pas votre application avec une URL `replit.dev`, corrigez l&#39;application avant de publier.

Demandez d&#39;abord à Agent de diagnostiquer Preview :

<AiPrompt>
  Cette application ne fonctionne pas dans Preview.<br />
  Vérifie la commande d&#39;exécution, l&#39;installation des dépendances, les erreurs de l&#39;application, les ports et les Secrets manquants.<br />
  Corrige d&#39;abord le plus petit problème et indique-moi comment vérifier que Preview fonctionne avant de publier.
</AiPrompt>

Si Preview ne fonctionne pas, la publication ne résoudra pas le problème.

<div id="if-preview-works-but-publishing-fails">
  ## Si Preview fonctionne, mais pas la publication
</div>

Si Preview fonctionne mais que la publication échoue, vérifiez la configuration spécifique à la publication.

<div id="check-logs">
  ### Vérifier les logs
</div>

Ouvrez l’onglet **Logs** dans le volet **Publishing**. Recherchez les traces de pile, les packages manquants, les commandes qui ont échoué, les variables d’environnement manquantes ou les erreurs de démarrage.

Collez l’erreur pertinente dans Agent :

<AiPrompt>
  La publication a échoué avec la sortie de log suivante : [collez l’erreur].<br />
  Expliquez la cause probable.<br />
  Indiquez s’il s’agit d’une erreur de commande, de dépendance, de Secret, de port, de build ou d’application.<br />
  Recommandez la correction la plus simple et indiquez comment la vérifier.
</AiPrompt>

<div id="check-run-and-build-commands">
  ### Vérifier les commandes d’exécution et de build
</div>

Les erreurs courantes incluent les fautes de frappe, les options incorrectes, les mauvais fichiers d’entrée ou les commandes qui ne fonctionnent qu’en local.

Vérifiez les commandes dans le volet **Publishing**. Si votre app nécessite une commande de build et une commande de démarrage, assurez-vous qu’elles sont toutes les deux correctes.

<div id="check-production-secrets">
  ### Vérifier les Secrets de production
</div>

Les Secrets définis dans le Project Editor ne sont pas automatiquement transférés vers votre app publiée. Ajoutez tous les Secrets et toutes les variables d’environnement de production dans le volet **Publishing**.

L’absence de Secrets peut entraîner des erreurs de valeurs non définies, des échecs d’appels API, des échecs de connexion à la base de données, des erreurs de connexion ou des échecs de paiement.

Consultez [Secrets](/fr/core-concepts/project-editor/app-setup/secrets).

<div id="check-long-running-process-behavior">
  ### Vérifier le comportement des processus de longue durée
</div>

Les apps publiées nécessitent que votre programme continue de s’exécuter. S’il s’exécute une seule fois puis s’arrête, la plateforme le redémarre automatiquement.

Assurez-vous que votre application lance un processus de longue durée, tel qu’un serveur web.

<div id="check-host-and-port-configuration">
  ### Vérifier la configuration de l’hôte et du port
</div>

Si vous exécutez un serveur web, Deployments peut détecter automatiquement le port utilisé par votre serveur, mais celui-ci doit écouter sur `0.0.0.0`. Écouter uniquement sur `localhost` ou `127.0.0.1` ne fonctionne pas pour les apps publiées.

Si des [ports sont spécifiés dans votre configuration `.replit`](/fr/features/project-setup/configuration), la détection automatique des ports est désactivée. Vous devez spécifier un port avec `externalPort` défini sur `80` pour que l’étape de promotion aboutisse. Vérifiez que votre serveur écoute sur le `localPort` spécifié.

Demandez à Agent de vérifier attentivement les points suivants :

<AiPrompt>
  Vérifiez que cette app est correctement configurée pour la publication.<br />
  Vérifiez que le serveur démarre un processus persistant, écoute sur 0.0.0.0, utilise le port attendu et correspond à toute configuration de port dans .replit.<br />
  Ne modifiez pas le comportement de l’app au-delà des corrections nécessaires à la publication.
</AiPrompt>

<div id="check-health-check-timing">
  ### Vérifier le délai de la vérification d’état
</div>

Avant de mettre votre app publiée en ligne, Replit envoie une requête HTTP à votre app. Si votre page d’accueil met plus de cinq secondes à répondre, la vérification d’état peut expirer et la publication peut échouer lors de l’étape finale.

Si le démarrage est lent, demandez à Agent de réduire les tâches effectuées au démarrage, de reporter les tâches coûteuses à une action de l’utilisateur ou de mettre les données en cache lorsque cela est approprié.

<div id="if-publishing-succeeds-but-the-public-url-is-broken">
  ## Si la publication réussit, mais que l’URL publique ne fonctionne pas
</div>

Si Preview fonctionne et que la publication réussit, mais que l’URL publique ne fonctionne pas, comparez le comportement dans Preview et en production.

Vérifiez :

* Les Secrets et les variables d’environnement de production.
* Les paramètres de connexion à la base de données.
* Les URL de rappel ou de redirection de connexion.
* Les paramètres de webhook ou de redirection de paiement.
* Les listes d’autorisation d’API ou les paramètres CORS.
* Les fichiers écrits localement au lieu d’être stockés dans une base de données ou un service de stockage.
* La disposition sur mobile et les différences entre navigateurs.

Demandez à Agent de comparer les environnements :

<AiPrompt>
  L’application fonctionne dans Preview, mais pas à l’URL publiée.<br />
  Aidez-moi à comparer le comportement dans Preview et en production.<br />
  Vérifiez les Secrets, les paramètres de la base de données, les appels d’API, les redirections de connexion, les redirections de paiement, la sortie du build et les logs.<br />
  Indiquez-moi la vérification la plus sûre à effectuer ensuite.
</AiPrompt>

<div id="static-deployment-issues">
  ## Problèmes de déploiement statique
</div>

Les déploiements statiques servent des fichiers tels que des fichiers HTML, CSS et JavaScript.

Si votre app comporte des fonctionnalités côté serveur, des routes API, des rappels d’authentification, des appels à la base de données depuis le serveur ou une logique backend s’exécutant sur une longue durée, elle n’est peut-être pas adaptée aux déploiements statiques. Modifiez plutôt le type de déploiement en Autoscale dans le volet **Publishing**.

Les problèmes de déploiement statique sont souvent dus à un répertoire public incorrect ou au choix de Static pour une app nécessitant un serveur.

<div id="file-and-size-limits">
  ## Limites de taille et de fichiers
</div>

Les déploiements VM réservée et Autoscale prennent en charge les Replit Apps jusqu&#39;à 8 Go. Les déploiements statiques prennent en charge jusqu&#39;à 1 Go.

Pour réduire la taille de l&#39;app, supprimez les fichiers inutiles, évitez de valider les fichiers générés ou utilisez un stockage externe pour les assets volumineux.

<Warning>
  Le système de fichiers des apps publiées n&#39;est pas persistant et se réinitialise chaque fois que vous publiez. Pour conserver les données, utilisez une base de données telle que [SQL Database](/fr/features/data-and-storage/sql-database).
</Warning>

Si des fichiers téléversés ou des données générées disparaissent après la publication, stockez-les plutôt dans une base de données ou un service de stockage que dans le système de fichiers de l&#39;app.

<div id="access-issues-with-replitapp-and-replitdev-urls">
  ## Problèmes d&#39;accès aux URL `replit.app` et `replit.dev`
</div>

Si vous avez des difficultés à accéder à votre app via son domaine `replit.app` ou `replit.dev`, des filtres web ou des restrictions réseau peuvent en être la cause.

Essayez d&#39;utiliser des résolveurs DNS publics, tels que Google DNS (`8.8.8.8`) ou Cloudflare DNS (`1.1.1.1`).

<div id="change-dns-settings">
  ### Modifier les paramètres DNS
</div>

<Tabs>
  <Tab title="Windows">
    1. Ouvrez le **Panneau de configuration**.
    2. Accédez au **Centre Réseau et partage**.
    3. Sélectionnez **Modifier les paramètres de la carte** dans le volet de gauche.
    4. Cliquez avec le bouton droit sur votre connexion réseau active, puis sélectionnez **Propriétés**.
    5. Sélectionnez **Protocole Internet version 4 (TCP/IPv4)**, puis **Propriétés**.
    6. Choisissez **Utiliser l&#39;adresse de serveur DNS suivante**.
    7. Saisissez l&#39;adresse IP d&#39;un serveur DNS public, par exemple `8.8.8.8` pour Google DNS ou `1.1.1.1` pour Cloudflare DNS.
    8. Sélectionnez **OK** pour enregistrer vos modifications.

    Pour obtenir des instructions plus détaillées, consultez le [guide de configuration DNS de Microsoft](https://support.microsoft.com/en-us/windows/change-tcp-ip-settings-bd0a07af-15f5-cd6a-363f-ca2b6f391ace).
  </Tab>

  <Tab title="macOS">
    1. Ouvrez les **Préférences Système**.
    2. Sélectionnez **Réseau**.
    3. Sélectionnez votre connexion réseau active dans le volet de gauche.
    4. Sélectionnez **Avancé** dans le coin inférieur droit.
    5. Accédez à l&#39;onglet **DNS**.
    6. Sélectionnez le bouton **+** pour ajouter un serveur DNS.
    7. Saisissez l&#39;adresse IP d&#39;un serveur DNS public, par exemple `8.8.8.8` pour Google DNS ou `1.1.1.1` pour Cloudflare DNS.
    8. Sélectionnez **OK**, puis **Appliquer**.

    Pour obtenir des instructions plus détaillées, consultez le [guide de configuration DNS d&#39;Apple](https://support.apple.com/guide/mac-help/change-dns-settings-on-mac-mh14127/mac).
  </Tab>

  <Tab title="Linux">
    1. Modifiez le fichier `/etc/resolv.conf` pour ajouter des serveurs DNS publics. La méthode exacte varie selon la distribution.
    2. Ajoutez les lignes suivantes :

    ```bash theme={null}
    nameserver 8.8.8.8
    nameserver 1.1.1.1
    ```

    Pour en savoir plus sur la configuration DNS selon les différentes distributions, consultez le [guide de configuration réseau du wiki Debian](https://wiki.debian.org/NetworkConfiguration#Defining_the_.28DNS.29_Nameservers).
  </Tab>
</Tabs>

<div id="clear-dns-cache">
  ### Vider le cache DNS
</div>

Après avoir modifié les paramètres DNS, videz le cache DNS pour appliquer la nouvelle configuration :

* **Windows** : exécutez `ipconfig /flushdns` dans l’Invite de commandes.
* **macOS et Linux** : exécutez `sudo systemctl restart NetworkManager` dans le Terminal. La commande exacte peut varier selon la distribution.

<Note>
  Afin d’améliorer les performances et la stabilité dans votre région, les URL `replit.dev` de vos
  Replit Apps peuvent occasionnellement changer lors de migrations de clusters. Une fois la migration
  terminée, les URL restent stables pendant environ un an, sauf si vous
  demandez explicitement un changement d’emplacement.
</Note>

<div id="publish-a-streamlit-application">
  ## Publier une application Streamlit
</div>

Les applications Streamlit sont compatibles avec les déploiements Replit. Le plus simple pour commencer est d&#39;utiliser le [template Streamlit](https://replit.com/@replit/Streamlit?v=1).

Vous pouvez également définir la commande d&#39;exécution utilisée pour la publication comme suit :

```bash theme={null}
streamlit run --server.address 0.0.0.0 --server.headless true --server.enableCORS=false --server.enableWebsocketCompression=false main.py
```

Si votre application utilise un autre fichier d’entrée, remplacez `main.py` par le nom de ce fichier.

<div id="youre-done-when">
  ## Vous avez terminé lorsque
</div>

* Preview fonctionne.
* La publication est terminée.
* L’URL publique se charge.
* Le flux principal de l’app fonctionne à l’URL publique.
* Les Secrets et les paramètres de production sont configurés.
* Les logs n’affichent aucune erreur de démarrage masquée.
