Chaque Replit App fonctionne avec deux bases de données. La **base de données de développement** est l&#39;espace où vous et Agent expérimentez pendant le développement. La **base de données de production** stocke les données en direct qui alimentent votre app publiée, ce qui met vos données réelles à l&#39;abri pendant que vous continuez à développer.

</Frame>

<div id="how-they-compare">
  ## Comparaison
</div>

| Aspect          | Base de données de développement                                 | Base de données de production                                  |
| --------------- | ---------------------------------------------------------------- | -------------------------------------------------------------- |
| **Objectif**    | Expérimentation et développement de fonctionnalités              | Servir de vrais utilisateurs et stocker les données métier     |
| **Données**     | Données de test, enregistrements fictifs, petits jeux de données | Données réelles des utilisateurs, informations critiques       |
| **Création**    | Automatiquement avec chaque Replit App                           | Lorsque vous publiez votre app                                 |
| **Agent**       | Agent peut créer et modifier des tables                          | Agent n&#39;y a pas accès                                      |
| **Changements** | Modifications fréquentes du schéma, itération rapide             | Changements réfléchis et planifiés, appliqués à la publication |
| **Facturation** | Incluse gratuitement avec chaque Replit App                      | À l&#39;usage                                                  |

<Note>
  Agent ne peut pas modifier la base de données de production. Cette restriction garantit la sécurité de votre base de données de production.

  Agent peut modifier votre base de données de développement. Au moment de la publication, toutes les modifications apportées avec Agent à la structure de votre base de données de développement (ajout et suppression de colonnes ou de tables) sont répercutées sur votre base de données de production.

  Vous pouvez modifier manuellement vos données de production à tout moment : ouvrez l&#39;outil **Database**, sélectionnez la base de données de production, ouvrez **My Data**, puis activez **Edit**.
</Note>

<div id="create-a-production-database-when-you-publish">
  ## Créer une base de données de production lors de la publication
</div>

Votre app publiée dispose de sa propre base de données de production, distincte de la base de données de développement que vous utilisez pendant le développement.

* **Infrastructure actuelle (Helium)** : Replit crée la base de données de production pour vous, au moment voulu pendant la publication. Aucune configuration n&#39;est nécessaire.
* **Anciennes bases de données de développement Neon** : vous créez la base de données de production depuis les paramètres de publication. Ouvrez **Production database settings** pendant la publication, activez **Create production database** et, si vous le souhaitez, activez **Set up your production database with your current development data** pour y copier vos données de développement.

<Frame caption="Paramètres de la base de données de production dans Publishing">
  <img src="/assets/mirror/production-database-settings-8855bf453da9.png" alt="Paramètres de publication affichant les options de création de la base de données de production" width="1406" height="1207" data-path="images/databases/shared-database-migration/production-database-settings.png" />
</Frame>

<Warning>
  Ne copiez des données de développement en production que si leur utilisation dans votre app en ligne est sans risque. Les données de développement peuvent contenir des comptes de test, des enregistrements d&#39;exemple ou du contenu incomplet.
</Warning>

Après la publication, votre app publiée utilise la base de données de production tandis que le Project Editor continue d&#39;utiliser la base de données de développement : vos futures modifications de développement ne touchent donc pas directement les données en production.

<div id="connection-pooling">
  ## Pooling de connexions
</div>

Par défaut, le pooling de connexions n&#39;est pas activé sur les bases de données de production. Votre App se connecte directement à la base de données via la chaîne de connexion `DATABASE_URL` : la plupart des frameworks doivent donc gérer eux-mêmes leur pool de connexions côté client.

<Note>
  Chaque projet Neon inclut une chaîne de connexion directe et une chaîne de connexion avec pooling. Une chaîne de connexion directe se présente ainsi : `postgresql://neondb_owner:<password>@<host>.<region>.neon.tech/<db>?sslmode=require`.

  Pour utiliser la connexion avec pooling, ajoutez `-pooler` à l&#39;hôte : `postgresql://neondb_owner:<password>@<host>-pooler.<region>.neon.tech/<db>?sslmode=require`.
</Note>

Si une chaîne de connexion de production a été exposée, [régénérez les identifiants de votre base de données de production](/fr/features/data-and-storage/connection-details#regenerate-production-database-credentials).

<div id="making-safe-changes-to-your-production-database">
  ## Modifier votre base de données de production en toute sécurité
</div>

Lorsque vous publiez des mises à jour qui incluent des modifications de la base de données, certains changements doivent être soigneusement planifiés afin d&#39;éviter toute interruption de service ou perte de données.

<Info>
  Vous pouvez constater une brève interruption de votre app publiée pendant la publication. Les modifications de la base de données nécessitent parfois d&#39;arrêter temporairement votre app afin d&#39;éviter les conflits et de protéger vos données pendant l&#39;application des changements.
</Info>

Les types de modifications suivants demandent généralement de la vigilance :

* **Supprimer des colonnes de la base de données** encore référencées par le code de votre application
* **Modifier le type de données d&#39;une colonne** d&#39;une manière que le code existant ne peut pas gérer
* **Ajouter des champs obligatoires** sans valeur par défaut à des tables existantes
* **Renommer des tables ou des colonnes**, ce qui casse les requêtes existantes
* **Modifier des contraintes** susceptibles de rejeter la logique applicative existante

<div id="test-changes-with-a-deployment-preview">
  ### Tester les modifications avec un aperçu de deployment
</div>

Un aperçu de deployment est une copie temporaire et isolée de votre environnement de production, dans laquelle vous pouvez tester les modifications de base de données et les mises à jour de l&#39;application avant qu&#39;elles n&#39;affectent vos utilisateurs réels. Utilisez-le pour :

* Vérifier que votre App fonctionne toujours une fois les modifications de base de données appliquées, sur l&#39;ensemble de vos principaux parcours utilisateur
* Confirmer que les données existantes ont bien été migrées et que les nouveaux champs contiennent les valeurs attendues
* Détecter d&#39;éventuelles régressions de performance dans les temps de réponse des requêtes

<div id="billing-and-resource-usage">
  ## Facturation et utilisation des ressources
</div>

Les bases de données de production sont facturées à l&#39;usage via Neon, un fournisseur de bases de données serverless. La base de données se met en veille après cinq minutes d&#39;inactivité, ce qui suspend la facturation du temps de calcul, puis se réactive instantanément dès qu&#39;elle reçoit une requête.

La vue d&#39;accueil de l&#39;outil Database affiche votre **Billing Period** et vos **Hours of Compute Used**. Pour connaître le stockage de chaque base de données, ouvrez l&#39;onglet **Settings** de la base concernée. Pour consulter l&#39;utilisation sur l&#39;ensemble de vos Replit Apps, ouvrez **Settings** → **Account** → **Account usage**, puis développez les lignes **PostgreSQL Storage** et **PostgreSQL Compute**.

Pour savoir comment Replit facture l&#39;utilisation des bases de données, consultez [Deployments and Database Billing](/fr/billing/about-usage-based-billing#databases).

<div id="removing-a-production-database">
  ## Supprimer une base de données de production
</div>

<Warning>
  L&#39;action de suppression est irréversible au-delà d&#39;une période de rétention de 7 jours. Veillez à sauvegarder toutes les données importantes avant de poursuivre. Les bases de données bénéficient d&#39;une période de suppression réversible de 7 jours pendant laquelle elles peuvent être restaurées ; contactez l&#39;assistance si vous avez besoin d&#39;aide. Passé ce délai de 7 jours, la base de données est définitivement supprimée et ne peut plus être récupérée.
</Warning>

<Accordion title="Comment supprimer une base de données">
  Depuis l&#39;outil **Database** :

  1. Sélectionnez la base de données, puis ouvrez l&#39;onglet **Settings**
  2. Sélectionnez **Remove database**, puis confirmez en sélectionnant **Yes, Remove database**
</Accordion>

<div id="legacy-development-database">
  ## Ancienne base de données de développement
</div>

Avant le 4 décembre 2025, la base de données de développement était hébergée sur <a href="https://neon.com/" target="_blank">Neon</a>. Toutes les nouvelles bases de données de développement sont hébergées sur l&#39;infrastructure de Replit (Helium). Vous pouvez vérifier laquelle utilise votre app dans l&#39;onglet **Settings** : une `DATABASE_URL` contenant `neon.tech` indique l&#39;ancienne infrastructure Neon ; `helium` indique l&#39;infrastructure actuelle.

| **Fonctionnalité**                 | **Replit (actuelle)**                                                                                                                                               | **Neon (ancienne)**                                                                                                                                                                         |
| ---------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Hébergement**                    | Hébergée sur l&#39;infrastructure de Replit                                                                                                                         | Hébergée sur Neon (fournisseur tiers)                                                                                                                                                       |
| **Facturation**                    | Incluse gratuitement avec chaque Replit App                                                                                                                         | Facturation à l&#39;usage. Consultez [la facturation de Publishing et des bases de données](/fr/billing/about-usage-based-billing#databases) pour en savoir plus.                              |
| **Restauration**                   | Restaurez votre base de données à partir de n&#39;importe quel checkpoint grâce à la [fonction de restauration](/fr/features/data-and-storage/data-recovery)           | Restauration à un instant donné (PITR) : restaurez-la à n&#39;importe quel point dans la période de conservation des sauvegardes.                                                           |
| **Sécurité de la connexion**       | Accessible uniquement depuis votre app ; jamais exposée publiquement.                                                                                               | Utilisait une chaîne de connexion complète. En cas de fuite, n&#39;importe qui pouvait accéder à votre base de données et la modifier.                                                      |
| **Comportement du remixage**       | Le [remixage](/fr/build/remix-an-app) crée une nouvelle base de données de développement contenant une copie des données, pour assurer l&#39;isolation et la sécurité. | Le remixage réutilise la même base de données pour toutes les copies ; les modifications apportées aux remixes pouvaient donc affecter l&#39;app d&#39;origine.                             |
| **Création de la base de données** | Créée automatiquement pour chaque Replit App.                                                                                                                       | Nécessitait une configuration explicite.                                                                                                                                                    |
| **Workflow de Publishing**         | Publishing crée une base de données de production distincte afin d&#39;isoler les environnements.                                                                   | Le développement et la production partageaient la même base de données ; des modifications involontaires apportées pendant le développement pouvaient donc affecter les apps en production. |

<div id="database-infrastructure-upgrade">
  ## Mise à niveau de l&#39;infrastructure de base de données
</div>

Replit fait migrer les bases de données de développement de Neon vers **Helium**, l&#39;infrastructure PostgreSQL managée de Replit. La mise à niveau est automatique, s&#39;exécute une seule fois par app lorsque vous l&#39;ouvrez dans le Project Editor et préserve l&#39;intégralité de vos données.

Ce qui change :

* **Latence réduite et stockage accru** : votre base de données s&#39;exécute sur l&#39;infrastructure Replit, aux côtés de votre app, et votre limite de stockage passe de 10 Go à 20 Go.
* **Même moteur de base de données** : Helium utilise PostgreSQL 16, la même version que Neon. Vos requêtes, vos schémas et vos données fonctionnent de la même manière.
* **Mise à jour automatique de la connexion** : `DATABASE_URL` est mis à jour pour pointer vers Helium. Votre ancienne chaîne de connexion Neon est conservée sous `NEON_DATABASE_URL` dans vos Secrets, à titre de référence.
* **Suppression des variables PG individuelles** : `PGHOST`, `PGPORT`, `PGUSER` et `PGPASSWORD` sont supprimées. Utilisez `DATABASE_URL` à la place.

Pendant la mise à niveau, un écran de progression **« Mise à niveau de votre base de données »** s&#39;affiche. L&#39;opération peut prendre de quelques minutes à quelques heures pour les bases volumineuses ; vous pouvez fermer l&#39;onglet et revenir plus tard. En cas de problème, la mise à niveau est automatiquement ignorée, puis relancée à la prochaine ouverture de votre app. Une fois terminée, une boîte de dialogue de confirmation s&#39;affiche.

Pour la plupart des créateurs, aucune action n&#39;est ensuite nécessaire. Vérifiez les points suivants s&#39;ils vous concernent :

* **Chaînes de connexion Neon codées en dur** : modifiez le code qui fait référence à une chaîne de connexion `neon.tech` afin d&#39;utiliser plutôt la variable d&#39;environnement `DATABASE_URL`.
* **Rôles PostgreSQL personnalisés** : les rôles et les permissions sont migrés automatiquement, mais les mots de passe des rôles ne peuvent pas être copiés. Réinitialisez les mots de passe des rôles personnalisés sur la nouvelle base de données.

<div id="ssl-connection-errors-after-the-upgrade">
  ### Erreurs de connexion SSL après la mise à niveau
</div>

Si vous voyez des erreurs telles que `The server does not support SSL connections`, c&#39;est que votre code de connexion force une négociation SSL. Neon exigeait SSL ; Helium s&#39;exécute localement aux côtés de votre app et ne l&#39;utilise pas. Rendez le paramètre SSL conditionnel selon l&#39;environnement :

<CodeGroup>
  ```js JavaScript theme={null}
  // Avant (ne fonctionne plus après la mise à niveau)
  const pool = new Pool({
    connectionString: process.env.DATABASE_URL,
    ssl: { rejectUnauthorized: false },
  });

  // Après (fonctionne en développement comme en production)
  const pool = new Pool({
    connectionString: process.env.DATABASE_URL,
    ssl:
      process.env.NODE_ENV === "production"
        ? { rejectUnauthorized: false }
        : false,
  });
  ```
</CodeGroup>

<Tip>
  Si vous utilisez un ORM tel que Drizzle, Prisma ou Sequelize, consultez sa documentation pour savoir comment configurer les paramètres SSL de manière conditionnelle. Le principe reste le même : désactivez SSL pour la base de données de développement et activez-le en production.
</Tip>

<div id="forked-apps-that-shared-a-database">
  ### Apps forkées partageant une base de données
</div>

Avec l&#39;ancien système Neon, forker une App copiait la variable `DATABASE_URL` de l&#39;App d&#39;origine : les deux Apps et leurs versions publiées se connectaient donc à la même base de données. Les anciennes bases de données partagées ont été arrêtées le **8 juin 2026**. Si votre App publiée ne fonctionne plus ou n&#39;a plus accès à ses données, consultez [Réparer une App publiée utilisant une base de données partagée](/fr/features/data-and-storage/shared-database-migration) ou [contactez l&#39;assistance](https://replit.com/support).
