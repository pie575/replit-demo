Vous trouverez ici des réponses sur la publication et les déploiements. Pour des instructions de dépannage étape par étape, consultez le [dépannage des déploiements](/fr/ja/build/troubleshooting). Pour en savoir plus sur les types de déploiement et le Monitoring, consultez les [déploiements Autoscale](/fr/ja/features/publishing/deployment-types#autoscale) et le [Monitoring des déploiements](/fr/ja/features/publishing/monitoring-a-deployment).

<AccordionGroup>
  <Accordion title="La publication échoue à l’étape « Créer un service Autoscale » : comment déboguer ce problème ?">
    La plupart des échecs de publication Autoscale peuvent être résolus en consultant les journaux de déploiement :

    1. Ouvrez **Publication** et recherchez le déploiement qui a échoué.
    2. Sélectionnez le menu à trois points à côté de celui-ci pour ouvrir les journaux.
    3. Copiez la sortie des journaux, ouvrez un nouveau chat Agent, collez-la, puis demandez quel est le problème et comment le résoudre.

    Si l’erreur `No run command configured` s’affiche alors que vous avez configuré une commande d’exécution, ouvrez les paramètres de déploiement, dissociez la commande d’exécution, ajoutez-la à nouveau, enregistrez, puis republiez. Consultez le [dépannage des déploiements](/fr/ja/build/troubleshooting).
  </Accordion>

  <Accordion title="Après une mise en ligne réussie, l’application affiche « Internal Server Error » : quel est le problème ?">
    Si la publication a réussi, mais que l’application en ligne renvoie une erreur 500, le problème vient du code de votre application, et non de l’infrastructure de Replit :

    1. Ouvrez **Publication**, affichez les journaux et copiez le message d’erreur complet.
    2. Ouvrez une nouvelle discussion avec Agent, collez les journaux et demandez-lui ce qui provoque l’erreur.
    3. Appliquez la correction et republiez.

    Si Agent ne parvient pas à identifier le problème, ouvrez **Publication → Historique**, trouvez la dernière version qui fonctionnait et redéployez-la. Consultez le [dépannage des déploiements](/fr/ja/build/troubleshooting).
  </Accordion>

  <Accordion title="Mon déploiement est bloqué pendant la compilation ou la migration : que dois-je faire ?">
    1. Ouvrez la palette de commandes avec `Cmd+K` sur Mac ou `Ctrl+K` sur Windows, puis recherchez et sélectionnez **Restart compute**.
    2. Ouvrez **Publication**, puis sélectionnez **Publication** pour déclencher un nouveau déploiement.
    3. Si l’échec se reproduit, ouvrez les journaux du déploiement échoué depuis le menu à trois points, copiez les journaux de build et collez-les dans une nouvelle conversation Agent afin de diagnostiquer le problème.

    Si le déploiement reste bloqué, contactez le [support Replit](https://replit.com/support) en incluant les journaux de build complets. Consultez le [dépannage des déploiements](/fr/ja/build/troubleshooting).
  </Accordion>

  <Accordion title="L’application fonctionne, mais elle est lente ou expire : que dois-je vérifier ?">
    1. Recherchez les messages récurrents de délai d&#39;attente dépassé ou de mémoire insuffisante dans les journaux de déploiement.
    2. Vérifiez les ressources du déploiement pour détecter d&#39;éventuelles limites de CPU ou de mémoire — consultez [Monitoring d&#39;un déploiement](/fr/ja/features/publishing/monitoring-a-deployment).
    3. Ouvrez une nouvelle conversation Agent, collez-y les journaux récents et demandez à Agent d&#39;identifier les goulots d&#39;étranglement.

    Parmi les causes courantes figurent les requêtes de base de données sans index, les opérations synchrones bloquantes et les fuites de mémoire. Avec les [déploiements Autoscale](/fr/ja/features/publishing/deployment-types#autoscale), la première requête après une mise à l&#39;échelle à zéro peut prendre quelques secondes — il s&#39;agit d&#39;un démarrage à froid normal.
  </Accordion>

  <Accordion title="Un échec de build s’affiche dans l’historique des déploiements : comment en identifier la cause ?">
    Ouvrez **Publishing → Historique**, sélectionnez le déploiement qui a échoué et affichez les logs de build. Repérez la première ligne marquée `ERROR` ou `FAILED` : c’est généralement la cause première, les lignes suivantes n’étant que des conséquences en cascade. Copiez cette section et collez-la dans un nouveau chat Agent pour obtenir un diagnostic. La plupart des échecs de build sont dus à des dépendances manquantes, à une commande d’exécution incorrecte ou à l’échec d’une migration de base de données. Consultez le [Monitoring des déploiements](/fr/ja/features/publishing/monitoring-a-deployment).
  </Accordion>

  <Accordion title="L’application fonctionne dans l’aperçu de l’éditeur, mais pas une fois publiée. Pourquoi ?">
    Il s&#39;agit presque toujours d&#39;une différence de configuration entre les environnements. Vérifiez les points suivants :

    * Toutes les clés du volet [Secrets](/fr/ja/core-concepts/project-editor/app-setup/secrets) de développement sont-elles également définies dans les secrets du déploiement ? Il s&#39;agit de deux environnements distincts.
    * `DATABASE_URL` pointe-t-il bien vers la base de données de production et non vers celle de développement ?
    * Reste-t-il des références codées en dur à `localhost` ou `127.0.0.1` ? Utilisez plutôt des chemins relatifs ou des URL basées sur l&#39;environnement.

    Consultez ensuite les journaux de déploiement pour repérer les erreurs propres à la production. Voir [Dépannage des déploiements](/fr/ja/build/troubleshooting).
  </Accordion>

  <Accordion title="Un déploiement Autoscale redémarre sans cesse — que signifient SIGTERM ou le code de sortie 1 ?">
    Les [déploiements Autoscale](/fr/ja/features/publishing/deployment-types#autoscale) redémarrent périodiquement par conception. La présence de `SIGTERM` dans les journaux indique que le processus s’est arrêté normalement — c’est normal. `Exit code 1` signifie que le processus lui-même a planté. Consultez les lignes précédentes pour identifier l’erreur réelle.

    Si les redémarrages sont assez fréquents pour affecter les utilisateurs, recherchez des promesses rejetées non gérées, des erreurs de mémoire insuffisante ou des variables d’environnement manquantes empêchant le démarrage.
  </Accordion>

  <Accordion title="J’ai mis à jour les variables d’environnement, mais ces modifications ne sont pas prises en compte dans mon application publiée — pourquoi ?">
    Replit stocke les secrets de développement et de production dans des espaces de stockage distincts : modifier l’un ne met pas l’autre à jour. Le panneau [Secrets de développement](/fr/ja/core-concepts/project-editor/app-setup/secrets) est disponible uniquement dans l’éditeur, tandis que les applications publiées utilisent les secrets de déploiement.

    Pour mettre à jour les variables d’une application en ligne, définissez-les dans les secrets de déploiement, puis ouvrez **Publier** et sélectionnez **Publier** pour la republier. Les nouvelles valeurs prennent effet au démarrage d’un nouveau déploiement. Consultez le [guide de dépannage des déploiements](/fr/ja/build/troubleshooting).
  </Accordion>

  <Accordion title="Comment déclencher un redéploiement sans modifier le code ?">
    Ouvrez **公開**, puis sélectionnez **公開**. Replit compile et publie le code actuel même en l&#39;absence de modifications — pratique après la mise à jour de secrets, la reprise d&#39;une base de données mise en pause ou pour intégrer des mises à jour de dépendances.

    Si votre application ne répond plus et qu&#39;un redéploiement complet vous semble trop lourd, ouvrez la palette de commandes avec `Cmd+K` sur Mac ou `Ctrl+K` sur Windows, puis recherchez et sélectionnez **Restart compute**.
  </Accordion>

  <Accordion title="Puis-je modifier la région de déploiement de l’application après sa publication ?">
    Non. Après avoir publié une application, vous ne pouvez pas modifier sa région de publication. Pour déplacer une application, remixez-la et publiez le remix dans une nouvelle région. Consultez [Région du projet](/fr/ja/features/publishing/project-geography).

    Vous ne pouvez pas non plus modifier la région de la base de données. Comme une application remixée peut recevoir un sous-domaine `.replit.app` différent, connectez d’abord un [domaine personnalisé](/fr/ja/features/publishing/custom-domains) si vous avez besoin d’une URL stable, puis ajoutez à nouveau les secrets de déploiement.
  </Accordion>

  <Accordion title="Pourquoi une analyse PCI ou de sécurité détecte-t-elle des cookies GAESA sur des applications publiées ?">
    L&#39;infrastructure de diffusion de Google ajoute un cookie `GAESA` (Google App Engine session affinity) aux apps Replit publiées afin d&#39;acheminer les requêtes vers l&#39;instance appropriée. Sa valeur est un identifiant de routage opaque : elle ne contient aucune information sensible ni donnée d&#39;application.

    Certains scanners de sécurité signalent `GAESA` au motif que les attributs `Secure` ou `HttpOnly` ne sont pas définis. Ce cookie n&#39;est pas créé par votre app, et vous ne pouvez ni le modifier ni le désactiver sur une app publiée.

    Si votre conformité PCI ou une analyse de sécurité signale ce cookie, contestez-le auprès de votre prestataire d&#39;analyse en tant que faux positif. Indiquez le nom du cookie et expliquez que c&#39;est l&#39;infrastructure de Google qui le définit pour le routage des requêtes. Les apps publiées ne peuvent ni le lire, ni le modifier, ni le désactiver, et ce cookie ne contient aucune donnée sensible.

    La conformité des apps que vous créez relève de votre responsabilité — consultez le [modèle de responsabilité partagée](/fr/ja/features/security/shared-responsibility-model). Si votre prestataire d&#39;analyse a besoin de précisions supplémentaires, [contactez l&#39;assistance Replit](https://replit.com/support).
  </Accordion>

  <Accordion title="Comment mettre une application hors ligne ou la dépublier ?">
    Ouvrez **Publishing**, sélectionnez l&#39;option d&#39;arrêt du deployment, puis confirmez. Votre application passe hors ligne et les frais de deployment cessent d&#39;être facturés. Les fichiers de votre projet, votre code et votre base de données ne sont pas supprimés — seul le deployment en production est arrêté. Les connexions des domaines personnalisés associés à ce deployment sont supprimées : pensez à les rajouter si vous republiez.

    Si les coûts vous préoccupent, sachez que les [deployments Autoscale](/fr/ja/features/publishing/deployment-types#autoscale) descendent à zéro en l&#39;absence de trafic, ce qui vous évite parfois d&#39;avoir à les arrêter.
  </Accordion>
</AccordionGroup>
