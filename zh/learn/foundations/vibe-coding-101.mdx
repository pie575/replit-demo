氛围编程能让你更快地将想法变成软件。无需从编写代码开始，你只需描述想要实现的内容，再借助 AI 将其转化为可查看、测试和改进的可用 App。

Replit 正是围绕这一流程打造的。你可以在同一个地方描述想法、预览结果、提供反馈、进行更改并发布。

本页面介绍氛围编程背后的思维方式。下一页 [使用 Agent 进行 Build](/zh/learn/build-with-agent) 将介绍如何使用 Agent 的工具。[有效编写提示词](/zh/learn/effective-prompting) 将介绍如何编写更清晰的指令。

<div id="software-used-to-be-a-team-loop">
  ## 软件开发曾是团队协作的循环
</div>

软件通常由团队共同开发。

产品经理或创始人确定要构建什么以及原因。设计师塑造用户体验。开发者将想法变成功能完善的软件。团队成员负责测试、提供反馈、发现 bug，并决定哪些内容已准备好发布。

这种协作模式很强大，因为每个角色都会带来不同的判断。产品决定什么最重要。设计决定体验应该如何呈现。工程决定功能应该如何实现。测试决定它是否真正按预期运行。

但这个循环可能很慢。每次更改都要经过交接：解释想法、设计流程、编写代码、审查结果、测试，然后再修改。

氛围编程压缩了这个循环。

借助 Replit，你可以亲自完成更多产品构建流程。你可以确定目标、生成初始版本、测试、提供反馈并持续改进，无需等待每个步骤在不同人员和工具之间流转。

<div id="your-role-changes">
  ## 你的角色正在改变
</div>

你无需成为开发者，也可以开始构建。

在氛围编程中，你的角色更接近产品负责人。你决定要做什么、面向谁、什么最重要，以及最终结果是否足够好。

Agent 协助实现，但你仍然主导整个过程。

你负责：

* 目标
* 受众
* 品味
* 约束条件
* 反馈
* 决定发布什么

Agent 协助：

* 将想法变成功能可用的软件
* 进行修改
* 解释行为
* 调试问题
* 持续改进 App

你的引导越到位，Agent 的构建效果就越好。

<div id="the-five-principles">
  ## 五项原则
</div>

遵循以下五项简单原则，能让 Vibe coding 发挥最佳效果：

1. 从目标出发。
2. 分块构建。
3. 管理上下文。
4. 审查和测试。
5. 根据反馈改进。

第一项原则指明方向。接下来的四项会形成一个循环：构建一个小模块，提供恰当的上下文，审查并改进它，然后构建下一个小模块。

这些原则比写出完美的第一个提示词更重要。你很难一步到位就得到最终的 App。目标是让这个过程保持清晰并不断推进。

<div id="start-with-the-goal">
  ## 从目标出发
</div>

一次好的氛围编程会话，始于一次好的产品沟通：

这是为谁设计的？他们应该能够做什么？怎样才能让它真正有用？

在让 Replit 开始构建前，先描述你想要达成的结果。

<AiPrompt>
  为一家本地面包店构建一个简单的网站。顾客应该能够查看今日特惠、了解餐饮服务，并提交餐饮服务请求。让网站风格温暖、精致，并且便于在移动设备上使用。
</AiPrompt>

之所以这样做有效，是因为你向 Replit 提供的是产品目标，而不只是一个 task。它说明了目标受众、核心操作以及第一个版本应具备的风格。

你暂时不需要了解技术实现细节。先从应用正常运行后应达到的效果开始。

<div id="build-in-small-slices">
  ## 分切片 Build
</div>

每一切片都是产品中足够完整、可以试用的一小部分。

对于烘焙网站，第一切片可以包括：

* 展示今日特色产品的主页
* 餐饮服务申请表单
* 适配移动设备的布局

这已经足够验证这个想法。你可以打开它，逐项点击体验，并决定下一步该改进什么。

避免一次性要求构建整个产品。大型请求更难审核，也更容易产生误解。分切片进行能帮助你持续推进，同时保持掌控。

第一切片正常运行后，再添加下一步。

<AiPrompt>
  在用户提交餐饮服务申请表单后添加确认消息。页面其余部分保持不变。
</AiPrompt>

这条指令简短、清晰且可测试。

<div id="manage-context">
  ## 管理上下文
</div>

上下文是 Replit 用来理解你的需求的信息。

有效的上下文可以包括：

* App 面向的用户
* 它要解决的问题
* 当前应包含的内容
* 可以留待后续处理的内容
* 不应更改的内容
* 示例、截图、草图、文件或数据
* 有关语气、风格或品牌的说明

管理上下文，就是在恰当的时机提供恰当的信息。

如果你要继续处理同一项功能，请留在同一个 Conversation 中，以便 Replit 利用之前的决策。如果你要开始另一项功能，或 Conversation 已变得杂乱，不妨重新开始，并简要总结关键信息。

例如：

<AiPrompt>
  上下文：这个烘焙店网站面向为孩子订购生日蛋糕的忙碌家长。请保持表单简短，让取货信息一目了然，并避免任何显得企业化的内容。本次仅改进餐饮服务请求部分。
</AiPrompt>

你不只是添加更多文字，而是在帮助 Replit 聚焦。

<div id="review-and-test">
  ## 审查和测试
</div>

Agent 可以构建应用，但是否真正可用由你决定。

每次完成一项重要更改后，都要打开 App，像目标用户一样使用它。不要只看 Agent 说它改了什么。亲自走一遍流程。

问问自己：

* 用户能否完成主要操作？
* 页面是否易于理解？
* 在移动设备上能否正常运行？
* 是否有任何重要功能出了问题？
* Replit 是否改动了本应保持不变的内容？
* 是否已经足够好，值得继续在此基础上构建？

审查和测试是最需要发挥产品判断力的环节。你需要确认软件是否符合预期。

<div id="improve-with-feedback">
  ## 根据反馈改进
</div>

切片的第一个版本只是草稿。这很正常。

氛围编程会在反馈中不断完善。告诉 Replit 哪些该保留、哪些该修改、哪些该移除，以及下一步该尝试什么。

不要这样说：

<AiPrompt>
  把它做得更好。
</AiPrompt>

试试这样说：

<AiPrompt>
  让餐饮请求表单更易于浏览。保留相同的字段，但优化间距、标签和提交按钮。不要更改特色菜部分。
</AiPrompt>

好的反馈要具体明确。它既能保留已经有效的部分，也能改进应用的某一部分。

当这个切片可用后，再回过头构建下一个小切片。

如果改动偏离了预期，就缩小范围。

<AiPrompt>
  改动太多了。保留新的按钮样式，但恢复原始布局，并且只更新餐饮表单。
</AiPrompt>

根据反馈不断改进，能让产品持续推进，同时保持掌控。

<div id="what-good-vibe-coding-feels-like">
  ## 良好的氛围编程体验是什么样的
</div>

出现以下情况时，说明你走在正确的路上：

* 你能用通俗易懂的语言说明目标
* 每次改动都足够小，便于审查
* 你知道 Agent 完成构建后该测试什么
* 你会提供上下文，而不是猜测 Agent 知道什么
* 你会告诉 Agent 应保留什么，而不只是要改什么
* 每一轮之后，App 都变得更实用

氛围编程并不意味着把一个想法交出去后就撒手不管。它意味着缩短想法、软件、反馈和改进之间的距离。
