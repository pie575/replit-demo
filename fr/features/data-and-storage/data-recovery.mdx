Les erreurs arrivent : une modification de schéma malencontreuse, des lignes supprimées ou une session Agent qui a mal tourné. Replit met à votre disposition une solution de récupération pour chaque base de données.

| Base de données | Méthode de récupération                                   | Disponibilité                                                                                               |
| --------------- | --------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------- |
| Développement   | Retour en arrière à un checkpoint                         | Tous les plans                                                                                              |
| Production      | Restauration à un instant donné et sauvegardes planifiées | Core : jusqu&#39;à 7 jours d&#39;historique. Pro et Enterprise : jusqu&#39;à 28 jours (7 jours par défaut). |

<div id="restore-your-development-database">
  ## Restaurer votre base de données de développement
</div>

Vous pouvez ramener votre app et votre base de données de développement à un état antérieur grâce à la [fonctionnalité de retour en arrière](/fr/features/version-control/checkpoints-and-rollbacks/). Vous pouvez ainsi restaurer votre base de données à n&#39;importe quel checkpoint créé par Agent.

<Info>
  Veillez à sélectionner « Database » sous « Additional retour en arrière options » lorsque
  vous restaurez l&#39;état d&#39;un checkpoint. Votre base de données retrouve ainsi
  l&#39;état dans lequel elle se trouvait au moment du checkpoint.
</Info>

<div id="restore-your-production-database">
  ## Restaurer votre base de données de production
</div>

Pour les bases de données de production, vous pouvez restaurer les données à un instant précis grâce à la restauration à un point dans le temps.

<Frame>
  <img
    src="/assets/mirror/database-rollbacks-f13dd20874ae.jpg"
    alt="Interface de retour en arrière de base de données affichant les options de
retour en arrière"
    width="1082"
    height="708"
    data-path="images/databases/database-rollbacks.jpg"
  />
</Frame>

La période sur laquelle vous pouvez remonter dépend de votre plan et de votre paramètre de conservation. Core conserve jusqu&#39;à 7 jours d&#39;historique, tandis que Pro et Enterprise en conservent jusqu&#39;à 28. Chaque plan démarre à 7 jours, et vous pouvez modifier cette fenêtre dans les paramètres de votre base de données de production. Une fenêtre plus longue consomme davantage de stockage : allonger la durée de conservation augmente donc vos coûts d&#39;utilisation. Si vous passez de Pro à Core, votre fenêtre de conservation est ramenée à 7 jours.

<Warning>
  Restaurer votre base de données ne restaure pas le code de votre app, et
  revenir en arrière sur votre app ne restaure pas votre base de données. Pour
  ramener les deux au même instant : restaurez la base de données, puis
  [revenez au checkpoint
  correspondant](/fr/features/version-control/checkpoints-and-rollbacks/) et
  publiez à nouveau votre app.
</Warning>

<div id="schedule-production-database-backups">
  ## Planifier les sauvegardes de la base de données de production
</div>

Les sauvegardes planifiées créent un point de restauration complet par jour. Replit planifie la sauvegarde aux alentours de minuit, selon le fuseau horaire actuel de votre navigateur, lorsque vous activez ou modifiez la planification.

1. Ouvrez l&#39;outil **Database** et sélectionnez la base de données de production.
2. Ouvrez **Settings**, puis développez **Scheduled backups** sous **Advanced**.
3. Pour activer les sauvegardes planifiées, sélectionnez une durée de conservation sous **Keep backups for**.

Les durées de conservation disponibles dépendent de votre offre : jusqu&#39;à 7 jours avec Core, et jusqu&#39;à 28 jours avec Pro et Enterprise.

<div id="storage-costs">
  ### Coûts de stockage
</div>

Replit facture séparément chaque catégorie de stockage de base de données de production :

| Catégorie de stockage                              | Prix par Gio et par mois |
| -------------------------------------------------- | -----------------------: |
| Stockage logique de la base de données             |                    $0,35 |
| Stockage de restauration à un instant donné (PITR) |                    $0,20 |
| Stockage des sauvegardes planifiées                |                    $0,09 |

<Note>Les coûts de stockage des bases de données bénéficient actuellement d&#39;une remise de 100 %.</Note>

Les frais de stockage logique de $0,35 s&#39;appliquent que vous utilisiez le PITR, les sauvegardes planifiées ou les deux. Le stockage des sauvegardes planifiées coûte moins cher par Gio que le stockage PITR. Si des points de restauration quotidiens vous suffisent, des sauvegardes planifiées associées à une fenêtre PITR plus courte peuvent réduire les coûts de stockage liés à la récupération. Votre coût total de sauvegarde dépend du volume de sauvegardes stocké et de la durée de conservation.

Le PITR offre davantage de points de restauration au sein de sa fenêtre, tandis que les sauvegardes planifiées n&#39;en fournissent qu&#39;un par jour : choisissez donc la méthode de récupération adaptée à vos besoins.

<Note>
  La planification utilise votre décalage UTC actuel. Un passage à l&#39;heure d&#39;été
  ou d&#39;hiver peut décaler l&#39;heure de sauvegarde d&#39;une heure tant que vous n&#39;avez pas
  mis à jour la planification. Les fuseaux horaires dont le décalage est fractionnaire
  utilisent l&#39;heure la plus proche.
</Note>

<div id="restore-a-scheduled-backup">
  ### Restaurer une sauvegarde planifiée
</div>

1. Ouvrez **Scheduled backups** dans les paramètres de la base de données de production.
2. Sélectionnez **View all backups**.
3. Sélectionnez **Restore** en regard du point de restauration souhaité.
4. Saisissez `restore`, puis sélectionnez **Continue**.

La restauration bascule votre base de données vers les données de la sauvegarde sélectionnée. Elle ne supprime pas les données actuelles, mais les services connectés peuvent se reconnecter brièvement.

<div id="troubleshooting-publishing-failures">
  ## Résoudre les échecs de publication
</div>

Si la publication échoue en raison de problèmes de base de données :

1. **Consultez les journaux de publication** pour repérer les messages d&#39;erreur précis concernant la connectivité de la base de données ou les conflits de schéma
2. **Passez en revue les modifications de schéma récentes** afin d&#39;identifier d&#39;éventuels conflits avec le code applicatif existant
3. **Testez vos modifications dans un aperçu du deployment** avant de republier
