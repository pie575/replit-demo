---
title: "Bases de données de développement et de production"
description: "Découvrez les deux bases de données de votre app : la base de données de développement, utilisée pendant le développement, et la base de données de production, qui alimente votre app publiée."
---

Chaque application Replit utilise deux bases de données. La **base de données de développement** est l&#39;espace où vous et Agent expérimentez pendant le développement. La **base de données de production** stocke les données réelles qui font fonctionner votre app publiée et les garde en sécurité pendant que vous continuez à développer.

<div id="section">
  ## Comparaison
</div>

| Aspect            | Base de données de développement                                 | Base de données de production                                                |
| ----------------- | ---------------------------------------------------------------- | ---------------------------------------------------------------------------- |
| **Objectif**      | Expérimentation et développement de fonctionnalités              | Service aux utilisateurs réels et stockage des données métier                |
| **Données**       | Données de test, enregistrements fictifs, petits jeux de données | Données réelles des utilisateurs, informations critiques pour l&#39;activité |
| **Création**      | Créée automatiquement pour chaque application Replit                     | Créée lors de la publication de l&#39;application                            |
| **Agent**         | Agent peut créer et modifier des tables                          | Agent n&#39;y a pas accès                                                    |
| **Modifications** | Changements de schéma fréquents, itérations rapides              | Modifications prudentes et planifiées, appliquées lors de la publication     |
| **Facturation**   | Incluse gratuitement avec chaque application Replit                      | Facturation à l&#39;usage                                                    |

<Note>
  Agent ne peut pas modifier la base de données de production. Cette restriction vise à préserver la sécurité de la base de données de production.

  Agent peut en revanche modifier la base de données de développement. Lors de la publication, les modifications qu&#39;Agent a apportées à la structure de la base de données de développement (ajout ou suppression de colonnes et de tables) sont appliquées à la base de données de production.

  Vous pouvez modifier manuellement les données de production à tout moment. Ouvrez l&#39;outil **Database**, sélectionnez la base de données de production, ouvrez **My Data**, puis activez **Edit**.
</Note>

<div id="section-2">
  ## Créer une base de données de production lors de la publication
</div>

Les applications publiées disposent d&#39;une base de données de production dédiée, distincte de la base de données de développement utilisée pendant leur création.

* **Infrastructure actuelle (Helium)** : Replit crée une base de données de production si nécessaire lors de la publication. Aucune configuration particulière n&#39;est requise.
* **Ancienne base de données de développement Neon** : créez une base de données de production depuis les paramètres de publication. Lors de la publication, ouvrez **Production database settings** et activez **Create production database**. Si nécessaire, activez également **Set up your production database with your current development data** pour copier vos données de développement actuelles.

<Frame caption="Paramètres Production database settings de Publishing">
  <img src="/assets/mirror/production-database-settings-8855bf453da9.png" alt="Paramètres de publication affichant l’option Create production database" width="1406" height="1207" data-path="images/databases/shared-database-migration/production-database-settings.png" />
</Frame>

<Warning>
  Ne copiez les données de développement dans l&#39;environnement de production que si elles peuvent être utilisées en toute sécurité dans l&#39;application en ligne. Les données de développement peuvent inclure des comptes de test, des exemples d&#39;enregistrements ou du contenu incomplet.
</Warning>

Après la publication, l&#39;application publiée utilise la base de données de production, tandis que le Project Editor continue d&#39;utiliser la base de données de développement. Les modifications apportées au cours des développements ultérieurs n&#39;affecteront donc pas directement les données en ligne.

<div id="section-3">
  ## Pool de connexions
</div>

Par défaut, le pool de connexions n’est pas activé pour les bases de données de production. Votre application se connecte directement à la base de données via la chaîne de connexion `DATABASE_URL`. La plupart des frameworks doivent donc gérer leur propre pool de connexions côté client.

<Note>
  Chaque projet Neon inclut une chaîne de connexion directe et une chaîne de connexion avec pool. La chaîne de connexion directe se présente sous la forme `postgresql://neondb_owner:<password>@<host>.<region>.neon.tech/<db>?sslmode=require`.

  Pour utiliser une connexion avec pool, ajoutez `-pooler` au nom d’hôte : `postgresql://neondb_owner:<password>@<host>-pooler.<region>.neon.tech/<db>?sslmode=require`.
</Note>

Si votre chaîne de connexion de production est compromise, [régénérez les identifiants de votre base de données de production](/fr/ja/features/data-and-storage/connection-details#regenerate-production-database-credentials).

<div id="section-4">
  ## Modifier la base de données de production en toute sécurité
</div>

Lors de la publication de mises à jour incluant des modifications de la base de données, certaines exigent une planification minutieuse afin d’éviter les interruptions de service ou les pertes de données.

<Info>
  Lors de la publication, votre application peut connaître une brève interruption de service. L’application de modifications à la base de données peut nécessiter l’arrêt temporaire de l’application afin d’éviter les conflits et de protéger les données.
</Info>

Les types de modifications suivants nécessitent généralement une attention particulière :

* **Suppression de colonnes de base de données** auxquelles le code de l’application fait encore référence
* **Modification du type de données d’une colonne** d’une manière que le code existant ne peut pas gérer
* **Ajout de champs obligatoires** à des tables existantes sans valeur par défaut
* **Renommage de tables ou de colonnes** qui rompt les requêtes existantes
* **Modification de contraintes** susceptible d’entrer en conflit avec la logique existante de l’application

<div id="section-5">
  ### Tester les modifications avec un aperçu de déploiement
</div>

Un aperçu de déploiement est une copie temporaire et isolée de votre environnement de production qui vous permet de tester les modifications apportées à la base de données et les mises à jour de l’application avant qu’elles n’affectent les utilisateurs réels. Utilisez-le pour :

* Vérifier que votre application fonctionne correctement tout au long des principaux parcours utilisateur, même après l’application de modifications à la base de données
* Vérifier que les données existantes sont correctement migrées et que les nouveaux champs contiennent les valeurs attendues
* Vérifier que les temps de réponse des requêtes ne se dégradent pas

<div id="section-6">
  ## Facturation et utilisation des ressources
</div>

Les bases de données de production sont facturées à l&#39;usage via Neon, un fournisseur de bases de données serverless. Une base de données se met en veille après cinq minutes d&#39;inactivité, ce qui suspend la facturation du temps de calcul, puis redémarre instantanément dès qu&#39;elle reçoit une requête.

La vue d&#39;accueil de l&#39;outil Database affiche **Billing Period** et **Hours of Compute Used**. Pour consulter le stockage de chaque base de données, ouvrez l&#39;onglet **paramètres** de la base concernée. Pour consulter l&#39;utilisation sur l&#39;ensemble de vos applications Replit, ouvrez **paramètres** → **Account** → **Account usage**, puis développez les lignes **PostgreSQL Storage** et **PostgreSQL Compute**.

Pour savoir comment Replit facture l&#39;utilisation des bases de données, consultez [Facturation des déploiements et des bases de données](/fr/ja/billing/about-usage-based-billing#databases).

<div id="section-7">
  ## Suppression de la base de données de production
</div>

<Warning>
  La suppression est irréversible après la période de conservation de 7 jours. Avant de continuer, veillez à sauvegarder toutes les données importantes. Les bases de données sont conservées en suppression réversible pendant 7 jours, période durant laquelle vous pouvez les restaurer. Contactez l’assistance si vous avez besoin d’aide. Après 7 jours, la base de données est définitivement supprimée et ne peut plus être restaurée.
</Warning>

<Accordion title="Supprimer une base de données">
  Dans l’outil **Database** :

  1. Sélectionnez la base de données et ouvrez l’onglet **paramètres**
  2. Sélectionnez **Supprimer la base de données**, puis confirmez en sélectionnant **Oui, supprimer la base de données**
</Accordion>

<div id="section-8">
  ## Base de données de développement héritée
</div>

Avant le 4 décembre 2025, les bases de données de développement étaient hébergées chez <a href="https://neon.com/" target="_blank">Neon</a>. Toutes les nouvelles bases de données de développement sont hébergées sur l’infrastructure propre à Replit (Helium). Vous pouvez vérifier celle qu’utilise votre App dans l’onglet **paramètres**. Si `DATABASE_URL` contient `neon.tech`, il s’agit de Neon hérité ; s’il contient `helium`, il s’agit de l’infrastructure actuelle.

| **Fonctionnalité**                 | **Replit (actuel)**                                                                                                                                                                         | **Neon (hérité)**                                                                                                                                                                    |
| ---------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **Hébergement**                    | Hébergé sur l’infrastructure propre à Replit                                                                                                                                                | Hébergé par Neon (fournisseur tiers)                                                                                                                                                 |
| **Facturation**                    | Inclus gratuitement pour toutes les applications Replit                                                                                                                                             | Facturation basée sur l’utilisation. Pour plus d’informations, consultez [Facturation de la publication et des bases de données](/fr/ja/billing/about-usage-based-billing#databases).   |
| **Fonctionnalité de restauration** | Vous pouvez restaurer la base de données à n’importe quel point de contrôle à l’aide de la [fonction de retour à une version antérieure](/fr/ja/features/data-and-storage/data-recovery)       | Restauration à un instant précis (PITR) : vous pouvez restaurer à n’importe quel instant durant la période de conservation des sauvegardes.                                          |
| **Sécurité des connexions**        | Accessible uniquement depuis l’application et jamais exposée publiquement.                                                                                                                  | Utilisait une chaîne de connexion complète. En cas de fuite, n’importe qui pouvait accéder à la base de données et la modifier.                                                      |
| **Comportement des remixes**       | Un [remix](/fr/ja/features/projects-and-artifacts/remix-an-app) crée une nouvelle base de données de développement contenant une copie des données, afin d’assurer l’isolation et la sécurité. | Les remixes réutilisaient la même base de données dans toutes les copies ; les modifications dans un remix pouvaient donc affecter l’application d’origine.                          |
| **Création de bases de données**   | Créée automatiquement pour chaque application Replit.                                                                                                                                               | Nécessitait une configuration explicite.                                                                                                                                             |
| **Processus de publication**       | Lors de la publication, une base de données de production distincte est créée afin d’isoler les environnements.                                                                             | Le développement et la production partageaient la même base de données ; des modifications de développement non intentionnelles pouvaient donc affecter l’application de production. |

<div id="section-9">
  ## Mise à niveau de l’infrastructure de base de données
</div>

Replit fait migrer les bases de données de développement de Neon vers **Helium**, son infrastructure PostgreSQL gérée. Cette mise à niveau s’effectue automatiquement, une fois par application lorsque vous l’ouvrez dans le Project Editor, et toutes les données sont conservées.

Modifications :

* **Latence réduite et capacité de stockage accrue** : les bases de données s’exécutent désormais sur la même infrastructure Replit que les applications, et la limite de stockage passe de 10 Go à 20 Go.
* **Même moteur de base de données** : Helium utilise la même version de PostgreSQL 16 que Neon. Le comportement des requêtes, des schémas et des données ne change pas.
* **Mise à jour automatique des informations de connexion** : `DATABASE_URL` est mis à jour pour pointer vers Helium. L’ancienne chaîne de connexion Neon est enregistrée dans Secrets sous le nom `NEON_DATABASE_URL` à titre de référence.
* **Suppression des variables PG individuelles** : `PGHOST`, `PGPORT`, `PGUSER`, `PGPASSWORD` sont supprimées. Utilisez plutôt `DATABASE_URL`.

Pendant la mise à niveau, un écran de progression intitulé **« Mise à niveau de votre base de données »** s’affiche. L’opération peut prendre de quelques minutes à plusieurs heures pour les bases de données volumineuses. Vous pouvez fermer l’onglet et revenir plus tard. Si un problème survient lors de la mise à niveau, celle-ci est automatiquement ignorée et réessayée la prochaine fois que vous ouvrez l’application. Une boîte de dialogue de confirmation s’affiche une fois l’opération terminée.

Pour la plupart des créateurs, aucune action particulière n’est requise après la mise à niveau. Vérifiez les éléments suivants s’ils s’appliquent à votre cas :

* **Chaînes de connexion Neon codées en dur** : mettez à jour tout code qui référence une chaîne de connexion `neon.tech` afin d’utiliser plutôt la variable d’environnement `DATABASE_URL`.
* **Rôles PostgreSQL personnalisés** : les rôles et les autorisations sont migrés automatiquement, mais les mots de passe des rôles ne peuvent pas être copiés. Réinitialisez les mots de passe des rôles personnalisés dans la nouvelle base de données.

<div id="ssl">
  ### Erreurs de connexion SSL après la mise à niveau
</div>

Si une erreur du type `The server does not support SSL connections` s&#39;affiche, c&#39;est que votre code de connexion force la négociation SSL. Neon imposait le SSL, mais Helium s&#39;exécute localement, aux côtés de votre application, et n&#39;utilise donc pas SSL. Configurez le paramètre SSL de manière conditionnelle, selon l&#39;environnement :

<CodeGroup>
  ```js JavaScript theme={null}
  // Avant (ne fonctionne plus après la mise à niveau)
  const pool = new Pool({
    connectionString: process.env.DATABASE_URL,
    ssl: { rejectUnauthorized: false },
  });

  // Après (fonctionne en développement comme en production)
  const pool = new Pool({
    connectionString: process.env.DATABASE_URL,
    ssl:
      process.env.NODE_ENV === "production"
        ? { rejectUnauthorized: false }
        : false,
  });
  ```
</CodeGroup>

<Tip>
  Si vous utilisez un ORM comme Drizzle, Prisma ou Sequelize, consultez sa documentation pour savoir comment configurer le SSL de façon conditionnelle. Le principe reste le même : désactivez le SSL sur la base de données de développement et activez-le en production.
</Tip>

<div id="section-10">
  ### Applications forkées partageant une base de données
</div>

Dans l&#39;ancien système Neon, lorsque vous forkiez une application, le `DATABASE_URL` de l&#39;application d&#39;origine était copié, et les deux applications ainsi que leurs versions publiées se connectaient à la même base de données. Les anciennes bases de données partagées ont été mises hors service le **8 juin 2026**. Si votre application publiée ne fonctionne plus ou n&#39;a plus accès aux données, consultez [Résoudre les problèmes des applications publiées utilisant des bases de données partagées](/fr/ja/features/data-and-storage/shared-database-migration) ou [contactez l&#39;assistance](https://replit.com/support).
