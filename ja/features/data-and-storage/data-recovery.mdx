失敗は起こるものです。スキーマの変更ミス、行の削除、Agentセッションが予期しない方向に進んでしまった場合など。Replitは各データベースに対応する復元手段を提供します。

| データベース | 復元方法                       | 利用可能なプラン                                          |
| ------ | -------------------------- | ------------------------------------------------- |
| 開発     | チェックポイントロールバック             | すべてのプラン                                           |
| 本番     | ポイントインタイム復元およびスケジュールバックアップ | Core：最大7日間の履歴。ProおよびEnterprise：最大28日間（デフォルトは7日間）。 |

## 開発データベースを復元する

[ロールバック機能](/ja/features/version-control/checkpoints-and-rollbacks/)を使って、アプリと開発データベースを以前の状態に戻すことができます。これにより、データベースはAgentが作成した任意のチェックポイントの状態に復元されます。

<Frame>
  <img src="/assets/mirror/checkpoint-rollback-476fde84864b.png" alt="ロールバックオプションが表示されているチェックポイントロールバックのインターフェース" width="3154" height="2366" data-path="images/replitai/checkpoint-rollback.png" />
</Frame>

<Info>
  チェックポイントの状態に復元する際は、必ず「Additional rollback options」の下にある「Database」を選択してください。これにより、データベースがチェックポイント作成時点の状態に復元されます。
</Info>

## 本番データベースを復元する

本番データベースの場合、ポイントインタイム復元を使って特定の時点に復元できます。

<Frame>
  <img src="/assets/mirror/database-rollbacks-f13dd20874ae.jpg" alt="ロールバックオプションを表示するデータベースロールバックインターフェース" width="1082" height="708" data-path="images/databases/database-rollbacks.jpg" />
</Frame>

どれだけ遡って復元できるかは、プランと保持設定によって異なります。Coreは最大7日間の履歴を保持し、ProおよびEnterpriseは最大28日間保持します。すべてのプランは7日間から始まり、本番データベースの設定でこの期間を変更できます。保持期間を長くするとストレージの使用量が増えるため、利用料金も増加します。ProからCoreにダウングレードした場合、保持期間は7日間に短縮されます。

<Warning>
  データベースを復元してもアプリのコードは復元されず、アプリをロールバックしてもデータベースは復元されません。両方を同じ時点に戻すには、データベースを復元した後、[対応するチェックポイントにロールバック](/ja/features/version-control/checkpoints-and-rollbacks/)してからアプリを再発行してください。
</Warning>

## 本番データベースのバックアップをスケジュールする

スケジュールバックアップは、1日に1つの完全な復元ポイントを作成します。スケジュールを有効にしたり更新したりすると、Replitはブラウザの現在のタイムゾーンで深夜近くにバックアップをスケジュールします。

1. **Database** ツールを開き、本番データベースを選択します。
2. **Settings** を開き、**Advanced** の下にある **Scheduled backups** を展開します。
3. スケジュールバックアップを有効にするには、**Keep backups for** の下で保持期間を選択します。

利用可能な保持期間はプランによって異なります。Coreは最大7日間、ProおよびEnterpriseは最大28日間をサポートします。

### ストレージコスト

Replitは本番データベースのストレージカテゴリごとに個別に使用量を計測します：

| ストレージカテゴリ              | GiBあたりの月額料金 |
| ---------------------- | ----------: |
| 論理データベースストレージ          |      \$0.35 |
| ポイントインタイム復元（PITR）ストレージ |      \$0.20 |
| スケジュールバックアップストレージ      |      \$0.09 |

<Note>データベースストレージのコストは現在100%割引されています。</Note>

\$0.35の論理ストレージ料金は、PITR、スケジュールバックアップ、またはその両方を使用する場合に適用されます。スケジュールバックアップストレージは、PITRストレージよりもGiBあたりの料金が低くなります。日次の復元ポイントで十分な場合は、PITRのウィンドウを短くしてスケジュールバックアップを利用することで、復元用ストレージのコストを削減できます。バックアップの総コストは、保存されるバックアップの量と保持期間によって決まります。

PITRはそのウィンドウ内でより多くの復元ポイントを提供します。スケジュールバックアップは1日に1つの復元ポイントを提供するため、ニーズに合った復元方法を選択してください。

<Note>
  スケジュールは現在のUTCオフセットを使用します。サマータイムの変更により、スケジュールを更新するまでバックアップの時刻が1時間ずれることがあります。分数オフセットのタイムゾーンでは、最も近い時間が使用されます。
</Note>

### スケジュールバックアップを復元する

1. 本番データベースの設定で **Scheduled backups** を開きます。
2. **View all backups** を選択します。
3. 復元したい復元ポイントの **Restore** を選択します。
4. `restore` と入力し、**Continue** を選択します。

復元を実行すると、データベースは選択したバックアップデータに切り替わります。現在のデータは削除されませんが、接続中のサービスが一時的に再接続することがあります。

## 発行の失敗のトラブルシューティング

データベースの問題で発行が失敗した場合：

1. **発行ログを確認**してデータベースの接続またはスキーマの競合に関する具体的なエラーメッセージを確認する
2. **最近のスキーマ変更を確認**して、既存のアプリケーションコードとの潜在的な競合を特定する
3. **再発行を試みる前にデプロイメントプレビューで変更をテスト**する
