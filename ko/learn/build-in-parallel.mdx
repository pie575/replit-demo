여러 작업을 동시에 처리하는 역량은 훌륭한 builder와 탁월한 builder를 가르는 skill 중 하나입니다. 이 페이지에서는 이런 방식으로 작업해 본 적이 없더라도 여러 기능을 동시에 안전하게 만드는 방법을 알려드립니다.

<div id="a-new-way-to-work-with-agent">
  ## Agent와 함께 일하는 새로운 방식
</div>

지금까지는 아마 Agent를 옆자리에 앉은 파트너처럼 여기며 작업해 왔을 것입니다. 요청하고, 지켜보고, 답하는 방식이죠. 병렬로 빌드하는 것은 이와는 전혀 다른 관계입니다. 기능 하나를 **task**로 Agent에게 넘겨두면, 여러분이 다른 일을 하는 동안 Agent가 백그라운드에서 그 기능을 만들어 냅니다.

사실 일상에서는 이미 이런 방식으로 일하고 있습니다. 세탁기가 다 돌아갈 때까지 그 앞에 서 있지는 않으니까요. 세탁기를 돌려놓고 요리를 하러 가죠. task도 마찬가지입니다. 하나를 시작해 두고, 그것이 실행되는 동안 다른 것을 시작하거나, 다른 작업을 검토하거나, main conversation에서 Agent와 계속 대화하면 됩니다.

이렇게 되면 여러분의 역할도 달라집니다. 하나의 빌드를 지켜보기만 하는 승객에서 벗어나, 여러 빌드를 지휘하는 감독이 되는 것입니다.

<div id="your-app-is-safe-while-tasks-run">
  ## task가 실행되는 동안에도 앱은 안전합니다
</div>

누구나 가장 먼저 던지는 질문이 있습니다. *내가 보지 않는 사이에 백그라운드 task가 앱을 망가뜨리면 어쩌지?*

그런 일은 없습니다. 각 task는 project의 **복사본**에서 작업합니다. task의 작업 결과를 검토하고 직접 적용하기 전까지 앱은 그대로입니다.

또한 각 task마다 별도의 Agent가 배정되고 전체 project context를 그대로 이어받으므로, 같은 설명을 다시 할 필요가 없습니다. task끼리는 서로 독립적이라 첫 번째 task가 실행되는 동안 바로 다음 task를 시작할 수 있습니다.

<div id="build-in-parallel">
  ## 병렬로 Build하기
</div>

<Steps>
  <Step title="프로젝트를 열고 사이드바를 고정하세요">
    기본 Build 레이아웃에서 시작하세요. 왼쪽에는 Agent chat, 오른쪽에는 Preview가 배치됩니다. 전역 사이드바를 펼친 후 고정해 두면 project의 task 컨트롤과 status 업데이트를 계속 확인할 수 있습니다.
  </Step>

  <Step title="프로젝트에서 task 만들기">
    사이드바에서 프로젝트를 펼친 다음 이름 옆의 **+** 버튼을 선택하세요. 백그라운드 task를 시작하는 가장 빠른 방법입니다.

    <Frame>
      <img src="/assets/mirror/build-in-parallel-new-task-sidebar-9a67150bc66c.jpg" width="700" height="578" data-path="images/replitai/build-in-parallel-new-task-sidebar.jpg" />
    </Frame>

    task를 만드는 또 다른 방법은 프로젝트 옆의 board 아이콘 위에 마우스를 올린 뒤 **New task**를 선택하는 것입니다. 같은 메뉴에서 board를 연 다음 하단의 **Plan a new task…**를 사용할 수도 있습니다.

    <Frame>
      <img src="/assets/mirror/build-in-parallel-board-shortcuts-267b99f4d424.jpg" alt="Board, Open, New task 작업이 있는 프로젝트 board 바로가기 메뉴" width="720" height="420" data-path="images/replitai/build-in-parallel-board-shortcuts.jpg" />
    </Frame>
  </Step>

  <Step title="하나의 구체적인 목표를 설명하세요">
    작업에 명확한 결과 하나만 지정한 후 전송하세요. Agent가 프로젝트를 분석해 메인 버전을 변경하지 않고 계획을 제안합니다.
  </Step>

  <Step title="계획을 검토하고 승인하세요">
    scope, 구현 단계, 완료 기준, 관련 파일, Agent 모드를 확인하세요. 계획이 의도에 맞을 때만 **Start building**을 선택하세요.

    <Frame>
      <img src="/assets/mirror/build-in-parallel-plan-review-2a2e1322ab59.jpg" alt="Start building 승인을 기다리는 백그라운드 task 계획 제안" width="1393" height="868" data-path="images/replitai/build-in-parallel-plan-review.jpg" />
    </Frame>

    **Start building**을 선택하면 task가 백그라운드에서 실행되고, 여러분은 메인 버전에서 하던 작업을 그대로 이어갈 수 있습니다.

    <Frame>
      <img src="/assets/mirror/build-in-parallel-task-active-c991ee7b52ee.jpg" alt="Preview 옆에 task 대화가 표시된 채로 빌드를 시작한 승인된 task" width="1393" height="868" data-path="images/replitai/build-in-parallel-task-active.jpg" />
    </Frame>
  </Step>

  <Step title="남은 태스크를 생성하고 승인하세요">
    한 번에 하나의 task씩 이 과정을 반복하세요. 서로 독립적인 작업에는 각각 별도의 결과물을 지정하세요. 의존 관계가 있는 작업은 필요한 기능이나 project 구조를 기준으로 설명해 Agent가 선행 조건을 인식할 수 있도록 하세요.

    새 task에 다른 task가 아직 만들고 있는 요소가 필요한 경우, Agent는 계획에 선행 조건을 명시하고 해당 작업이 완료되어 승인된 후에 새 task를 시작하도록 일정을 잡습니다.

    <Frame>
      <img src="/assets/mirror/build-in-parallel-dependent-plan-232d5472df15.jpg" alt="선행 task를 명시하고 그 작업이 완료된 후에 새 task를 시작하도록 일정을 잡은 Agent의 계획" width="1393" height="868" data-path="images/replitai/build-in-parallel-dependent-plan.jpg" />
    </Frame>
  </Step>

  <Step title="Agent에게 작업을 예약하게 하세요">
    board를 열면 **Drafts**, **Active**, **Ready**, **Done** 상태를 추적할 수 있습니다. 독립적인 task는 여유 용량이 생기면 실행됩니다. 의존성이 있는 task는 무엇 때문에 차단되었는지 표시되며, 선행 작업이 적용될 때까지 대기열에 남아 있습니다.
  </Step>

  <Step title="Ready 작업 검토 및 적용">
    Ready 상태의 task를 하나씩 열어 작업 내용과 테스트 결과를 확인하고, Preview에서 해당 기능을 직접 사용해 보세요. 기대에 부합한다면 **Apply**를 선택하세요. 선행 task를 적용하면 이를 의존하는 task들이 자동으로 잠금 해제됩니다.

    <Frame>
      <img src="/assets/mirror/build-in-parallel-board-ready-71e960b13e34.jpg" alt="Ready 상태의 완료된 선행 task와 Apply 및 Review 작업이 표시된 task board" width="650" height="270" data-path="images/replitai/build-in-parallel-board-ready.jpg" />
    </Frame>

    선행 task를 적용하고 나면, 이를 의존하는 task들은 자동으로 Active 상태로 이동합니다.

    <Frame>
      <img src="/assets/mirror/build-in-parallel-board-unlocked-0ffa3861a9f2.jpg" alt="첫 번째 task를 적용한 후 의존 task들이 자동으로 활성화된 task board" width="1393" height="868" data-path="images/replitai/build-in-parallel-board-unlocked.jpg" />
    </Frame>
  </Step>

  <Step title="기본 버전 확인">
    Apply할 때마다 기본 Build 보기로 돌아가세요. Preview에서 메인 버전의 결과를 직접 확인하고, Agent chat에서 구현 요약과 점검 항목, 경고, 아직 처리가 필요한 사항을 살펴보세요.

    <Frame>
      <img src="/assets/mirror/build-in-parallel-verify-main-version-62016529b118.jpg" alt="메인 카페 사이트 Preview 옆에 Agent chat이 표시된 기본 Build 보기" width="1393" height="868" data-path="images/replitai/build-in-parallel-verify-main-version.jpg" />
    </Frame>
  </Step>
</Steps>

승인된 모든 task가 **Done** 상태가 될 때까지 검토, 적용, 확인 과정을 반복하세요.

<Frame>
  <img src="/assets/mirror/build-in-parallel-board-done-a4ef1c2f1e59.jpg" alt="승인된 네 개의 task가 모두 Done 상태인 Task board" width="1393" height="868" data-path="images/replitai/build-in-parallel-board-done.jpg" />
</Frame>

<div id="a-worked-example-four-features-at-once">
  ## 실전 예시: 네 가지 기능을 한 번에
</div>

카페 opening site를 만든다고 가정해 봅시다. 다음 네 가지 개선 사항을 추가하려고 합니다.

* accessibility를 고려한 건너뛰기 링크와 안정적인 랜드마크 ID
* 이 ID를 활용하는 간결한 섹션 내비게이션
* accessibility 기반 위에서 개선되는 뉴스레터 폼 feedback
* 문서 head만 변경하는 Open Graph 메타데이터

여기서 핵심은 무엇이 무엇에 의존하는지 정하는 일입니다. 메타데이터 task는 문서 head만 건드리므로 나머지 세 가지와 겹치는 부분이 없어 곧바로 실행할 수 있습니다. 반면 내비게이션과 뉴스레터 task는 모두 랜드마크 task가 만든 안정적인 ID와 페이지 구조를 전제로 하므로, 그 작업이 끝날 때까지 기다려야 합니다. 이 구조를 기준으로 설명하면 Agent가 선행 조건을 스스로 파악합니다.

이 schedule을 직접 챙길 필요는 없습니다. 대기 중인 카드에는 board에 선행 조건이 표시되고, 서로 관련 없는 작업은 Active 상태로 실행됩니다.

<div id="slice-your-work-small">
  ## 작업을 작게 나누기
</div>

병렬 빌드를 성공시키는 핵심 기술은 기능을 작고 독립적인 task로 쪼개는 것입니다. 작은 task는 더 빨리 끝나고, 검토하기 쉬우며, 서로 간섭할 가능성도 적습니다.

유용한 규칙 하나: **task 설명에 &quot;그리고&quot;가 들어간다면, 나눌 수 있는지 검토해 보세요.**

* 좋은 예: &quot;이벤트 페이지 추가&quot;, &quot;문의 양식 추가&quot;
* 너무 큰 예: &quot;이벤트와 등록, 이메일 알림, 관리자 화면 추가&quot;

큰 버전이 잘못된 것은 아니지만, 이렇게 하면 Agent 하나가 모든 것을 순차적으로 처리해야 합니다. 작은 task 네 개로 나누면 Agent가 이를 한꺼번에 실행할 수 있습니다.

스스로 확인해 보세요. 다음 중 병렬로 실행할 수 있는 것은 무엇일까요?

1. 다크 모드 토글 추가
2. 고객 리뷰 섹션 추가
3. 고객이 리뷰에 답글을 달 수 있게 하기
4. 앱을 프랑스어로 번역하기

<Accordion title="정답">
  1, 2, 4번 task는 서로 독립적이므로 모두 동시에 실행할 수 있습니다. 3번 task는 2번에 의존합니다. 리뷰가 있어야 답글을 달 대상도 생기기 때문입니다. 이를 직접 파악할 필요는 없습니다. Agent가 의존 관계를 감지해 두 task의 순서를 알아서 정해 줍니다.
</Accordion>

<div id="apply-changes-safely">
  ## 안전하게 변경 사항 적용하기
</div>

각 task는 project의 격리된 복사본에서 실행됩니다. 한 task를 적용하면 메인 버전이 바뀌지만, 다른 task는 여전히 이전 버전을 기준으로 작업 중일 수 있습니다.

<Tip>
  여러 task의 변경 사항을 적용할 때 Agent가 충돌을 자동으로 처리합니다. 적용할 때마다 결과 앱을 확인하세요. 이상이 있으면 task thread나 main conversation에서 Agent에게 수정을 요청하세요.
</Tip>

두 task가 같은 파일을 변경한 경우, **Apply**를 선택한 뒤 Ready 카드에 **Resolving conflicts**가 잠시 표시될 수 있습니다. Agent가 병합을 마치고 결과를 다시 확인할 때까지 기다리세요. 파일을 직접 수동으로 해결할 필요는 없습니다.

<div id="review-like-a-manager">
  ## 관리자처럼 검토하기
</div>

병렬 빌드를 하면 여러분은 관리자가 됩니다. 그리고 관리자가 흔히 저지르는 실수는 직접 확인하지 않은 작업을 승인하는 것입니다. 지켜야 할 원칙은 간단합니다. 한 번에 하나의 task씩 다음 loop를 반복하세요.

<Steps>
  <Step title="task의 결과물 테스트하기">
    완료된 task를 열고 기능을 직접 사용해 보세요. 실제 사용자처럼 하나씩 클릭해 봅니다.
  </Step>

  <Step title="적용하기">
    만족스러운가요? 그렇다면 changes를 메인 App에 Apply하세요.
  </Step>

  <Step title="메인 버전 확인하기">
    적용된 기능이 App에 이미 반영된 changes와 문제없이 함께 동작하는지 확인하세요.
  </Step>

  <Step title="반복하기">
    모든 task가 반영될 때까지 다음 Ready 상태의 task를 테스트하고 적용하세요.
  </Step>
</Steps>

절대 한꺼번에 승인하지 마세요. 검토하지 않은 기능 세 개를 한 번에 적용하면, 문제가 생겼을 때 의심할 대상이 셋으로 늘어납니다.

<div id="when-to-stay-sequential">
  ## 순차적으로 진행해야 할 때
</div>

병렬 빌드는 도구일 뿐 규칙이 아닙니다. 다음과 같은 경우에는 main conversation에서 한 번에 하나씩 진행하세요.

* **두 아이디어가 같은 화면을 건드릴 때.** &quot;홈 페이지 재설계&quot;와 &quot;내비게이션 변경&quot;은 서로 충돌합니다. 순서대로 진행하세요.
* **탐색 중일 때.** Design 작업에서는 한 번의 시도 결과에 따라 다음에 원하는 방향이 달라집니다. 탐색은 작업 지시서가 아니라 대화입니다.
* **task를 한 문장으로 설명할 수 없을 때.** 간단히 말할 수 없다면 아직 위임할 준비가 되지 않은 것입니다.

<div id="work-within-your-limits">
  ## 한도 내에서 작업하기
</div>

plan에 따라 동시에 실행할 수 있는 백그라운드 task 수가 결정됩니다. 초과된 task는 대기열에 들어가고, 슬롯이 생기는 대로 시작됩니다. 현재 한도는 [task 시스템](/ko/core-concepts/agent/task-system#availability)에서 확인하세요.

여러분의 집중력에도 한도가 있습니다. task 두 개로 시작해 보세요. 검토가 부담스럽지 않다면 세 개로 늘려 보세요. 모든 단계를 감독할 필요는 없지만, 적용하기 전에 각 결과를 테스트하는 일은 빼놓을 수 없습니다.
