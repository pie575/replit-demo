Если в вашем приложении уже работает система аутентификации и есть база данных с реальными пользователями, переход на [Clerk Auth](/ru/pt/core-concepts/project-editor/auth-and-security/clerk-auth) — **это не просто правка кода**, а миграция данных. Без продуманного плана каждая существующая строка в вашей таблице `users` окажется для Clerk чужой: новые учётные записи создаются при первом входе, ни одна из них не связана с вашими историческими данными, а у вернувшихся клиентов возникает ощущение, что они «потеряли» свои учётные записи.

По сути, правильно сделать нужно всего две вещи.

<Note>
  Эта страница предназначена для разработчиков, у которых уже есть работающее приложение с собственной аутентификацией. Если вы только начинаете новое приложение, см. [обзор Clerk Auth](/ru/pt/core-concepts/project-editor/auth-and-security/clerk-auth) — миграция не потребуется.
</Note>

<div id="1-importe-seus-usurios-existentes-para-o-clerk">
  ## 1. Импортируйте существующих пользователей в Clerk
</div>

Каждый активный пользователь вашего App должен существовать как пользователь Clerk *до* того, как Clerk Auth вступит в работу. Как минимум, каждый импорт должен включать:

* **Электронную почту** (обязательно)
* **Доступные метаданные профиля**: имя, статус верификации и всё остальное, что вы хотите видеть в панели Auth
* **Хеш пароля**: существующий хеш пароля пользователя
* **Алгоритм хеширования**: алгоритм/формат этого хеша — именно в том виде, в каком его ожидает Clerk

Именно в алгоритме хеширования легче всего ошибиться. Clerk принимает только определённый набор форматов хешей паролей, и у каждого есть свой строковый идентификатор (`bcrypt`, `scrypt_firebase`, `argon2i`, `pbkdf2_sha256` и т. д.). Полный список и точный формат дайджеста для каждого из них смотрите в [справочнике API создания пользователя Clerk](https://clerk.com/docs/reference/backend/user/create-user).

Для этого шага одного однострочного prompt недостаточно. Agent, который проводит миграцию, должен **досконально понимать, как пароли хешируются в вашем текущем коде**: какая библиотека, какие параметры (фактор стоимости, раскладка соли, pepper и т. д.) и как всё это соотносится с одним из алгоритмов, поддерживаемых Clerk. Хорошо составленный prompt выглядит примерно так:

```
Изучи мой текущий код аутентификации и определи, как именно хешируются пароли
(библиотека, алгоритм, параметры и в каком формате хранится значение).
Затем напиши разовый скрипт импорта, который для каждого пользователя из моей таблицы users
вызывает Backend API Clerk и передаёт e-mail, метаданные профиля, дайджест пароля ровно
в том формате, которого ожидает соответствующий алгоритм Clerk, и правильное значение `passwordHasher`.
Прежде чем запускать, скажи, какой алгоритм Clerk ты выбрал и почему.
```

Если ваша схема хеширования не имеет однозначного соответствия ни одному из алгоритмов, поддерживаемых Clerk, импортированные пользователи не смогут войти со своим текущим паролем. В этом случае импортируйте их без дайджеста и при переходе отправьте письмо для сброса пароля.

<div id="2-resolva-usurios-clerk-de-volta-para-seus-ids-de-usurio-existentes">
  ## 2. Сопоставьте пользователей Clerk с их существующими идентификаторами
</div>

Как только импортированные пользователи войдут в систему, каждый аутентифицированный запрос будет содержать идентификационные данные Clerk. Ваш сервер должен сопоставить их со строкой в таблице `users` — иначе идентификатор пользователя Clerk не совпадёт ни с одним из существующих внешних ключей (`orders.user_id`, `documents.owner_id` и т. д.), и исторические данные будут выглядеть потерянными.

Clerk под управлением Replit упрощает эту задачу: если при импорте пользователя вы укажете его существующий идентификатор в качестве `externalId` пользователя Clerk, это значение автоматически запишется в claims сессии как `sessionClaims.userId`. Вашему промежуточному обработчику останется лишь отдавать предпочтение этому значению, а не исходному идентификатору пользователя Clerk:

```ts theme={null}
import { getAuth } from "@clerk/express";

const requireAuth = (req: any, res: any, next: any) => {
  const auth = getAuth(req);
  const userId = auth?.sessionClaims?.userId || auth?.userId;
  if (!userId) {
    return res.status(401).json({ error: "Unauthorized" });
  }
  req.userId = userId;
  next();
};
```

При таком подходе:

* **Импортированные пользователи** сопоставляются со своим существующим `users.id` через `sessionClaims.userId` — все их исторические данные остаются привязанными.
* **Новые пользователи** (зарегистрировавшиеся после перехода и не имеющие `externalId`) используют `auth.userId` — их идентификатор пользователя в Clerk. Используйте идентификатор пользователя Clerk в качестве первичного ключа для таких новых строк либо создавайте строку при первом входе и связывайте её с существующей записью.

  ## Вот и всё
</div>

Всё остальное — параллельная работа старой системы аутентификации, тестовый прогон с реальными учётными записями, отслеживание дублирующихся пользователей после перехода, отключение старой системы — это обычные правила гигиены миграции, не имеющие отношения именно к Clerk Auth.
