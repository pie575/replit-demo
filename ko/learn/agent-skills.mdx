skill은 Agent에게 새로운 능력을 가르칩니다. 여러분의 전문 지식, 선호하는 패턴, 특화된 노하우를 Agent에 전달해 더 우수하고 일관된 결과를 얻을 수 있습니다.

<div id="why-skills-matter">
  ## skill이 중요한 이유
</div>

Agent로 무언가를 만들 때마다 문제 해결 방법, 설계 결정, 프레임워크 선호도 같은 유용한 context가 쌓입니다. 하지만 Chat이 끝나면 그 context는 사라집니다. skill은 이를 그대로 남겨 둡니다.

GSAP 애니메이션 skill은 특정 라이브러리를 올바르게 사용하는 방법을 Agent에게 알려 줍니다. design system skill은 여러분이 정한 color와 spacing 규칙을 정확히 적용하게 해 줍니다. 버그 수정 skill은 해결책을 기록해 두어 Agent가 같은 실수를 반복하지 않게 합니다. 이전에는 결과가 들쭉날쭉했던 task도 안정적으로 처리됩니다.

skill은 [개방형 표준](https://agentskills.io/specification)이기도 합니다. Replit Agent를 비롯한 모든 에이전트에서 동작하므로 도구를 옮겨 다니며 그대로 쓸 수 있습니다.

<div id="proactive-vs-reactive-skills">
  ## 선제적 skill과 반응적 skill
</div>

skill을 언제, 어떻게 만들지 판단하는 데 도움이 되는 프레임워크입니다. 두 가지 패턴을 모두 이해하면 skill을 훨씬 효과적으로 활용할 수 있습니다.

<div id="proactive-skills">
  ### 선제적 skill
</div>

선제적 skill은 building을 시작하기 *전에* 미리 추가해 두는 skill입니다. 사용하려는 라이브러리나 패턴을 미리 조사하고, 그에 맞는 skill을 찾거나 만든 다음 prompting을 시작하세요.

**예시:** 손글씨 느낌의 SVG 애니메이션이 들어간 포트폴리오 사이트를 만들기 전에, 애니메이션 라이브러리를 조사해 GSAP을 찾습니다. GSAP React skill을 설치한 뒤 Agent에게 애니메이션을 만들어 달라고 prompt를 보냅니다. 이렇게 하면 Agent가 처음부터 필요한 전문 지식을 갖추게 되어 해당 라이브러리의 API와 모범 사례, 일반적인 패턴을 이해한 상태로 작업합니다. skill이 없으면 뻔하거나 잘못된 결과물이 나올 수 있습니다.

이 방식은 다음과 같은 경우에 특히 효과적입니다.

* 널리 쓰이지만 Agent가 혼자서는 정확히 다루기 어려운 미묘한 패턴이 있는 라이브러리를 사용할 때
* project 전반에 일관된 디자인 선택(typography, spacing, 애니메이션 스타일)을 유지하고 싶을 때
* project를 시작하는 시점에 이미 기술적인 direction이 정해져 있을 때

<div id="reactive-skills">
  ### 반응적 skill
</div>

반응적 skill은 문제를 해결한 *후에* 만드는 skill입니다. 어떤 문제를 만나 Agent와 함께 디버깅하고 수정한 다음, 같은 일이 다시 발생하지 않도록 그 해결책을 기록해 두는 방식입니다.

**예시:** mobile app용 canvas를 만들던 중 확대할수록 심해지는 이미지의 들쭉날쭉한 가장자리를 발견했다고 가정해 봅시다. Agent와 디버깅해 보니 원인은 축소 앨리어싱(minification aliasing)이었습니다. 직관과 달리 이미지가 작아질수록 더 나빠 보이는 렌더링 문제입니다. 수정을 적용한 뒤 Agent에게 skill을 만들어 달라고 요청하세요.

<AiPrompt>
  축소 앨리어싱 해결에 대해 방금 알아낸 내용을 담은 skill을 만들어 줘. 근본 원인, 해결책, 그리고 이 문제가 주로 언제 발생하는지를 포함해서 앞으로 예방할 수 있게 해 줘.
</AiPrompt>

Agent는 conversa 기록을 바탕으로 해당 project에 특화된 skill을 작성합니다. 다음에 같은 문제가 생기면 처음부터 디버깅하는 대신 Agent에게 그 skill을 알려주기만 하면 됩니다.

이 패턴은 다음과 같은 경우에 특히 유용합니다.

* 눈에 잘 띄지 않는 버그를 수정했고, 재발을 막고 싶을 때
* 디버깅 과정에서 앱 아키텍처에 대해 새로 알게 된 점이 있을 때
* 찾아내는 데 상당한 노력이 든 해결책을 기록해 두고 싶을 때

<div id="being-selective-with-skills">
  ## skill은 선별해서 사용하기
</div>

skill은 친구에게 우리 집 찾아오는 길을 알려주는 것과 비슷하다고 생각해 보세요. 핵심만 짚은 안내는 효과가 있지만, 서류철 가득한 문서는 그렇지 않습니다. 그걸 다 읽을 시간이 있는 사람은 없고, 정작 중요한 내용은 묻혀버리니까요.

Agent도 마찬가지입니다. skill을 너무 많이 추가하면 Agent가 혼란스러워할 수 있습니다. 해당 project에 어떤 skill을 활성화할지 신중하게 판단하고, 더 이상 필요 없는 skill은 제거하세요.

<Note>
  skill은 일반적인 지침보다 구체적이고 반복 가능한 패턴을 담을 때 가장 효과적입니다. 구체적인 workflow, 확립된 conventions, 검증된 해결책에 집중하세요.
</Note>

<div id="authoring-skills-well">
  ## skill을 잘 작성하는 방법
</div>

skill은 복잡하고 정교해질 수 있습니다. 다음 원칙을 지키면 skill을 효과적으로 유지할 수 있습니다.

* **정상 경로를 설명하세요.** Agent에게 그 일을 제대로 하는 방법을 알려주세요. *하지 말아야 할* 것들을 나열하고 있다면, 대개 접근 방식 자체를 다시 짜야 한다는 신호입니다.
* **가능한 한 스크립트를 활용하세요.** 결정론적인 스크립트는 Agent가 고민할 부담을 덜어주며, 매번 같은 단계를 추론하게 시키는 것보다 훨씬 안정적입니다.
* **링크로 연결하세요.** skill이 다른 마크다운 파일을 가리키도록 구성하면, Agent는 눈앞의 task에 필요한 파일만 가져옵니다.
* **정기적으로 벤치마크하세요.** 잘 되고 있으려니 짐작하는 대신, skill이 실제로 작동하는지 확인하는 방법입니다.
* **직접 작성하세요.** 목표는 간결하고 의도가 담긴 context이며, 통째로 생성하기보다 손으로 직접 써야 그 목표에 도달할 수 있습니다. Agent가 초안 작성을 도울 수는 있지만, 모든 줄이 제 몫을 하도록 직접 다듬으세요.
* **맞춤형으로 유지하세요.** 코드 정돈이나 보안 같은 일반적인 skill은 만들지 마세요. 이미 Agent에 기본 포함되어 있습니다. skill에는 본인이나 조직에만 해당하는 내용을 담아야 합니다.

대부분의 skill은 원인을 진단할 수 있는 방식으로 실패합니다.

* **실행되지 말아야 할 때 skill이 실행됩니다.** 설명이 너무 광범위한 경우입니다. 범위를 좁히고, *언제 사용하지 말아야 하는지*도 적어주세요. &quot;블로그 post나 도움말 문서에는 사용하지 않음&quot;이 어떤 긍정형 지시보다 유용할 때가 많습니다.
* **skill이 실행되지만 결과물이 어긋납니다.** 지시가 너무 두루뭉술한 경우입니다. &quot;전문적으로 만들어라&quot; 같은 모호한 안내는 정확한 이름, 구체적인 requirements, 명시적으로 피해야 할 사항 같은 구체적인 규칙으로 바꾸세요.
* **두 skill이 충돌합니다.** 두 skill이 같은 task에서 동시에 실행되지 않도록 설명을 수정하세요. 충돌은 거의 항상 지시의 문제가 아니라 범위 설정의 문제입니다.

skill은 시간이 지나면 낡기 마련이므로, 꾸준히 관리하는 문서처럼 다루세요.

<div id="taking-skills-workspace-wide">
  ## skills를 workspace 전체로 확장하기
</div>

지금까지의 내용은 모두 단일 project 안의 skills에 해당합니다. 팀에서는 workspace 전체에 Agent를 맞춤 설정할 수도 있어, 모든 구성원이 동일한 conventions에서 출발하고 project마다 이를 다시 설명하지 않아도 됩니다. workspace 맞춤 설정은 두 가지로 나뉩니다.

* **Custom instructions** — 누군가 prompt를 입력하기도 전에, 모든 project와 모든 메시지에서 Agent의 context에 주입되는 상시 적용 규칙입니다. &quot;자격 증명을 절대 평문으로 저장하지 않는다&quot;처럼 정말로 보편적인 소수의 규칙에만 사용하세요. 매 turn마다 로드되므로 단어 하나하나가 Agent의 context 예산을 차지합니다. 되도록 짧게 유지하세요.
* **Workspace skills** — 위에서 설명한 것과 같은 skills를 workspace의 모든 구성원이 쓸 수 있도록 열어 두고 중앙에서 관리하는 방식입니다. 관련된 task가 호출하기 전까지는 비용이 거의 들지 않으므로, 출력 품질을 떨어뜨리지 않으면서 많은 skills를 제공할 수 있습니다.

무엇을 어디에 둘지 판단하는 간단한 기준이 있습니다. 누가 무엇을 만들든 항상 지켜야 하는 규칙이라면 custom instruction이고, 특정 종류의 task에서만 필요한 규칙이라면 skill입니다.

custom instructions와 workspace skills를 설정하는 방법과 관리 권한이 있는 사람에 대해서는 [Agent Customization](/ko/features/agent/agent-customization)을 참고하세요.

<div id="security-considerations">
  ## 보안 고려사항
</div>

Replit Skills pane에 있는 skill은 안전성 검증을 거칩니다. 하지만 skill은 어디서든 설치할 수 있으며, 누구나 기여할 수 있는 [오픈 소스 저장소](https://github.com/vercel-labs/skills)에서 제공됩니다.

skill은 Agent가 따르는 지침이므로, 악의적인 skill은 Agent가 프로젝트의 민감한 데이터를 외부로 유출하도록 유도할 수 있습니다. 외부 소스에서 skill을 설치하기 전에 다음을 확인하세요.

1. **파일을 여세요.** skill은 마크다운 문서일 뿐입니다. 사용하기 전에 `/.agents/skills/`에 있는 내용을 읽어보세요.
2. **출처를 확인하세요.** 해당 skill이 신뢰할 수 있는 저장소나 작성자에게서 온 것인지 확인하세요.
3. **어떤 지시가 담겨 있는지 검토하세요.** skill이 의심스러운 외부 URL을 참조하거나 민감한 정보를 요구하지 않는지 확인하세요.

<Warning>
  외부 소스에서 가져온 skill은 설치하기 전에 반드시 검토하세요. Replit Skills pane의 skill은 검증을 거쳤지만, CLI로 설치하거나 인터넷에서 복사한 skill은 그렇지 않습니다.
</Warning>

<div id="skills-vs-mcp-servers">
  ## skill과 MCP server 비교
</div>

skill과 MCP server는 에이전트를 확장하는 두 가지 주요 방법이며, 각각 용도가 다릅니다.

**skill**은 context를 적게 사용합니다. skill이 호출되기 전까지는 간단한 설명만 로드됩니다. 다음과 같은 경우에 skill을 사용하세요:

* workflow와 conventions(&quot;게시하는 방법&quot;, &quot;코드 리뷰 체크리스트&quot;)
* 참고 자료(API 패턴, 스타일 가이드, design system)
* 재사용 가능한 prompt와 전문 지식(애니메이션 라이브러리, 프레임워크 패턴)

**MCP server**는 context를 많이 사용합니다. 모든 도구 설명이 처음부터 한꺼번에 로드되므로, 너무 많이 추가하면 출력 품질이 떨어질 수 있습니다. 다음과 같은 경우에 MCP server를 사용하세요:

* 외부 서비스 연결(Notion, Linear, Figma)
* API 액세스가 필요한 작업
* 단순히 지시만 하는 것이 아니라 실제로 무언가를 *수행하는* 도구

핵심적인 차이는 이렇습니다. skill은 에이전트가 *어떻게* 작업해야 하는지를 정의하고, MCP server는 에이전트가 *무엇에* 액세스할 수 있는지를 정의합니다. 둘 다 Replit Agent 같은 코딩 에이전트에서도, 직접 만든 에이전트에서도 사용할 수 있습니다.
