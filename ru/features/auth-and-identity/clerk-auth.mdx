Clerk Auth даёт вашему приложению собственную систему аутентификации на базе [Clerk](https://clerk.com). В отличие от [Replit Auth](/ru/features/auth-and-identity/authentication), который использует систему входа Replit и создаёт учётные записи Replit, Clerk Auth разворачивает для вашего приложения **отдельный тенант Clerk**. Пользователи создают учётные записи прямо в вашем приложении — а не в Replit — а вы получаете полный контроль над брендингом, способами входа и всем процессом аутентификации.

<Note>
  **Clerk Auth или Replit Auth** — с **Clerk Auth** (эта страница) ваше приложение получает собственный тенант аутентификации с полностью настраиваемым брендингом и учётными записями пользователей, независимыми от Replit. С **[Replit Auth](/ru/features/auth-and-identity/authentication)** пользователи входят под учётными записями Replit и видят страницы входа с брендингом Replit. Выбирайте Clerk Auth, если хотите видеть собственный бренд на страницах входа или вам нужны учётные записи, не связанные с Replit.
</Note>

<div id="clerk-auth-vs-replit-auth-at-a-glance">
  ## Clerk Auth и Replit Auth: краткое сравнение
</div>

|                                  | Clerk Auth                                                                              | Replit Auth                                                |
| -------------------------------- | --------------------------------------------------------------------------------------- | ---------------------------------------------------------- |
| **Учётные записи пользователей** | Пользователи создают учётные записи в вашем приложении (учётная запись Replit не нужна) | Пользователи входят через учётную запись Replit            |
| **Брендинг**                     | Полностью настраивается — название, значок и цвета вашего приложения                    | Страница входа с брендингом Replit                         |
| **Учётные данные SSO**           | Собственные учётные данные OAuth для каждого провайдера                                 | Используются общие OAuth-приложения Replit                 |
| **Среды**                        | Раздельные среды разработки и Production                                                | Одна среда                                                 |
| **Рефералы**                     | Интеграции с реферальной программой Replit нет                                          | Регистрации засчитываются в Replit Referrals               |
| **Лучше всего подходит**         | Приложениям с собственным брендингом, профессиональным и коммерческим продуктам         | Быстрого запуска, приложений, где брендинг Replit допустим |

<div id="getting-started">
  ## Начало работы
</div>

Чтобы добавить Clerk Auth в свой app, укажите это в prompt для Agent:

```
Помоги мне создать app, который [ваша идея приложения], и в нём должна быть аутентификация через Clerk Auth.
```

Agent берёт всё на себя — создаёт тенант Clerk, сохраняет учётные данные, настраивает маршруты и добавляет middleware. Вам не потребуется ни аккаунт Clerk, ни ручная настройка.

<div id="how-clerk-auth-works-with-replit">
  ## Как Clerk Auth работает с Replit
</div>

Когда Agent настраивает Clerk Auth для вашего App, он:

1. **Создаёт отдельный тенант Clerk** — ваш App получает собственное приложение Clerk с раздельными средами Development и Production
2. **Выдаёт учётные данные** — API-ключи и Secrets сохраняются как переменные окружения
3. **Настраивает прокси** — аутентификация без сбоев работает на вашем опубликованном домене
4. **Создаёт маршруты входа и регистрации** — в ваш App добавляются готовые React-компоненты Clerk
5. **Добавляет серверное промежуточное ПО** — ваши маршруты API защищаются с помощью middleware Clerk для Express

<Note>
  Вам не нужно создавать учётную запись Clerk или管理 инфраструктуру. Replit берёт всё это на себя автоматически.
</Note>

<div id="capabilities">
  ## Возможности
</div>

<div id="whats-supported">
  ### Что поддерживается
</div>

Clerk Auth предоставляет вашему приложению:

* **Независимые учётные записи пользователей** — пользователи вашего приложения не являются пользователями Replit; они существуют только внутри Clerk-тенанта вашего приложения
* **Страницы входа в вашем фирменном стиле** — название приложения, логотип, цвета, шрифты и тексты на страницах входа и регистрации задаются в коде вашего приложения
* **SSO в вашем фирменном стиле** — укажите собственные учётные данные OAuth для каждого провайдера, чтобы на экране согласия OAuth отображались название и оформление вашего приложения, а не стандартные значения
* **Аутентификация по email и паролю** — встроенные регистрация и вход с подтверждением адреса электронной почты
* **Вход через социальные сети (SSO)** — дайте пользователям возможность входить через Google, GitHub, Apple или X (Twitter)
* **Управление пользователями** — просматривайте, ищите и модерируйте пользователей на панели Auth
* **Работа с сессиями** — токены сессий защищены и управляются автоматически
* **Среды разработки и Production** — протестируйте аутентификацию в среде разработки до запуска

<Note>
  Большинство настроек Clerk Auth доступны в инструменте **Auth** в Project Editor — учётная запись Clerk не нужна, как и работа с панелью управления Clerk.
</Note>

<div id="whats-not-supported">
  ### Что не поддерживается
</div>

Следующие возможности пока недоступны в Clerk Auth (по сравнению с внешним приложением Clerk, которое вы настраиваете самостоятельно). Подробное сравнение см. в [этом разделе FAQ](#how-does-clerk-auth-compare-to-external-clerk).

* **Вход по номеру телефона** — вход и подтверждение через SMS
* **Поддержка MFA** — многофакторная аутентификация для конечных пользователей
* **Полный набор SSO-провайдеров** — пока поддерживаются только Google, GitHub, Apple и X
* **Организации как тенанты** — функции организаций и членства в командах в Clerk

<div id="development-and-production-environments">
  ## Среды Development и Production
</div>

Для каждого App с Clerk Auth создаются две полностью независимые среды Clerk: среда **Development**, которая обслуживает ваше приложение для разработки и Preview во время работы над ним, и среда **Production**, которая обслуживает опубликованное приложение. Такая изоляция заложена изначально: у сред разные ключи API и разные хранилища пользователей.

<div id="separate-api-keys">
  ### Отдельные ключи API
</div>

У каждой среды есть собственные публичные и секретные ключи API. Ключи, доступные вашему приложению, автоматически переключаются в зависимости от того, запущено ли приложение в среде разработки или в рабочей среде:

* В вашем workspace секреты `CLERK_PUBLISHABLE_KEY` и `CLERK_SECRET_KEY` содержат **тестовые ключи** (`pk_test...` и `sk_test...`), указывающие на среду разработки.

<Frame>
  <img src="/assets/mirror/clerk-check-dev-keys-5a23f6b7dd0c.png" alt="Инструмент Secrets в Workspace, показывающий CLERK_SECRET_KEY и CLERK_PUBLISHABLE_KEY с префиксами sk_test_ и pk_test_" width="1946" height="402" data-path="images/workspace/auth/clerk-check-dev-keys.png" />
</Frame>

* После публикации приложения опубликованное развертывание использует **боевые ключи** (`pk_live...` и `sk_live...`), указывающие на Production. Чтобы проверить префиксы, откройте **Publishing → Overview → Adjust settings** и проверьте `CLERK_PUBLISHABLE_KEY` и `CLERK_SECRET_KEY`.

<Frame>
  <img src="/assets/mirror/clerk-check-prod-keys-acccd7f68da1.png" alt="Раздел Overview в Publishing, показывающий секреты приложения в Production: CLERK_SECRET_KEY и CLERK_PUBLISHABLE_KEY с префиксами sk_live_ и pk_live_" width="1924" height="1664" data-path="images/workspace/auth/clerk-check-prod-keys.png" />
</Frame>

<Note>
  Для переключения между средами ничего делать не нужно — Replit автоматически управляет ключами как для Development, так и для Production. Просто разрабатывайте, тестируйте и публикуйте приложение — всё готово.
</Note>

<Warning>
  Не заменяйте тестовые ключи боевыми, не редактируйте их на панели Secrets и не настраивайте ничего вручную в панели Clerk. Иначе автоматическое переключение между средами разработки и Production перестанет работать. Replit-managed Clerk Auth такой способ настройки не поддерживает.
</Warning>

<div id="separate-user-stores">
  ### Раздельные хранилища пользователей
</div>

У каждой среды собственное хранилище пользователей. Учётные записи, созданные при регистрации в среде Development, **не** существуют в среде Production, и наоборот:

* Пользователь, зарегистрировавшийся во время тестирования в dev/preview-приложении, создаётся только в хранилище Development.
* Пользователь, зарегистрировавшийся в вашем опубликованном приложении, создаётся только в хранилище Production.
* Сессии, метаданные пользователей и любые данные, привязанные к `userId` из Clerk, также относятся только к той среде, в которой была создана учётная запись.

Это ожидаемое поведение. Чтобы просмотреть пользователей в каждой среде, откройте панель **Auth** в Workspace и переключайтесь между Development и Production с помощью переключателя среды на вкладке **Users**.

<Note>
  Development — среда для экспериментов и разработки, а Production обслуживает реальных пользователей вашего работающего приложения. Эти две среды намеренно изолированы друг от друга, поэтому учётные записи и данные, созданные в Development, не появятся в Production.
</Note>

<div id="managing-users">
  ## Управление пользователями
</div>

**Панель Auth** в Project Editor дает полное представление об аутентифицированных пользователях. Поскольку Clerk Auth создает для вашего app отдельное хранилище пользователей, перечисленные здесь пользователи — это учетные записи в вашем app, а не учетные записи Replit.

<Frame>
  <img src="/assets/mirror/clerk-users-4940ed365605.png" alt="Вкладка пользователей Clerk Auth с аутентифицированными пользователями на панели Auth" width="2136" height="794" data-path="images/workspace/auth/clerk-users.png" />
</Frame>

На вкладке **Users** вы можете:

* **Просматривать всех пользователей** с такими данными, как электронная почта, имя, последний вход и дата создания учетной записи
* **Искать и фильтровать**, чтобы найти нужных пользователей
* **Блокировать и разблокировать пользователей**, управляя доступом к вашему app
* **Сортировать пользователей** по различным критериям
* **Переключать среды** — переходить между Development и Production, чтобы управлять пользователями в каждой из них

<div id="customizing-your-sign-in-page">
  ## Настройка страницы входа
</div>

Визуальное оформление страниц входа и регистрации — название приложения, логотип, цвета, шрифты и тексты — задаётся в коде вашего App, а не на панели Auth. Чтобы изменить его, попросите Agent:

```
Обнови страницу входа: сделай заголовком [название вашего приложения], добавь [описание вашего логотипа] и подбери цвета под оформление моего сайта.
```

Под капотом за это отвечают свойства `appearance` и `localization`, передаваемые в `<ClerkProvider>`, а также файл логотипа в каталоге `public/` вашего приложения. Agent поддерживает их в соответствии с остальной темой оформления приложения.

<Note>
  Название приложения, которое отображается **на собственном экране согласия Google, Apple, GitHub или X** (тот экран, который появляется после нажатия «Войти через Google» и т. п.), задаётся отдельно — оно берётся из OAuth-приложения, зарегистрированного у этого провайдера, и **не** меняется при редактировании кода страницы входа. Чтобы изменить его, настройте [собственные учётные данные OAuth](#configuring-oauth-credentials-for-an-sso-provider) для этого провайдера.
</Note>

<div id="configuring-login-providers">
  ## Настройка провайдеров входа
</div>

Clerk Auth поддерживает Google, GitHub, Apple и X в качестве провайдеров входа через социальные сети. На вкладке **Configure** панели Auth вы определяете, какие провайдеры отображаются на странице входа, а в среде Production — использует ли каждый провайдер учетные данные OAuth, управляемые Replit, или ваши собственные для входа с фирменным оформлением.

<Frame>
  <img src="/assets/mirror/clerk-configure-60169c473d64.png" alt="Вкладка Configure с провайдерами SSO в боковой панели, выбранной средой Production и списком провайдеров с переключателями включения и действиями Edit" width="923" height="378" data-path="images/workspace/auth/clerk-configure.png" />
</Frame>

Откройте вкладку **Configure**. В боковой панели в разделе **SSO providers** выберите **Development** или **Production**: **Development** отвечает за приложение для разработки и предпросмотра в Workspace, а **Production** — за ваше опубликованное приложение. У каждой среды свой список в основной панели. Здесь вы можете:

* **Включить или отключить провайдера** — используйте переключатель, чтобы задать, отображается ли провайдер на странице входа. Отключенные провайдеры не видны пользователям.
* **Настроить собственные учетные данные OAuth (только для Production)** — см. раздел [Настройка учетных данных OAuth для провайдера SSO](#configuring-oauth-credentials-for-an-sso-provider) ниже.

<div id="configuring-oauth-credentials-for-an-sso-provider">
  ### Настройка учётных данных OAuth для SSO-провайдера
</div>

По умолчанию провайдеры используют **учётные данные, управляемые Replit** — вход работает сразу, но на экране согласия OAuth отображается брендинг Replit. Переключитесь на **Собственные учётные данные**, чтобы использовать собственного OAuth-клиента из консоли разработчика провайдера. Тогда на экране согласия будут отображаться название и брендинг вашего приложения.

1. Откройте панель **Auth** в Project Editor. Перейдите на вкладку **Configure**, затем на боковой панели в разделе **SSO providers** выберите **Production**.

<Frame>
  <img src="/assets/mirror/clerk-configure-60169c473d64.png" width="923" height="378" data-path="images/workspace/auth/clerk-configure.png" />
</Frame>

2. Нажмите значок **Edit** рядом с провайдером, который хотите настроить. По умолчанию выбраны **учётные данные, управляемые Replit**.

<Frame>
  <img src="/assets/mirror/clerk-sso-default-credentials-525090775408.png" alt="Панель редактирования провайдера с вариантами учётных данных, управляемых Replit, и собственных учётных данных" width="1468" height="960" data-path="images/workspace/auth/clerk-sso-default-credentials.png" />
</Frame>

3. Выберите **Собственные учётные данные**. Панель развернётся, отобразив поля учётных данных и контрольный список **Настройка провайдера** со значениями, которые необходимо зарегистрировать у провайдера.

<Frame>
  <img src="/assets/mirror/clerk-sso-custom-credentials-f24112a5cf07.png" alt="Панель собственных учётных данных с полями идентификатора и секрета OAuth-клиента, а также контрольным списком настройки провайдера с URL-адресами перенаправления для обратного вызова и источниками JavaScript" width="1468" height="2246" data-path="images/workspace/auth/clerk-sso-custom-credentials.png" />
</Frame>

4. Следуйте инструкциям, чтобы завершить настройку. В них есть прямые ссылки на консоль и соответствующую справочную документацию. Документацию для вашего провайдера также можно найти в разделе [Дополнительные ресурсы](#additional-resources).
5. Заполните все обязательные значения учётных данных.
6. В консоли разработчика провайдера зарегистрируйте на портале разработчика все значения из контрольного списка **Настройка провайдера**. Используйте значки копирования, чтобы точно скопировать каждое значение, и отмечайте пункты по мере выполнения либо выберите **Отметить всё как выполненное** после завершения.
7. Выберите **Сохранить изменения**.

<div id="rechecking-setup-after-domain-changes">
  ### Повторная проверка настройки после изменения домена
</div>

Операции с доменами — например, привязка нового внешнего домена или [покупка домена через Replit](/ru/build/domain-purchasing) — могут изменить URL обратных вызовов и источники JavaScript вашего приложения. В этом случае для каждого провайдера, настроенного с собственными учётными данными, может потребоваться зарегистрировать новые значения в его консоли разработчика.

После изменения домена вернитесь на вкладку **Configure**. Напоминания о настройке отображаются в виде значков предупреждения на вкладке, на боковой панели и рядом с провайдерами в списке **SSO providers**. Значок предупреждения и надпись **setup steps remaining** рядом с провайдером означают, что в его контрольном списке **Provider setup** появились новые пункты.

<Frame>
  <img src="/assets/mirror/clerk-sso-setup-reminders-a5b092846006.png" alt="Вкладка Configure и боковая панель с предупреждением о настройке, а также список SSO providers со значком предупреждения и надписью «setup steps remaining» рядом с провайдером после изменения домена" width="923" height="378" data-path="images/workspace/auth/clerk-sso-setup-reminders.png" />
</Frame>

Откройте панель редактирования провайдера, скопируйте обновлённые значения из раздела **Provider setup**, зарегистрируйте их в консоли разработчика провайдера и выберите **Mark all as done**.

<div id="domain-setup-for-email-verification">
  ## Настройка домена для подтверждения по электронной почте
</div>

Если ваш App поддерживает **регистрацию по электронной почте и паролю**, Clerk отправляет код подтверждения на почту каждого нового пользователя. Настройка домена для доставки писем гарантирует, что эти коды будут приходить с адреса вашего App, а не задерживаться или блокироваться спам-фильтрами.

<div id="when-you-need-this-setup">
  ### Когда эта настройка нужна
</div>

Настраивать DNS-записи нужно только в том случае, если ваш App подключает **внешний домен, управляемый другим провайдером** (например, домен, зарегистрированный в Cloudflare, GoDaddy, Namecheap или подобном сервисе).

Настройка не требуется, если ваш App доступен по одному из следующих адресов:

* поддомен `.replit.app`;
* домен, [приобретённый через Replit](/ru/build/domain-purchasing).

В обоих случаях Replit управляет DNS-записями за вас.

<div id="add-dns-records-for-email-sending">
  ### Добавьте DNS-записи для отправки писем
</div>

Чтобы приложение могло отправлять письма с кодами подтверждения с вашего внешнего домена, добавьте набор DNS-записей у своего провайдера домена.

1. В Project Editor откройте **Publishing**.
2. Выберите **Domains**.
3. Найдите привязанный внешний домен и нажмите **Manage**.
4. В разделе **Authentication DNS setup required** скопируйте CNAME-записи, которые показывает Replit, — именно они нужны Clerk для отправки писем с кодами подтверждения с вашего домена.
5. Войдите в панель своего DNS-провайдера (Cloudflare, GoDaddy, Namecheap и т. д.) и добавьте каждую запись в точности так, как она указана.

  <img src="/assets/mirror/clerk-domain-8797ea9f41fc.png" alt="Панель Manage домена с разделом Authentication DNS setup required и CNAME-записями для доставки писем через Clerk" width="1156" height="1524" data-path="images/workspace/auth/clerk-domain.png" />
</Frame>

Распространение изменений DNS может занять до 48 часов. Как только записи вступят в силу, при регистрации по электронной почте и паролю коды подтверждения будут автоматически отправляться с вашего домена — никаких дополнительных действий на панели Auth не потребуется.

<div id="troubleshooting">
  ### Устранение неполадок
</div>

* **Письма для подтверждения не приходят** — убедитесь, что каждая запись добавлена в точности так, как показано на панели Manage, включая завершающие точки, если их требует ваш DNS-провайдер. Проверьте папку «Спам» получателя.
* **Записи по-прежнему не обнаруживаются** — дайте время на распространение DNS (до 48 часов) и снова проверьте на панели Manage, какие записи всё ещё помечены как отсутствующие.

<div id="security-best-practices">
  ## Рекомендации по безопасности
</div>

* **Всегда проверяйте на стороне сервера** — проверяйте аутентификацию в маршрутах API, а не только в интерфейсе
* **Используйте переменные окружения** — никогда не указывайте ключи и секреты прямо в коде
* **Подключайте middleware прокси первым** — прокси Clerk должен подключаться до парсеров тела запроса в вашем приложении Express
* **Не перенаправляйте главную страницу на вход** — оставьте лендинг доступным для неаутентифицированных посетителей

<div id="faq">
  ## Часто задаваемые вопросы
</div>

<div id="do-i-need-a-clerk-account-to-use-clerk-auth">
  ### Нужна ли учётная запись Clerk для использования Clerk Auth?
</div>

Нет. Тенант Clerk, на котором работает Clerk Auth, Replit создаёт и обслуживает автоматически, когда Agent настраивает ваш app, — вам не нужно регистрироваться в Clerk или самостоятельно управлять какой-либо инфраструктурой Clerk.

<div id="can-i-access-the-clerk-dashboard-for-the-replit-managed-clerk-instance">
  ### Могу ли я получить доступ к панели управления Clerk для экземпляра Clerk, управляемого Replit?
</div>

Нет. Экземпляр Clerk, управляемый Replit, недоступен через панель управления Clerk. Управляйте им через инструмент **Auth** в Project Editor — именно там настраиваются провайдеры, просматриваются пользователи и выполняется переключение между средами Development и Production.

<div id="my-clerk-publishable-key-starts-with-pk_test-how-do-i-switch-to-a-live-key">
  ### Мой публикуемый ключ Clerk начинается с `pk_test`. Как переключиться на рабочий ключ?
</div>

Этого не требуется. Ключи `pk_test...` и `sk_test...`, которые вы видите на панели Secrets в workspace, относятся к среде **Development** Clerk для вашего приложения и используются во время разработки. При публикации приложения deployment автоматически запускается с ключами `pk_live...` и `sk_live...` для среды Production. Чтобы проверить это, откройте **Publishing → Overview → Adjust settings** в своём Workspace и посмотрите значение `CLERK_PUBLISHABLE_KEY` для опубликованного приложения — оно будет начинаться с `pk_live`. Не редактируйте эти ключи вручную. Подробности см. в разделе [Среды Development и Production](#development-and-production-environments).

<div id="why-cant-i-sign-in-to-my-published-app-with-the-account-i-created-during-development">
  ### Почему я не могу войти в опубликованное приложение под учётной записью, созданной во время разработки?
</div>

У сред **Development** и **Production** в Clerk Auth разные хранилища пользователей. Учётная запись, созданная в dev/preview-версии приложения, существует только в среде Development и при публикации не копируется в Production — в опубликованном приложении потребуется зарегистрироваться заново. То же самое относится к любым данным, привязанным к `userId` из Clerk. Откройте панель **Auth** в Workspace и с помощью переключателя сред на вкладке **Users** просмотрите пользователей в каждой из сред. Подробнее см. [Раздельные хранилища пользователей](#separate-user-stores).

<div id="is-clerk-auth-free-to-use">
  ### Clerk Auth бесплатен?
</div>

Пока да, Clerk Auth бесплатен. Позже может появиться оплата по объёму использования — как и у других подобных сервисов Replit. Все будущие списания будут проходить через ваш текущий биллинг Replit: отдельный счёт или способ оплаты для Clerk не понадобится.

<div id="does-clerk-auth-have-an-mau-limit-like-external-clerk-plans">
  ### Есть ли в Clerk Auth ограничение по MAU, как во внешних тарифах Clerk?
</div>

Нет. В Clerk Auth нет лимита на количество активных пользователей в месяц (MAU), в отличие от внешних тарифов Clerk, где число MAU ограничено в зависимости от уровня тарифа.

<div id="how-does-clerk-auth-compare-to-external-clerk">
  ### Чем Clerk Auth отличается от внешнего Clerk?
</div>

Управляемый Replit тенант Clerk, используемый в Clerk Auth, имеет ряд особенностей по сравнению с приложениями Clerk, которые вы создаёте в собственном аккаунте Clerk (**внешний Clerk**). В таблице ниже показаны текущие различия между ними. Она отражает текущее состояние Clerk Auth, а набор поддерживаемых функций будет и дальше расширяться.

|                                         | Clerk Auth                                                                            | Внешний Clerk                           |
| --------------------------------------- | ------------------------------------------------------------------------------------- | --------------------------------------- |
| **Настройка**                           | Автоматически предоставляется Replit                                                  | Настраивается самостоятельно            |
| **Владение тенантом Clerk**             | Управляется Replit, принадлежит вашему приложению                                     | Принадлежит вашему аккаунту Clerk       |
| **Модель оплаты**                       | Пока бесплатно (в будущем планируется оплата по мере использования)                   | Подписка + оплата по мере использования |
| **Оплата**                              | Через Replit (пока бесплатно)                                                         | Через ваш аккаунт Clerk                 |
| **Лимит MAU**                           | Неограничен                                                                           | Зависит от тарифа                       |
| **Настройка прокси и домена**           | Автоматически для replit.app и приобретённого домена, вручную для привязанного домена | Вручную                                 |
| **Провайдеры SSO**                      | Поддерживаются некоторые провайдеры: Google, Apple, GitHub, X                         | Поддерживается больше провайдеров       |
| **Интерфейс управления пользователями** | Инструмент Auth в Project Editor                                                      | Панель управления приложения Clerk      |
| **SMS**                                 | Не поддерживается                                                                     | Поддерживается                          |
| **MFA**                                 | Не поддерживается                                                                     | Поддерживается                          |
| **Тенанты организаций**                 | Не поддерживается                                                                     | Поддерживается                          |

<div id="what-common-clerk-auth-setup-do-i-need-to-handle-manually">
  ### Какие типовые настройки Clerk Auth приходится выполнять вручную?
</div>

Большая часть настройки Clerk Auth выполняется автоматически, но некоторые параметры требуют действий за пределами инструмента **Auth**:

* **Собственные учётные данные OAuth для SSO-провайдеров** — если вы хотите, чтобы на экране согласия провайдера отображались название и оформление вашего приложения (а не стандартные значения Replit), зарегистрируйте OAuth-приложение в консоли разработчика провайдера и вставьте полученные учётные данные в панель Auth. См. [Настройка учётных данных OAuth для SSO-провайдера](#configuring-oauth-credentials-for-an-sso-provider).
* **DNS-записи для подтверждения адресов электронной почты на внешних доменах** — если к вашему приложению привязан внешний домен, управляемый другим провайдером, потребуется добавить DNS-записи, чтобы письма с подтверждением отправлялись с вашего домена. См. [Настройка домена для подтверждения электронной почты](#domain-setup-for-email-verification).

<div id="can-i-bring-my-own-clerk-app-instead-of-using-the-replit-managed-one">
  ### Можно ли использовать собственное приложение Clerk вместо приложения, управляемого Replit?
</div>

Да. Если для вашего приложения уже создано приложение Clerk, управляемое Replit, сначала удалите его, а затем подключите собственное внешнее приложение Clerk:

1. Откройте панель **Auth** в Project Editor.
2. Перейдите на вкладку **Configure**.
3. Прокрутите страницу до конца и нажмите **Delete Clerk app**.

При удалении приложения Clerk удаляются управляемый Replit тенант Clerk и все привязанные к нему домены, которые затем можно использовать с собственным приложением Clerk. Если для вашего приложения ещё не создано приложение Clerk, управляемое Replit, пропустите этот шаг и сразу интегрируйте внешнее приложение Clerk.
