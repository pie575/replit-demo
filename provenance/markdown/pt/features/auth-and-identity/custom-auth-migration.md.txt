# Planeje uma migração de autenticação personalizada

> Planeje uma migração segura de um sistema de autenticação personalizado para o Clerk Auth preservando os dados de usuário e as regras de acesso do seu app.

Use esta página quando seu app tiver seu próprio sistema de autenticação, base de usuários ou lógica de sessão. Migrar para o [Clerk Auth](/pt/features/auth-and-identity/clerk-auth) é uma migração de dados e identidade, não apenas uma mudança de código. Sem um plano, usuários que retornam podem parecer ter perdido o acesso aos seus dados existentes.

<Note>
  **Usando o Replit Auth?** O fluxo de migração automatizado é apenas para apps elegíveis do Replit Auth. Siga [Migre do Replit Auth para o Clerk](/pt/features/auth-and-identity/migrate-auth-to-clerk) em vez disso.

  O Replit não migra automaticamente um sistema de autenticação personalizado. Esta página oferece orientação de planejamento e validação, não um procedimento de importação automatizado.
</Note>

## Planeje a continuidade de identidade

* Identifique o valor estável que conecta uma pessoa aos dados do seu app hoje. Pode ser um ID de usuário, endereço de e-mail, nome de usuário ou um registro de conta separado.
* Faça um inventário de cada tabela e serviço que depende desse valor, incluindo propriedade, permissões, assinaturas, preferências e registros de auditoria.
* Decida como o novo sistema de identidade vai resolver cada registro local existente antes de alterar o comportamento de login.
* Defina como os usuários totalmente novos serão atribuídos e vinculados a registros locais após a migração.

<Warning>
  Não presuma que o ID de usuário de um provedor, um endereço de e-mail ou uma nova conta criada no primeiro login vão corresponder aos seus registros existentes. Verifique o mapeamento com contas representativas antes da migração.
</Warning>

## Credenciais de conta e sessões

* Faça um inventário separado dos seus hashes de senha, identidades OAuth, fatores de MFA, estado de verificação e sessões ativas. Eles podem ter requisitos diferentes de portabilidade e segurança.
* Valide qualquer migração de senha em relação à documentação atual do provedor escolhido antes de processar contas reais. Se uma credencial não puder ser migrada com segurança, planeje um fluxo de redefinição de senha ou de vinculação de conta.
* Não presuma que identidades OAuth ou sessões ativas são transferidas automaticamente. Planeje como os usuários existentes vão fazer login novamente e como você vai evitar contas duplicadas.
* Mantenha a autorização e os dados específicos do app no seu modelo de dados local, a menos que você tenha planejado explicitamente uma substituição. Autenticação e autorização geralmente exigem trabalhos de migração separados.

## Teste antes da migração

* Teste em um ambiente que não seja de produção, com contas e dados representativos e não sensíveis.
* Faça login como uma conta existente e abra páginas que leem dados específicos do usuário, como um painel, perfil ou itens salvos.
* Verifique as regras de autorização, a recuperação de conta, o logout e um fluxo de nova conta.
* Monitore registros duplicados e falhas de acesso durante a migração. Mantenha um plano de reversão até que sua validação esteja completa.

## Obtenha ajuda

* Se você precisar migrar um sistema de autenticação personalizado para o Clerk Auth gerenciado pelo Replit, [entre em contato com o Suporte do Replit](https://replit.com/support) antes de alterar dados de conta em produção.
* Se você gerencia a autenticação com outro provedor, use a documentação de migração atual desse provedor e valide seu mapeamento de identidade antes da migração.
