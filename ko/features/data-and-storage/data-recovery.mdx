실수는 누구에게나 일어납니다. 잘못된 schema 변경, 실수로 삭제한 행, 의도와 다르게 흘러간 Agent session 등이 그렇습니다. Replit은 database별로 복구 방법을 제공합니다.

| Database    | 복구 방법                                     | 제공 범위                                              |
| ----------- | ----------------------------------------- | -------------------------------------------------- |
| Development | Checkpoint rollback                       | 모든 요금제                                            |
| Production  | Point-in-time restore 및 예약 백업 | Core: 최대 7일치 기록. Pro 및 Enterprise: 최대 28일(기본값 7일). |

<div id="restore-your-development-database">
  ## 개발 데이터베이스 복원하기
</div>

[rollback 기능](/ko/features/version-control/checkpoints-and-rollbacks/)을 사용하면 앱과 개발 데이터베이스를 이전 상태로 되돌릴 수 있습니다. Agent가 생성한 어떤 checkpoint 시점으로든 데이터베이스를 복원할 수 있습니다.

  꼭 선택하세요. 이렇게 하면 데이터베이스가 해당 checkpoint 당시의 상태로 복원됩니다.
</Info>

<div id="restore-your-production-database">
  ## 프로덕션 데이터베이스 복원하기
</div>

프로덕션 데이터베이스는 point-in-time restore를 사용해 원하는 시점으로 복원할 수 있습니다.

<Frame>
  <img src="/assets/mirror/database-rollbacks-f13dd20874ae.jpg" alt="rollback 옵션을 보여주는 데이터베이스 rollback 인터페이스" width="1082" height="708" data-path="images/databases/database-rollbacks.jpg" />
</Frame>

복원 가능한 시점의 범위는 요금제과 보존 기간 설정에 따라 달라집니다. Core는 최대 7일, Pro와 Enterprise는 최대 28일까지 기록을 보관합니다. 모든 요금제은 기본 7일로 시작하며, 프로덕션 데이터베이스 설정에서 이 기간을 변경할 수 있습니다. 기간이 길수록 저장 공간을 더 많이 사용하므로 보존 기간을 늘리면 usage 비용도 늘어납니다. Pro에서 Core로 downgrade하면 보존 기간은 7일로 줄어듭니다.

<Warning>
  데이터베이스를 복원해도 앱의 코드는 복원되지 않으며, 앱을 roll back해도
  데이터베이스는 복원되지 않습니다. 둘 다 같은 시점으로 되돌리려면
  데이터베이스를 복원한 다음, [해당 시점의 checkpoint로
  roll back](/ko/features/version-control/checkpoints-and-rollbacks/)하고 앱을 다시
  Publish하세요.
</Warning>

<div id="schedule-production-database-backups">
  ## 프로덕션 데이터베이스 백업 예약
</div>

예약 백업은 매일 하나의 전체 복원 지점을 생성합니다. Replit은 예약을 활성화하거나 업데이트할 때 브라우저의 현재 시간대를 기준으로 자정 무렵에 백업을 예약합니다.

1. **Database** 도구를 열고 프로덕션 데이터베이스를 선택합니다.
2. **Settings**를 열고 **Advanced** 아래의 **예약 백업**를 펼칩니다.
3. 예약 백업을 활성화하려면 **Keep backups for**에서 보존 기간을 선택합니다.

선택할 수 있는 보존 기간은 요금제에 따라 다릅니다. Core는 최대 7일, Pro와 Enterprise는 최대 28일까지 지원합니다.

<div id="storage-costs">
  ### 스토리지 비용
</div>

Replit은 프로덕션 데이터베이스의 스토리지 범주별로 사용량을 각각 측정합니다.

| 스토리지 범주                          | GiB당 월 요금 |
| -------------------------------- | --------: |
| 논리적 데이터베이스 스토리지                  |     $0.35 |
| Point-in-time restore(PITR) 스토리지 |     $0.20 |
| 예약 백업 스토리지                       |     $0.09 |

<Note>데이터베이스 스토리지 비용은 현재 100% 할인이 적용됩니다.</Note>

$0.35의 논리적 스토리지 요금은 PITR, 예약 백업 또는 둘 다를 사용하는 경우 모두 동일하게 적용됩니다. 예약 백업 스토리지는 GiB당 비용이 PITR 스토리지보다 저렴합니다. 하루 단위 복원 지점만으로 충분하다면, PITR 기간을 짧게 설정하고 예약 백업를 활용해 복구 스토리지 비용을 줄일 수 있습니다. 총 백업 비용은 저장된 백업 volume과 보존 기간에 따라 달라집니다.

PITR은 설정된 기간 내에서 더 많은 복원 지점을 제공하고, 예약 백업는 하루에 하나의 복원 지점을 제공합니다. 필요에 맞는 복구 방법을 선택하세요.

<Note>
  schedule은 현재 UTC 오프셋을 기준으로 합니다. 서머타임이 변경되면
  schedule을 업데이트하기 전까지 백업 시각이 한 시간 밀릴 수 있습니다. 오프셋이
  시간 단위로 딱 떨어지지 않는 시간대는 가장 가까운 시각을 사용합니다.
</Note>

<div id="restore-a-scheduled-backup">
  ### 예약 백업 복원
</div>

1. 프로덕션 데이터베이스 설정에서 **예약 백업**를 엽니다.
2. **View all backups**를 선택합니다.
3. 원하는 복원 지점에서 **Restore**를 선택합니다.
4. `restore`를 입력한 다음 **Continue**를 선택합니다.

복원을 실행하면 database가 선택한 백업 데이터로 전환됩니다. 현재 데이터가 삭제되지는 않지만, 연결된 서비스가 잠시 재연결될 수 있습니다.

<div id="troubleshooting-publishing-failures">
  ## Publishing 실패 문제 해결
</div>

database 문제로 Publishing이 실패하는 경우:

1. **Publishing logs 확인** — database 연결 또는 schema 충돌에 대한 구체적인 오류 메시지를 확인하세요
2. **최근 schema changes 검토** — 기존 애플리케이션 코드와 충돌할 가능성이 있는지 검토하세요
3. **deployment Preview에서 changes 테스트** — Republish하기 전에 먼저 테스트하세요
