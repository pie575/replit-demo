---
title: "Jetons d'accès externe"
description: "Permettez aux pipelines CI, aux webhooks et à d'autres services automatisés d'accéder à votre Replit App privée sans avoir à se connecter."
---

Les jetons d&#39;accès externe sont des bearer jetons que vous créez pour une Replit App spécifique.
Ils permettent aux services automatisés — pipelines CI, webhooks, vérificateurs d&#39;uptime, bots Slack,
scripts internes — d&#39;accéder à l&#39;app même lorsque son URL est protégée par
[une URL de Dev privée](/fr/pt/features/publishing/private-deployments)
ou par un [Private Deployment](/fr/pt/features/publishing/private-deployments).

Traitez chaque jeton comme un mot de passe : toute personne qui le détient peut accéder à votre app tant qu&#39;il n&#39;a pas expiré ou n&#39;a pas été révoqué.

<Note>
  Les jetons d&#39;accès externe sont disponibles dès lors que vous sélectionnez
  l&#39;accès privé pour un deployment. Aucune activation au niveau du workspace
  n&#39;est nécessaire. Dans un workspace Enterprise, seuls les administrateurs du
  workspace peuvent gérer les jetons.
</Note>

<div id="quando-usar-um-token">
  ## Quand utiliser un jeton
</div>

Utilisez un jeton d&#39;accès externe lorsqu&#39;un élément *extérieur* à votre navigateur doit appeler votre Replit App privée. Cas courants :

* Un workflow GitHub Actions qui exécute un test de fumée sur votre URL de développement à chaque commit.
* Un moniteur d&#39;uptime (Better Stack, Pingdom, UptimeRobot) qui interroge un endpoint de santé sur votre app publiée.
* Un récepteur de webhook — Stripe, Slack, GitHub — qui envoie un POST vers un Private Deployment.
* Un appel `curl` ou `fetch` depuis la machine d&#39;un coéquipier pendant le débogage.

Les jetons d&#39;accès externe sont conçus pour le **trafic d&#39;API**, et non pour ouvrir des pages d&#39;interface dans le navigateur. Les applications monopages (Vite, Next.js, etc.) chargent des bundles JavaScript via des requêtes ultérieures qui ne transporteront pas votre jeton : ces requêtes échoueront donc. Pour une navigation interactive, connectez-vous normalement.

<div id="ambientes-de-tokens">
  ## Environnements de jetons
</div>

Chaque jeton est lié à un environnement :

| Environnement | Où il fonctionne                                                             | Utilisation                                                         |
| :------------ | :--------------------------------------------------------------------------- | :------------------------------------------------------------------ |
| `Development` | L&#39;URL de dev du workspace de l&#39;app (`*.replit.dev`)                  | Accéder à un Repl en cours d&#39;exécution pendant le développement |
| `Production`  | Le deployment publié de l&#39;app (`*.replit.app` et domaines personnalisés) | Accéder à un Private Deployment depuis des services externes        |

Un jeton `Production` reste valide après une republication, y compris lors de la publication
d&#39;une nouvelle version. Replit le révoque lorsque vous :

* Dépubliez le deployment.
* Supprimez le deployment.
* Faites passer l&#39;accès de l&#39;app de privé à public.

Un jeton cesse également de fonctionner lorsqu&#39;il expire ou lorsque vous le révoquez.

<div id="criar-um-token-de-acesso-externo">
  ## Créer un jeton d&#39;accès externe
</div>

<Steps>
  <Step>
    Ouvrez l&#39;app que vous souhaitez exposer, puis ouvrez l&#39;outil **Publishing**.
  </Step>

  <Step>
    Sélectionnez **Adjust settings** pour afficher les options de republication.
  </Step>

  <Step>
    Dans la section **Security**, repérez **External access tokens**.
  </Step>

  <Step>
    Sélectionnez **Create access token**, puis renseignez :

    * **Label** (facultatif) : un nom court permettant d&#39;identifier le jeton par la suite,
      comme `CI` ou `Stripe webhook`. 120 caractères maximum.
    * **Environment** : choisissez `Development` ou `Production` selon l&#39;environnement depuis lequel le
      service appelant doit accéder à l&#39;app.
    * **Expires after** : choisissez une durée de validité — `1 hour`, `24 hours`, `7 days`,
      `30 days`, `3 months`, `1 year` ou `5 years`. Retenez la durée la plus courte
      qui réponde à votre besoin. Il n&#39;existe pas d&#39;option « n&#39;expire jamais ».
  </Step>

  <Step>
    Sélectionnez **Create**.
  </Step>
</Steps>

Replit n&#39;affiche le jeton **qu&#39;une seule fois**. Copiez-le immédiatement : une fois la boîte de dialogue fermée, il est impossible de le consulter à nouveau. Si vous le perdez, révoquez-le et créez-en un nouveau.

L&#39;écran d&#39;affichage propose deux actions de copie :

* **Copy query parameter** — copie `?project-protection-bypass=<token>` afin de
  l&#39;ajouter à une URL. Pratique pour des vérifications rapides avec `curl`.
* **Copy token only** — copie le jeton brut, à envoyer dans un
  en-tête `Authorization: Bearer`.

<Info>
  La création du premier jeton active automatiquement l&#39;accès externe pour l&#39;app, si ce
  n&#39;est pas déjà fait. Sans protection, le jeton n&#39;aurait rien à contourner.
</Info>

<div id="usar-um-token">
  ## Utiliser un jeton
</div>

Présentez le jeton de l&#39;une des deux façons suivantes :

<div id="cabealho-authorization-recomendado">
  ### En-tête Authorization (recommandé)
</div>

```bash theme={null}
curl -H "Authorization: Bearer <token>" https://your-app.replit.app/health
```

C&#39;est le bon choix dans presque tous les cas : webhooks, scripts de CI,
appels de backend à backend. Le jeton n&#39;apparaît jamais dans les journaux qui enregistrent les URL
et ne se retrouve jamais dans l&#39;historique du navigateur.

<div id="parmetro-de-consulta">
  ### Paramètre de requête
</div>

```bash theme={null}
curl "https://your-app.replit.app/health?project-protection-bypass=<token>"
```

N&#39;utilisez la forme en paramètre de requête que lorsqu&#39;il est impossible de définir des en-têtes — par exemple, dans un
service qui n&#39;accepte qu&#39;une URL. Les URL contenant des jetons se retrouvent souvent dans les journaux de proxy,
l&#39;historique du Shell et les captures d&#39;écran : privilégiez donc l&#39;en-tête dès que possible.

<div id="gerenciar-tokens-existentes">
  ## Gérer les jetons existants
</div>

La section **External access tokens** répertorie tous les jetons que vous avez créés pour
l&#39;app — du plus récent au plus ancien — avec leur libellé, leur environnement, leur date de création,
leur validité et leur statut de révocation. Les derniers caractères de chaque jeton sont affichés
sur chaque ligne pour vous aider à les distinguer, car la valeur complète n&#39;apparaît
qu&#39;au moment de la création.

Vous ne voyez que les jetons que *vous* avez créés. Ceux des autres collaborateurs leur restent privés,
même si vous êtes le propriétaire de l&#39;app.

<div id="revogar-um-token">
  ## Révoquer un jeton
</div>

Révoquez un jeton dès qu&#39;il n&#39;est plus nécessaire, ou dès que vous soupçonnez
qu&#39;il a pu être exposé. Pour le révoquer :

<Steps>
  <Step>
    Ouvrez la section **External access tokens** dans les paramètres de publication de l&#39;app.
  </Step>

  <Step>
    Repérez le jeton dans la liste et sélectionnez l&#39;icône de corbeille.
  </Step>

  <Step>
    Confirmez la révocation.
  </Step>
</Steps>

La révocation est **immédiate et irréversible**. Tout trafic utilisant encore ce
jeton est rejeté en quelques secondes. Si vous avez de nouveau besoin d&#39;un accès, créez un
nouveau jeton.

Vous ne pouvez révoquer que les jetons que vous avez créés. Retirer un collaborateur du
workspace révoque automatiquement les jetons qu&#39;il a créés pour cette app.

<div id="mantenha-seus-tokens-seguros">
  ## Protégez vos jetons
</div>

Les jetons d&#39;accès externes sont des identifiants. Traitez-les avec le même soin
qu&#39;une clé d&#39;API ou un mot de passe.

<div id="o-que-fazer">
  ### Ce qu&#39;il faut faire
</div>

* **Stockez les jetons dans un gestionnaire de secrets** — les secrets GitHub Actions, le coffre-fort de votre
  fournisseur de CI, le stockage de secrets de votre fournisseur cloud ou un gestionnaire de mots de passe.
  Ne les committez jamais dans un dépôt.
* **Utilisez des durées de vie courtes** dans la mesure du possible. Un jeton de 7 jours pour une
  intégration ponctuelle est plus sûr qu&#39;un jeton de 5 ans qui traîne.
* **Libellez chaque jeton** afin de savoir à quoi il sert et s&#39;il est encore utilisé. Les jetons sans libellé sont les premiers à fuiter et les derniers à être révoqués.
* **Créez un jeton distinct par consommateur.** Un jeton par job de CI, un par
  source de webhook, un par contrôle d&#39;uptime. En cas de compromission — ou
  lorsqu&#39;un fournisseur n&#39;est plus nécessaire — vous ne révoquez que celui-là.
* **Privilégiez l&#39;en-tête `Authorization`** plutôt que les paramètres de requête, afin d&#39;éviter que le jeton
  ne fuite via les journaux d&#39;URL, l&#39;historique du navigateur ou les en-têtes de référence.
* **Révoquez immédiatement** tout jeton susceptible d&#39;avoir été exposé — un journal divulgué,
  un commit dans un dépôt public, un enregistrement d&#39;écran, l&#39;ordinateur portable d&#39;un ancien employé.
  La révocation prend effet immédiatement ; créez un jeton de remplacement ensuite.

<div id="o-que-no-fazer">
  ### À ne pas faire
</div>

* **Ne partagez pas un jeton entre coéquipiers ou entre services.** Si deux systèmes partagent
  un même jeton, vous ne pouvez pas en révoquer un sans casser l&#39;autre.
* **Ne collez pas de jetons dans un chat, un e-mail, une capture d&#39;écran ou un outil de suivi de tickets.**
  Ces canaux sont archivés, indexés et partagés de manières imprévisibles.
* **N&#39;intégrez pas de jetons dans du code côté client** — applications web, applications mobiles,
  binaires de bureau. Tout ce qui est livré sur l&#39;appareil d&#39;un utilisateur doit être considéré comme public.
* **Ne comptez pas sur les jetons pour les sessions de navigateur.** Les jetons servent aux appels d&#39;API,
  pas au chargement d&#39;une SPA dans un onglet de navigateur. Utilisez pour cela une connexion Replit classique.
* **N&#39;optez pas par défaut pour une validité de 5 ans.** Adaptez la durée de vie à la période
  pendant laquelle le consommateur a réellement besoin d&#39;un accès.

<div id="soluo-de-problemas">
  ## Dépannage
</div>

<Accordion title="Mon jeton de production a soudainement cessé de fonctionner">
  Les jetons de production restent valides lors des republications normales. Vérifiez
  si le jeton a expiré ou si vous l&#39;avez révoqué. Vérifiez également si vous avez annulé la
  publication, supprimé le deployment ou fait passer l&#39;app de privée à publique.
  Si l&#39;app n&#39;a plus de deployment privé, republiez-la en mode privé, puis créez
  un nouveau jeton. Un jeton expiré ou révoqué ne peut pas être restauré.
</Accordion>

<Accordion title="Mon jeton fonctionne avec `curl`, mais le navigateur affiche toujours la page de connexion">
  Les jetons d&#39;accès externe sont conçus pour le trafic d&#39;API, pas pour les sessions de navigateur. Lorsqu&#39;une application monopage se charge dans le navigateur, la requête HTML initiale peut transmettre le jeton via un paramètre de requête, mais les requêtes suivantes vers les bundles JavaScript, les fichiers CSS et les appels d&#39;API ne l&#39;incluront pas et seront rejetées. Pour naviguer dans l&#39;app de façon interactive, connectez-vous à Replit normalement.
</Accordion>

<Accordion title="J'ai perdu le jeton — puis-je le consulter à nouveau ?">
  Non. Replit n&#39;affiche le jeton qu&#39;une seule fois, au moment de sa création. La vue en liste affiche
  les métadonnées (libellé, environnement, validité, derniers caractères), mais jamais la valeur complète du jeton. Si vous l&#39;avez perdu, révoquez ce jeton et créez-en un nouveau.
</Accordion>
