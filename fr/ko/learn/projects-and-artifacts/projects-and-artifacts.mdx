**Un projet** est le conteneur de tout ce que vous créez dans Replit. Les **artefacts** sont les résultats publiables qu’il contient — applications web, applications mobiles, présentations, animations, visualisations de données, jeux 3D et designs.

Lorsque vous créez plusieurs éléments, vous avez deux options : ajouter plusieurs artefacts à un même projet ou créer des projets distincts. Le bon choix dépend du fait que vos applications partagent ou non des données, de la logique et des cycles de déploiement. Cette page explique ces deux termes en détail et indique quand conserver les artefacts dans un seul projet et quand créer des projets distincts.

<div id="section">
  ## Qu’est-ce qu’un projet ?
</div>

Un projet est un conteneur qui regroupe votre code, vos données et tous les artefacts que vous créez. Dites à Agent ce que vous souhaitez, et il configurera un projet et y générera des artefacts.

Considérez un projet comme un espace de travail sur un bureau. Tout se trouve au même endroit et peut partager les mêmes informations, mais chaque élément a un objectif différent.

Par exemple, si vous demandez à Agent de créer une application de suivi de la condition physique, il créera un projet incluant le backend, la base de données et le stockage nécessaires, ainsi qu’un artefact d’application mobile.

Concepts clés :

* **Projet** : un conteneur pour votre code, vos données et tous vos artefacts.
* **Artefact** : un résultat publiable dans un projet (application web, présentation, vidéo, etc.).
* **Ressources** : tous les artefacts peuvent accéder automatiquement au backend, à la base de données et au stockage de fichiers sans configuration distincte.

Pour en savoir plus sur tout ce que vous pouvez faire avec les projets — gestion, filtrage, épinglage et tri — consultez [Projects](/fr/ko/features/projects-and-artifacts/projects).

<div id="section-2">
  ## Que sont les artefacts ?
</div>

Les artefacts sont les éléments que vous pouvez publier sur Replit. Chacun constitue un résultat complet et autonome, avec sa propre URL partageable une fois publié.

Le reste de votre projet — fichiers, images, CSV, code — sert à créer les artefacts, mais ne peut pas être publié seul.

<div id="section-3">
  ## Ce que partagent les artefacts d’un projet
</div>

Lorsque des [artefacts](/fr/ko/features/projects-and-artifacts/artifacts) se trouvent dans le même [projet](/fr/ko/features/projects-and-artifacts/projects), ils partagent automatiquement les éléments suivants :

* **Base de données** : si un artefact écrit des données, les autres peuvent les lire immédiatement.
* **Backend et API** : logique serveur partagée, sans duplication de code.
* **Stockage de fichiers** : images, documents et fichiers importés accessibles depuis tous les artefacts.
* **Déploiement** : lorsque vous publiez, tout est synchronisé et mis à jour en temps réel.

Vous n’avez donc pas besoin de configurer des connexions ni de dupliquer du code entre les artefacts. Cependant, vous ne pouvez pas publier un seul artefact sans publier les autres.

<div id="section-4">
  ## Guide rapide
</div>

Voici les principaux scénarios à prendre en compte pour décider s’il faut ajouter un artefact à un projet existant ou créer un projet distinct.

| **Utiliser plusieurs artefacts dans un même projet**                                                        | **Utiliser des projets distincts**                                                      |
| ----------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------- |
| Les applications partagent les mêmes données et le même backend                                             | Les applications ne partagent ni logique métier ni données                              |
| Vous souhaitez tout publier ensemble                                                                        | Vous avez besoin de cycles de publication indépendants                                  |
| Les applications sont complémentaires (comme une application client et un tableau de bord d’administration) | Il s’agit de produits sans lien entre eux ou destinés à des clients différents          |
| Vous souhaitez que les modifications apportées à un artefact se répercutent automatiquement sur les autres  | Projets à court terme, comme une page de destination de campagne ou un site d’événement |

<div id="section-5">
  ## Exemples
</div>

<div id="section-6">
  ### Même projet : application web et application mobile pour un même produit
</div>

Un restaurant crée une application web permettant aux clients de consulter le menu et une application mobile permettant au personnel de gérer les commandes. Les deux applications sont connectées à la même base de données contenant les éléments du menu, les commandes et les informations clients.

**Pourquoi il s’agit d’un même projet :** les applications partagent les mêmes données et le même backend. Lorsqu’un client passe une commande via l’application web, le personnel la voit immédiatement dans l’application mobile.

<div id="section-7">
  ### Un même projet : application + tableau de bord d’administration + présentation destinée aux investisseurs
</div>

Une startup développe son produit principal, un panneau d’administration interne pour gérer le contenu et une présentation destinée à lever des fonds au sein d’un même projet.

**Pourquoi un seul projet :** le tableau de bord d’administration gère les mêmes données que l’application affiche, et la présentation peut s’appuyer sur des indicateurs en temps réel provenant du backend partagé.

<div id="section-8">
  ### Projets distincts : deux applications clientes indépendantes
</div>

Un freelance développe une boutique e-commerce pour un client et un système de réservation pour un autre.

**Pourquoi des projets distincts :** les applications ne partagent ni données ni logique. Chaque client a besoin d’une publication indépendante et souhaite qu’aucune modification n’affecte l’autre.

<div id="section-9">
  ### Projet distinct : page de destination de campagne associée au produit principal
</div>

Vous avez une application de production active toute l’année et des pages de destination temporaires pour vos campagnes marketing.

**Pourquoi un projet distinct :** les pages de campagne ont leur propre cycle de vie — elles sont lancées, restent en ligne quelques semaines, puis sont retirées. Les gérer séparément évite de complexifier le produit principal et vous permet de les publier ou de les supprimer indépendamment.

<div id="section-10">
  ## Questions fréquentes
</div>

<Accordion title="Puis-je déplacer un artefact vers un autre projet ?">
  Ce n’est pas possible pour le moment. Si vous devez séparer un artefact, créez un nouveau [projet](/fr/ko/features/projects-and-artifacts/projects) et demandez à Agent de le recréer.
</Accordion>

<Accordion title="Le nombre d’artefacts dans un projet est-il limité ?">
  Un projet peut contenir jusqu’à 7 artefacts, avec une limite de **1 application mobile par projet**. Cette limite s’explique par le fait que des artefacts supplémentaires peuvent consommer davantage de mémoire et ralentir l’aperçu. Si vous avez besoin de plus d’artefacts, créez un autre [projet](/fr/ko/features/projects-and-artifacts/projects).
</Accordion>

<Accordion title="Puis-je publier un seul artefact d’un projet ?">
  Ce n’est pas possible pour le moment. Lorsque vous publiez, tout est mis en ligne en même temps. Si vous avez besoin de publications indépendantes, utilisez des projets distincts.
</Accordion>

<Accordion title="Les artefacts partagent-ils des données entre eux ?">
  Oui. Tous les artefacts d’un projet partagent la même base de données et les mêmes services backend. Si une application web écrit des données, l’application mobile et le tableau de bord de données peuvent les lire immédiatement.
</Accordion>

<Accordion title="Quelle est la différence entre un artefact et un fichier ?">
  Les artefacts sont des éléments que vous pouvez publier — applications, diapositives, vidéos, etc. Les fichiers (CSV, images, code, etc.) sont des ressources du projet qui servent aux artefacts, mais ne peuvent pas être publiés seuls.
</Accordion>
