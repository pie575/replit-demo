Clerk Auth는 [Clerk](https://clerk.com)를 기반으로 앱 전용 인증 시스템을 제공합니다. Replit의 로그인 시스템을 사용해 Replit 계정을 생성하는 [Replit Auth](/ko/features/auth-and-identity/authentication)와 달리, Clerk Auth는 앱마다 **별도의 Clerk 테넌트**를 프로비저닝합니다. 앱 사용자는 Replit 계정이 아니라 앱 내에서 직접 계정을 만들며, 브랜딩과 로그인 방식, 로그인 경험 전반을 완전히 제어할 수 있습니다.

<Note>
  **Clerk Auth와 Replit Auth 비교** — **Clerk Auth**(이 페이지)를 사용하면 앱이 자체 인증 테넌트를 갖게 되어, 브랜딩을 완전히 사용자 지정할 수 있고 Replit과 독립적인 사용자 계정을 운영할 수 있습니다. **[Replit Auth](/ko/features/auth-and-identity/authentication)**를 사용하면 사용자가 Replit 계정으로 로그인하며 Replit 브랜딩이 적용된 로그인 페이지를 보게 됩니다. 로그인 경험에 자체 브랜드를 적용하고 싶거나 Replit과 분리된 사용자 계정이 필요하다면 Clerk Auth를 선택하세요.
</Note>

<div id="clerk-auth-vs-replit-auth-at-a-glance">
  ## Clerk Auth와 Replit Auth 한눈에 비교
</div>

|               | Clerk Auth                          | Replit Auth                  |
| ------------- | ----------------------------------- | ---------------------------- |
| **사용자 계정**    | 사용자가 앱 내에서 계정을 생성합니다(Replit 계정 불필요) | 사용자가 Replit 계정으로 로그인합니다      |
| **브랜딩**       | 앱 이름, 아이콘, 색상까지 완전히 맞춤 설정 가능        | Replit 브랜드가 적용된 로그인 페이지      |
| **SSO 자격 증명** | provider별로 직접 준비한 OAuth 자격 증명 사용    | Replit의 공용 OAuth 앱 사용        |
| **환경**        | Development와 Production 환경 분리       | 단일 환경                        |
| **추천**        | Replit 추천 연동 없음                     | 가입이 Replit Referrals 실적에 반영됨 |
| **적합한 경우**    | 맞춤 브랜딩이 필요한 앱, 전문/상업용 제품            | 빠른 설정, Replit 브랜딩이 무방한 앱     |

<div id="getting-started">
  ## 시작하기
</div>

앱에 Clerk Auth를 추가하려면 Agent 프롬프트에 다음과 같이 포함하세요:

```
[내 앱 아이디어]를 하는 앱을 만들어 줘. Clerk Auth를 포함해야 해.
```

Agent가 Clerk 테넌트 생성, 자격 증명 저장, 라우트 구성, middleware 추가까지 모든 작업을 알아서 처리합니다. Clerk 계정이나 별도의 수동 설정은 필요하지 않습니다.

<div id="how-clerk-auth-works-with-replit">
  ## Clerk Auth가 Replit에서 작동하는 방식
</div>

Agent가 앱에 Clerk Auth를 설정하면 다음 작업이 이루어집니다.

1. **전용 Clerk 테넌트 생성** — 앱마다 Development 환경과 Production 환경이 분리된 전용 Clerk 애플리케이션이 만들어집니다
2. **자격 증명 프로비저닝** — API key와 secret이 환경 변수로 저장됩니다
3. **프록시 구성** — 게시된 도메인에서 인증이 매끄럽게 작동합니다
4. **로그인 및 회원가입 경로 설정** — 미리 만들어진 Clerk React 컴포넌트가 앱에 추가됩니다
5. **서버 측 middleware 추가** — Clerk의 Express middleware로 API 경로가 보호됩니다

<Note>
  Clerk 계정을 만들거나 인프라를 직접 관리할 필요가 없습니다. 모든 것을 Replit이 자동으로 관리해 줍니다.
</Note>

<div id="capabilities">
  ## 기능
</div>

<div id="whats-supported">
  ### 지원되는 기능
</div>

Clerk Auth는 앱에 다음과 같은 기능을 제공합니다.

* **독립적인 사용자 계정** — 앱의 사용자는 Replit 사용자가 아니며, 앱의 Clerk 테넌트 안에서만 존재합니다
* **브랜드가 완전히 적용된 로그인 페이지** — 로그인 및 가입 페이지에 표시되는 앱 이름, logo, 색상, 글꼴, 문구를 앱 코드에서 설정합니다
* **맞춤 브랜딩 SSO** — provider별로 직접 발급한 OAuth 자격 증명을 등록하면, provider의 OAuth 동의 화면에 일반적인 기본값 대신 앱 이름과 브랜딩이 표시됩니다
* **이메일 및 비밀번호 authentication** — email verification을 포함한 기본 제공 가입 및 로그인
* **소셜 로그인(SSO)** — 사용자가 Google, GitHub, Apple, X(Twitter) 계정으로 로그인할 수 있습니다
* **사용자 관리** — Auth pane에서 사용자를 확인, 검색, 관리합니다
* **session 처리** — 안전한 session token을 자동으로 관리합니다
* **Development 및 Production 환경** — 실제 서비스에 배포하기 전 development에서 authentication을 테스트합니다

<Note>
  대부분의 Clerk Auth 설정은 Project Editor의 **Auth** 도구에서 관리할 수 있습니다. Clerk 계정도, Clerk dashboard에 접속할 필요도 없습니다.
</Note>

<div id="whats-not-supported">
  ### 지원되지 않는 기능
</div>

다음 기능은 현재 Clerk Auth에서 사용할 수 없습니다(직접 설정한 외부 Clerk 앱과 비교했을 때). 자세한 비교는 [이 FAQ](#how-does-clerk-auth-compare-to-external-clerk)를 참고하세요.

* **전화번호 로그인** — SMS 기반 로그인 및 인증
* **MFA 지원** — 최종 사용자를 위한 다중 요소 인증
* **모든 SSO provider 지원** — 현재는 Google, GitHub, Apple, X만 지원
* **Organization tenant** — Clerk의 Organization 및 팀 membership 기능

<div id="development-and-production-environments">
  ## Development 및 Production 환경
</div>

Clerk Auth를 사용하는 모든 앱에는 완전히 분리된 두 개의 Clerk 환경이 제공됩니다. 앱을 만드는 동안 dev/preview 앱을 구동하는 **Development** 환경과, 게시된 앱을 구동하는 **Production** 환경입니다. 두 환경은 설계상 서로 격리되어 있어 API key와 사용자 저장소가 각각 별도로 존재합니다.

<div id="separate-api-keys">
  ### 환경별로 분리된 API keys
</div>

각 환경에는 자체 publishable key와 secret API key가 있습니다. 앱에 노출되는 키는 앱이 development에서 실행되는지 production에서 실행되는지에 따라 자동으로 전환됩니다.

* workspace에서는 `CLERK_PUBLISHABLE_KEY`와 `CLERK_SECRET_KEY` secret에 Development 환경을 가리키는 **테스트 키**(`pk_test...` 및 `sk_test...`)가 들어 있습니다.

<Frame>
  <img src="/assets/mirror/clerk-check-dev-keys-5a23f6b7dd0c.png" alt="Workspace의 Secrets 도구에 sk_test_ 및 pk_test_ 접두사가 붙은 CLERK_SECRET_KEY와 CLERK_PUBLISHABLE_KEY가 표시된 모습" width="1946" height="402" data-path="images/workspace/auth/clerk-check-dev-keys.png" />
</Frame>

* 앱을 publish하면 게시된 deployment는 Production 환경을 가리키는 **live key**(`pk_live...` 및 `sk_live...`)로 실행됩니다. 접두사를 확인하려면 **Publishing → Overview → Adjust settings**를 열고 `CLERK_PUBLISHABLE_KEY`와 `CLERK_SECRET_KEY`를 확인하세요.

<Frame>
  <img src="/assets/mirror/clerk-check-prod-keys-acccd7f68da1.png" alt="Publishing Overview에 sk_live_ 및 pk_live_ 접두사를 사용하는 CLERK_SECRET_KEY와 CLERK_PUBLISHABLE_KEY가 Production 앱 secret으로 표시된 모습" width="1924" height="1664" data-path="images/workspace/auth/clerk-check-prod-keys.png" />
</Frame>

<Note>
  환경을 전환하기 위해 따로 해야 할 일은 없습니다. Replit이 Development와 Production 양쪽 키를 자동으로 관리합니다. 개발하고, 테스트하고, publish하기만 하면 됩니다.
</Note>

<Warning>
  테스트 키를 live key로 교체하거나, Secrets pane에서 직접 수정하거나, Clerk dashboard에서 수동으로 설정하지 마세요. 이렇게 하면 development/production 자동 전환이 작동하지 않으며, Replit이 관리하는 Clerk Auth에서는 지원되지 않습니다.
</Warning>

<div id="separate-user-stores">
  ### 분리된 사용자 저장소
</div>

각 환경은 자체 사용자 저장소를 갖습니다. Development 환경에서 가입한 계정은 Production 환경에 존재하지 **않으며**, 그 반대도 마찬가지입니다.

* 개발/미리보기 앱에서 테스트하는 중에 가입한 사용자는 Development 저장소에만 생성됩니다.
* 게시된 앱에서 가입한 사용자는 Production 저장소에만 생성됩니다.
* 세션, 사용자 메타데이터, Clerk `userId`를 키로 사용하는 모든 데이터 역시 해당 계정이 생성된 환경으로 범위가 한정됩니다.

이는 정상적인 동작입니다. 각 환경의 사용자를 확인하려면 Workspace에서 **Auth pane**을 열고 **Users** 탭의 환경 토글로 Development와 Production을 전환하세요.

<Note>
  Development는 실험하고 빌드하는 공간이고, Production은 라이브 앱의 실제 사용자에게 서비스를 제공하는 환경입니다. 두 환경은 의도적으로 격리되어 있으므로 Development에서 만든 계정과 데이터는 Production에 나타나지 않습니다.
</Note>

<div id="managing-users">
  ## 사용자 관리
</div>

Project Editor의 **Auth pane**에서는 인증된 사용자를 한눈에 확인할 수 있습니다. Clerk Auth는 앱 전용의 별도 사용자 저장소를 생성하므로, 여기에 표시되는 사용자는 Replit accounts가 아니라 앱에 속한 계정입니다.

<Frame>
  <img src="/assets/mirror/clerk-users-4940ed365605.png" alt="Auth pane에서 인증된 사용자를 보여주는 Clerk Auth 사용자 탭" width="2136" height="794" data-path="images/workspace/auth/clerk-users.png" />
</Frame>

**Users** tab에서는 다음 작업을 할 수 있습니다.

* **모든 사용자 보기** — 이메일, 이름, 마지막 login, 계정 생성 날짜 등의 세부 정보 확인
* **검색 및 filter** — 특정 사용자 찾기
* **사용자 차단 또는 차단 해제** — 앱 접근 제어
* **사용자 정렬** — 다양한 기준으로 정렬
* **환경 전환** — Development와 Production을 전환하며 각 환경의 사용자 관리

<div id="customizing-your-sign-in-page">
  ## 로그인 페이지 사용자 지정하기
</div>

로그인 및 회원가입 페이지의 시각적 브랜딩(앱 이름, 로고, 색상, 글꼴, 문구)은 Auth pane이 아니라 앱 코드에서 설정합니다. 이를 변경하려면 Agent에게 다음과 같이 요청하세요.

```
로그인 페이지의 제목을 [앱 이름]으로 바꾸고, [로고 설명]을 적용하고, 사이트 색상에 맞춰 줘.
```

내부적으로는 `<ClerkProvider>`에 전달되는 `appearance` 및 `localization` props와 앱의 `public/` 디렉터리에 있는 로고 파일이 이를 제어합니다. Agent는 이 항목들을 앱의 나머지 테마와 동기화된 상태로 유지합니다.

<Note>
  **Google, Apple, GitHub 또는 X의 자체 동의 화면**(사용자가 &quot;Google로 로그인&quot; 등을 클릭한 후 나타나는 화면)에 표시되는 앱 이름은 별개입니다. 이 이름은 해당 provider에 등록된 OAuth app에서 가져오므로, 로그인 페이지 코드를 수정해도 변경되지 **않습니다**. 변경하려면 해당 provider에 대해 [사용자 지정 OAuth 자격 증명](#configuring-oauth-credentials-for-an-sso-provider)을 구성하세요.
</Note>

<div id="configuring-login-providers">
  ## login providers 구성하기
</div>

Clerk Auth는 Google, GitHub, Apple, X를 소셜 sign-in providers로 지원합니다. Auth pane의 **Configure** tab에서 로그인 페이지에 어떤 providers를 표시할지 제어할 수 있으며, Production에서는 각 provider가 Replit이 관리하는 OAuth 자격 증명을 사용할지, 브랜드에 맞춘 sign-in을 위해 custom credentials를 사용할지도 지정할 수 있습니다.

<Frame>
  <img src="/assets/mirror/clerk-configure-60169c473d64.png" alt="사이드바에 SSO providers가 표시되고 Production이 선택된 Configure tab, provider 목록에 활성화 토글과 Edit 작업이 표시된 모습" width="923" height="378" data-path="images/workspace/auth/clerk-configure.png" />
</Frame>

**Configure** tab을 엽니다. 사이드바의 **SSO providers** 아래에서 **Development** 또는 **Production**을 선택합니다. **Development**는 Workspace의 개발/preview 앱을, **Production**은 게시된 앱을 구동합니다. 환경별로 메인 패널에 별도의 목록이 표시됩니다. 여기에서 다음 작업을 할 수 있습니다.

* **provider 활성화 또는 비활성화** — 토글로 해당 provider를 로그인 페이지에 표시할지 제어합니다. 비활성화된 providers는 사용자에게 표시되지 않습니다.
* **custom OAuth 자격 증명 구성(Production 전용)** — 아래 [SSO provider의 OAuth 자격 증명 구성하기](#configuring-oauth-credentials-for-an-sso-provider)를 참고하세요.

<div id="configuring-oauth-credentials-for-an-sso-provider">
  ### SSO provider의 OAuth 자격 증명 구성하기
</div>

기본적으로 provider는 **Replit 관리 자격 증명**을 사용합니다. 별도 설정 없이도 로그인이 작동하지만, OAuth 동의 화면에 Replit 브랜딩이 표시됩니다. **Custom credentials**로 전환하면 provider의 개발자 콘솔에서 발급한 자체 OAuth 클라이언트를 사용할 수 있어, 동의 화면에 앱의 이름과 브랜딩이 표시됩니다.

1. Project Editor에서 **Auth pane**을 엽니다. **Configure** tab으로 이동한 뒤 사이드바의 **SSO providers** 아래에서 **Production**을 선택합니다.

<Frame>
  <img src="/assets/mirror/clerk-configure-60169c473d64.png" width="923" height="378" data-path="images/workspace/auth/clerk-configure.png" />
</Frame>

2. 구성하려는 provider 옆의 **Edit** icon을 선택합니다. 기본값으로 **Replit 관리 자격 증명**이 선택되어 있습니다.

<Frame>
  <img src="/assets/mirror/clerk-sso-default-credentials-525090775408.png" alt="Replit 관리 자격 증명과 Custom credentials 옵션을 보여주는 provider 편집 패널" width="1468" height="960" data-path="images/workspace/auth/clerk-sso-default-credentials.png" />
</Frame>

3. **Custom credentials**를 선택합니다. 패널이 확장되면서 자격 증명 입력란과 provider 측에 등록해야 할 값이 담긴 **Provider setup** 체크리스트가 나타납니다.

<Frame>
  <img src="/assets/mirror/clerk-sso-custom-credentials-f24112a5cf07.png" alt="OAuth Client ID 및 secret 입력란과 리디렉션 콜백 URL, JavaScript 원본이 포함된 Provider setup 체크리스트를 보여주는 Custom credentials 패널" width="1468" height="2246" data-path="images/workspace/auth/clerk-sso-custom-credentials.png" />
</Frame>

4. 안내에 따라 구성을 완료합니다. 안내에는 콘솔과 관련 도움말 문서로 바로 연결되는 링크가 포함되어 있습니다. 이러한 도움말 문서는 사용 중인 provider의 [추가 리소스](#additional-resources)에서도 확인할 수 있습니다.
5. 필요한 자격 증명 값을 모두 입력합니다.
6. provider의 개발자 콘솔에서 **Provider setup** 체크리스트에 나열된 모든 항목을 provider의 개발자 포털에 등록합니다. 복사 icon으로 각 값을 정확히 복사하고, 완료한 항목은 하나씩 체크하거나 모두 마쳤다면 **Mark all as done**을 선택하세요.
7. **Save changes**를 선택합니다.

<div id="rechecking-setup-after-domain-changes">
  ### 도메인 변경 후 설정 다시 확인하기
</div>

새 외부 도메인을 연결하거나 [Replit에서 도메인을 구매](/ko/build/domain-purchasing)하는 등의 도메인 관련 작업은 앱의 리디렉션 콜백 URL과 JavaScript 원본을 변경할 수 있습니다. 이 경우 custom credentials로 구성된 provider는 해당 개발자 콘솔에 새 값을 등록해야 할 수 있습니다.

도메인을 변경한 후에는 **Configure** 탭으로 돌아가세요. 설정 알림은 탭과 사이드바, 그리고 **SSO providers** 목록의 provider 옆에 경고 icon으로 표시됩니다. provider 옆에 경고 icon과 **setup steps remaining**이 함께 표시되면 해당 provider의 **Provider setup** 체크리스트에 완료해야 할 새 항목이 있다는 뜻입니다.

<Frame>
  <img src="/assets/mirror/clerk-sso-setup-reminders-a5b092846006.png" alt="설정 경고가 표시된 Configure 탭과 사이드바, 그리고 도메인 변경 후 provider 옆에 경고 icon과 'setup steps remaining'이 표시된 SSO providers 목록" width="923" height="378" data-path="images/workspace/auth/clerk-sso-setup-reminders.png" />
</Frame>

provider의 편집 pane을 열어 **Provider setup** 아래의 업데이트된 값을 복사한 다음, provider의 개발자 콘솔에 등록하고 **Mark all as done**을 선택하세요.

<div id="domain-setup-for-email-verification">
  ## 이메일 인증을 위한 도메인 설정
</div>

앱에서 **이메일 및 비밀번호 가입**을 제공하는 경우, Clerk은 새로운 사용자 각각의 Inbox로 인증 코드를 전송합니다. 이메일 전송용으로 도메인을 구성하면 인증 코드가 스팸 필터에 의해 지연되거나 차단되지 않고 앱의 URL에서 발송됩니다.

<div id="when-you-need-this-setup">
  ### 이 설정이 필요한 경우
</div>

DNS 레코드 설정은 앱에 **다른 provider가 관리하는 외부 도메인**(예: Cloudflare, GoDaddy, Namecheap 등에서 등록한 도메인)을 연결할 때만 필요합니다.

앱이 다음 위치에서 serve되는 경우에는 별도의 설정이 필요하지 않습니다.

* `.replit.app` 하위 도메인
* [Replit을 통해 구매한](/ko/build/domain-purchasing) 도메인

두 경우 모두 Replit이 DNS 레코드를 대신 관리합니다.

<div id="add-dns-records-for-email-sending">
  ### 이메일 발송을 위한 DNS 레코드 추가
</div>

외부 도메인에서 인증 이메일을 보낼 수 있도록 앱에 권한을 부여하려면 도메인 provider에서 DNS 레코드 세트를 추가하세요.

1. Project Editor에서 **Publishing**을 엽니다.
2. **Domains**를 선택합니다.
3. 연결된 외부 도메인을 찾아 **Manage**를 선택합니다.
4. **Authentication DNS setup required** 아래에 Replit이 표시하는 CNAME 레코드를 복사합니다. Clerk가 해당 도메인에서 인증 이메일을 보내려면 이 레코드가 필요합니다.
5. DNS provider(Cloudflare, GoDaddy, Namecheap 등)에 로그인해 각 레코드를 표시된 그대로 추가합니다.

<Frame>
  <img src="/assets/mirror/clerk-domain-8797ea9f41fc.png" alt="Clerk 이메일 전송을 위한 CNAME 레코드가 포함된 Authentication DNS setup required 섹션이 표시된 Domain Manage 패널" width="1156" height="1524" data-path="images/workspace/auth/clerk-domain.png" />
</Frame>

DNS 변경 사항이 전파되는 데 최대 48시간이 걸릴 수 있습니다. 레코드가 적용되면 이메일 및 비밀번호 가입 시 해당 도메인에서 인증 코드가 자동으로 전송되며, Auth pane에서 별도로 해야 할 작업은 없습니다.

<div id="troubleshooting">
  ### 문제 해결
</div>

* **인증 이메일이 도착하지 않는 경우** — Manage 패널에 표시된 것과 정확히 동일하게 모든 레코드를 추가했는지 확인하세요. DNS provider가 요구한다면 맨 끝의 점(.)까지 그대로 입력해야 합니다. 수신자의 스팸함도 확인해 보세요.
* **레코드가 여전히 감지되지 않는 경우** — DNS 전파에 필요한 시간(최대 48시간)을 기다린 후, Manage 패널에서 아직 누락으로 표시된 레코드가 있는지 다시 확인하세요.

<div id="security-best-practices">
  ## 보안 모범 사례
</div>

* **항상 서버 측에서 검증하세요** — UI에서만이 아니라 API 라우트에서도 authentication을 확인하세요
* **환경 변수를 사용하세요** — 키나 secret을 코드에 하드코딩하지 마세요
* **프록시 middleware를 가장 먼저 배치하세요** — Express 앱에서 Clerk 프록시는 body parser보다 앞에 마운트해야 합니다
* **홈페이지를 로그인 화면으로 리디렉션하지 마세요** — landing page는 인증되지 않은 방문자도 접근할 수 있도록 유지하세요

<div id="faq">
  ## 자주 묻는 질문
</div>

<div id="do-i-need-a-clerk-account-to-use-clerk-auth">
  ### Clerk Auth를 사용하려면 Clerk 계정이 필요한가요?
</div>

아니요. Clerk Auth를 구동하는 Clerk 테넌트는 Agent가 앱을 설정할 때 Replit이 자동으로 생성하고 관리합니다. 따라서 Clerk에 직접 가입하거나 Clerk 인프라를 관리할 필요가 없습니다.

<div id="can-i-access-the-clerk-dashboard-for-the-replit-managed-clerk-instance">
  ### Replit이 관리하는 Clerk 인스턴스의 Clerk dashboard에 접근할 수 있나요?
</div>

아니요. Replit이 관리하는 Clerk 인스턴스는 Clerk dashboard에서 제공되지 않습니다. 대신 Project Editor의 **Auth** 도구에서 관리하세요. 이곳에서 provider를 구성하고, 사용자를 확인하고, Development와 Production 환경을 전환할 수 있습니다.

<div id="my-clerk-publishable-key-starts-with-pk_test-how-do-i-switch-to-a-live-key">
  ### Clerk publishable key가 `pk_test`로 시작합니다. live key로 어떻게 전환하나요?
</div>

전환하실 필요가 없습니다. workspace의 Secrets pane에 표시되는 `pk_test...` 및 `sk_test...` 키는 앱의 **Development** Clerk 환경에 해당하며, 개발 중에 사용됩니다. 앱을 publish하면 deployment는 Production 환경용 `pk_live...` 및 `sk_live...` 키로 자동 실행됩니다. 확인하려면 Workspace에서 **Publishing → Overview → Adjust settings**를 열고 게시된 앱의 `CLERK_PUBLISHABLE_KEY` 값을 확인하세요. `pk_live`로 시작합니다. 이 키를 직접 수정하지 마세요. 전체 내용은 [Development 및 Production 환경](#development-and-production-environments)을 참조하세요.

<div id="why-cant-i-sign-in-to-my-published-app-with-the-account-i-created-during-development">
  ### 개발 중에 만든 계정으로 게시된 앱에 로그인할 수 없는 이유는 무엇인가요?
</div>

Clerk Auth의 **Development** 환경과 **Production** 환경은 사용자 저장소가 서로 분리되어 있습니다. 개발/Preview 앱에서 만든 계정은 Development 환경에만 존재하며 publish할 때 Production으로 복사되지 않으므로, 게시된 앱에서 다시 가입해야 합니다. Clerk `userId`를 기준으로 저장한 데이터도 마찬가지입니다. Workspace에서 **Auth pane**을 열고 **Users** 탭의 환경 전환 기능을 사용하면 각 환경의 사용자를 확인할 수 있습니다. 자세한 내용은 [사용자 저장소 분리](#separate-user-stores)를 참고하세요.

<div id="is-clerk-auth-free-to-use">
  ### Clerk Auth는 무료로 사용할 수 있나요?
</div>

현재 Clerk Auth는 무료입니다. 다만 Replit의 다른 사용량 기반 서비스와 마찬가지로 추후 사용량 기반 요금제가 도입될 수 있습니다. 향후 발생하는 요금은 기존 Replit 청구서를 통해 부과되므로, 별도의 Clerk 인보이스나 결제 수단은 필요하지 않습니다.

<div id="does-clerk-auth-have-an-mau-limit-like-external-clerk-plans">
  ### Clerk Auth에도 외부 Clerk 플랜처럼 MAU 한도가 있나요?
</div>

아니요. 티어별로 MAU를 제한하는 외부 Clerk 플랜과 달리, Clerk Auth에는 월간 활성 사용자(MAU) 한도가 없습니다.

<div id="how-does-clerk-auth-compare-to-external-clerk">
  ### Clerk Auth는 외부 Clerk와 어떻게 다른가요?
</div>

Clerk Auth를 뒷받침하는 Replit 관리형 Clerk 테넌트는 직접 자신의 Clerk 계정에서 만든 Clerk 앱(**외부 Clerk**)과 몇 가지 차이가 있습니다. 아래 표는 현재 두 방식의 차이점을 정리한 것으로, Clerk Auth의 현재 상태를 반영하며 지원 기능은 계속 확대될 예정입니다.

|                      | Clerk Auth                               | 외부 Clerk           |
| -------------------- | ---------------------------------------- | ------------------ |
| **설정**               | Replit이 자동으로 프로비저닝                       | 직접 설정              |
| **Clerk 테넌트 소유권** | Replit이 관리하고, 앱이 소유                      | 사용자의 Clerk 계정이 소유  |
| **요금 구조**            | 현재 무료(향후 종량제 도입 예정)                      | 구독 + 종량제           |
| **Billing**          | Replit billing(현재 무료)                    | 사용자의 Clerk 계정에서 청구 |
| **MAU limit**        | 무제한                                      | 등급별 제한             |
| **프록시 및 도메인 구성**     | replit.app 및 구매한 도메인은 자동, 연결된 도메인은 수동    | 수동                 |
| **SSO providers**    | 일부 provider 지원: Google, Apple, GitHub, X | 더 많은 provider 지원   |
| **User 관리 화면**       | Project Editor의 Auth 도구                  | Clerk 앱 dashboard  |
| **SMS**              | 지원하지 않음                                  | 지원                 |
| **MFA**              | 지원하지 않음                                  | 지원                 |
| **조직 tenant**        | 지원하지 않음                                  | 지원                 |

<div id="what-common-clerk-auth-setup-do-i-need-to-handle-manually">
  ### 직접 처리해야 하는 일반적인 Clerk Auth 설정은 무엇인가요?
</div>

Clerk Auth 설정은 대부분 자동으로 처리되지만, 일부 설정은 **Auth** 도구 밖에서 직접 조치해야 합니다.

* **SSO provider용 사용자 지정 OAuth 자격 증명** — provider의 동의 화면에 Replit 기본값 대신 앱 이름과 브랜딩을 표시하려면, provider의 개발자 콘솔에서 OAuth app을 등록한 뒤 발급받은 자격 증명을 Auth pane에 붙여넣으세요. [SSO provider의 OAuth 자격 증명 구성](#configuring-oauth-credentials-for-an-sso-provider)을 참조하세요.
* **외부 도메인의 email verification용 DNS 레코드** — 앱에 다른 provider가 관리하는 외부 도메인을 연결한 경우, 인증 메일이 해당 도메인에서 발송되도록 DNS 레코드를 추가해야 합니다. [email verification을 위한 도메인 설정](#domain-setup-for-email-verification)을 참조하세요.

<div id="can-i-bring-my-own-clerk-app-instead-of-using-the-replit-managed-one">
  ### Replit에서 관리하는 Clerk 앱 대신 직접 보유한 Clerk 앱을 사용할 수 있나요?
</div>

가능합니다. App에 이미 Replit에서 관리하는 Clerk 앱이 프로비저닝되어 있다면, 외부 Clerk 앱을 연결하기 전에 먼저 삭제하세요.

1. Project Editor에서 **Auth** pane을 엽니다.
2. **Configure** tab으로 이동합니다.
3. 페이지 맨 아래로 스크롤한 후 **Delete Clerk app**을 클릭합니다.

Clerk 앱을 삭제하면 Replit에서 관리하는 Clerk 테넌트가 제거되고 여기에 연결된 도메인도 해제되므로, 직접 보유한 Clerk 앱을 연결해 해당 도메인을 그대로 다시 사용할 수 있습니다. App에 Replit에서 관리하는 Clerk 앱이 아직 없다면 이 단계를 건너뛰고 외부 Clerk 앱을 바로 연동하면 됩니다.
